# Урок 26. Центральности

Предполагается, что пройден урок 25: понятны проекции, каталог графов и режимы `.stream`, `.stats`, `.mutate`, `.write`. Все примеры работают на уже загруженном графе магазина.

> **Важно**: приведённые в уроке выводы сняты на базовом датасете из урока 9 — 30 реальных пользователей, без синтетики. Если генератор синтетических данных уже запускался, в результатах будут аккаунты вида `synth1234@shop.io`, а абсолютные значения окажутся другими: структура ответа и выводы сохраняются, конкретные числа — нет. Сравнивать имеет смысл форму результата, а не цифры.

## Что измеряет центральность

Центральность — это число, которое отвечает на вопрос «насколько важен этот узел». Проблема в том, что «важен» — не одно понятие, а как минимум четыре разных, и они дают разные ответы на одном и том же графе.

| Метрика | Что считает | Кто окажется наверху |
|---|---|---|
| Degree | Количество связей | У кого много подписчиков |
| PageRank | Связи с поправкой на важность соседей | На кого подписаны влиятельные |
| Betweenness | Сколько кратчайших путей проходит через узел | Кто соединяет разные группы |
| Closeness | Насколько узел близок ко всем остальным | Кто быстрее всех доносит информацию |
| Eigenvector | Влиятельность как собственный вектор матрицы связей | Ядро плотного кластера |

Практический вывод: не бывает «самого важного пользователя вообще». Есть самый заметный, самый влиятельный и самый связующий — и это обычно разные люди. Дальше в уроке будет пример, где пользователь с максимальным PageRank имеет один из самых низких betweenness.

## Проекции для урока

Направленная — для degree и PageRank, где направление подписки имеет смысл:

```cypher
MATCH (u:User)-[:FOLLOWS]->(v:User)
RETURN gds.graph.project('social', u, v) AS g;
```

Ненаправленная — для betweenness и closeness, где важна связность, а не кто на кого подписался:

```cypher
MATCH (u:User)-[:FOLLOWS]->(v:User)
RETURN gds.graph.project('socialU', u, v,
  {}, {undirectedRelationshipTypes: ['*']}) AS g;
```

> **Важно**: в `MATCH` стрелка остаётся направленной даже для ненаправленной проекции. Если написать `(u)-[:FOLLOWS]-(v)`, каждая связь придёт в проекцию дважды, и `relationshipCount` вырастет с 154 до 308. На суммах это не всегда заметно, но на весах и на памяти — заметно всегда. Направление снимает опция `undirectedRelationshipTypes`, а не шаблон запроса.

## Degree — сколько связей

Самая дешёвая метрика: просто счётчик рёбер. Считается за один проход, память почти не занимает.

```cypher
CALL gds.degree.stream('social')
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).email AS email, score
ORDER BY score DESC, email LIMIT 5;
```

```
╒══════════════════╤═══════╕
│email             │score  │
╞══════════════════╪═══════╡
│"daria@shop.io"   │5.0    │
│"sofia@shop.io"   │5.0    │
│"anna@shop.io"    │4.0    │
│"banned1@shop.io" │4.0    │
│"denis@shop.io"   │4.0    │
└──────────────────┴───────┘
```

По умолчанию считаются исходящие связи — то есть на кого пользователь подписан сам. Это метрика активности, а не популярности. Популярность — это входящие связи, и для них нужна опция `orientation`:

```cypher
CALL gds.degree.stream('social', {orientation: 'REVERSE'})
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).email AS email, score
ORDER BY score DESC, email LIMIT 5;
```

```
╒══════════════════╤═══════╕
│email             │score  │
╞══════════════════╪═══════╡
│"mult3@shop.io"   │6.0    │
│"sergey@shop.io"  │5.0    │
│"sofia@shop.io"   │5.0    │
│"timur@shop.io"   │5.0    │
│"egor@shop.io"    │4.0    │
└──────────────────┴───────┘
```

Списки почти не пересекаются: `daria` активно подписывается, но её саму читают мало. Путать эти два числа — самая частая ошибка при работе с degree.

| `orientation` | Что считает |
|---|---|
| `NATURAL` (по умолчанию) | Исходящие связи |
| `REVERSE` | Входящие связи |
| `UNDIRECTED` | Все связи независимо от направления |

### Взвешенный degree

С `relationshipWeightProperty` вместо количества рёбер суммируется вес. На проекции `purchases` из урока 25 это даёт разницу между «сколько раз товар покупали» и «сколько штук купили».

```cypher
MATCH (u:User)-[:PLACED]->(o:Order)-[c:CONTAINS]->(p:Product)
RETURN gds.graph.project('purchases', u, p, {
  sourceNodeLabels: ['User'],
  targetNodeLabels: ['Product'],
  relationshipType: 'BOUGHT',
  relationshipProperties: { qty: toFloat(c.qty) }
}) AS g;

CALL gds.degree.stream('purchases', {
  orientation: 'REVERSE',
  relationshipWeightProperty: 'qty'
})
YIELD nodeId, score
WITH gds.util.asNode(nodeId) AS n, score
WHERE n:Product
RETURN n.title AS product, score
ORDER BY score DESC LIMIT 5;
```

```
╒═════════════════════════════════╤═══════╕
│product                          │score  │
╞═════════════════════════════════╪═══════╡
│"Наушники Wave Studio"           │11.0   │
│"Комплект полотенец Cozy Soft"   │11.0   │
│"Кофеварка Aroma Mini"           │10.0   │
│"Блендер Turbo Max"              │9.0    │
│"Наушники Echo Light"            │9.0    │
└─────────────────────────────────┴───────┘
```

Без веса первым идёт «Блендер Turbo Max» с 9 покупками, а «Комплект полотенец» опускается на пятое место с 8. Полотенца берут реже, но по несколько штук за раз. Какая метрика правильная — зависит от вопроса: для витрины «часто покупают» нужна первая, для закупок склада вторая.

> **Внимание**: `toFloat(c.qty)` здесь не обязателен — целочисленное свойство проецируется и считается корректно, GDS приведёт его к `double` сам. Явное приведение стоит писать по другой причине: оно фиксирует тип на входе, и результат не зависит от того, что пришло из CSV. Смешивать в одном свойстве целые и дробные значения нельзя — вот это уже ошибка проекции.

## PageRank — влиятельность соседей

Degree считает все связи одинаковыми. PageRank исходит из того, что подписка от влиятельного пользователя весит больше, чем от случайного. Формально это вероятность оказаться в узле при случайном блуждании по графу.

```cypher
CALL gds.pageRank.stream('social')
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).email AS email, round(score, 3) AS score
ORDER BY score DESC LIMIT 5;
```

```
╒══════════════════╤═══════╕
│email             │score  │
╞══════════════════╪═══════╡
│"oleg@shop.io"    │2.105  │
│"mult1@shop.io"   │2.059  │
│"sergey@shop.io"  │1.932  │
│"elena@shop.io"   │1.469  │
│"mult3@shop.io"   │1.36   │
└──────────────────┴───────┘
```

`oleg` не входил в топ-5 по входящим связям, но занял первое место по PageRank: на него подписаны немногие, зато влиятельные.

### Сходимость

PageRank итеративный, и результат выше — не окончательный.

```cypher
CALL gds.pageRank.stats('social')
YIELD ranIterations, didConverge
RETURN ranIterations, didConverge;
```

```
╒═══════════════╤═════════════╕
│ranIterations  │didConverge  │
╞═══════════════╪═════════════╡
│20             │FALSE        │
└───────────────┴─────────────┘
```

`didConverge: FALSE` означает, что алгоритм упёрся в лимит итераций (по умолчанию 20) и остановился на промежуточных значениях. На графе из 30 узлов до настоящей сходимости нужно 79 итераций:

```cypher
CALL gds.pageRank.stats('social', {maxIterations: 100, tolerance: 0.0000001})
YIELD ranIterations, didConverge
RETURN ranIterations, didConverge;
```

```
╒═══════════════╤═════════════╕
│ranIterations  │didConverge  │
╞═══════════════╪═════════════╡
│79             │TRUE         │
└───────────────┴─────────────┘
```

> **Важно**: всегда смотри на `didConverge`. Несошедшийся PageRank даёт правдоподобные, но нестабильные числа: следующий запуск с другим лимитом переставит местами соседние позиции. Порядок топа при этом обычно сохраняется, а конкретные значения — нет, и сравнивать их между запусками нельзя.

Два параметра управляют вычислением:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `maxIterations` | 20 | Потолок числа итераций |
| `tolerance` | 0.0000001 | Порог изменения, ниже которого считается сошедшимся |
| `dampingFactor` | 0.85 | Вероятность продолжить блуждание, а не прыгнуть в случайный узел |

`dampingFactor` — про то, насколько далеко распространяется влияние. При 0.5 картина меняется:

```cypher
CALL gds.pageRank.stream('social', {dampingFactor: 0.5})
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).email AS email, round(score, 3) AS score
ORDER BY score DESC LIMIT 5;
```

```
╒══════════════════╤═══════╕
│email             │score  │
╞══════════════════╪═══════╡
│"sergey@shop.io"  │1.719  │
│"oleg@shop.io"    │1.594  │
│"sofia@shop.io"   │1.438  │
│"mult1@shop.io"   │1.415  │
│"mult3@shop.io"   │1.363  │
└──────────────────┴───────┘
```

Первое место перешло к `sergey`: при низком damping влияние затухает быстро, и выигрывает тот, у кого много прямых подписчиков, а не тот, у кого подписчики влиятельные. 0.85 — стандартное значение, менять его стоит осознанно.

### Персонализированный PageRank

С параметром `sourceNodes` случайное блуждание всегда возвращается в заданные узлы. Получается «влиятельность с точки зрения конкретного пользователя» — база для рекомендаций «кого читать».

```cypher
MATCH (a:User {email: 'anna@shop.io'})
CALL gds.pageRank.stream('socialU', {sourceNodes: [a]})
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).email AS email, round(score, 4) AS score
ORDER BY score DESC LIMIT 5;
```

```
╒══════════════════╤════════╕
│email             │score   │
╞══════════════════╪════════╡
│"anna@shop.io"    │0.1983  │
│"sofia@shop.io"   │0.0963  │
│"artem@shop.io"   │0.0714  │
│"lidia@shop.io"   │0.0693  │
│"julia@shop.io"   │0.0609  │
└──────────────────┴────────┘
```

Сама `anna` закономерно на первом месте — её из выдачи нужно отфильтровать. Остальные упорядочены по близости к её окружению, а не по глобальной популярности: `oleg`, лидер общего рейтинга, сюда не попал вовсе. Этот же приём используется в уроке 30 для рекомендаций товаров.

### ArticleRank и Eigenvector

Два варианта той же идеи с разными поправками.

**ArticleRank** уменьшает вклад узлов с большим числом исходящих связей: тот, кто подписан на всех подряд, раздаёт меньше веса. Полезно там, где массовая подписка ничего не стоит.

```cypher
CALL gds.articleRank.stream('social')
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).email AS email, round(score, 3) AS score
ORDER BY score DESC LIMIT 5;
```

```
╒══════════════════╤═══════╕
│email             │score  │
╞══════════════════╪═══════╡
│"sergey@shop.io"  │0.364  │
│"mult3@shop.io"   │0.359  │
│"sofia@shop.io"   │0.349  │
│"oleg@shop.io"    │0.309  │
│"egor@shop.io"    │0.307  │
└──────────────────┴───────┘
```

**Eigenvector** — PageRank без телепортации: чистая мера принадлежности к плотному ядру графа. Числа нормированы, сумма квадратов равна единице.

```cypher
CALL gds.eigenvector.stream('social')
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).email AS email, round(score, 3) AS score
ORDER BY score DESC LIMIT 5;
```

```
╒══════════════════╤═══════╕
│email             │score  │
╞══════════════════╪═══════╡
│"mult3@shop.io"   │0.37   │
│"sergey@shop.io"  │0.358  │
│"egor@shop.io"    │0.307  │
│"oleg@shop.io"    │0.288  │
│"gleb@shop.io"    │0.276  │
└──────────────────┴───────┘
```

Оба варианта поднимают наверх `mult3` и `sergey` — узлы из плотной части графа, а `oleg` опускают. Расхождение с PageRank как раз и говорит, что высокий PageRank у `oleg` держится на нескольких сильных подписчиках, а не на положении в ядре.

## Betweenness — кто соединяет группы

Betweenness считает, через сколько кратчайших путей между всеми парами узлов проходит данный узел. Высокое значение означает, что узел — мост: убери его, и части графа окажутся друг от друга дальше.

```cypher
CALL gds.betweenness.stream('socialU')
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).email AS email, round(score, 1) AS score
ORDER BY score DESC LIMIT 5;
```

```
╒══════════════════╤═══════╕
│email             │score  │
╞══════════════════╪═══════╡
│"sofia@shop.io"   │75.3   │
│"kirill@shop.io"  │62.0   │
│"mult3@shop.io"   │59.4   │
│"sergey@shop.io"  │42.6   │
│"mult2@shop.io"   │36.0   │
└──────────────────┴───────┘
```

Это самый дорогой алгоритм из перечисленных: сложность порядка `O(V × E)`, то есть на графе из миллиона узлов и десяти миллионов рёбер он считается часами. Для таких случаев есть выборочный режим — кратчайшие пути строятся не от всех узлов, а от случайной подвыборки:

```cypher
CALL gds.betweenness.stream('socialU', {samplingSize: 10, samplingSeed: 42})
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).email AS email, round(score, 1) AS score
ORDER BY score DESC LIMIT 5;
```

```
╒══════════════════╤═══════╕
│email             │score  │
╞══════════════════╪═══════╡
│"mult3@shop.io"   │17.2   │
│"mult2@shop.io"   │15.1   │
│"sofia@shop.io"   │14.6   │
│"sergey@shop.io"  │13.6   │
│"kirill@shop.io"  │11.2   │
└──────────────────┴───────┘
```

Абсолютные значения упали втрое — они и не сопоставимы с полным расчётом. Состав топ-5 сохранился, порядок внутри него сдвинулся. Это и есть цена приближения: выборочный betweenness годится, чтобы найти кандидатов в мосты, но не чтобы ранжировать их точно. `samplingSeed` фиксирует выборку, иначе результат будет меняться от запуска к запуску.

## Closeness — близость ко всем

Closeness — величина, обратная средней длине кратчайшего пути до всех достижимых узлов. Значение близко к 1 означает, что до всех остальных рукой подать.

На направленном графе метрика ведёт себя коварно:

```cypher
CALL gds.closeness.stream('social')
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).email AS email, round(score, 3) AS score
ORDER BY score DESC LIMIT 5;
```

```
╒══════════════════╤═══════╕
│email             │score  │
╞══════════════════╪═══════╡
│"roman@shop.io"   │1.0    │
│"ksenia@shop.io"  │1.0    │
│"mult3@shop.io"   │0.438  │
│"sergey@shop.io"  │0.394  │
│"elena@shop.io"   │0.384  │
└──────────────────┴───────┘
```

Идеальная единица у `roman` — не признак центральности, а артефакт. У него ровно одна исходящая подписка, и от неё дальше идти некуда: множество достижимых узлов состоит из одного соседа на расстоянии 1, средняя длина пути равна 1, closeness равен 1. Метрика считается только по достижимым узлам, поэтому изоляция даёт максимальный балл.

Отсюда правило: closeness считают на ненаправленном графе, а на направленном — только если недостижимость сама по себе несёт смысл.

```cypher
CALL gds.closeness.stream('socialU')
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).email AS email, round(score, 3) AS score
ORDER BY score DESC LIMIT 5;
```

```
╒══════════════════╤═══════╕
│email             │score  │
╞══════════════════╪═══════╡
│"mult3@shop.io"   │0.547  │
│"sofia@shop.io"   │0.537  │
│"mult2@shop.io"   │0.509  │
│"sergey@shop.io"  │0.492  │
│"elena@shop.io"   │0.492  │
└──────────────────┴───────┘
```

Теперь картина осмысленная, а `roman` уехал вниз.

## Распределение вместо топа

Режим `.stats` возвращает `centralityDistribution` — перцентили по всему графу. Топ-5 показывает лидеров, распределение показывает, есть ли они вообще.

```cypher
CALL gds.betweenness.stats('socialU')
YIELD centralityDistribution
RETURN round(centralityDistribution.max, 1) AS max,
       round(centralityDistribution.mean, 2) AS mean,
       round(centralityDistribution.p50, 1) AS p50,
       round(centralityDistribution.p95, 1) AS p95;
```

Если `max` близок к `p50` — центральность распределена равномерно и выделять лидеров бессмысленно. Если `max` на порядок выше `p95` — в графе есть настоящие хабы. На нашем графе `max` равен 75.3 при среднем 18.57: хабы есть, но выражены умеренно.

## Запись результата и сравнение метрик

Полезнее всего центральности становятся, когда их несколько и они записаны в граф рядом.

```cypher
CALL gds.pageRank.write('social', {writeProperty: 'influence', maxIterations: 100})
YIELD nodePropertiesWritten, ranIterations, didConverge
RETURN nodePropertiesWritten, ranIterations, didConverge;

CALL gds.betweenness.write('socialU', {writeProperty: 'bridging'})
YIELD nodePropertiesWritten
RETURN nodePropertiesWritten;

MATCH (u:User) WHERE u.influence IS NOT NULL
RETURN u.email AS email,
       round(u.influence, 2) AS influence,
       round(u.bridging, 1) AS bridging
ORDER BY influence DESC LIMIT 6;
```

```
╒══════════════════╤═══════════╤══════════╕
│email             │influence  │bridging  │
╞══════════════════╪═══════════╪══════════╡
│"oleg@shop.io"    │2.17       │4.8       │
│"mult1@shop.io"   │2.13       │28.5      │
│"sergey@shop.io"  │1.98       │42.6      │
│"elena@shop.io"   │1.52       │24.7      │
│"mult3@shop.io"   │1.39       │59.4      │
│"sofia@shop.io"   │1.36       │75.3      │
└──────────────────┴───────────┴──────────┘
```

Таблица читается по диагонали. `oleg` — первый по влиянию и последний по мостовитости: у него сильная, но замкнутая аудитория, реклама через него до других групп не дойдёт. `sofia` — ровно наоборот: скромное влияние при максимальном betweenness, то есть через неё информация растекается по всему графу. Для посевной рассылки нужна `sofia`, для прямых продаж внутри её группы — `oleg`.

Заметно и другое: `mult1` и `mult3` из кольца мультиаккаунтов держатся высоко в обеих колонках. Искусственно созданная плотная группа выглядит как влиятельное сообщество — этим займётся урок 31.

## Что выбирать под задачу

| Задача | Метрика | Почему |
|---|---|---|
| Найти лидеров мнений для рекламы | PageRank | Учитывает качество аудитории, а не только размер |
| Рекомендовать «кого читать» конкретному пользователю | PageRank с `sourceNodes` | Локальная важность вместо глобальной |
| Найти узкие места в сети поставок | Betweenness | Показывает точки отказа |
| Выбрать точку посева информации | Closeness | Минимальное среднее расстояние до всех |
| Быстро оценить активность или популярность | Degree | Один проход, работает на любом объёме |
| Найти ядро плотного кластера | Eigenvector | Не размывается телепортацией |

Стоимость растёт в том же порядке: degree — линейный, PageRank — линейный на итерацию, closeness и betweenness — обход от каждого узла. Перед запуском betweenness на большом графе `.estimate` обязателен:

```cypher
CALL gds.betweenness.stream.estimate(
  {nodeCount: 20000000, relationshipCount: 200000000,
   nodeProjection: '*', relationshipProjection: '*'}, {})
YIELD requiredMemory
RETURN requiredMemory;
```

## Итоги урока

- Центральность — не одно понятие: degree, PageRank, betweenness, closeness и eigenvector отвечают на разные вопросы и дают разные топы на одном графе.
- Degree по умолчанию считает исходящие связи, то есть активность; популярность требует `orientation: 'REVERSE'`.
- `relationshipWeightProperty` превращает degree из счётчика связей в сумму весов; целое свойство GDS приводит к `double` сам, но явный `toFloat` при проекции делает тип предсказуемым.
- PageRank учитывает влиятельность соседей и потому поднимает наверх узлы с немногочисленной, но сильной аудиторией.
- PageRank итеративный: при `didConverge: FALSE` значения промежуточные и несравнимы между запусками, лимит по умолчанию — 20 итераций.
- `dampingFactor` управляет дальностью распространения влияния; 0.85 — стандарт, снижение смещает результат в сторону прямых связей.
- `sourceNodes` превращает PageRank в персонализированный: важность считается относительно заданного узла, а не графа целиком.
- Betweenness находит мосты между группами и стоит `O(V × E)`; `samplingSize` даёт приближение, пригодное для поиска кандидатов, но не для точного ранжирования.
- Closeness на направленном графе даёт 1.0 узлам с крошечным множеством достижимых соседей — считать его нужно на ненаправленной проекции.
- В ненаправленной проекции стрелка в `MATCH` остаётся: шаблон `-[:FOLLOWS]-` задваивает связи, направление снимает опция `undirectedRelationshipTypes`.
- `centralityDistribution` из режима `.stats` показывает, есть ли в графе выраженные хабы, — топ-5 сам по себе этого не говорит.
- Несколько центральностей, записанных в граф рядом, дают больше, чем любая по отдельности: расхождение между высоким PageRank и низким betweenness — это описание роли узла.
