# Урок 29. Поиск путей

Предполагается, что пройдены урок 25 (проекции и режимы выполнения) и урок 06, где разбирался нативный поиск путей средствами Cypher. Уроки 26–28 не требуются.

## Когда Cypher не справляется

Cypher умеет искать кратчайший путь сам:

```cypher
MATCH p = SHORTEST 1 (s:City {name: 'Брест'})-[:ROAD]-+(t:City {name: 'Могилёв'})
RETURN [n IN nodes(p) | n.name] AS route,
       reduce(km = 0.0, r IN relationships(p) | km + r.km) AS totalKm;
```

```
╒═══════════════════════════════════════════════╤══════════╕
│route                                          │totalKm   │
╞═══════════════════════════════════════════════╪══════════╡
│["Брест","Барановичи","Минск","Могилёв"]       │545.0     │
└───────────────────────────────────────────────┴──────────┘
```

Но «кратчайший» здесь означает «с наименьшим числом переходов». Вес связи Cypher при поиске не учитывает — он его даже не видит, `reduce` только досчитывает километры уже найденного маршрута. А маршрут в 515 километров существует:

```cypher
MATCH p = (s:City {name: 'Брест'})-[:ROAD]-+(t:City {name: 'Могилёв'})
RETURN [n IN nodes(p) | n.name] AS route,
       reduce(km = 0.0, r IN relationships(p) | km + r.km) AS totalKm
ORDER BY totalKm LIMIT 2;
```

```
╒══════════════════════════════════════════════════════════╤══════════╕
│route                                                     │totalKm   │
╞══════════════════════════════════════════════════════════╪══════════╡
│["Брест","Барановичи","Слуцк","Бобруйск","Могилёв"]      │515.0     │
│["Брест","Барановичи","Минск","Могилёв"]                 │545.0     │
└──────────────────────────────────────────────────────────┴──────────┘
```

Этот запрос перебирает все пути целиком и сортирует их. На графе из 12 городов он отрабатывает мгновенно, на графе из тысячи узлов число путей растёт комбинаторно и запрос не завершится никогда.

Отсюда граница ответственности:

| Задача | Инструмент |
|---|---|
| Кратчайший по числу переходов | Cypher `SHORTEST` |
| Все кратчайшие по числу переходов | Cypher `ALL SHORTEST` |
| Кратчайший по сумме весов | GDS Dijkstra |
| То же с географией | GDS A* |
| Несколько лучших маршрутов подряд | GDS Yen's |
| Расстояния от одного узла до всех | GDS single-source Dijkstra |
| Минимальная связывающая сеть | GDS spanning tree |

## Граф для примеров

В датасете магазина нет взвешенного графа с координатами, поэтому для этого урока нужен небольшой дорожный граф. Создай его — в конце урока он удаляется.

```cypher
UNWIND [
  {name: 'Минск',      lat: 53.902, lon: 27.562},
  {name: 'Брест',      lat: 52.098, lon: 23.734},
  {name: 'Гродно',     lat: 53.677, lon: 23.829},
  {name: 'Витебск',    lat: 55.184, lon: 30.201},
  {name: 'Гомель',     lat: 52.441, lon: 30.988},
  {name: 'Могилёв',    lat: 53.900, lon: 30.331},
  {name: 'Барановичи', lat: 53.132, lon: 26.014},
  {name: 'Бобруйск',   lat: 53.148, lon: 29.224},
  {name: 'Пинск',      lat: 52.121, lon: 26.096},
  {name: 'Орша',       lat: 54.509, lon: 30.425},
  {name: 'Молодечно',  lat: 54.316, lon: 26.855},
  {name: 'Слуцк',      lat: 53.027, lon: 27.560}
] AS c
CREATE (:City {name: c.name, latitude: c.lat, longitude: c.lon});

UNWIND [
  ['Минск','Барановичи',145], ['Барановичи','Брест',200], ['Барановичи','Пинск',175],
  ['Пинск','Брест',180],      ['Минск','Слуцк',105],      ['Слуцк','Бобруйск',100],
  ['Бобруйск','Могилёв',110], ['Минск','Могилёв',200],    ['Могилёв','Орша',80],
  ['Орша','Витебск',80],      ['Минск','Орша',215],       ['Минск','Молодечно',75],
  ['Молодечно','Гродно',250], ['Барановичи','Гродно',235], ['Бобруйск','Гомель',180],
  ['Могилёв','Гомель',285],   ['Минск','Витебск',280],    ['Слуцк','Барановичи',105]
] AS r
MATCH (a:City {name: r[0]}), (b:City {name: r[1]})
CREATE (a)-[:ROAD {km: toFloat(r[2])}]->(b);
```

Проекция: дороги двусторонние, вес и координаты нужны алгоритмам.

```cypher
MATCH (a:City)-[r:ROAD]->(b:City)
RETURN gds.graph.project('roads', a, b, {
  sourceNodeProperties: {latitude: a.latitude, longitude: a.longitude},
  targetNodeProperties: {latitude: b.latitude, longitude: b.longitude},
  relationshipProperties: {km: r.km}
}, {undirectedRelationshipTypes: ['*']}) AS g;
```

Координаты подаются на **обе** стороны связи: в проекции нет понятия «узел вообще», свойства грузятся отдельно для источника и цели. Пропустишь `targetNodeProperties` — у городов, которые встречаются только справа, координат не окажется.

## Dijkstra — кратчайший по весу

```cypher
MATCH (s:City {name: 'Брест'}), (t:City {name: 'Могилёв'})
CALL gds.shortestPath.dijkstra.stream('roads', {
  sourceNode: s,
  targetNode: t,
  relationshipWeightProperty: 'km'
})
YIELD totalCost, nodeIds, costs
RETURN totalCost, [n IN nodeIds | gds.util.asNode(n).name] AS route, costs;
```

```
╒═══════════╤══════════════════════════════════════════════════════╤═════════════════════════════╕
│totalCost  │route                                                 │costs                        │
╞═══════════╪══════════════════════════════════════════════════════╪═════════════════════════════╡
│515.0      │["Брест","Барановичи","Слуцк","Бобруйск","Могилёв"]  │[0.0,200.0,305.0,405.0,515.0]│
└───────────┴──────────────────────────────────────────────────────┴─────────────────────────────┘
```

`costs` — накопленная стоимость на каждом шаге, а не стоимость отдельного перехода. Разность соседних элементов даёт длину участка.

Маршрут состоит из четырёх переездов вместо трёх, но короче на 30 километров. Именно эту разницу Cypher увидеть не может.

Без `relationshipWeightProperty` Dijkstra считает вес каждой связи равным единице и вырождается в обычный поиск по числу переходов — тот же результат, что у `SHORTEST 1`.

> **Внимание**: свойство веса должно быть неотрицательным. Отрицательные веса Dijkstra не поддерживает ни в одной реализации: алгоритм считает уже закрытые узлы окончательными, и отрицательное ребро это допущение ломает. Если вес — это прибыль, которую нужно максимизировать, задача переформулируется в минимизацию, а не решается знаком.

## Single-source — расстояния до всех

Убери `targetNode`, и алгоритм посчитает расстояния от источника до каждого достижимого узла за один проход.

```cypher
MATCH (s:City {name: 'Минск'})
CALL gds.allShortestPaths.dijkstra.stream('roads', {
  sourceNode: s,
  relationshipWeightProperty: 'km'
})
YIELD targetNode, totalCost
RETURN gds.util.asNode(targetNode).name AS city, totalCost
ORDER BY totalCost DESC LIMIT 5;
```

```
╒═════════════╤═══════════╕
│city         │totalCost  │
╞═════════════╪═══════════╡
│"Гомель"     │385.0      │
│"Брест"      │345.0      │
│"Гродно"     │325.0      │
│"Пинск"      │320.0      │
│"Витебск"    │280.0      │
└─────────────┴───────────┘
```

Это стандартная основа для зон доставки: посчитать один раз от склада, записать расстояние свойством, дальше фильтровать обычным Cypher.

Для больших графов есть `gds.allShortestPaths.delta` — дельта-шаговый вариант того же алгоритма, который распараллеливается, тогда как классический Dijkstra последовательный по природе.

```cypher
MATCH (s:City {name: 'Минск'})
CALL gds.allShortestPaths.delta.stream('roads', {
  sourceNode: s,
  relationshipWeightProperty: 'km',
  delta: 50.0
})
YIELD targetNode, totalCost
RETURN gds.util.asNode(targetNode).name AS city, totalCost
ORDER BY totalCost DESC LIMIT 3;
```

Результат совпадает с точностью до строки: дельта-шаговый алгоритм точный, а не приближённый. Параметр `delta` — ширина «корзины» весов, которая обрабатывается параллельно: больше значение — больше параллелизма и больше лишней работы. Подбирается по порядку типичного веса связи.

## A* — Dijkstra с подсказкой

Dijkstra расходится от источника во все стороны одинаково. Если известны координаты, разумно в первую очередь проверять узлы, которые географически ближе к цели. Это и делает A*: к накопленной стоимости он добавляет оценку оставшегося расстояния по прямой.

```cypher
MATCH (s:City {name: 'Брест'}), (t:City {name: 'Могилёв'})
CALL gds.shortestPath.astar.stream('roads', {
  sourceNode: s,
  targetNode: t,
  relationshipWeightProperty: 'km',
  latitudeProperty: 'latitude',
  longitudeProperty: 'longitude'
})
YIELD totalCost, nodeIds
RETURN totalCost, [n IN nodeIds | gds.util.asNode(n).name] AS route;
```

```
╒═══════════╤══════════════════════════════════════════════════════╕
│totalCost  │route                                                 │
╞═══════════╪══════════════════════════════════════════════════════╪
│515.0      │["Брест","Барановичи","Слуцк","Бобруйск","Могилёв"]  │
└───────────┴──────────────────────────────────────────────────────┘
```

Тот же маршрут и та же стоимость. Так и должно быть: A* даёт **точный** ответ, он лишь просматривает меньше узлов по дороге к нему. На двенадцати городах экономии не видно, на дорожной сети страны она составляет порядок.

Гарантия точности держится на одном условии: оценка оставшегося расстояния не должна быть завышена. Расстояние по прямой всегда не больше расстояния по дорогам, поэтому условие выполняется автоматически. Отсюда и ограничение области применения: A* в GDS работает только с географическими координатами, для абстрактных графов эвристики нет.

Имена свойств проверяются в момент запуска:

```
The property `lat` has not been loaded.
```

Такая ошибка означает, что `latitudeProperty` не совпадает с именем свойства в проекции. Загруженное свойство должно называться точно так же, как указано в конфигурации, — и быть загруженным с обеих сторон связи.

## Yen's — K лучших маршрутов

Один кратчайший маршрут бесполезен, если по нему нельзя проехать. Yen's возвращает `k` путей в порядке возрастания стоимости, причём различающихся, а не вариаций одного и того же.

```cypher
MATCH (s:City {name: 'Брест'}), (t:City {name: 'Могилёв'})
CALL gds.shortestPath.yens.stream('roads', {
  sourceNode: s,
  targetNode: t,
  k: 3,
  relationshipWeightProperty: 'km'
})
YIELD index, totalCost, nodeIds
RETURN index, totalCost, [n IN nodeIds | gds.util.asNode(n).name] AS route;
```

```
╒═══════╤═══════════╤══════════════════════════════════════════════════════╕
│index  │totalCost  │route                                                 │
╞═══════╪═══════════╪══════════════════════════════════════════════════════╡
│0      │515.0      │["Брест","Барановичи","Слуцк","Бобруйск","Могилёв"]  │
│1      │545.0      │["Брест","Барановичи","Минск","Могилёв"]             │
│2      │610.0      │["Брест","Барановичи","Слуцк","Минск","Могилёв"]     │
└───────┴───────────┴──────────────────────────────────────────────────────┘
```

Нулевой индекс всегда совпадает с ответом Dijkstra. Разница между первым и вторым маршрутом — 30 километров, и если на первом ремонт, второй ничем не хуже.

Стоимость: Yen's запускает Dijkstra примерно `k × длина_пути` раз. Просить `k: 100` на большом графе — верный способ надолго занять сервер.

Типичные применения: резервные маршруты доставки, альтернативные цепочки поставок, объяснение рекомендации несколькими путями вместо одного.

## Spanning tree — минимальная связывающая сеть

Задача другая: не «как добраться из А в Б», а «какие связи оставить, чтобы всё осталось связным, а суммарная стоимость была минимальной».

```cypher
MATCH (s:City {name: 'Минск'})
CALL gds.spanningTree.stream('roads', {
  sourceNode: s,
  relationshipWeightProperty: 'km'
})
YIELD nodeId, parentId, weight
RETURN gds.util.asNode(parentId).name AS parent,
       gds.util.asNode(nodeId).name AS child,
       weight
ORDER BY weight;
```

```
╒═══════════════╤═══════════════╤═════════╕
│parent         │child          │weight   │
╞═══════════════╪═══════════════╪═════════╡
│"Минск"        │"Минск"        │0.0      │
│"Минск"        │"Молодечно"    │75.0     │
│"Орша"         │"Витебск"      │80.0     │
│"Могилёв"      │"Орша"         │80.0     │
│"Слуцк"        │"Бобруйск"     │100.0    │
│"Слуцк"        │"Барановичи"   │105.0    │
│"Минск"        │"Слуцк"        │105.0    │
│"Бобруйск"     │"Могилёв"      │110.0    │
│"Барановичи"   │"Пинск"        │175.0    │
│"Пинск"        │"Брест"        │180.0    │
│"Бобруйск"     │"Гомель"       │180.0    │
│"Барановичи"   │"Гродно"       │235.0    │
└───────────────┴───────────────┴─────────┘
```

Первая строка — сам источник, у него родитель равен ему самому и вес ноль. Остальные одиннадцать строк — рёбра дерева: двенадцать узлов, одиннадцать связей, ни одного цикла.

```cypher
MATCH (s:City {name: 'Минск'})
CALL gds.spanningTree.stats('roads', {sourceNode: s, relationshipWeightProperty: 'km'})
YIELD effectiveNodeCount, totalWeight
RETURN effectiveNodeCount, totalWeight;
```

```
╒════════════════════╤══════════════╕
│effectiveNodeCount  │totalWeight   │
╞════════════════════╪══════════════╡
│12                  │1425.0        │
└────────────────────┴══════════════┘
```

1425 километров вместо 3000 на всех восемнадцати дорогах — более чем вдвое дешевле при сохранении связности. С параметром `objective: 'maximum'` тот же алгоритм ищет самое дорогое дерево, и получается 2275: полезно, когда вес означает не затраты, а надёжность или пропускную способность.

> **Важно**: результат — дерево, а не сеть маршрутов. Путь между двумя городами по этому дереву почти наверняка длиннее кратчайшего. Минимальное остовное дерево отвечает на вопрос «что проложить», а не «как ехать».

Типичные применения: планирование кабельной или дорожной инфраструктуры, кластеризация через удаление самых тяжёлых рёбер дерева, скелет графа для визуализации.

## BFS и DFS — обход без весов

Иногда нужен не путь, а порядок обхода. Оба алгоритма работают на невзвешенном графе. На иерархии категорий магазина это видно нагляднее всего.

```cypher
MATCH (c:Category)-[:SUBCATEGORY_OF]->(p:Category)
RETURN gds.graph.project('tree', p, c, {relationshipType: 'HAS_CHILD'}) AS g;
```

Обрати внимание на порядок аргументов: в базе связь идёт от ребёнка к родителю, а в проекции нужна от родителя к ребёнку, поэтому `p` стоит перед `c`. Разворачивать направление через проекцию проще, чем менять модель данных.

```cypher
MATCH (s:Category {name: 'Кухня'})
CALL gds.bfs.stream('tree', {sourceNode: s})
YIELD path
RETURN [n IN nodes(path) | n.name] AS order;
```

```
╒═══════════════════════════════════════════════════════════════════════════════════════╕
│order                                                                                  │
╞═══════════════════════════════════════════════════════════════════════════════════════╡
│["Кухня","Кофеварки","Кофемолки","Чайники","Блендеры","Эспрессо-кофеварки",            │
│ "Капельные кофеварки"]                                                                │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

BFS идёт по уровням: сначала все прямые подкатегории «Кухни», затем всё, что вложено в них.

```cypher
MATCH (s:Category {name: 'Кухня'})
CALL gds.dfs.stream('tree', {sourceNode: s})
YIELD path
RETURN [n IN nodes(path) | n.name] AS order;
```

```
╒═══════════════════════════════════════════════════════════════════════════════════════╕
│order                                                                                  │
╞═══════════════════════════════════════════════════════════════════════════════════════╡
│["Кухня","Блендеры","Чайники","Кофемолки","Кофеварки","Капельные кофеварки",          │
│ "Эспрессо-кофеварки"]                                                                 │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

DFS уходит вглубь по одной ветке до конца, и «Капельные кофеварки» оказываются раньше, чем исчерпаны соседи верхнего уровня.

Ограничения обхода задаются параметрами:

```cypher
MATCH (s:Category {name: 'Кухня'})
CALL gds.bfs.stream('tree', {sourceNode: s, maxDepth: 1})
YIELD path
RETURN [n IN nodes(path) | n.name] AS order;
```

```
╒═════════════════════════════════════════════════════════════╕
│order                                                        │
╞═════════════════════════════════════════════════════════════╡
│["Кухня","Кофеварки","Кофемолки","Чайники","Блендеры"]      │
└─────────────────────────────────────────────────────────────┘
```

Есть и `targetNodes` — остановиться, как только достигнут любой из перечисленных узлов. Для навигации по каталогу BFS с `maxDepth` — прямой ответ на вопрос «что показать в меню на один уровень вниз».

## Запись маршрута в базу

Режим `.write` создаёт связь между началом и концом маршрута и вешает на неё детали.

```cypher
MATCH (s:City {name: 'Брест'}), (t:City {name: 'Могилёв'})
CALL gds.shortestPath.dijkstra.write('roads', {
  sourceNode: s,
  targetNode: t,
  relationshipWeightProperty: 'km',
  writeRelationshipType: 'ROUTE',
  writeNodeIds: true,
  writeCosts: true
})
YIELD relationshipsWritten
RETURN relationshipsWritten;

MATCH (a)-[r:ROUTE]->(b)
RETURN a.name AS from, b.name AS to, r.totalCost AS km, size(r.nodeIds) AS hops;
```

```
╒═════════╤═══════════╤═════════╤═══════╕
│from     │to         │km       │hops   │
╞═════════╪═══════════╪═════════╪═══════╡
│"Брест"  │"Могилёв"  │515.0    │5      │
└─────────┴───────────┴─────────┴───────┘
```

Без `writeNodeIds` и `writeCosts` в связь попадёт только итоговая стоимость, а сам маршрут будет потерян. `nodeIds` при этом хранит внутренние идентификаторы проекции — сами по себе они бесполезны, разворачивать их обратно нужно через `gds.util.asNode` в том же сеансе, пока проекция жива.

## Что выбирать

| Задача | Алгоритм | Условие |
|---|---|---|
| Минимум переходов | Cypher `SHORTEST` | Веса не нужны |
| Минимум суммы весов | `shortestPath.dijkstra` | Веса неотрицательны |
| То же с координатами | `shortestPath.astar` | Есть широта и долгота |
| Резервные маршруты | `shortestPath.yens` | Небольшое `k` |
| Расстояния до всех | `allShortestPaths.dijkstra` | Один источник |
| То же на большом графе | `allShortestPaths.delta` | Нужен параллелизм |
| Минимальная сеть связей | `spanningTree` | Нужна связность, не маршруты |
| Порядок обхода, уровни | `bfs` / `dfs` | Веса игнорируются |

Практическое правило: если веса нет — оставайся в Cypher, он проще и не требует проекции. Как только появляется вес, стоимость или расстояние, переходи в GDS.

## Практика

1. Создай граф городов и дорог, построй ненаправленную проекцию `roads` с весом и координатами.
2. Найди маршрут Брест — Могилёв через Cypher `SHORTEST 1` и через Dijkstra с весом. Объясни расхождение в километрах.
3. Убери `relationshipWeightProperty` из вызова Dijkstra и убедись, что результат совпал с `SHORTEST 1`.
4. Разбери массив `costs` в выдаче Dijkstra: посчитай из него длину каждого участка.
5. Посчитай расстояния от Минска до всех городов одним вызовом и найди самый удалённый.
6. Запусти тот же расчёт через `allShortestPaths.delta` с разными значениями `delta` и убедись, что результат не меняется.
7. Запусти A* и сравни маршрут с ответом Dijkstra. Затем укажи `latitudeProperty: 'lat'` и разбери текст ошибки.
8. Найди три лучших маршрута Брест — Могилёв через Yen's и оцени, насколько второй хуже первого.
9. Построй минимальное остовное дерево от Минска, посчитай его суммарный вес и сравни с суммой всех дорог.
10. Запусти spanning tree с `objective: 'maximum'` и объясни, в какой задаче нужен именно такой результат.
11. Построй проекцию `tree` по категориям и сравни порядок обхода BFS и DFS от «Кухни».
12. Получи через BFS с `maxDepth: 1` список прямых подкатегорий «Кухни».
13. Запиши маршрут Брест — Могилёв связью `ROUTE` с `writeNodeIds` и `writeCosts`, прочитай её обычным Cypher.
14. Удали проекции, связи `ROUTE` и весь граф городов: `MATCH (c:City) DETACH DELETE c`.

## Итоги урока

- Cypher `SHORTEST` минимизирует число переходов и не видит весов; перебор всех путей с `reduce` даёт верный ответ, но не масштабируется.
- Dijkstra находит путь минимальной суммы весов и требует неотрицательных весов — отрицательные ломают само допущение алгоритма.
- Без `relationshipWeightProperty` Dijkstra считает все связи единичными и вырождается в поиск по числу переходов.
- Массив `costs` содержит накопленную стоимость на каждом шаге, а не длину отдельного участка.
- Вариант без `targetNode` считает расстояния от источника до всех достижимых узлов за один проход — основа для зон доставки.
- `allShortestPaths.delta` — точный параллельный аналог Dijkstra для больших графов; `delta` управляет шириной параллельно обрабатываемой корзины весов.
- A* даёт тот же точный результат, что Dijkstra, но просматривает меньше узлов; в GDS он работает только с географическими координатами.
- В проекции свойства грузятся отдельно для источника и цели связи: координаты нужно указывать и в `sourceNodeProperties`, и в `targetNodeProperties`.
- Yen's возвращает `k` различных маршрутов по возрастанию стоимости и запускает Dijkstra многократно, поэтому большое `k` дорого.
- Минимальное остовное дерево отвечает на вопрос «какие связи проложить», а не «как проехать»: путь по дереву обычно длиннее кратчайшего.
- BFS обходит по уровням, DFS уходит вглубь ветки; `maxDepth` и `targetNodes` ограничивают обход.
- Направление связи разворачивается порядком аргументов в `gds.graph.project` — менять ради этого модель данных не нужно.
- `.write` сохраняет маршрут связью между концами, но сам путь попадает в неё только с `writeNodeIds` и `writeCosts`.
