# Урок 28. Similarity и эмбеддинги

Предполагается, что пройден урок 25: проекции, каталог графов и режимы выполнения. Проекция `purchases` из урока 25 используется здесь как основная.

> **Важно**: выводы в уроке сняты на базовом датасете из урока 9, без синтетики. После генератора в парах похожих пользователей появятся аккаунты `synth*`, а коэффициенты сходства дойдут до 1.0 — синтетические заказы собираются из случайных товаров, и совпадения там встречаются чаще. Смотри на форму результата, а не на конкретные пары.

## Две постановки задачи «похожести»

Похожесть узлов считают двумя принципиально разными способами.

**Явное сравнение соседей.** Два пользователя похожи, если купили одни и те же товары. Считается точно, объясняется одной фразой, но требует сравнить каждого с каждым.

**Сравнение векторов.** Каждому узлу сопоставляется вектор из нескольких десятков чисел, отражающий его положение в графе, дальше сравниваются векторы. Считается быстро на любом объёме, но объяснить, почему числа именно такие, невозможно.

| | Node Similarity | KNN + эмбеддинги |
|---|---|---|
| Основа | Общие соседи | Векторы признаков |
| Точность | Точный ответ | Приближение |
| Сложность | Квадратичная по числу узлов | Линейная с константой |
| Объяснимость | Полная | Отсутствует |
| Когда | До миллионов узлов, нужны объяснения | Десятки миллионов узлов и больше |

Практический маршрут обычно такой: Node Similarity на первых версиях продукта, эмбеддинги — когда граф перестаёт помещаться в квадратичный алгоритм или когда результат идёт в ML-модель.

## Проекция для сравнения покупателей

```cypher
MATCH (u:User)-[:PLACED]->(o:Order)-[c:CONTAINS]->(p:Product)
RETURN gds.graph.project('purchases', u, p, {
  sourceNodeLabels: ['User'],
  targetNodeLabels: ['Product'],
  relationshipType: 'BOUGHT',
  relationshipProperties: { qty: toFloat(c.qty) }
}) AS g;
```

Получается двудольный граф: пользователи слева, товары справа, связи только между долями. Это стандартная форма входа для Node Similarity.

## Node Similarity — общие соседи

Алгоритм считает коэффициент Жаккара: размер пересечения множеств соседей, делённый на размер объединения. Полностью совпали покупки — 1.0, не пересеклись вовсе — 0.0.

```cypher
CALL gds.nodeSimilarity.stream('purchases')
YIELD node1, node2, similarity
RETURN gds.util.asNode(node1).email AS a,
       gds.util.asNode(node2).email AS b,
       round(similarity, 3) AS sim
ORDER BY sim DESC, a LIMIT 6;
```

```
╒══════════════════╤══════════════════╤═══════╕
│a                 │b                 │sim    │
╞══════════════════╪══════════════════╪═══════╡
│"maria@shop.io"   │"mult4@shop.io"   │0.6    │
│"mult4@shop.io"   │"maria@shop.io"   │0.6    │
│"denis@shop.io"   │"egor@shop.io"    │0.5    │
│"egor@shop.io"    │"denis@shop.io"   │0.5    │
│"julia@shop.io"   │"timur@shop.io"   │0.5    │
│"mult2@shop.io"   │"pavel@shop.io"   │0.5    │
└──────────────────┴──────────────────┴───────┘
```

Каждая пара приходит дважды — в обе стороны. Это не дефект: `topK` применяется отдельно к каждому узлу, поэтому `a → b` может попасть в выдачу, а `b → a` нет. Если нужны уникальные пары, фильтруй `WHERE node1 < node2`.

Алгоритм сравнивает только **исходящие** узлы проекции, то есть в `purchases` — пользователей. Товары в выдачу не попадают: у них в этой проекции нет исходящих связей. Чтобы сравнивать товары, нужна проекция с обратным направлением:

```cypher
MATCH (u:User)-[:PLACED]->(o:Order)-[:CONTAINS]->(p:Product)
RETURN gds.graph.project('boughtBy', p, u, {
  sourceNodeLabels: ['Product'],
  targetNodeLabels: ['User'],
  relationshipType: 'BOUGHT_BY'
}) AS g;

CALL gds.nodeSimilarity.stream('boughtBy', {topK: 1})
YIELD node1, node2, similarity
RETURN gds.util.asNode(node1).title AS p1,
       gds.util.asNode(node2).title AS p2,
       round(similarity, 3) AS sim
ORDER BY sim DESC LIMIT 6;
```

```

│p1                               │p2                               │sim    │
╞═════════════════════════════════╪═════════════════════════════════╪═══════╡
│"Кофеварка Aroma Pro"            │"Чайник Steam Classic"           │0.4    │
│"Чайник Steam Classic"           │"Кофеварка Aroma Pro"            │0.4    │
│"Эспрессо-машина Barista One"    │"Торшер Lumen Floor"             │0.4    │
│"Торшер Lumen Floor"             │"Эспрессо-машина Barista One"    │0.4    │
```

Три пары из четырёх осмысленны: кофеварка и чайник, два блендера. Четвёртая — эспрессо-машина и торшер — напоминание, что на 24 товарах и 127 покупках совпадение из четырёх пользователей может быть случайным. Это не проблема алгоритма, а нехватка данных.

### Ограничение выдачи

Без ограничений алгоритм возвращает все пары с ненулевой похожестью — на 29 сравниваемых узлах это 257 строк, на миллионе узлов это неподъёмный объём.

```cypher
CALL gds.nodeSimilarity.stats('purchases')
YIELD nodesCompared, similarityPairs, similarityDistribution
RETURN nodesCompared, similarityPairs,
       round(similarityDistribution.mean, 3) AS mean,
       round(similarityDistribution.max, 3) AS max;
```

```
╒════════════════╤══════════════════╤═══════╤═══════╕
│nodesCompared   │similarityPairs   │mean   │max    │
╞════════════════╪══════════════════╪═══════╪═══════╡
│29              │257               │0.222  │0.6    │
└────────────────┴──────────────────┴───────┴───────┘
```

Два параметра режут выдачу:

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `topK` | 10 | Сколько лучших соседей оставить у каждого узла |
| `similarityCutoff` | 1E-42 | Порог похожести, ниже которого пара отбрасывается |
| `degreeCutoff` | 1 | Минимальная степень узла, чтобы вообще участвовать |

```cypher
CALL gds.nodeSimilarity.stats('purchases', {topK: 3, similarityCutoff: 0.3})
YIELD nodesCompared, similarityPairs
RETURN nodesCompared, similarityPairs;
```

257 пар превращаются в 43. Для рекомендаций `topK` в районе 10–20 практически всегда достаточно, а `similarityCutoff` отсекает шум из пар с одной случайно совпавшей покупкой.

### Веса и косинус

Жаккар не различает «купил один раз» и «купил десять раз». С весом и метрикой `COSINE` количество начинает учитываться:

```cypher
CALL gds.nodeSimilarity.stream('purchases', {
  relationshipWeightProperty: 'qty',
  similarityMetric: 'COSINE',
  topK: 2
})
YIELD node1, node2, similarity
RETURN gds.util.asNode(node1).email AS a,
       gds.util.asNode(node2).email AS b,
       round(similarity, 3) AS sim
ORDER BY sim DESC, a LIMIT 4;
```

### Запись результата связями

Similarity — единственный из рассмотренных алгоритмов, который пишет в базу не свойства, а **связи**.

```cypher
CALL gds.nodeSimilarity.write('boughtBy', {
  topK: 3,
  similarityCutoff: 0.2,
  writeRelationshipType: 'SIMILAR_TO',
  writeProperty: 'score'
})
YIELD relationshipsWritten, nodesCompared
RETURN relationshipsWritten, nodesCompared;
```

```
╒══════════════════════╤════════════════╕
│relationshipsWritten  │nodesCompared   │
╞══════════════════════╪════════════════╡
│60                    │23              │
└──────────────────────┴────────────────┘
```

Дальше блок «с этим товаром покупают» — обычный запрос на один переход:

```cypher
MATCH (p:Product {title: 'Кофеварка Aroma Pro'})-[s:SIMILAR_TO]->(o:Product)
RETURN o.title AS also, round(s.score, 3) AS score
ORDER BY score DESC;
```

```
╒═════════════════════════╤════════╕
│also                     │score   │
╞═════════════════════════╪════════╡
│"Чайник Steam Classic"   │0.4     │
│"Наушники Echo Light"    │0.222   │
└─────────────────────────┴────────┘
```

Это и есть смысл предвычисления: тяжёлый алгоритм отработал ночью, а запрос на витрине выполняется за миллисекунды.

> **Внимание**: повторный `.write` не заменяет старые связи, а добавляет новые поверх. Перед пересчётом связи предыдущего запуска нужно удалять явно — `MATCH ()-[s:SIMILAR_TO]->() DELETE s`, на большом графе через `CALL {} IN TRANSACTIONS` из урока 21.

## KNN — похожесть по векторам

KNN сравнивает не соседей, а **свойства узлов**. Он не перебирает все пары: начинает со случайных кандидатов и итеративно улучшает список соседей, спрашивая «а с кем дружат мои соседи». Отсюда линейная сложность и приближённость результата.

Ключевой момент — какие свойства подать на вход. Наивный вариант работает плохо:

```cypher
MATCH (p:Product)
RETURN gds.graph.project('catalog', p, null,
  {sourceNodeProperties: {price: p.price}, targetNodeProperties: null}) AS g;

CALL gds.knn.stream('catalog', {nodeProperties: ['price'], topK: 1, randomSeed: 42, concurrency: 1})
YIELD node1, node2, similarity
RETURN gds.util.asNode(node1).title AS a, gds.util.asNode(node2).title AS b,
       round(similarity, 4) AS sim
ORDER BY sim DESC LIMIT 3;
```

```
╒═════════════════════════════╤═════════════════════════════╤═══════╕
│a                            │b                            │sim    │
╞═════════════════════════════╪═════════════════════════════╪═══════╡
│"Чайник Steam Classic"       │"Кофемолка Aroma Compact"    │1.0    │
│"Кофеварка Aroma Mini"       │"Плед Cozy Wool"             │1.0    │
│"Кофемолка Fine Grind"       │"Наушники Echo Light"        │1.0    │
└─────────────────────────────┴─────────────────────────────┴───────┘
```

Кофеварка «похожа» на плед с оценкой 1.0, потому что у них одинаковая цена 3290. Для одного числового свойства GDS считает похожесть как `1 / (1 + |a − b|)`, и совпадение цены даёт единицу. Ни о какой содержательной похожести речи нет.

Вывод: KNN хорош ровно настолько, насколько хороши поданные ему признаки. Признаки, отражающие положение узла в графе, даёт следующий шаг.

## FastRP — эмбеддинги за один проход

FastRP превращает положение узла в графе в вектор фиксированной длины. Каждому узлу выдаётся случайный вектор, затем несколько раз усредняется с векторами соседей — так информация о структуре растекается по вектору. Узлы с похожим окружением получают близкие векторы.

```cypher
CALL gds.fastRP.stream('socialU', {embeddingDimension: 8, randomSeed: 42})
YIELD nodeId, embedding
RETURN gds.util.asNode(nodeId).email AS email,
       [x IN embedding | round(x, 3)] AS embedding
ORDER BY email LIMIT 3;
```

```
╒══════════════════╤═════════════════════════════════════════════════════════════╕
│email             │embedding                                                    │
╞══════════════════╪═════════════════════════════════════════════════════════════╡
│"alina@shop.io"   │[-0.937,-1.082,0.13,-0.689,-0.155,0.423,-0.194,0.537]        │
│"anna@shop.io"    │[-0.99,-0.179,-0.783,-0.662,0.676,1.004,-0.05,0.451]         │
│"artem@shop.io"   │[-0.94,-0.178,-0.782,-0.631,0.735,0.902,0.134,0.444]         │
└──────────────────┴─────────────────────────────────────────────────────────────┘
```

Векторы `anna` и `artem` почти совпадают покомпонентно, а у `alina` они заметно другие. Отдельные числа при этом не значат ничего: у измерений нет интерпретации, значение имеет только расстояние между векторами.

Основные параметры:

| Параметр | Смысл |
|---|---|
| `embeddingDimension` | Длина вектора. 128–256 для больших графов, 64 достаточно для десятков тысяч узлов |
| `iterationWeights` | Веса шагов распространения. Длина списка — число итераций, то есть радиус охвата |
| `randomSeed` | Воспроизводимость. Без него каждый запуск даёт другие векторы |
| `propertyRatio` | Доля вектора, отведённая под свойства узла, а не под структуру |

`iterationWeights` по умолчанию `[0.0, 1.0, 1.0]`: первый ноль отбрасывает исходный случайный вектор, остаётся информация о соседях первого и второго порядка. Список `[0.0, 1.0, 1.0, 1.0]` расширяет охват до трёх шагов.

> **Важно**: без `randomSeed` FastRP при каждом запуске выдаёт другие числа. Векторы из разных запусков сравнивать между собой нельзя — они лежат в разных случайных базисах. Если эмбеддинги сохраняются в базу и используются приложением, seed фиксируется и хранится вместе с моделью данных.

### FastRP плюс KNN

Канонический конвейер: FastRP кладёт вектор в проекцию режимом `.mutate`, KNN сразу его использует.

```cypher
CALL gds.fastRP.mutate('socialU',
  {embeddingDimension: 64, randomSeed: 42, mutateProperty: 'emb'})
YIELD nodePropertiesWritten
RETURN nodePropertiesWritten;

CALL gds.knn.stream('socialU',
  {nodeProperties: ['emb'], topK: 2, randomSeed: 42, concurrency: 1})
YIELD node1, node2, similarity
RETURN gds.util.asNode(node1).email AS a,
       gds.util.asNode(node2).email AS b,
       round(similarity, 3) AS sim
ORDER BY sim DESC LIMIT 6;
```

```
╒══════════════════╤══════════════════╤═══════╕
│a                 │b                 │sim    │
╞══════════════════╪══════════════════╪═══════╡
│"banned1@shop.io" │"roman@shop.io"   │0.989  │
│"roman@shop.io"   │"banned1@shop.io" │0.989  │
│"anna@shop.io"    │"artem@shop.io"   │0.988  │
│"artem@shop.io"   │"anna@shop.io"    │0.988  │
│"sergey@shop.io"  │"petr@shop.io"    │0.984  │
│"petr@shop.io"    │"sergey@shop.io"  │0.984  │
└──────────────────┴──────────────────┴───────┘
```

Здесь виден смысл всей связки. У `anna` и `artem` нет ни одного общего купленного товара — на проекции `purchases` их похожесть по Жаккару равна нулю, и Node Similarity никогда бы их не сопоставил. Но в сети подписок они занимают почти одинаковые позиции: похожее окружение, похожие связи второго порядка. FastRP закодировал это в вектор, KNN нашёл по вектору.

Обрати внимание и на другое: похожесть у всех пар в топе выше 0.98, а разброс между первым и шестым местом — тысячные доли. На плотном графе из 30 узлов структурные позиции близки почти у всех, и абсолютные значения косинуса теряют смысл. Работает только порядок, да и тот на таком графе неустойчив.

Значения `.mutate` живут только в проекции. `CALL gds.graph.drop` уничтожает их вместе с ней; чтобы эмбеддинги пережили перезапуск, нужен `.write`:

```cypher
CALL gds.fastRP.write('socialU',
  {embeddingDimension: 64, randomSeed: 42, writeProperty: 'embedding'})
YIELD nodePropertiesWritten
RETURN nodePropertiesWritten;
```

### Сравнение сохранённых векторов

Записанный в базу эмбеддинг — обычный список чисел, и сравнивать его можно прямо в Cypher.

```cypher
MATCH (a:User {email: 'anna@shop.io'}), (b:User) WHERE b <> a
RETURN b.email AS email, round(gds.similarity.cosine(a.embedding, b.embedding), 3) AS sim
ORDER BY sim DESC LIMIT 4;
```

```
╒══════════════════╤═══════╕
│email             │sim    │
╞══════════════════╪═══════╡
│"artem@shop.io"   │0.977  │
│"lidia@shop.io"   │0.929  │
│"ivan@shop.io"    │0.92   │
│"pavel@shop.io"   │0.89   │
└──────────────────┴───────┘
```

> **Внимание**: у Neo4j есть встроенная функция `vector.similarity.cosine` с другой шкалой. Она возвращает `(1 + cos) / 2`, то есть отображает диапазон `[-1, 1]` в `[0, 1]`. Для той же пары `anna`–`artem` она даёт 0.9884 против 0.977 у `gds.similarity.cosine`. Числа не взаимозаменяемы: пороги, подобранные для одной функции, для другой неверны.

Полный перебор всех пар в Cypher работает на десятках тысяч узлов, но не на миллионах. Для больших графов эмбеддинги кладут в векторный индекс — это тема урока 35.

## GraphSAGE — обучаемые эмбеддинги

FastRP не обучается: он применяет фиксированное случайное преобразование. GraphSAGE обучает нейронную сеть, которая агрегирует признаки соседей, и сохраняет её как модель.

Практическая разница в одном: обученную модель можно применить к **новому** узлу, которого не было при обучении. FastRP при появлении новых узлов нужно пересчитывать целиком.

Обучение требует числовых признаков на узлах. Возьмём степень узла и уже посчитанный FastRP-вектор:

```cypher
CALL gds.degree.mutate('socialU', {mutateProperty: 'deg'})
YIELD nodePropertiesWritten RETURN nodePropertiesWritten;

CALL gds.beta.graphSage.train('socialU', {
  modelName: 'socialSage',
  featureProperties: ['deg', 'emb'],
  embeddingDimension: 16,
  epochs: 2,
  sampleSizes: [5, 3],
  randomSeed: 42
})
YIELD modelInfo
RETURN modelInfo.metrics.didConverge AS didConverge,
       modelInfo.metrics.ranEpochs AS ranEpochs;
```

```
╒═════════════╤════════════╕
│didConverge  │ranEpochs   │
╞═════════════╪════════════╡
│TRUE         │1           │
└─────────────┴────────────┘
```

Применение обученной модели:

```cypher
CALL gds.beta.graphSage.stream('socialU', {modelName: 'socialSage'})
YIELD nodeId, embedding
RETURN gds.util.asNode(nodeId).email AS email, size(embedding) AS dim
ORDER BY email LIMIT 3;
```

Модели живут в отдельном каталоге и, как и проекции, занимают память:

```cypher
CALL gds.model.list() YIELD modelName, modelType RETURN modelName, modelType;
CALL gds.model.drop('socialSage') YIELD modelName RETURN modelName;
```

`sampleSizes: [5, 3]` — сколько соседей сэмплируется на каждом слое: пять на первом, три на втором. Именно сэмплирование делает GraphSAGE применимым к графам, где у отдельных узлов миллионы связей.

> **Важно**: в Community сохранение моделей на диск недоступно — при перезапуске сервера модель теряется и требует переобучения. Процедуры находятся в пространстве `gds.beta`, то есть API ещё может измениться.

## Что выбирать

| Задача | Инструмент |
|---|---|
| «С этим товаром покупают» | Node Similarity на двудольном графе покупок |
| «Похожие на вас покупатели» | Node Similarity, метрика COSINE с весом `qty` |
| Похожесть по структурной роли, а не по общим соседям | FastRP + KNN |
| Признаки для внешней ML-модели | FastRP `.write`, вектор как фича |
| Граф постоянно пополняется новыми узлами | GraphSAGE |
| Семантический поиск по графу | Эмбеддинги плюс векторный индекс, урок 35 |

Порядок действий на практике: начинать с Node Similarity, потому что результат объясним и проверяем глазами. Переходить на эмбеддинги, когда квадратичная сложность перестаёт помещаться в окно пересчёта или когда нужны структурные похожести без общих соседей.

## Практика

1. Построй проекцию `purchases` и запусти Node Similarity в режиме `.stream`. Убедись, что каждая пара приходит дважды, и оставь уникальные через `WHERE node1 < node2`.
2. Посмотри `.stats`: сколько пар возвращается без ограничений и каково среднее значение похожести.
3. Подбери `topK` и `similarityCutoff` так, чтобы осталось около 40 пар.
4. Построй проекцию `boughtBy` с обратным направлением и найди похожие товары. Объясни, почему на `purchases` товары в выдачу не попадали.
5. Сравни результат Жаккара и метрики `COSINE` с весом `qty`, найди пару, которая появилась только во втором варианте.
6. Запиши похожесть товаров связями `SIMILAR_TO` и собери запрос «с этим товаром покупают» для любого товара.
7. Запусти `.write` второй раз и посчитай, сколько связей `SIMILAR_TO` стало. Напиши запрос, который удаляет старые перед пересчётом.
8. Запусти KNN на одном свойстве `price` и найди пары с похожестью 1.0. Объясни, откуда единица.
9. Посчитай FastRP с `embeddingDimension: 8` дважды без `randomSeed` и убедись, что векторы разные.
10. Сделай конвейер FastRP `.mutate` → KNN и найди в топе пару пользователей без единого общего купленного товара.
11. Запиши эмбеддинги в базу и посчитай косинус между двумя пользователями через `gds.similarity.cosine` и `vector.similarity.cosine`. Объясни расхождение.
12. Обучи GraphSAGE на признаках `deg` и `emb`, примени модель, затем удали её из каталога моделей.
13. Удали все проекции, свойство `embedding` и связи `SIMILAR_TO`.

## Итоги урока

- Похожесть считают двумя способами: по общим соседям — точно и объяснимо, по векторам — быстро и приближённо.
- Node Similarity считает коэффициент Жаккара и сравнивает только узлы с исходящими связями: чтобы сравнить товары вместо пользователей, нужна проекция с обратным направлением.
- Каждая пара приходит в выдаче дважды, потому что `topK` применяется к каждому узлу отдельно.
- Без `topK` и `similarityCutoff` алгоритм возвращает все ненулевые пары — на большом графе это неподъёмный объём.
- Метрика `COSINE` с весом связи учитывает количество, а не только факт покупки, и поднимает пары со схожими пропорциями.
- Node Similarity пишет в базу связи, а не свойства, и повторный `.write` добавляет их поверх старых, а не заменяет.
- KNN сравнивает свойства узлов и хорош ровно настолько, насколько осмысленны признаки: на одной цене он объявляет кофеварку похожей на плед.
- FastRP кодирует положение узла в графе вектором фиксированной длины; отдельные компоненты не интерпретируются, значение имеет только расстояние.
- Без `randomSeed` эмбеддинги FastRP несравнимы между запусками — они лежат в разных случайных базисах.
- Связка FastRP плюс KNN сопоставляет узлы по структурной позиции, включая пары без единого общего товара, которым Node Similarity на графе покупок даёт ноль.
- `gds.similarity.cosine` и встроенная `vector.similarity.cosine` работают в разных шкалах: вторая возвращает `(1 + cos) / 2`, и пороги между ними не переносятся.
- GraphSAGE обучает модель, применимую к новым узлам без полного пересчёта; модели живут в отдельном каталоге, в Community не сохраняются на диск и теряются при перезапуске.
