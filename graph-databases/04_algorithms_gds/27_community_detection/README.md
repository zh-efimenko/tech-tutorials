# Урок 27. Выделение сообществ

Предполагается, что пройден урок 25. Урок 26 не обязателен, но полезен: там разобрана та же проекция `socialU` и разница между направленным и ненаправленным графом.

> **Важно**: выводы в уроке сняты на базовом датасете из урока 9, без синтетики. Разделы про сеть подписок после запуска генератора дадут другие числа — там будут десятки тысяч узлов вместо тридцати. Раздел про антифрод (`identity`) от синтетики не зависит: она не создаёт устройств, карт и адресов, поэтому результаты воспроизводятся один в один.

## Что такое сообщество

Сообщество — это подмножество узлов, внутри которого связей заметно больше, чем наружу. Никакого заранее заданного признака у него нет: алгоритм не знает про города, категории и возраст, он смотрит только на структуру связей.

Отсюда главное свойство метода: сегментация получается такой, какой её создали сами пользователи, а не такой, какую придумал аналитик. Это одновременно и сила, и ограничение — объяснять найденные сообщества приходится постфактум.

Типовые задачи:

| Задача | Что ищем |
|---|---|
| Сегментация аудитории для рассылок | Группы с плотными взаимными подписками |
| Антифрод | Кольца аккаунтов, связанных общими устройствами и картами |
| Дедупликация | Кластеры записей, ссылающихся на один реальный объект |
| Разбиение монолита | Модули с плотной внутренней связностью |
| Санитарная проверка данных | Изолированные куски графа, которых быть не должно |

## Две группы алгоритмов

Разница между ними принципиальнее, чем разница внутри каждой.

**Компоненты связности** (`wcc`, `scc`) отвечают на вопрос «между какими узлами вообще есть путь». Результат детерминирован, параметров почти нет, ответ единственно верный. Это не столько аналитика, сколько факт о графе.

**Модулярные алгоритмы** (`louvain`, `leiden`, `labelPropagation`) ищут места, где связей плотнее. Ответ не единственный, зависит от параметров и от случайности, и качество приходится измерять отдельно.

Начинать всегда стоит с WCC: если граф распадается на компоненты, искать сообщества внутри одного большого куска бессмысленно, пока не понятно, что это за куски.

## Проекция

```cypher
MATCH (u:User)-[:FOLLOWS]->(v:User)
RETURN gds.graph.project('socialU', u, v,
  {}, {undirectedRelationshipTypes: ['*']}) AS g;
```

> **Важно**: Louvain, Leiden и label propagation определены на ненаправленном графе. Запустить их на направленной проекции технически можно, но результат будет другим и хуже — ниже в уроке есть цифры.

## WCC — компоненты связности

Weakly Connected Components разбивает граф на куски, между которыми нет ни одного пути, если игнорировать направление связей.

```cypher
CALL gds.wcc.stream('socialU')
YIELD nodeId, componentId
RETURN componentId, count(*) AS members
ORDER BY members DESC;
```

```
╒═════════════╤═════════╕
│componentId  │members  │
╞═════════════╪═════════╡
│0            │30       │
└─────────────┴─────────┘
```

Одна компонента на все 30 пользователей: сеть подписок связная, изолированных островов нет. Это ожидаемый и скучный результат — и именно поэтому проверка полезна. Если бы компонент оказалось три, любая последующая аналитика по «сообществам» считалась бы отдельно внутри каждой.

WCC линеен по числу рёбер и практически бесплатен. Запускать его первым — дешёвая привычка.

### WCC с порогом веса

Настоящая сила WCC раскрывается на графах, которые строятся под задачу. Возьмём антифрод: свяжем пользователей, у которых есть общие устройства, карты или адреса, и весом сделаем количество общих идентификаторов.

```cypher
MATCH (a:User)-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]->(x)
      <-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]-(b:User)
WHERE elementId(a) < elementId(b)
WITH a, b, count(DISTINCT x) AS shared
RETURN gds.graph.project('identity', a, b,
  {relationshipType: 'SHARES', relationshipProperties: {shared: toFloat(shared)}},
  {undirectedRelationshipTypes: ['*']}) AS g;
```

Условие `elementId(a) < elementId(b)` берёт каждую пару один раз: без него `MATCH` вернёт и `(a, b)`, и `(b, a)`. В проекции окажется 7 узлов и 22 связи — только те пользователи, у кого вообще есть общие идентификаторы.

```cypher
CALL gds.wcc.stream('identity')
YIELD nodeId, componentId
WITH componentId, collect(gds.util.asNode(nodeId).email) AS emails
WHERE size(emails) > 1
RETURN componentId, size(emails) AS members, emails
ORDER BY members DESC;
```

```
╒═════════════╤═════════╤══════════════════════════════════════════════════════╕
│componentId  │members  │emails                                                │
╞═════════════╪═════════╪══════════════════════════════════════════════════════╡
│2            │5        │["mult1@shop.io", "mult2@shop.io", "mult3@shop.io",   │
│             │         │ "mult4@shop.io", "banned1@shop.io"]                  │
│0            │2        │["ivan@shop.io", "petr@shop.io"]                      │
└─────────────┴─────────┴──────────────────────────────────────────────────────┘
```

Найдены две группы. Первая — кольцо мультиаккаунтов: пять учёток делят одно устройство, одну карту и один адрес, причём у `banned1` статус `banned`. Вторая — `ivan` и `petr`, у которых общее устройство и общий адрес доставки. Это семья, а не мошенники.

Отличить их помогает порог по весу: параметр `threshold` отбрасывает связи, вес которых **не превышает** заданный.

```cypher
CALL gds.wcc.stream('identity', {relationshipWeightProperty: 'shared', threshold: 2.0})
YIELD nodeId, componentId
WITH componentId, collect(gds.util.asNode(nodeId).email) AS emails
WHERE size(emails) > 1
RETURN componentId, size(emails) AS members
ORDER BY members DESC;
```

```
╒═════════════╤═════════╕
│componentId  │members  │
╞═════════════╪═════════╡
│2            │5        │
└─────────────┴─────────┘
```

У пары `ivan`–`petr` вес 2, у пар внутри кольца — 3. Порог 2.0 оставляет только строго большее, и легальный шеринг отсеивается. Это ровно тот случай, ради которого стоит держать вес на связи: одна цифра в конфигурации разделяет ложное срабатывание и настоящий сигнал. Подбирать её нужно на размеченных данных, а не на глаз, — подробнее в уроке 31.

## SCC — сильная связность

Strongly Connected Components учитывает направление: узлы попадают в одну компоненту, только если путь есть в обе стороны. Для сети подписок это означает «взаимно достижимы по цепочке подписок».

```cypher
CALL gds.scc.stream('social')
YIELD nodeId, componentId
RETURN componentId, count(*) AS members
ORDER BY members DESC LIMIT 5;
```

```
╒═════════════╤═════════╕
│componentId  │members  │
╞═════════════╪═════════╡
│0            │23       │
│3            │1        │
│17           │1        │
│18           │1        │
│21           │1        │
└─────────────┴─────────┘
```

Здесь нужна **направленная** проекция `social` — на ненаправленной SCC вырождается в WCC и всегда даёт один компонент.

Картина типичная для социального графа: плотное ядро из 23 пользователей, где до каждого можно дойти от каждого, и семь узлов-одиночек по краям. Одиночки — это те, кто либо только подписывается, либо только собирает подписчиков, но не замкнут в цикл. Один из них, `roman`, уже встречался в уроке 26: его closeness на направленном графе равнялся 1.0 по той же самой причине.

SCC применяют там, где направление означает зависимость: циклические зависимости между модулями, кольцевые переводы денег, взаимные ссылки в каталоге.

## Louvain — модулярная оптимизация

Louvain максимизирует **модулярность** — насколько плотнее связи внутри найденных групп по сравнению со случайным графом такой же степени. Значение лежит примерно в диапазоне от −0.5 до 1; на реальных графах 0.3–0.7 считается содержательным результатом, ниже 0.2 — что структуры почти нет.

```cypher
CALL gds.louvain.stats('socialU')
YIELD communityCount, modularity, ranLevels, modularities
RETURN communityCount, round(modularity, 4) AS modularity, ranLevels, modularities;
```

```
╒════════════════╤════════════╤═══════════╤══════════════════════════════════╕
│communityCount  │modularity  │ranLevels  │modularities                      │
╞════════════════╪════════════╪═══════════╪══════════════════════════════════╡
│5               │0.3632      │2          │[0.3517456569, 0.3632147074]      │
└────────────────┴────────────┴───────────┴──────────────────────────────────┘
```

Louvain работает иерархически. На первом уровне он объединяет отдельные узлы в мелкие группы, затем стягивает каждую группу в один суперузел и повторяет процедуру. `ranLevels: 2` означает два таких прохода, `modularities` — качество после каждого. Здесь второй уровень улучшил модулярность с 0.3517 до 0.3632: несколько мелких групп слились в более крупные, и стало лучше.

Уровень можно ограничить:

```cypher
CALL gds.louvain.stats('socialU', {maxLevels: 1})
YIELD communityCount, modularity
RETURN communityCount, round(modularity, 4) AS modularity;
```

```
╒════════════════╤════════════╕
│communityCount  │modularity  │
╞════════════════╪════════════╡
│6               │0.3517      │
└────────────────┴────────────┘
```

Шесть групп вместо пяти и модулярность ниже. Это рычаг для управления зернистостью: если сообществ получилось слишком мало и крупно, `maxLevels: 1` даст более дробное разбиение ценой качества.

Промежуточные уровни доступны и в `.stream`:

```cypher
CALL gds.louvain.stream('socialU', {includeIntermediateCommunities: true})
YIELD nodeId, communityId, intermediateCommunityIds
RETURN gds.util.asNode(nodeId).email AS email, communityId, intermediateCommunityIds
ORDER BY email LIMIT 3;
```

```
╒══════════════════╤═════════════╤═════════════════════════╕
│email             │communityId  │intermediateCommunityIds │
╞══════════════════╪═════════════╪═════════════════════════╡
│"alina@shop.io"   │6            │[6, 6]                   │
│"anna@shop.io"    │24           │[24, 24]                 │
│"artem@shop.io"   │24           │[24, 24]                 │
└──────────────────┴─────────────┴─────────────────────────┘
```

Так строится дерево сообществ: «отдел внутри департамента внутри компании».

### Направление ломает результат

```cypher
CALL gds.louvain.stats('social')
YIELD communityCount, modularity
RETURN communityCount, round(modularity, 4) AS modularity;
```

```
╒════════════════╤════════════╕
│communityCount  │modularity  │
╞════════════════╪════════════╡
│2               │0.2157      │
└────────────────┴────────────┘
```

На направленной проекции — два сообщества и модулярность 0.2157 против пяти и 0.3632. Разбиение стало вдвое грубее, качество упало почти вдвое. Модулярность как раз для того и нужна: без неё оба ответа выглядят одинаково правдоподобно.

### Идентификаторы сообществ

По умолчанию `communityId` — это внутренний идентификатор одного из узлов группы: 6, 24, 28 в примерах выше. Числа не по порядку и меняются от запуска к запуску. Опция `consecutiveIds: true` перенумеровывает их подряд с нуля.

```cypher
CALL gds.louvain.write('socialU', {writeProperty: 'community', consecutiveIds: true})
YIELD communityCount, modularity, nodePropertiesWritten
RETURN communityCount, round(modularity, 4) AS modularity, nodePropertiesWritten;
```

> **Внимание**: `consecutiveIds` делает идентификаторы аккуратными, но не стабильными. После пересчёта на изменившемся графе сообщество «2» может оказаться совсем другой группой людей. Привязывать к этим числам бизнес-логику, названия сегментов или настройки рассылок нельзя — нужен собственный слой сопоставления по составу.

## Leiden — исправленный Louvain

У Louvain есть известный дефект: он изредка возвращает сообщество, которое внутри себя несвязно, — алгоритм на промежуточном шаге объединяет узлы, между которыми потом не остаётся пути. Leiden добавляет фазу уточнения, которая это гарантированно исключает, и обычно даёт модулярность чуть выше.

```cypher
CALL gds.leiden.stats('socialU', {randomSeed: 42})
YIELD communityCount, modularity, ranLevels
RETURN communityCount, round(modularity, 4) AS modularity, ranLevels;
```

```
╒════════════════╤════════════╤═══════════╕
│communityCount  │modularity  │ranLevels  │
╞════════════════╪════════════╪═══════════╡
│5               │0.3725      │2          │
└────────────────┴────────────┴───────────┘
```

Столько же сообществ, модулярность 0.3725 против 0.3632. Разница на графе из 30 узлов невелика, на графах в миллионы узлов она заметнее, а гарантия связности важна всегда.

Состав при этом другой:

```cypher
CALL gds.leiden.stream('socialU', {randomSeed: 42})
YIELD nodeId, communityId
RETURN communityId, count(*) AS members
ORDER BY members DESC;
```

```
╒═════════════╤═════════╕
│communityId  │members  │
╞═════════════╪═════════╡
│8            │11       │
│7            │8        │
│1            │4        │
│2            │4        │
│3            │3        │
└─────────────┴─────────┘
```

Louvain дал размеры 10, 6, 5, 5, 4 — Leiden 11, 8, 4, 4, 3. Одно и то же число групп, разные границы. Ждать совпадения не нужно: у задачи нет единственного правильного ответа, и обе разметки допустимы.

`randomSeed` фиксирует результат, но только вместе с числом потоков: `{randomSeed: 42}` на четырёх потоках и на одном дают разные разметки — здесь 5 сообществ против 6. Порядок обработки узлов между потоками не детерминирован, и seed на это не влияет. Для полной воспроизводимости нужны оба параметра:

```cypher
CALL gds.leiden.stats('socialU', {randomSeed: 42, concurrency: 1})
YIELD communityCount, modularity
RETURN communityCount, round(modularity, 4) AS modularity;
```

Без seed Leiden при каждом запуске даёт немного разные сообщества — для отчётов, которые кто-то будет сравнивать между собой, он обязателен. Параметр `gamma` (по умолчанию 1.0) управляет зернистостью: больше — мельче группы.

## Label Propagation — быстрый черновик

Каждый узел итеративно принимает метку, которая чаще всего встречается у его соседей. Сходится за несколько итераций и работает быстрее всех остальных.

```cypher
CALL gds.labelPropagation.stats('socialU')
YIELD communityCount, ranIterations, didConverge
RETURN communityCount, ranIterations, didConverge;
```

```
╒════════════════╤═══════════════╤═════════════╕
│communityCount  │ranIterations  │didConverge  │
╞════════════════╪═══════════════╪═════════════╡
│3               │3              │TRUE         │
└────────────────┴───────────────┴─────────────┘
```

```cypher
CALL gds.labelPropagation.stream('socialU')
YIELD nodeId, communityId
RETURN communityId, count(*) AS members
ORDER BY members DESC;
```

```
╒═════════════╤═════════╕
│communityId  │members  │
╞═════════════╪═════════╡
│53           │15       │
│49           │11       │
│52           │4        │
└─────────────┴─────────┘
```

Три группы вместо пяти, причём одна занимает половину графа. Это характерное поведение label propagation: крупная группа поглощает соседей, и разбиение получается грубее. Ничего не оптимизируется явно, поэтому и модулярности в выдаче нет.

Ниша алгоритма — предварительная разведка на графе, где Louvain считался бы слишком долго, и полу-размеченные задачи: `seedProperty` позволяет задать часть меток заранее и распространить их на остальной граф.

## Как выбрать

| Алгоритм | Детерминирован | Оптимизирует | Когда |
|---|---|---|---|
| WCC | Да | — | Всегда первым, санитарная проверка, антифрод по общим атрибутам |
| SCC | Да | — | Направление означает зависимость: циклы, взаимная достижимость |
| Louvain | Нет | Модулярность | Основной инструмент сегментации, есть иерархия уровней |
| Leiden | Нет, но есть `randomSeed` | Модулярность | То же, что Louvain, но с гарантией связности сообществ |
| Label Propagation | Нет | — | Разведка на очень больших графах, распространение известных меток |

Практический порядок: WCC → Louvain или Leiden с `.stats` → сравнение модулярности при разных параметрах → `.write` победившей конфигурации.

Дальше сообщества используются как обычный атрибут: интересы группы, товары, популярные внутри неё, пользователи, чьё поведение расходится с их сообществом. Урок 30 строит на этом рекомендации, урок 31 — антифрод.

## Практика

1. Запусти WCC на `socialU` и убедись, что граф подписок связный.
2. Построй проекцию `identity` по общим устройствам, картам и адресам. Убери условие `elementId(a) < elementId(b)` и объясни, как изменился `relationshipCount`.
3. Найди на `identity` группы через WCC и определи, какая из них — кольцо мультиаккаунтов, а какая — легальный шеринг.
4. Подбери значение `threshold`, при котором остаётся только кольцо. Проверь граничные значения 1.0, 2.0 и 3.0.
5. Запусти SCC на направленной проекции `social`, найди узлы-одиночки и объясни запросом к базе, почему они не вошли в ядро.
6. Сравни `communityCount` и `modularity` у Louvain на `social` и на `socialU`.
7. Посмотри `modularities` и `ranLevels` у Louvain, затем запусти с `maxLevels: 1` и объясни, почему сообществ стало больше, а модулярность ниже.
8. Сравни Louvain и Leiden на `socialU` по модулярности и по размерам сообществ.
9. Запусти Leiden дважды без `randomSeed` и убедись, что результат отличается. Затем зафиксируй seed.
10. Запусти label propagation и объясни, почему одно сообщество вобрало половину графа.
11. Запиши результат Louvain в граф с `consecutiveIds: true` и посчитай долю связей, не выходящих за границы сообществ.
12. Удали все проекции и свойство `community` из графа.

## Итоги урока

- Сообщество определяется только структурой связей: алгоритм не знает про атрибуты узлов, и объяснять найденное разбиение приходится постфактум.
- Компоненты связности дают единственно верный ответ, модулярные алгоритмы — один из многих, поэтому WCC запускают первым, а качество Louvain и Leiden измеряют модулярностью.
- WCC на графе общих устройств, карт и адресов находит кольца аккаунтов; порог `threshold` по весу отделяет их от легального шеринга внутри семьи.
- `threshold` отбрасывает связи с весом, не превышающим заданный: при 2.0 пара с двумя общими идентификаторами уже не попадает в компоненту.
- SCC требует направленной проекции и находит взаимно достижимые ядра; на ненаправленном графе он вырождается в WCC.
- Модулярность 0.3–0.7 говорит о содержательной структуре, ниже 0.2 — что её почти нет; она же позволяет сравнивать конфигурации между собой.
- Louvain иерархичен: `ranLevels` и `modularities` показывают, что дало укрупнение, а `maxLevels` управляет зернистостью разбиения.
- Запуск Louvain на направленной проекции ухудшил модулярность с 0.3632 до 0.2157 и вдвое огрубил разбиение.
- Leiden гарантирует связность сообществ и обычно даёт модулярность выше Louvain; `randomSeed` нужен для воспроизводимости.
- `consecutiveIds` делает идентификаторы аккуратными, но не стабильными между пересчётами — привязывать к ним бизнес-логику нельзя.
- Label propagation быстрее всех и ничего не оптимизирует явно, поэтому склонен к одному разросшемуся сообществу; его ниша — разведка и распространение уже известных меток через `seedProperty`.
- После `.write` сообщество становится обычным свойством узла, и доля связей внутри групп — понятная проверка качества разбиения.
