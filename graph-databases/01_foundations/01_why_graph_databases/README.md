# Урок 1. Зачем нужны графовые базы данных

## Что такое графовая база данных

Графовая база данных хранит данные как **узлы** (сущности) и **связи** между ними. Связь — такой же полноценный объект хранения, как строка в таблице: у неё есть тип, направление и собственные свойства. Это отличает граф от реляционной модели, где связь существует только как значение внешнего ключа и материализуется в момент выполнения JOIN.

Neo4j использует модель **property graph** (LPG, labeled property graph): узел имеет метки и свойства, связь имеет тип и свойства.

```
     (:User {name: "Анна"})
            │
            │ [:PLACED {createdAt: "2026-03-01"}]
            ▼
     (:Order {total: 4990})
            │
            │ [:CONTAINS {qty: 2}]
            ▼
     (:Product {title: "Кофеварка"})
```

Читается как предложение: пользователь Анна разместила заказ, который содержит два товара «Кофеварка».

## Проблема: взрыв JOIN

Реляционная модель отлично справляется с запросами «дай все заказы пользователя». Проблема начинается, когда запрос идёт вглубь связей.

Задача: «найти товары, которые покупали люди, покупавшие то же, что и Анна» — классическая коллаборативная рекомендация. Глубина обхода — три шага.

```sql
-- PostgreSQL
SELECT DISTINCT p2.id, p2.title
FROM users u
         JOIN orders o1 ON o1.user_id = u.id
         JOIN order_items oi1 ON oi1.order_id = o1.id
         JOIN order_items oi2 ON oi2.product_id = oi1.product_id
         JOIN orders o2 ON o2.id = oi2.order_id AND o2.user_id <> u.id
         JOIN order_items oi3 ON oi3.order_id = o2.id
         JOIN products p2 ON p2.id = oi3.product_id
WHERE u.name = 'Анна'
  AND p2.id NOT IN (SELECT oi.product_id
                    FROM order_items oi
                             JOIN orders o ON o.id = oi.order_id
                    WHERE o.user_id = u.id);
```

Шесть JOIN и подзапрос ради трёх шагов по связям. То же самое на Cypher:

```cypher
MATCH (u:User {name: 'Анна'})-[:PLACED]->(:Order)-[:CONTAINS]->(p:Product)
      <-[:CONTAINS]-(:Order)<-[:PLACED]-(other:User)
MATCH (other)-[:PLACED]->(:Order)-[:CONTAINS]->(rec:Product)
WHERE other <> u AND NOT (u)-[:PLACED]->(:Order)-[:CONTAINS]->(rec)
RETURN DISTINCT rec.title;
```

Запрос читается как рисунок связей на доске. Но дело не только в синтаксисе.

## Index-free adjacency

Ключевая техническая причина, по которой граф выигрывает на обходах — **index-free adjacency**: каждый узел физически хранит ссылки на свои связи. Переход от узла к соседу — это разыменование указателя, а не поиск по индексу.

| Операция | PostgreSQL | Neo4j |
|---|---|---|
| Найти стартовый узел | Поиск по индексу, O(log n) | Поиск по индексу, O(log n) |
| Шаг к соседу | JOIN: поиск по индексу, O(log n) | Переход по ссылке, O(1) |
| Обход глубины k | O(log n) на каждом уровне, растёт с размером таблиц | O(1) на связь, зависит только от локальной плотности |

Практическое следствие: время обхода в графе **не зависит от общего размера базы**. Найти друзей друзей конкретного пользователя в графе на 10 миллионов узлов стоит столько же, сколько в графе на 100 тысяч — при одинаковой плотности связей. В реляционной СУБД тот же запрос замедляется по мере роста таблиц.

> **Важно**: это работает только для локальных обходов от известной стартовой точки. Запрос «посчитай средний чек по всем заказам» в графе будет медленнее, чем в PostgreSQL, и несопоставимо медленнее, чем в ClickHouse. Граф не ускоряет полное сканирование — он ускоряет движение по связям.

## Где графовая модель выигрывает

| Область | Задача | Почему граф |
|---|---|---|
| Рекомендации | Товары, контент, люди | Обходы глубины 2-4 по связям «купил», «смотрел», «подписан» |
| Антифрод | Кольца мошенников, мультиаккаунты | Связи через общие устройства, карты и адреса — переменная глубина, заранее неизвестная |
| Социальные сети | Лента, охват, влияние | Friends-of-friends, транзитивное замыкание |
| Управление доступом | Иерархические роли и наследование прав | Рекурсивные обходы вверх по дереву |
| Граф зависимостей | Микросервисы, SBOM, data lineage | Impact analysis: кто сломается, если упадёт этот сервис |
| Master data | Разрешение дублей сущностей | Кластеризация по пересечению атрибутов |
| Маршрутизация | Логистика, сети, навигация | Взвешенный поиск кратчайшего пути |
| Knowledge graph | Онтологии, RAG над связанными данными | Обход как способ собрать релевантный контекст |

Общий признак: **связи между данными несут не меньше смысла, чем сами данные**, а глубина обхода заранее неизвестна.

## Когда графовая БД не нужна

Честный список — это важнее списка достоинств.

- **Табличная аналитика и агрегации по большим объёмам.** Считать выручку по дням за два года — работа для ClickHouse, не для Neo4j.
- **Транзакционный учёт с фиксированной схемой.** Заказы, платежи, остатки со связями глубины 1-2 отлично живут в PostgreSQL. Граф не даст выигрыша, а операционная сложность вырастет.
- **Key-value доступ.** Достать сессию по ключу — Redis.
- **Полнотекстовый поиск как основной сценарий.** Elasticsearch. У Neo4j есть full-text индексы, но это дополнение к обходам, а не замена поисковому движку.
- **Данные без интересных связей.** Если единственные связи — это классические справочники, графовая модель ничего не добавит.
- **Запись очень больших объёмов событий.** Поток телеметрии не место для графа.

Типичная продакшн-архитектура — не «граф вместо реляционки», а граф **рядом** с ней: PostgreSQL хранит транзакционную истину, Neo4j хранит проекцию тех же данных, оптимизированную под связи, и отвечает на вопросы про связи.

## Сравнение моделей

| Аспект | Реляционная | Документная | Графовая |
|---|---|---|---|
| Единица хранения | Строка в таблице | Документ | Узел и связь |
| Связи | Внешний ключ, JOIN при чтении | Вложенность или ручные ссылки | Материализованы физически |
| Стоимость глубокого обхода | Растёт с глубиной и размером таблиц | Требует нескольких запросов | Постоянна на связь |
| Схема | Жёсткая | Гибкая | Опциональная (constraints по желанию) |
| Сильная сторона | Целостность, агрегации | Автономные агрегаты | Связность |
| Слабая сторона | Многоуровневые связи | Связи между документами | Массовые агрегации |

## Практика

1. Опиши своими словами разницу между «связь как внешний ключ» и «связь как объект хранения». Приведи пример свойства, которое естественно живёт на связи, а не на узле.
2. Возьми схему любого текущего проекта и выпиши три запроса, где приходится делать три и больше JOIN подряд по цепочке сущностей.
3. Для каждого из них оцени, действительно ли там обход по связям, или это агрегация — во втором случае граф не поможет.
4. Нарисуй на бумаге фрагмент своей предметной области в виде узлов и связей: 5-7 узлов, 4-6 типов связей. Проверь, что каждая связь читается как предложение с глаголом.
5. Выпиши два вопроса к этим данным, на которые сейчас ответить сложно, и оцени глубину обхода для каждого.
6. Найди в своём проекте случай, где графовая БД была бы плохим выбором, и сформулируй почему.

## Итоги урока

- Графовая БД хранит связи физически: у связи есть тип, направление и собственные свойства, она не вычисляется в момент запроса.
- Neo4j использует модель property graph — узлы с метками и свойствами, связи с типом и свойствами.
- Index-free adjacency делает переход к соседнему узлу операцией O(1), поэтому время локального обхода не зависит от общего размера базы.
- Запрос, требующий шести JOIN в SQL, в Cypher выражается одним паттерном из трёх шагов.
- Граф выигрывает там, где глубина обхода заранее неизвестна: рекомендации, антифрод, права доступа, зависимости, разрешение дублей.
- Граф проигрывает на массовых агрегациях, key-value доступе и полнотекстовом поиске — это задачи для ClickHouse, Redis и Elasticsearch.
- Рабочая архитектура — граф рядом с реляционной СУБД как специализированная проекция под вопросы о связях, а не замена основному хранилищу.
