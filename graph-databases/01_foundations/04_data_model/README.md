# Урок 4. Модель данных

## Из чего состоит property graph

Четыре элемента, и это весь словарь модели.

| Элемент | Что это | Пример |
|---|---|---|
| **Узел** (node) | Сущность | Пользователь, товар, заказ |
| **Метка** (label) | Тип узла, узел может иметь несколько | `:User`, `:Product` |
| **Связь** (relationship) | Направленное ребро с типом | `:PLACED`, `:CONTAINS` |
| **Свойство** (property) | Пара ключ-значение на узле или связи | `name: "Анна"`, `qty: 2` |

```
   ┌─────────────────────────┐        ┌──────────────────────┐
   │ :User                   │        │ :Order               │
   │ id: 42                  │        │ id: 1001             │
   │ name: "Анна"            ├───────▶│ total: 4990          │
   │ email: "a@shop.io"      │        │ status: "delivered"  │
   └─────────────────────────┘        └──────────────────────┘
              [:PLACED {createdAt: date('2026-03-01'),
                        channel: 'mobile'}]
```

Соответствие реляционным понятиям — приблизительное, но помогает на старте:

| Реляционная модель | Property graph |
|---|---|
| Таблица | Метка |
| Строка | Узел |
| Колонка | Свойство |
| Внешний ключ | Связь |
| Таблица связи many-to-many | Связь (часто со свойствами) |

Ключевая разница: таблица связи в SQL — вынужденная конструкция, в графе такая связь исчезает как отдельная сущность и становится ребром со свойствами.

## Метки

Метка задаёт тип узла. У одного узла может быть ноль, одна или несколько меток.

```cypher
// Одна метка
CREATE (:Product {sku: 'CM-100', title: 'Кофеварка', price: 4990});

// Несколько меток на одном узле
CREATE (:User:Employee {email: 'ivan@shop.io', name: 'Иван', department: 'support'});
```

Несколько меток — способ выразить «пользователь, который одновременно сотрудник», без дублирования узла. Запрос `MATCH (u:User)` найдёт такой узел, `MATCH (u:Employee)` тоже.

Метки — основной способ ограничить область поиска. Запрос без метки сканирует весь граф.

```cypher
// Плохо: полное сканирование всех узлов базы
MATCH (n {sku: 'CM-100'}) RETURN n;

// Хорошо: сканируются только узлы с меткой Product, а с индексом — поиск по индексу
MATCH (p:Product {sku: 'CM-100'}) RETURN p;
```

**Соглашение об именовании**: метки — `PascalCase` в единственном числе (`User`, `OrderItem`), типы связей — `UPPER_SNAKE_CASE` (`PLACED`, `LOGGED_IN_FROM`), свойства — `camelCase` (`createdAt`, `totalAmount`). Это не требование движка, но нарушение сразу делает запросы нечитаемыми.

## Связи

У связи есть три обязательных характеристики: тип, направление, два конца. Свойства опциональны.

```cypher
// Форма записи; узлов с такими ключами в графе ещё нет,
// поэтому запрос ничего не создаст — рабочий вариант ниже, в «Первых данных»
MATCH (u:User {email: 'a@shop.io'}), (o:Order {id: 1001})
CREATE (u)-[:PLACED {createdAt: date('2026-03-01'), channel: 'mobile'}]->(o);
```

Это важная особенность `CREATE` после `MATCH`: если паттерн поиска ничего не нашёл, создавать нечего и запрос молча завершается без изменений. Ошибки не будет.

### Направление

Связь всегда хранится направленной, но при чтении направление можно игнорировать.

```cypher
// Только исходящие: пользователь разместил заказ
MATCH (u:User)-[:PLACED]->(o:Order) RETURN u, o;

// Только входящие
MATCH (u:User)<-[:REFERRED]-(inviter:User) RETURN u, inviter;

// Без учёта направления
MATCH (u:User)-[:FOLLOWS]-(other:User) RETURN u, other;
```

> **Важно**: если связь по смыслу симметрична (дружба, «похожий товар»), создавай **одну** связь и читай её без направления. Две встречные связи ради симметрии удваивают объём и создают риск рассинхронизации.

Направление выбирается по смыслу глагола: `(:User)-[:PLACED]->(:Order)` читается «пользователь разместил заказ». Обратное чтение `(:Order)<-[:PLACED]-(:User)` даёт «заказ размещён пользователем» — та же связь, тот же запрос по стоимости.

### Связь как объект

Свойство на связи — то, чего нет в реляционной модели без промежуточной таблицы.

```cypher
// Количество товара — свойство именно связи, а не заказа и не товара
MATCH (o:Order {id: 1001}), (p:Product {sku: 'CM-100'})
CREATE (o)-[:CONTAINS {qty: 2, priceAtPurchase: 4990}]->(p);
```

`priceAtPurchase` на связи фиксирует цену на момент покупки — цена товара потом изменится, а история заказа останется корректной.

## Типы данных

| Тип | Пример литерала | Комментарий |
|---|---|---|
| `INTEGER` | `42` | 64-битное знаковое |
| `FLOAT` | `49.90` | Двойная точность |
| `STRING` | `'Кофеварка'` | UTF-8, одинарные или двойные кавычки |
| `BOOLEAN` | `true` | |
| `DATE` | `date('2026-03-01')` | |
| `LOCAL_DATETIME` | `localdatetime('2026-03-01T10:00')` | Без часового пояса |
| `ZONED_DATETIME` | `datetime('2026-03-01T10:00+03:00')` | С часовым поясом, тип по умолчанию для `datetime()` |
| `DURATION` | `duration('P1M')` | Интервал |
| `POINT` | `point({latitude: 53.9, longitude: 27.56})` | Геоточка, есть отдельный индекс |
| `LIST` | `['red', 'black']` | Однородный список примитивов |

```cypher
CREATE (p:Product {
  sku: 'CM-100',
  title: 'Кофеварка',
  price: 4990.0,
  inStock: true,
  tags: ['kitchen', 'coffee'],          // список примитивов
  createdAt: datetime(),                 // текущее время с зоной
  warehouse: point({latitude: 53.9, longitude: 27.56})
});
```

### Чего в свойствах не бывает

Свойство хранит только примитив или список примитивов. **Вложенных объектов и map в свойствах нет** — в этом принципиальное отличие от MongoDB.

```cypher
// Так нельзя: свойство не может быть map
CREATE (u:User {address: {city: 'Минск', street: 'Немига'}});
```

Вложенная структура в графе выражается отдельным узлом:

```cypher
CREATE (u:User {email: 'a@shop.io'})
CREATE (a:Address {city: 'Минск', street: 'Немига'})
CREATE (u)-[:SHIPPED_TO]->(a);
```

Это не обходной путь, а правильное моделирование: адрес становится узлом, который могут разделять несколько пользователей — и именно на этом строится антифрод в уроке 31.

### NULL

Свойства со значением `null` **не хранятся**. Присвоение `null` удаляет свойство.

```cypher
// Свойство discount просто не появится
CREATE (p:Product {sku: 'CM-101', title: 'Чайник', discount: null});

// Проверка отсутствия свойства
MATCH (p:Product) WHERE p.discount IS NULL RETURN p.sku;
```

Прямое следствие: в графе нет фиксированной «схемы колонок». Два узла с меткой `:Product` могут иметь разный набор свойств, и это нормально.

## Идентификаторы

У каждого узла и связи есть системный идентификатор, доступный через `elementId()`.

```cypher
MATCH (p:Product {sku: 'CM-100'})
RETURN elementId(p) AS elementId, p.sku AS businessKey;
```

> **Внимание**: `elementId` — внутренний идентификатор конкретной базы. Он не переносится между инстансами, может измениться после восстановления из бэкапа и переиспользуется после удаления. Хранить его во внешних системах или использовать как бизнес-ключ нельзя. Для идентификации всегда заводи собственное свойство (`sku`, `email`, UUID) и вешай на него ограничение уникальности — это делается в уроке 12.

Устаревшая функция `id()` из Cypher 5 в Cypher 25 не используется.

## Первые данные

Соберём фрагмент модели курса руками, чтобы дальше было с чем работать.

```cypher
// Пользователи
CREATE (anna:User  {email: 'anna@shop.io',  name: 'Анна',  registeredAt: date('2025-11-04')})
CREATE (ivan:User  {email: 'ivan@shop.io',  name: 'Иван',  registeredAt: date('2026-01-17')})

// Категории с иерархией
CREATE (kitchen:Category {name: 'Кухня'})
CREATE (coffee:Category  {name: 'Кофеварки'})
CREATE (coffee)-[:SUBCATEGORY_OF]->(kitchen)

// Товары
CREATE (cm:Product {sku: 'CM-100', title: 'Кофеварка Aroma', price: 4990.0})
CREATE (gr:Product {sku: 'GR-200', title: 'Кофемолка Fine',  price: 2490.0})
CREATE (cm)-[:IN_CATEGORY]->(coffee)
CREATE (gr)-[:IN_CATEGORY]->(coffee)

// Заказ Анны на два товара
CREATE (o1:Order {id: 1001, total: 7480.0, status: 'delivered'})
CREATE (anna)-[:PLACED {createdAt: date('2026-03-01'), channel: 'mobile'}]->(o1)
CREATE (o1)-[:CONTAINS {qty: 1, priceAtPurchase: 4990.0}]->(cm)
CREATE (o1)-[:CONTAINS {qty: 1, priceAtPurchase: 2490.0}]->(gr)

// Заказ Ивана на один товар
CREATE (o2:Order {id: 1002, total: 4990.0, status: 'shipped'})
CREATE (ivan)-[:PLACED {createdAt: date('2026-03-05'), channel: 'web'}]->(o2)
CREATE (o2)-[:CONTAINS {qty: 1, priceAtPurchase: 4990.0}]->(cm);
```

Первая проверка, что граф действительно связный:

```cypher
// Кто что покупал
MATCH (u:User)-[:PLACED]->(:Order)-[:CONTAINS]->(p:Product)
RETURN u.name AS user, collect(p.title) AS products;
```

```
╒═══════╤═══════════════════════════════════════╕
│user   │products                               │
╞═══════╪═══════════════════════════════════════╡
│"Анна" │["Кофеварка Aroma", "Кофемолка Fine"]  │
│"Иван" │["Кофеварка Aroma"]                    │
└───────┴───────────────────────────────────────┘
```

## Осмотр модели

```cypher
// Какие метки есть в базе
CALL db.labels();

// Какие типы связей
CALL db.relationshipTypes();

// Какие свойства встречаются у каждой метки — по факту, а не по схеме
CALL db.schema.nodeTypeProperties();

// Визуальная схема графа (в Browser рисуется картинкой)
CALL db.schema.visualization();
```

`db.schema.nodeTypeProperties()` показывает реально встречающиеся свойства и их типы. На графе, собранном разными людьми, это первое, что стоит запускать: там сразу видно, что где-то `price` оказался строкой, а где-то числом.

## Практика

1. Выполни скрипт создания данных из этого урока в `cypher-shell`.
2. Добавь третьего пользователя, который зарегистрировался по приглашению Анны — используй связь `REFERRED` в правильном направлении.
3. Создай товар с несколькими метками: `:Product:Bestseller`. Проверь, что он находится обоими запросами — по `:Product` и по `:Bestseller`.
4. Добавь узел `:Address` и свяжи с ним обоих пользователей связью `SHIPPED_TO`. Убедись, что один адрес может быть общим для нескольких пользователей.
5. Попробуй создать узел со свойством-map и зафиксируй текст ошибки.
6. Создай узел со свойством `discount: null`, затем проверь через `db.schema.nodeTypeProperties()`, появилось ли это свойство.
7. Выведи `elementId()` любого товара, удали товар, создай заново и сравни идентификаторы.
8. Запусти `CALL db.schema.visualization()` в Neo4j Browser и сверь картинку со схемой из урока.

## Итоги урока

- Property graph состоит из четырёх элементов: узлы, метки, связи и свойства; связь всегда имеет тип и направление.
- Узел может иметь несколько меток одновременно — так выражается принадлежность к нескольким типам без дублирования.
- Запрос без метки сканирует весь граф, поэтому метка в паттерне — базовое требование к производительности.
- Свойства на связи заменяют промежуточную таблицу many-to-many и позволяют фиксировать данные момента, например цену на дату покупки.
- Свойство хранит только примитив или список примитивов: вложенных объектов нет, структура выражается отдельным узлом.
- Свойства со значением `null` не хранятся, поэтому узлы одной метки могут иметь разный набор свойств.
- `elementId()` — внутренний идентификатор базы, он не переносим и переиспользуется; для бизнес-идентификации нужно собственное свойство с ограничением уникальности.
- `db.schema.nodeTypeProperties()` показывает фактическую структуру графа, а не декларированную схему — это основной инструмент осмотра незнакомой базы.
