# Урок 6. Cypher: запись данных

## CREATE

Создаёт узлы и связи безусловно. Каждый вызов создаёт новые объекты, даже если такие уже есть.

```cypher
// Узел
CREATE (p:Product {sku: 'KT-300', title: 'Чайник Steam', price: 1990.0});

// Несколько узлов одним запросом
CREATE (:Category {name: 'Техника'}), (:Category {name: 'Посуда'});

// Узел со связью за один шаг
CREATE (u:User {email: 'petr@shop.io', name: 'Пётр'})-[:SHIPPED_TO]->(:Address {city: 'Гомель'});

// Связь между существующими узлами: сначала найти, потом создать
MATCH (p:Product {sku: 'KT-300'}), (c:Category {name: 'Посуда'})
CREATE (p)-[:IN_CATEGORY]->(c);
```

> **Внимание**: `CREATE` не проверяет дубликаты. Три запуска первого запроса дадут три узла `:Product` с одинаковым `sku`. Защита — либо ограничение уникальности (урок 12), либо `MERGE`.

`CREATE` уместен там, где сущность заведомо новая: событие, запись лога, узел из первичной загрузки в пустую базу.

## MERGE

`MERGE` — «найди или создай». Это рабочая лошадка загрузки данных, и её семантику нужно понимать точно, иначе она создаёт дубликаты вместо того, чтобы их предотвращать.

```cypher
// Если товар с таким sku есть — найдёт, если нет — создаст
MERGE (p:Product {sku: 'KT-300'});
```

### Главное правило: MERGE работает по всему паттерну целиком

`MERGE` ищет совпадение **всего** указанного паттерна. Не нашёл — создаёт **весь** паттерн заново.

```cypher
// Опасно: если у товара с sku KT-300 сейчас другая цена,
// совпадения не будет и создастся ВТОРОЙ узел с тем же sku
MERGE (p:Product {sku: 'KT-300', price: 1990.0});
```

Правильный подход: в `MERGE` указывать только идентифицирующие свойства, остальное задавать через `ON CREATE` и `ON MATCH`.

```cypher
MERGE (p:Product {sku: 'KT-300'})
ON CREATE SET p.title     = 'Чайник Steam',
              p.price     = 1990.0,
              p.createdAt = datetime()
ON MATCH  SET p.price     = 1990.0,
              p.updatedAt = datetime();
```

| Секция | Когда выполняется |
|---|---|
| `ON CREATE SET` | Только если узел создан |
| `ON MATCH SET` | Только если узел найден |
| `SET` после `MERGE` без секций | Всегда |

Это полный аналог `INSERT ... ON CONFLICT DO UPDATE` из PostgreSQL, только выразительнее.

### MERGE связи

```cypher
// Сначала MERGE узлов по отдельности, потом MERGE связи между ними
MERGE (u:User {email: 'petr@shop.io'})
MERGE (p:Product {sku: 'KT-300'})
MERGE (u)-[r:VIEWED]->(p)
  ON CREATE SET r.firstViewedAt = datetime(), r.views = 1
  ON MATCH  SET r.lastViewedAt  = datetime(), r.views = r.views + 1;
```

Разделение на три отдельных `MERGE` принципиально. Если написать одним паттерном:

```cypher
// Плохо: если паттерн целиком не найден, создадутся НОВЫЕ узлы User и Product,
// даже если такие уже есть в базе
MERGE (:User {email: 'petr@shop.io'})-[:VIEWED]->(:Product {sku: 'KT-300'});
```

> **Внимание**: выполнив этот запрос сразу после предыдущего, задвоения не увидишь — связь `VIEWED` там уже создана, паттерн находится целиком, и `MERGE` ничего не делает. Чтобы воспроизвести проблему, сначала удали связь: `MATCH (:User {email: 'petr@shop.io'})-[r:VIEWED]->(:Product {sku: 'KT-300'}) DELETE r`. После этого «плохой» `MERGE` не найдёт паттерн и создаст вторые узлы вместо переиспользования существующих.

**Правило**: `MERGE` по одному узлу за раз, связь — отдельным `MERGE` по уже связанным переменным.

> **Важно**: без ограничения уникальности на `sku` два параллельных `MERGE` могут создать два узла — проверка и вставка не атомарны относительно других транзакций. Ограничение уникальности не только защищает данные, но и заставляет `MERGE` брать блокировку. Поэтому индексы и ограничения создаются **до** массовой загрузки, а не после.

## SET

```cypher
// Одно свойство
MATCH (p:Product {sku: 'KT-300'}) SET p.price = 2190.0;

// Несколько
MATCH (p:Product {sku: 'KT-300'}) SET p.price = 2190.0, p.updatedAt = datetime();

// Из map: перезаписывает ТОЛЬКО перечисленные свойства
MATCH (p:Product {sku: 'KT-300'}) SET p += {price: 2190.0, discount: 10};

// Из map со знаком =: ЗАМЕНЯЕТ весь набор свойств, остальные удаляются
MATCH (p:Product {sku: 'KT-300'}) SET p = {sku: 'KT-300', title: 'Чайник Steam'};

// Добавить метку
MATCH (p:Product {sku: 'CM-100'}) SET p:Bestseller;
```

> **Внимание**: разница между `SET p = {...}` и `SET p += {...}` — источник потери данных. Первый вариант стирает все свойства, которых нет в map, включая `sku`, если его туда не положили. В приложениях почти всегда нужен `+=`.

Присваивание `null` удаляет свойство:

```cypher
MATCH (p:Product {sku: 'KT-300'}) SET p.discount = null;
```

## REMOVE

```cypher
// Удалить свойство
MATCH (p:Product {sku: 'KT-300'}) REMOVE p.discount;

// Удалить метку
MATCH (p:Product {sku: 'CM-100'}) REMOVE p:Bestseller;
```

`REMOVE p.discount` и `SET p.discount = null` дают одинаковый результат. `REMOVE` читается яснее.

## DELETE и DETACH DELETE

```cypher
// Удалить связь
MATCH (:Order {id: 1002})-[r:CONTAINS]->(:Product {sku: 'CM-100'}) DELETE r;

// Удалить узел без связей
MATCH (c:Category {name: 'Техника'}) DELETE c;

// Удалить узел вместе со всеми его связями
MATCH (o:Order {id: 1002}) DETACH DELETE o;
```

Узел со связями нельзя удалить простым `DELETE` — будет ошибка. Это встроенная защита ссылочной целостности: в графе не бывает висячей связи.

```
G1001: dependent object error - edges still exist
```

`DETACH DELETE` снимает эту защиту, удаляя связи вместе с узлом.

> **Внимание**: `DETACH DELETE` каскадно удаляет только связи, но не соседние узлы. Удаление заказа не удалит товары — и это правильно. Но удаление пользователя оставит его заказы висеть без владельца. Каскад по смыслу приходится писать вручную:

```cypher
// Удалить пользователя вместе с его заказами
MATCH (u:User {email: 'petr@shop.io'})
OPTIONAL MATCH (u)-[:PLACED]->(o:Order)
DETACH DELETE o, u;
```

## Идемпотентность

Загрузка данных должна выдерживать повторный запуск: сбой посреди импорта, ретрай очереди, повторная доставка события — норма жизни.

```cypher
// Неидемпотентно: каждый запуск добавляет дубликаты
CREATE (u:User {email: 'anna@shop.io'})
CREATE (o:Order {id: 1001})
CREATE (u)-[:PLACED]->(o);

// Идемпотентно: сколько раз ни запусти, результат один
MERGE (u:User {email: 'anna@shop.io'})
  ON CREATE SET u.registeredAt = datetime()
MERGE (o:Order {id: 1001})
  ON CREATE SET o.createdAt = datetime()
SET o.total = 7480.0, o.status = 'delivered'
MERGE (u)-[:PLACED]->(o);
```

Разбор: неизменяемые при повторе поля (`registeredAt`, `createdAt`) идут в `ON CREATE SET`, актуальное состояние (`total`, `status`) — в обычный `SET`, который выполняется всегда.

Приём с накоплением счётчика идемпотентным не будет — при повторной доставке события счётчик вырастет дважды:

```cypher
// Осторожно: не идемпотентно
MERGE (u)-[r:VIEWED]->(p) ON MATCH SET r.views = r.views + 1;
```

Если события могут дублироваться, счётчик считают из узлов-событий, а не инкрементом. Этот паттерн разбирается в уроке 11.

## Порядок выполнения и WITH

Запрос выполняется как конвейер: каждое предложение получает строки от предыдущего.

```cypher
// Найти доставленные заказы, пометить пользователей как активных
MATCH (u:User)-[:PLACED]->(o:Order {status: 'delivered'})
WITH DISTINCT u
SET u:ActiveBuyer
RETURN count(u) AS marked;
```

`WITH` передаёт результат дальше по конвейеру и позволяет вставить `DISTINCT`, агрегацию или фильтр между этапами. Подробно — в уроке 7.

> **Важно**: `MATCH`, порождающий несколько строк, выполнит следующий за ним `SET` на каждой строке. Без `DISTINCT` в примере выше пользователь с тремя доставленными заказами получил бы метку трижды — на результат это не влияет, но это три лишние операции записи.

## Транзакции

Каждый запрос в `cypher-shell` и в драйвере выполняется в своей транзакции: либо целиком, либо никак. Явное управление транзакциями появляется в уроке 15 и в Java-коде трека 3.

Практическое ограничение: транзакция целиком держится в heap. Запрос вида `MATCH (n) DETACH DELETE n` на миллионе узлов упрётся в память. Решение — батчи:

```cypher
// Удаление партиями по 10 000 узлов, каждая партия — своя транзакция.
// ВНИМАНИЕ: этот запрос стирает весь граф. Не запускай его сейчас —
// данные урока 4 нужны в уроках 5-8. Здесь он приведён как образец синтаксиса
MATCH (n)
CALL (n) {
  DETACH DELETE n
} IN TRANSACTIONS OF 10000 ROWS;
```

Синтаксис `CALL {} IN TRANSACTIONS` подробно разбирается в уроках 9 и 14.

## Практика

1. Создай через `CREATE` товар `:Product {sku: 'BL-400'}` три раза подряд. Посчитай, сколько узлов получилось, и удали лишние.
2. Сделай то же самое через `MERGE` и убедись, что узел остался один.
3. Напиши `MERGE` для товара `BL-400`, который при создании ставит `createdAt`, а при каждом попадании обновляет `updatedAt` и цену.
4. Выполни намеренно ошибочный `MERGE` с ценой внутри паттерна дважды с разными ценами и убедись, что появились два узла с одним `sku`. Удали дубликаты.
5. Сравни поведение `SET p = {...}` и `SET p += {...}` на тестовом товаре: проверь через `keys(p)`, какие свойства остались.
6. Попробуй удалить пользователя простым `DELETE` и зафиксируй текст ошибки. Затем удали через `DETACH DELETE`.
7. Напиши идемпотентный скрипт, который заводит пользователя, его заказ и связь между ними. Запусти три раза и проверь через `count`, что данные не размножились.
8. Пометь меткой `:ActiveBuyer` всех пользователей с доставленными заказами, использовав `WITH DISTINCT`.

## Итоги урока

- `CREATE` создаёт объекты безусловно и не проверяет дубликаты; он уместен только для заведомо новых сущностей.
- `MERGE` ищет совпадение всего паттерна целиком: лишнее свойство внутри паттерна приводит к созданию дубликата вместо обновления.
- В `MERGE` указывают только идентифицирующие свойства, остальные задают через `ON CREATE SET` и `ON MATCH SET`.
- Узлы мёрджатся по одному, связь — отдельным `MERGE` по уже найденным переменным; единый паттерн создаст новые узлы.
- Без ограничения уникальности параллельные `MERGE` способны создать дубликаты, поэтому ограничения создаются до загрузки данных.
- `SET p = {...}` заменяет весь набор свойств, `SET p += {...}` дописывает перечисленные — первая форма молча теряет данные.
- Узел со связями не удаляется простым `DELETE`: в графе не бывает висячих связей, для удаления нужен `DETACH DELETE`.
- Идемпотентность достигается разделением полей на неизменяемые в `ON CREATE SET` и актуализируемые в обычном `SET`; инкремент счётчика идемпотентным не бывает.
