# Урок 8. Cypher 25: что нового

## Зачем нужны две версии языка

С релиза Neo4j 2025.06 язык запросов отделён от версии базы. Существуют две версии:

| Версия | Состояние | Что с ней происходит |
|---|---|---|
| **Cypher 5** | Заморожена | Только исправления ошибок и оптимизации. Новых возможностей не будет |
| **Cypher 25** | Развивается | Все новые возможности идут сюда, синтаксис приводится к стандарту GQL |

Cypher 25 создан как копия Cypher 5, из которой убрали ранее объявленное устаревшим и в которую добавляют новое. После первого выпуска изменения в Cypher 25 только additive — существующие запросы ломаться не будут.

Логика такая же, как у версионирования API: одна версия обратно совместимая, другая эволюционирующая, и приложение само решает, когда переходить.

> **Важно**: базы, созданные до 2026.02, по умолчанию остаются на Cypher 5 даже после обновления сервера. Переход на Cypher 25 — явное действие. Базы, созданные на 2026.02 и новее, используют Cypher 25 по умолчанию.

## Выбор версии

Три уровня, от общего к частному:

```cypher
// 1. Версия по умолчанию для новых баз — настройка сервера
//    db.query.default_language

// 2. Версия конкретной базы данных
ALTER DATABASE neo4j SET DEFAULT LANGUAGE CYPHER 25;

// 3. Версия отдельного запроса — префикс перекрывает всё остальное
CYPHER 5  MATCH (n:User) RETURN n LIMIT 1;
CYPHER 25 MATCH (n:User) RETURN n LIMIT 1;
```

Проверить текущую версию базы:

```cypher
SHOW DATABASES YIELD name, defaultLanguage;
```

```
╒═════════╤═════════════════╕
│name     │defaultLanguage  │
╞═════════╪═════════════════╡
│"neo4j"  │"CYPHER 25"      │
│"system" │"CYPHER 25"      │
└─────────┴─────────────────┘
```

> **Внимание**: версии языка нет в колонке `options` — она остаётся пустой. Нужна именно `defaultLanguage`; в выводе `SHOW DATABASES` без `YIELD` эта колонка тоже не показывается, её видно только через `YIELD *` или явное перечисление.

Префикс запроса задуман как инструмент миграции: перевести базу на Cypher 25 целиком, а отдельные ещё не переписанные запросы временно помечать `CYPHER 5`. Держать всё приложение на префиксах — плохая стратегия, потому что поддержка Cypher 5 когда-нибудь закончится.

> **Внимание**: процедуры и функции, включая APOC, тоже привязаны к версии языка. Одна и та же процедура может вести себя по-разному под `CYPHER 5` и `CYPHER 25`, а часть процедур APOC под Cypher 25 недоступна. При странном поведении APOC первым делом проверяй, под какой версией языка выполняется запрос.

## Quantified path patterns

Главное синтаксическое нововведение из GQL — квантификаторы вместо звёздочки.

### Квантифицированная связь

```cypher
// Старый синтаксис
MATCH (c:Category)-[:SUBCATEGORY_OF*1..3]->(root:Category) RETURN root.name;

// Новый: квантификатор в фигурных скобках после связи
MATCH (c:Category)-[:SUBCATEGORY_OF]->{1,3}(root:Category) RETURN root.name;
```

| Квантификатор | Значение | Аналог в Cypher 5 |
|---|---|---|
| `{1,3}` | От 1 до 3 | `*1..3` |
| `{2}` | Ровно 2 | `*2` |
| `{,5}` | От 0 до 5 | `*0..5` |
| `{2,}` | От 2 и больше | `*2..` |
| `+` | Один и более | `*` |
| `*` | Ноль и более | `*0..` |

### Квантифицированный путь

Настоящая сила синтаксиса — в том, что квантифицировать можно не одну связь, а **целый паттерн**. Этого в старом синтаксисе не было вообще.

```cypher
// Цепочка «заказ → товар той же категории → заказ», повторённая 1-2 раза.
// Звёздочкой такое не выразить: она умеет повторять только одну связь
MATCH path = (start:User)
             ((u:User)-[:PLACED]->(:Order)-[:CONTAINS]->(p:Product)
                                  <-[:CONTAINS]-(:Order)<-[:PLACED]-(next:User)){1,2}
             (end:User)
RETURN [n IN nodes(path) WHERE n:User | n.name] AS chain;
```

Внутри квантифицированного паттерна можно ставить условия, и переменные внутри становятся списками:

```cypher
// Цепочка приглашений, где каждый следующий приглашён позже, чем зарегистрировался предыдущий
MATCH path = (root:User {email: 'anna@shop.io'})
             ((a:User)-[r:REFERRED]->(b:User) WHERE b.registeredAt > a.registeredAt){1,4}
             (leaf:User)
RETURN leaf.name, [n IN nodes(path) | n.name] AS chain, size(r) AS depth;
```

Направление стрелки внутри квантифицированного паттерна такое же, как в самих данных: `REFERRED` идёт от пригласившего к приглашённому. Условие внутри скобок фильтрует каждое повторение паттерна отдельно, а переменная `r` снаружи становится списком связей — отсюда `size(r)` как глубина цепочки.

## SHORTEST: новый способ искать кратчайшие пути

Функции `shortestPath()` и `allShortestPaths()` продолжают работать, но они не соответствуют GQL. Их место занял селектор пути перед паттерном.

```cypher
// Старый способ
MATCH (a:User {email: 'anna@shop.io'}), (b:User {email: 'petr@shop.io'})
MATCH path = shortestPath((a)-[*..6]-(b))
RETURN length(path);

// Новый способ
MATCH path = SHORTEST 1 (a:User {email: 'anna@shop.io'})-[]-{1,6}(b:User {email: 'petr@shop.io'})
RETURN length(path);
```

| Селектор | Что возвращает |
|---|---|
| `SHORTEST k` | k кратчайших путей: `SHORTEST 1`, `SHORTEST 3` |
| `ALL SHORTEST` | Все пути минимальной длины |
| `SHORTEST k GROUPS` | Все пути k наименьших длин, сгруппированные по длине |
| `ANY` | Любой путь — используется для проверки достижимости |

`ANY` — заметно дешевле остальных, когда важен сам факт связи, а не её длина:

```cypher
// Есть ли вообще связь между аккаунтом и заблокированным пользователем.
// Планировщик остановится на первом найденном пути
MATCH path = ANY (suspect:User {email: 'x@shop.io'})-[]-{1,5}(banned:User {status: 'banned'})
RETURN count(path) > 0 AS isLinked;
```

Селекторы работают с параметрами, что важно для приложений:

```cypher
:param k => 3
MATCH path = SHORTEST $k (a:User)-[:FOLLOWS]-{1,6}(b:User)
RETURN length(path);
```

> **Важно**: `SHORTEST` считает длину в количестве связей. Взвешенный кратчайший путь, A* и Yen's K-shortest — по-прежнему задача для GDS, урок 29.

## Режимы обхода

По умолчанию Cypher не позволяет пройти по одной связи дважды в рамках одного пути — это правило уникальности связей из урока 5. Cypher 25 сделал режим явно управляемым.

```cypher
// Поведение по умолчанию, теперь его можно записать явно
MATCH DIFFERENT RELATIONSHIPS path = (a:User)-[:FOLLOWS]->{1,4}(b:User)
RETURN path;

// Разрешить повторный проход по связям — нужно для задач вроде обхода маршрутов
MATCH REPEATABLE ELEMENTS path = (a:User)-[:FOLLOWS]->{1,4}(b:User)
RETURN path;

// Запретить повторение УЗЛОВ внутри пути — путь без циклов
MATCH path = ACYCLIC (u:User)-[:FOLLOWS]->{1,4}(other:User)
RETURN path;
```

> **Внимание**: режимы обхода и режимы пути стоят в разных местах. `REPEATABLE ELEMENTS` и `DIFFERENT RELATIONSHIPS` — это режимы **обхода**, они пишутся сразу после `MATCH`, до переменной пути. `ACYCLIC` и `TRAIL` — режимы **пути**, они пишутся внутри, после `path =`. Перепутанный порядок даёт синтаксическую ошибку.

| Ключевое слово | Где пишется | Что запрещает |
|---|---|---|
| `DIFFERENT RELATIONSHIPS` | После `MATCH` | Повтор связей — поведение по умолчанию |
| `REPEATABLE ELEMENTS` | После `MATCH` | Ничего, разрешён повтор и узлов, и связей |
| `ACYCLIC` | После `path =` | Повтор узлов внутри одного пути |
| `TRAIL` | После `path =` | Повтор связей внутри одного пути |

`ACYCLIC` — практичное решение проблемы циклов. В графе подписок пользователи легко образуют кольцо, и обход глубины 4 без этого режима вернёт пути, которые ходят по кругу. На загруженном датасете разница видна сразу:

```cypher
// 28 путей: часть из них проходит по кольцу подписок
MATCH path = TRAIL (u:User {email: 'anna@shop.io'})-[:FOLLOWS]->{1,3}(other:User)
RETURN count(path);

// 27 путей: цикл отброшен
MATCH path = ACYCLIC (u:User {email: 'anna@shop.io'})-[:FOLLOWS]->{1,3}(other:User)
RETURN count(path);
```

Режимы пути комбинируются с селекторами:

```cypher
MATCH path = ANY SHORTEST ACYCLIC (a:User)-[]-{1,6}(b:User {status: 'banned'})
RETURN length(path);
```

## FILTER

Отдельное предложение для фильтрации в середине запроса. Отличие от `WHERE` принципиальное: `WHERE` встраивается в условия поиска паттерна, `FILTER` применяется к уже найденным строкам.

```cypher
// WHERE участвует в поиске: планировщик учтёт условие при обходе
MATCH (u:User)-[:PLACED]->(o:Order) WHERE o.total > 5000 RETURN u.name;

// FILTER отсекает уже посчитанное — удобно после агрегации
MATCH (u:User)-[:PLACED]->(o:Order)
WITH u, sum(o.total) AS revenue
FILTER revenue > 10000
RETURN u.name, revenue;
```

Раньше на месте `FILTER` писали `WITH ... WHERE`. Новая форма короче и яснее выражает намерение.

Отдельный практический случай — фильтрация после `SHORTEST`. Условие на длину пути, поставленное в `WHERE`, заставляет планировщик перебирать все пути вместо быстрого поиска. `FILTER` применяется после и сохраняет быстрый алгоритм:

```cypher
MATCH path = SHORTEST 1 (a:User)-[]-{1,8}(b:User {status: 'banned'})
FILTER length(path) >= 3
RETURN a.email, length(path);
```

## NEXT: цепочка запросов

`NEXT` соединяет самостоятельные запросы в конвейер: результат предыдущего становится входом следующего. Граница между блоками — обычный `RETURN`.

```cypher
MATCH (u:User)-[:PLACED]->(o:Order)
RETURN u, sum(o.total) AS revenue
NEXT
MATCH (u)-[:FOLLOWS]->(other:User)
RETURN u.name, revenue, count(other) AS following;
```

Отличие от `WITH` в том, что каждый блок — законченный запрос со своим `RETURN`, а не продолжение одного длинного. На сложных многоэтапных сценариях это заметно улучшает читаемость.

## Условные запросы: WHEN

Ветвление внутри запроса. Раньше это приходилось выносить в код приложения или изворачиваться через `FOREACH` с трюками.

```cypher
WHEN date().dayOfWeek <= 5 THEN
  MATCH (p:Product) WHERE p.price < 3000 RETURN p.title AS title
ELSE
  MATCH (p:Product) WHERE p.price > 10000 RETURN p.title AS title
```

> **Внимание**: `WHEN` — ведущее предложение, оно не может стоять после `MATCH` напрямую. Чтобы ветвиться по данным из графа, блоки соединяются через `NEXT`: сначала запрос находит данные и возвращает их, потом `WHEN` разбирает случаи.

```cypher
// Расставить ценовые метки товарам одним запросом
MATCH (p:Product)
RETURN p
NEXT
WHEN p.price > 10000 THEN
  SET p:Premium
WHEN p.price > 4000 THEN
  SET p:Mid
ELSE
  SET p:Budget
```

Каждая ветка — самостоятельный фрагмент запроса, в том числе изменяющий данные. Это закрывает сценарии upsert со сложной логикой, которые раньше требовали двух обращений к базе.

## LET

`LET` добавляет переменную, не отбрасывая остальные. `WITH` требует перечислить всё, что должно остаться дальше, — на длинных запросах этот список становится источником ошибок.

```cypher
MATCH (u:User)-[:PLACED]->(o:Order)
LET discounted = o.total * 0.9
RETURN u.email, o.id, o.total, discounted;
```

> Заказы урока 4 идентифицируются свойством `id`; после загрузки датасета в уроке 9 то же поле называется `orderId`. Если колонка пришла пустой — проверь, какое из них есть в твоём графе.

Эквивалент на `WITH`, где переменные приходится перечислять руками:

```cypher
MATCH (u:User)-[:PLACED]->(o:Order)
WITH u, o, o.total * 0.9 AS discounted
RETURN u.email, o.orderId, o.total, discounted;
```

## Что убрали в Cypher 25

Самое частое, на что натыкаются при миграции.

**Узел или связь справа от `SET`.** Раньше можно было скопировать свойства узла в другой узел напрямую, теперь нужна явная функция `properties()`.

```cypher
// Cypher 5 — больше не работает
MATCH (o:Order)-[:SHIPPED_TO]->(a:Address) SET o += a;

// Cypher 25
MATCH (o:Order)-[:SHIPPED_TO]->(a:Address) SET o += properties(a);
```

**Изменения в `db.schema.nodeTypeProperties()`.** Колонка `propertyTypes` теперь возвращает типы Cypher, а не Java-типы. Скрипты, разбиравшие строки вроде `String` или `Long`, придётся поправить.

**`SHOW TRANSACTIONS`.** Колонки `startTime` и `currentQueryStartTime` стали типом `ZONED DATETIME` вместо строки.

**Подзапросы-выражения.** В `COLLECT {}`, `COUNT {}` и `EXISTS {}` внешние переменные раньше участвовали как ключи группировки, из-за чего агрегация при отсутствии совпадений не возвращала строк. В Cypher 25 они трактуются как константы — поведение стало интуитивным, но результаты старых запросов могут измениться.

Полный список изменений — в разделе документации о deprecations и removals; при миграции проходить по нему обязательно.

## Псевдонимы функций по GQL

Часть функций получила вторые имена, соответствующие стандарту. Старые имена работают.

| Cypher | Псевдоним по GQL |
|---|---|
| `size(string)` | `char_length(string)` |
| `toLower`, `toUpper` | `lower`, `upper` |
| `collect` | `collect_list` |
| `length(path)` | `path_length(path)` |
| `ceil` | `ceiling` |
| `log` | `ln` |

Плюс новая функция `cardinality()` — универсальный размер: количество ключей в map, элементов в списке или узлов и связей в пути.

Для нового кода лучше использовать GQL-имена: при переходе на другой движок, поддерживающий GQL, такие запросы перенесутся без правок.

## Практика

1. Проверь через `SHOW DATABASES YIELD name, defaultLanguage`, какая версия языка стоит по умолчанию для твоей базы.
2. Выполни один и тот же запрос с префиксами `CYPHER 5` и `CYPHER 25`, убедись, что оба работают.
3. Переведи базу на Cypher 25 через `ALTER DATABASE neo4j SET DEFAULT LANGUAGE CYPHER 25`, если она ещё на Cypher 5. Выполни ту же команду без слова `DEFAULT` и зафиксируй ошибку `42I06` — это частая опечатка.
4. Перепиши запрос обхода иерархии категорий со старого синтаксиса `*1..3` на квантификатор `{1,3}`.
5. Напиши квантифицированный путь, который повторяет паттерн из двух связей — такой, который через звёздочку не выражается.
6. Замени `shortestPath()` из урока 7 на `SHORTEST 1` и сравни результаты.
7. Используй `ANY` для проверки, связан ли конкретный пользователь с любым заблокированным на глубине до 5.
8. Создай цикл подписок из трёх пользователей и сравни количество путей при обходе `{1,5}` с режимом `ACYCLIC` и без него.
9. Перепиши фильтр по агрегату с `WITH ... WHERE` на `FILTER`.
10. Выполни `SET o += a` без `properties()` и зафиксируй текст ошибки, затем исправь запрос.

## Итоги урока

- С Neo4j 2025.06 язык отделён от версии базы: Cypher 5 заморожен, Cypher 25 развивается и приводится к стандарту GQL.
- Версия выбирается на трёх уровнях: настройка сервера, `ALTER DATABASE SET DEFAULT LANGUAGE`, префикс `CYPHER 25` у запроса; префикс задуман как временный инструмент миграции.
- Текущую версию языка базы показывает колонка `defaultLanguage` в `SHOW DATABASES`, а не `options`.
- Процедуры и функции, включая APOC, привязаны к версии языка и могут вести себя по-разному под Cypher 5 и Cypher 25.
- Квантификаторы `{1,3}` и `+` заменяют `*1..3`, а квантифицировать можно целый паттерн, а не только одну связь — этого в старом синтаксисе не было.
- Селекторы `SHORTEST k`, `ALL SHORTEST` и `ANY` заменяют `shortestPath()` и `allShortestPaths()` и соответствуют GQL; `ANY` дешевле остальных для проверки достижимости.
- Режимы `ACYCLIC`, `TRAIL`, `REPEATABLE ELEMENTS` и `DIFFERENT RELATIONSHIPS` явно управляют повторным прохождением узлов и связей.
- `FILTER` фильтрует уже найденные строки, в отличие от `WHERE`, который встраивается в поиск паттерна — это важно для сохранения быстрого алгоритма после `SHORTEST`.
- Режимы обхода `REPEATABLE ELEMENTS` и `DIFFERENT RELATIONSHIPS` пишутся после `MATCH`, режимы пути `ACYCLIC` и `TRAIL` — внутри, после `path =`.
- `NEXT` соединяет самостоятельные запросы в конвейер, `WHEN ... THEN ... ELSE` даёт ветвление, но только как ведущее предложение — по данным графа ветвятся через `RETURN ... NEXT WHEN`.
- `LET` добавляет переменную, не требуя перечислять остальные, в отличие от `WITH`.
- Главные удалённые возможности: узел или связь справа от `SET` (теперь нужен `properties()`), изменённые типы колонок в `db.schema.nodeTypeProperties()` и `SHOW TRANSACTIONS`.
