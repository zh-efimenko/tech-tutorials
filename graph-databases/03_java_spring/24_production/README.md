# Урок 24. Production

## Конфигурация подключения

Значения по умолчанию рассчитаны на разработку. В продакшне их задают осознанно.

```yaml
spring:
  neo4j:
    uri: neo4j://neo4j-cluster:7687
    authentication:
      username: ${NEO4J_USER}
      password: ${NEO4J_PASSWORD}
    pool:
      max-connection-pool-size: 50
      connection-acquisition-timeout: 30s
      max-connection-lifetime: 1h
      idle-time-before-connection-test: 30s
    connection-timeout: 10s
  data:
    neo4j:
      database: shop
```

| Параметр | Как выбирать |
|---|---|
| `max-connection-pool-size` | Не меньше количества одновременных потоков, обращающихся к базе |
| `connection-acquisition-timeout` | Меньше таймаута HTTP-запроса, иначе клиент отвалится раньше |
| `max-connection-lifetime` | Час — за балансировщиком обязателен, иначе соединения залипают на выбывших узлах |
| `idle-time-before-connection-test` | Проверка живости простаивающих соединений |

> **Важно**: пул на 50 соединений при 200 потоках приложения — гарантированные таймауты под нагрузкой. Считать нужно от количества потоков, а с виртуальными потоками Java 21+ — от реальной конкурентности обращений к базе, потому что виртуальных потоков может быть десятки тысяч.

## Схемы URI и кластер

| Схема | Поведение |
|---|---|
| `bolt://` | Прямое соединение с одним узлом |
| `neo4j://` | Маршрутизация: драйвер получает таблицу маршрутов и сам распределяет запросы |
| `bolt+s://`, `neo4j+s://` | То же с TLS и проверкой сертификата |
| `bolt+ssc://`, `neo4j+ssc://` | TLS с самоподписанным сертификатом |

В кластере используется только `neo4j://`. Драйвер сам определяет лидера для записи и реплики для чтения — балансировщик перед кластером не нужен и вреден, потому что ломает маршрутизацию.

```
                     ┌──────────────┐
   приложение ──────▶│   Driver     │
                     │ routing table│
                     └──┬────┬────┬─┘
              write ────┘    │    └──── read
                    ▼        ▼         ▼
                 Leader  Follower  Follower
```

Маршрутизация работает только если запрос помечен как читающий. Отсюда практический вывод: `@Transactional(readOnly = true)` из урока 21 — это не оптимизация «на будущее», а условие того, что реплики вообще будут задействованы.

> **Внимание**: кластеризация доступна только в Enterprise. В Community `neo4j://` работает, но маршрутизировать некуда — всё идёт на единственный инстанс.

## Причинная согласованность

В кластере запись уходит на лидера, а чтение может попасть на реплику, которая ещё не получила изменение. Драйвер решает это закладками: сессия запоминает позицию и требует от реплики догнать её.

```java
// Внутри одной сессии согласованность гарантирована
try (Session session = driver.session()) {
    session.executeWrite(tx -> tx.run("CREATE (o:Order {orderId: $id})", params));
    session.executeRead(tx -> tx.run("MATCH (o:Order {orderId: $id}) RETURN o", params));
}
```

Между разными сессиями — нет. В Spring каждая транзакция открывает свою сессию, поэтому «записали в одном методе, прочитали в другом» может не увидеть изменений. Если это критично, обе операции объединяют в одну транзакцию.

## Таймауты

Три уровня, и все нужны.

```yaml
spring:
  neo4j:
    connection-timeout: 10s          # установка TCP-соединения
```

```java
@Transactional(timeout = 5)          // выполнение на сервере
public void placeOrder(...) { }
```

```cypher
-- глобальный предохранитель на сервере
CALL dbms.listConfig() YIELD name, value WHERE name = 'db.transaction.timeout' RETURN name, value;
```

Без таймаута транзакции зависший обход переменной длины из урока 14 держит блокировки, пока не сработает глобальный лимит — обычно куда больший, чем допустимо для веб-запроса.

## Безопасность

В Community доступна только базовая аутентификация: один набор пользователей без ролей и без прав на уровне узлов.

```cypher
-- Смена пароля
ALTER CURRENT USER SET PASSWORD FROM 'old' TO 'new';

-- Создание пользователя доступно и в Community
CREATE USER app IF NOT EXISTS SET PASSWORD 'strong-password' CHANGE NOT REQUIRED;

SHOW USERS YIELD user RETURN user;
```

Ролевая модель, права на метки и свойства, ограничение процедур — Enterprise. В Community `CREATE ROLE` завершается ошибкой `51N27: not supported in this edition`:

```cypher
CREATE ROLE reader;
GRANT MATCH {*} ON GRAPH shop NODES User, Product TO reader;
DENY READ {email} ON GRAPH shop NODES User TO reader;
```

Практические требования вне зависимости от редакции:

- пароль в переменных окружения или секретах, никогда в `application.yml` в репозитории;
- TLS между приложением и базой (`neo4j+s://`) при выходе за пределы одной машины;
- отдельный пользователь для приложения, а не `neo4j`;
- порт 7474 (Browser) закрыт снаружи, наружу смотрит только 7687.

> **Важно**: в Community нет прав на уровне узлов и свойств. Если требуется скрыть часть графа от части пользователей, это решается на уровне приложения или разделением на инстансы — на уровне базы такого механизма нет.

## Бэкапы

| Способ | Требует остановки | Редакция |
|---|---|---|
| `neo4j-admin database dump` | Да | Community и Enterprise |
| `neo4j-admin database backup` | Нет, онлайн | Только Enterprise |
| Снапшот тома или диска | Зависит от инфраструктуры | Любая |

Дамп требует остановленной базы. В Community остановить её запросом нельзя — `STOP DATABASE` отвечает `51N27`, а на работающем инстансе `neo4j-admin` упирается в блокировку файла:

```
Failed to dump database 'neo4j': The database is in use. Stop database 'neo4j' and try again.

Lock file has been locked by another process: /data/databases/neo4j/database_lock.
Please ensure no other process is using this database, and that the directory is writable
```

Поэтому останавливается весь контейнер, а `neo4j-admin` запускается отдельным одноразовым контейнером на тех же томах:

```bash
mkdir -p backups

# 1. Остановить сервис
docker compose stop neo4j

# 2. Снять дамп одноразовым контейнером с примонтированным каталогом бэкапов
docker compose run --rm -v "$(pwd)/backups:/backups" --entrypoint neo4j-admin neo4j \
  database dump neo4j --to-path=/backups

# 3. Восстановление — так же, при остановленном сервисе
docker compose run --rm -v "$(pwd)/backups:/backups" --entrypoint neo4j-admin neo4j \
  database load neo4j --from-path=/backups --overwrite-destination

# 4. Поднять обратно
docker compose start neo4j
```

Каталог `backups` монтируется явно: без этого дамп ляжет внутрь одноразового контейнера и исчезнет вместе с ним по `--rm`.

> **Внимание**: в Community онлайн-бэкапа нет. Практический вывод: либо окно обслуживания, либо снапшот тома на уровне инфраструктуры с пониманием, что это crash-consistent копия. Бэкап, который ни разу не восстанавливали, бэкапом не является — проверка восстановления должна быть регулярной процедурой.

## Память сервера

```bash
docker exec neo4j neo4j-admin server memory-recommendation
```

Команда выдаёт рекомендации по page cache и heap исходя из объёма машины и размера данных. Ориентиры из урока 3 остаются в силе: page cache — по размеру графа на диске, heap — по сложности запросов и проекциям GDS.

```cypher
-- Насколько граф помещается в page cache
CALL dbms.listConfig() YIELD name, value
WHERE name IN ['server.memory.pagecache.size', 'server.memory.heap.max_size']
RETURN name, value;
```

Признак нехватки page cache — рост `Page Cache Misses` в `PROFILE` из урока 13 на повторных запусках одного запроса.

## Развёртывание схемы

Ограничения и индексы — часть приложения, а не ручная операция. Механизм из урока 16:

```yaml
org:
  neo4j:
    migrations:
      enabled: true
      transaction-mode: PER_STATEMENT
      validate-on-migrate: true
```

При нескольких экземплярах приложения миграции стартуют одновременно. Neo4j-Migrations берёт блокировку, поэтому применит их ровно один экземпляр, а остальные подождут. Но миграции данных на большом графе могут выйти за таймаут старта — такие миграции лучше выносить в отдельную задачу, а не запускать при старте сервиса.

## Чеклист перед выкаткой

**Схема**

- ограничения уникальности на все бизнес-ключи;
- индексы под фильтры всех запросов приложения, проверено через `PROFILE`;
- миграции применяются автоматически и проверены на копии production-объёма.

**Запросы**

- у всех обходов переменной длины есть верхняя граница;
- в планах нет `AllNodesScan` и незапланированных `CartesianProduct`;
- в изменяющих запросах нет `Eager`;
- массовая запись идёт через `UNWIND $rows`, а не пообъектно;
- наружу отдаются проекции, а не сущности целиком.

**Подключение**

- размер пула согласован с конкурентностью приложения;
- заданы все три таймаута;
- `max-connection-lifetime` установлен, если между приложением и базой есть балансировщик;
- читающие транзакции помечены `readOnly = true`.

**Надёжность**

- `TransientException` обрабатывается повтором, а операции идемпотентны;
- порядок захвата узлов детерминирован, чтобы не плодить deadlock;
- батчевые операции вынесены из управляемых транзакций.

**Эксплуатация**

- health в readiness, но не в liveness;
- трассировка через Observation SPI включена, исчерпание пула под алертом;
- query log с порогом включён (Enterprise);
- notifications логируются;
- бэкап настроен и восстановление проверено;
- счётчики узлов и связей под наблюдением.

## Практика

1. Вынеси пароль из `application.yml` в переменные окружения и проверь запуск.
2. Настрой пул, таймауты и `max-connection-lifetime` явными значениями.
3. Создай отдельного пользователя базы для приложения и переключись на него.
4. Попробуй создать роль и выдать права — зафиксируй ограничение Community.
5. Сделай дамп базы по последовательности из урока, удали часть данных и восстанови из дампа. Замерь время. Попробуй сначала выполнить дамп на работающем контейнере и зафиксируй ошибку блокировки.
6. Выполни `neo4j-admin server memory-recommendation` и сравни с настройками в `compose.yml`.
7. Найди в `PROFILE` повторного запуска запроса ненулевые `Page Cache Misses` и объясни причину.
8. Пройди по чеклисту запросов: возьми все `@Query` своего приложения и сними `PROFILE` с каждого.
9. Проверь, что все читающие сервисные методы помечены `readOnly = true`.
10. Смоделируй исчерпание пула: поставь размер 1, дай нагрузку и убедись, что таймауты видны в метриках.

## Итоги урока

- Размер пула считается от реальной конкурентности обращений к базе; с виртуальными потоками число потоков перестаёт быть ориентиром.
- В кластере используется только схема `neo4j://`: драйвер сам маршрутизирует запросы, и балансировщик перед кластером ломает эту логику.
- Реплики задействуются только для транзакций, помеченных как читающие, — `readOnly = true` является условием маршрутизации, а не украшением.
- Причинная согласованность гарантирована внутри одной сессии; в Spring каждая транзакция открывает свою, поэтому запись и чтение через границу транзакций могут разойтись.
- Таймауты нужны на трёх уровнях: соединение, транзакция, глобальный предохранитель сервера.
- В Community нет ролей и прав на уровне узлов — разграничение доступа решается приложением или разделением инстансов.
- Онлайн-бэкап доступен только в Enterprise; в Community остаются дамп с остановкой и снапшот тома, причём в Docker останавливать приходится весь контейнер — `STOP DATABASE` в Community недоступен.
- Бэкап без проверенного восстановления бэкапом не является.
- Миграции при старте применит один экземпляр благодаря блокировке, но тяжёлые миграции данных выносят в отдельную задачу.
- Чеклист перед выкаткой закрывает пять областей: схема, запросы, подключение, надёжность и эксплуатация.
