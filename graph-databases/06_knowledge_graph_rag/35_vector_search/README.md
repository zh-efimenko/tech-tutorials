# Урок 35. Векторный поиск в Neo4j

Предполагается, что пройдены треки 1 и 2. Урок 28 полезен — там разбирались эмбеддинги узлов из GDS, но здесь речь о других векторах: не о положении в графе, а о смысле текста.

## Зачем графовой базе векторы

Обычный индекс отвечает на вопрос «где точно такое значение». Полнотекстовый — «где встречаются эти слова». Векторный — «где что-то похожее по смыслу», даже если ни одно слово не совпало.

Отдельно взятый векторный поиск даёт специализированная база: Qdrant, Milvus, pgvector. Neo4j выигрывает не скоростью поиска по вектору, а тем, что происходит **после** него: найденный узел лежит в графе, и от него сразу доступны категория, бренд, отзывы, покупатели, связанные документы. Именно это делает GraphRAG возможным — тема уроков 37 и 38.

| | Отдельное векторное хранилище | Neo4j |
|---|---|---|
| Скорость поиска по вектору | Выше | Достаточная |
| Что доступно после поиска | Идентификатор и метаданные | Весь граф от найденного узла |
| Фильтрация по связям | Нет | Обычный Cypher |
| Согласованность с основными данными | Отдельная синхронизация | Одна транзакция |

## Векторный индекс

```cypher
CREATE VECTOR INDEX product_embedding IF NOT EXISTS
FOR (p:Product) ON (p.embedding)
OPTIONS {indexConfig: {
  `vector.dimensions`: 4,
  `vector.similarity_function`: 'cosine'
}};
```

Обратные кавычки вокруг ключей обязательны: точка в имени иначе читается как обращение к полю.

Два параметра задаются при создании и не меняются потом:

**`vector.dimensions`** — длина вектора. Определяется моделью эмбеддингов: `nomic-embed-text` даёт 768, `text-embedding-3-small` — 1536. Сменить модель без пересоздания индекса нельзя.

**`vector.similarity_function`** — `cosine` или `euclidean`. Косинус смотрит на направление вектора и игнорирует длину, евклидово расстояние учитывает и то и другое. Для текстовых эмбеддингов практически всегда нужен `cosine`.

В учебном примере размерность 4, чтобы векторы помещались в вывод. В реальном проекте она диктуется моделью.

```cypher
SHOW INDEXES YIELD name, type, state, options
WHERE type = 'VECTOR'
RETURN name, state, options;
```

```
╒═════════════════════╤══════════╤═══════════════════════════════════════════════════════════════════════════╕
│name                 │state     │options                                                                    │
╞═════════════════════╪══════════╪═══════════════════════════════════════════════════════════════════════════╡
│"product_embedding"  │"ONLINE"  │{indexConfig: {`vector.dimensions`: 4,                                     │
│                     │          │ `vector.default_search_expansion_factor`: 1.5, `vector.hnsw.m`: 16,       │
│                     │          │ `vector.quantization.type`: "SCALAR",                                     │
│                     │          │ `vector.similarity_function`: "COSINE",                                   │
│                     │          │ `vector.hnsw.ef_construction`: 100}}                                      │
└─────────────────────┴──────────┴───────────────────────────────────────────────────────────────────────────┘
```

Остальные параметры проставились по умолчанию и раскрывают устройство индекса.

`vector.hnsw.m` и `vector.hnsw.ef_construction` — параметры HNSW, иерархического графа для приближённого поиска ближайших соседей. Индекс сам является графом: узлы-векторы соединены рёбрами к близким соседям, поиск идёт жадным спуском по слоям. `m` — число связей на узел, `ef_construction` — ширина просмотра при построении. Больше значения — точнее поиск, больше памяти и дольше построение.

`vector.quantization.type: SCALAR` — векторы хранятся сжатыми до одного байта на компоненту вместо четырёх. Экономия памяти вчетверо ценой небольшой потери точности.

> **Важно**: HNSW — **приближённый** поиск. Ближайший сосед может не попасть в выдачу. На практике потеря составляет проценты и окупается скоростью, но полагаться на полноту результата нельзя. Если нужен точный ответ на небольшом наборе — перебор с `vector.similarity.cosine` в обычном `MATCH` честнее.

## Запись эмбеддингов

Эмбеддинг — это обычное свойство-список чисел с плавающей точкой.

```cypher
MATCH (p:Product {sku: 'SKU-001'})
SET p.embedding = [0.12, -0.45, 0.88, 0.03];
```

Есть и специальная процедура, которая проверяет тип и не даёт записать список целых:

```cypher
MATCH (p:Product) WITH p LIMIT 1
CALL db.create.setNodeVectorProperty(p, 'embedding', [0.5, 0.5, 0.5, 0.5])
RETURN p.title, p.embedding;
```

Для связей есть парная `db.create.setRelationshipVectorProperty`, а вместе с ней и векторные индексы на связях — `db.index.vector.queryRelationships`.

Проверка типа сохранённого значения:

```cypher
MATCH (p:Product) WITH p LIMIT 1 RETURN valueType(p.embedding) AS t;
```

```
╒═══════════════════════════════╕
│t                              │
╞═══════════════════════════════╡
│"LIST<FLOAT NOT NULL> NOT NULL"│
└───────────────────────────────┘
```

В Cypher 25 есть отдельный тип `VECTOR` и функция-конструктор `vector([0.1, 0.2, 0.3, 0.4], 4, FLOAT32)`. Но записать его в узел на стандартном формате хранилища не получится:

```
51N77: storing properties of type vector is not supported in aligned store format
```

Практический вывод: эмбеддинги хранятся списком `FLOAT`, и это рабочий вариант — векторный индекс с ним работает штатно.

## Поиск

```cypher
CALL db.index.vector.queryNodes('product_embedding', 5, [1.0, 0.1, 0.2, 0.5])
YIELD node, score
RETURN node.title AS product, round(score, 4) AS score;
```

```
╒═════════════════════════════════╤═════════╕
│product                          │score    │
╞═════════════════════════════════╪═════════╡
│"Кофеварка Aroma Pro"            │0.9998   │
│"Кофеварка Aroma Mini"           │0.9984   │
│"Рожковая кофеварка Crema S"     │0.9969   │
│"Эспрессо-машина Barista One"    │0.9719   │
│"Эспрессо-машина Barista Duo"    │0.9411   │
└─────────────────────────────────┴─────────┘
```

Три аргумента: имя индекса, число ближайших соседей, вектор запроса. `score` нормирован в диапазон от 0 до 1, где 1 — полное совпадение направления.

Размерность вектора запроса обязана совпадать с индексом:

```
51N65: Vector index `product_embedding` has a configured dimensionality of 4,
but the provided vector has a dimension 2.
```

Ошибка проявляется на запросе, а не на записи, и это типовая причина падений после смены модели эмбеддингов.

## Фильтрация: главная ловушка

Процедура возвращает ровно `k` записей, и только **потом** к ним применяется `WHERE`.

```cypher
CALL db.index.vector.queryNodes('product_embedding', 3, [1.0, 0.1, 0.2, 0.5])
YIELD node, score
WHERE node.price < 5000
RETURN node.title AS product, node.price AS price;
```

```
╒═════════════════════════╤═════════╕
│product                  │price    │
╞═════════════════════════╪═════════╡
│"Кофеварка Aroma Pro"    │4990.0   │
│"Кофеварка Aroma Mini"   │3290.0   │
└─────────────────────────┴─────────┘
```

Просили три, получили две. Запрошенный лимит израсходован до фильтра, и подходящие товары за пределами топ-3 в выдачу не попали. С жёстким фильтром результат может оказаться пустым при том, что подходящих записей в базе сотни.

Обход — брать заведомо больше и резать после:

```cypher
CALL db.index.vector.queryNodes('product_embedding', 20, [1.0, 0.1, 0.2, 0.5])
YIELD node, score
WHERE node.price < 5000
RETURN node.title AS product, node.price AS price, round(score, 4) AS score
LIMIT 3;
```

Коэффициент запаса зависит от селективности фильтра: если условию удовлетворяет каждая десятая запись, брать нужно раз в двадцать больше. Универсального числа нет, подбирается замером.

Альтернатива для очень селективных фильтров — сначала отобрать кандидатов обычным индексом, затем считать похожесть перебором:

```cypher
MATCH (p:Product)-[:IN_CATEGORY]->(c:Category {name: 'Капельные кофеварки'})
WITH p, vector.similarity.cosine(p.embedding, [1.0, 0.1, 0.2, 0.5]) AS score
RETURN p.title AS product, round(score, 4) AS score
ORDER BY score DESC LIMIT 3;
```

Здесь векторный индекс не используется вовсе, зато результат точный и фильтр применён до ранжирования. Работает, пока кандидатов после фильтра — тысячи, а не миллионы.

> **Внимание**: `vector.similarity.cosine` возвращает `(1 + cos) / 2`, отображая диапазон `[-1, 1]` в `[0, 1]`. Это та же нормировка, что у `score` из индекса, но не то же, что `gds.similarity.cosine` из урока 28. Пороги между этими функциями не переносятся.

## Гибридный поиск

Векторный поиск плох на точных совпадениях: артикул, номер модели, редкий термин размываются в эмбеддинге. Полнотекстовый плох на синонимах и перефразировках. Комбинация закрывает обе дыры.

```cypher
CREATE FULLTEXT INDEX product_text IF NOT EXISTS
FOR (p:Product) ON EACH [p.title];

CALL db.index.fulltext.queryNodes('product_text', 'кофеварка')
YIELD node, score
RETURN node.title AS product, round(score, 3) AS score LIMIT 3;
```

```
╒═════════════════════════════════╤═════════╕
│product                          │score    │
╞═════════════════════════════════╪═════════╡
│"Кофеварка Aroma Pro"            │0.932    │
│"Кофеварка Aroma Mini"           │0.932    │
│"Рожковая кофеварка Crema S"     │0.826    │
└─────────────────────────────────┴─────────┘
```

Складывать оценки двух индексов напрямую нельзя: они в разных шкалах и разных распределениях. Стандартное решение — **Reciprocal Rank Fusion**: складываются не оценки, а обратные позиции в рейтингах.

```cypher
CALL () {
  CALL db.index.vector.queryNodes('product_embedding', 8, [1.0, 0.1, 0.2, 0.5])
  YIELD node, score
  WITH node, score ORDER BY score DESC
  WITH collect(node) AS ranked
  UNWIND range(0, size(ranked) - 1) AS i
  RETURN ranked[i] AS node, 1.0 / (60 + i + 1) AS rrf
UNION
  CALL db.index.fulltext.queryNodes('product_text', 'кофеварка OR эспрессо')
  YIELD node, score
  WITH node, score ORDER BY score DESC
  WITH collect(node) AS ranked
  UNWIND range(0, size(ranked) - 1) AS i
  RETURN ranked[i] AS node, 1.0 / (60 + i + 1) AS rrf
}
RETURN node.title AS product, round(sum(rrf), 5) AS score
ORDER BY score DESC LIMIT 5;
```

```
╒═════════════════════════════════╤═══════════╕
│product                          │score      │
╞═════════════════════════════════╪═══════════╡
│"Эспрессо-машина Barista One"    │0.03202    │
│"Кофеварка Aroma Pro"            │0.03202    │
│"Кофеварка Aroma Mini"           │0.032      │
│"Эспрессо-машина Barista Duo"    │0.03151    │
│"Рожковая кофеварка Crema S"     │0.03126    │
└─────────────────────────────────┴───────────┘
```

Разбор:

- `collect` плюс `UNWIND range(...)` превращают отсортированный список в пары «узел — позиция»; собственного оператора нумерации строк в Cypher нет;
- константа 60 в знаменателе — стандартное значение из статьи, где RRF был предложен; она сглаживает разницу между первыми позициями, не давая одному источнику доминировать;
- `sum(rrf)` складывает вклады: документ, попавший в оба рейтинга, поднимается выше документа, который лидирует в одном;
- `CALL () { ... }` — вызываемый подзапрос без импорта переменных, форма Cypher 25.

Обрати внимание на результат: «Эспрессо-машина Barista One» вышла на первое место, хотя в векторном поиске была четвёртой, а в текстовом её нашло только слово «эспрессо». Присутствие в обоих рейтингах перевесило.

## Ради чего всё это — обогащение графом

Дальше начинается то, чего отдельное векторное хранилище не даёт: от найденного узла идёт обычный обход.

```cypher
CALL db.index.vector.queryNodes('product_embedding', 3, [1.0, 0.1, 0.2, 0.5])
YIELD node AS p, score
MATCH (p)-[:IN_CATEGORY]->(c:Category), (p)-[:MADE_BY]->(b:Brand)
OPTIONAL MATCH (r:Review)-[:ABOUT]->(p)
RETURN p.title AS product, round(score, 3) AS score,
       c.name AS category, b.name AS brand, round(avg(r.rating), 2) AS rating;
```

```
╒═════════════════════════════════╤═════════╤═══════════════════════════╤═════════╤═════════╕
│product                          │score    │category                   │brand    │rating   │
╞═════════════════════════════════╪═════════╪═══════════════════════════╪═════════╪═════════╡
│"Кофеварка Aroma Pro"            │1.0      │"Капельные кофеварки"      │"Aroma"  │5.0      │
│"Кофеварка Aroma Mini"           │0.998    │"Капельные кофеварки"      │"Aroma"  │1.0      │
│"Рожковая кофеварка Crema S"     │0.997    │"Эспрессо-кофеварки"       │"Crema"  │NULL     │
└─────────────────────────────────┴─────────┴───────────────────────────┴─────────┴─────────┘
```

Две почти одинаковые по вектору кофеварки одного бренда имеют рейтинг 5.0 и 1.0. Вектор эту разницу не видит — она в графе. В векторном хранилище пришлось бы либо тащить рейтинг в метаданные и синхронизировать его, либо делать второй запрос в основную базу.

Ещё дальше — обогащение через людей:

```cypher
CALL db.index.vector.queryNodes('product_embedding', 3, [1.0, 0.1, 0.2, 0.5])
YIELD node AS p, score
MATCH (p)<-[:CONTAINS]-(:Order)<-[:PLACED]-(u:User)
MATCH (u)-[:PLACED]->(:Order)-[:CONTAINS]->(also:Product)
WHERE also <> p
RETURN p.title AS product, collect(DISTINCT also.title)[0..3] AS alsoBought;
```

Один запрос: семантический поиск, переход к покупателям, переход к их другим покупкам. Это и есть аргумент за векторный индекс внутри графовой базы.

## Практическая сторона

**Откуда берутся векторы.** Их считает модель эмбеддингов вне базы: OpenAI, локальная модель через Ollama, Spring AI. Neo4j векторы только хранит и ищет по ним. Пайплайн генерации — урок 38.

**Что именно эмбеддить.** Не голое название. Строка вида `title + категория + бренд + первые предложения описания` работает заметно лучше, потому что несёт контекст. Сборка такой строки — обычный Cypher по графу.

**Стоимость обновления.** Изменилось описание товара — нужно пересчитать эмбеддинг. Отслеживается это хешем исходного текста, записанным рядом с вектором: совпал хеш — пересчёт не нужен.

**Память.** Вектор из 1536 чисел `float32` — 6 КБ на узел, миллион узлов — 6 ГБ плюс структура HNSW. Квантизация сокращает это вчетверо. Планировать heap и page cache нужно с учётом этого.

**Смена модели.** Другая модель — другая размерность и другое пространство. Индекс пересоздаётся, все векторы пересчитываются. Старые и новые эмбеддинги несравнимы, промежуточного состояния не бывает — только полная замена.

## Практика

1. Создай векторный индекс на `Product.embedding` размерности 4 с косинусной метрикой и посмотри все проставленные по умолчанию опции.
2. Проставь товарам простые эмбеддинги: первая компонента — признак кофеварки, вторая — аудиотехники, третья — нормированная цена, четвёртая — константа.
3. Найди пять ближайших к вектору `[1.0, 0.1, 0.2, 0.5]` товаров.
4. Вызови поиск с вектором другой размерности и разбери текст ошибки.
5. Добавь `WHERE node.price < 5000` при `k = 3` и объясни, почему вернулось меньше трёх строк.
6. Подбери `k`, при котором после фильтра остаётся три товара.
7. Перепиши тот же запрос через перебор с `vector.similarity.cosine` внутри одной категории и сравни результаты.
8. Создай полнотекстовый индекс по названиям и найди товары по слову «кофеварка».
9. Собери RRF-объединение векторного и полнотекстового поиска. Поменяй константу 60 на 5 и посмотри, как изменится порядок.
10. Найди товар, который поднялся в объединённом рейтинге выше, чем был в каждом из исходных, и объясни почему.
11. Обогати результат векторного поиска категорией, брендом и средним рейтингом одним запросом.
12. Собери запрос «семантический поиск товара плюс что ещё покупают его покупатели».
13. Удали индексы и свойство `embedding`.

## Итоги урока

- Векторный индекс отвечает на вопрос о смысловой близости, точный индекс — о равенстве, полнотекстовый — о словах.
- Преимущество Neo4j не в скорости векторного поиска, а в том, что от найденного узла доступен весь граф без второго запроса и без синхронизации метаданных.
- `vector.dimensions` и `vector.similarity_function` задаются при создании и не меняются: смена модели эмбеддингов означает пересоздание индекса и пересчёт всех векторов.
- Для текстовых эмбеддингов используется косинусная метрика, потому что важно направление вектора, а не его длина.
- Внутри векторный индекс — это HNSW, то есть тоже граф; поиск по нему приближённый, и ближайший сосед может не попасть в выдачу.
- Эмбеддинги хранятся как `LIST<FLOAT>`; тип `VECTOR` из Cypher 25 на стандартном формате хранилища не сохраняется.
- `db.create.setNodeVectorProperty` проверяет тип при записи, для связей есть парная процедура и собственные векторные индексы.
- Фильтр `WHERE` применяется после того, как индекс вернул `k` записей: с жёстким условием результат может оказаться пустым при сотнях подходящих записей в базе.
- Обходные пути — запрашивать с запасом либо отбирать кандидатов обычным индексом и считать похожесть перебором через `vector.similarity.cosine`.
- Оценки векторного и полнотекстового индексов лежат в разных шкалах и складываются через Reciprocal Rank Fusion — по позициям, а не по значениям.
- Нумерация строк собирается через `collect` и `UNWIND range(...)`: собственного оператора для этого в Cypher нет.
- Эмбеддить стоит не название, а собранную из графа строку с категорией, брендом и описанием; необходимость пересчёта отслеживается хешем исходного текста.
