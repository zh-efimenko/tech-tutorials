# Урок 36. Построение knowledge graph

Предполагается, что пройден урок 35 — там разбирались векторные индексы и хранение эмбеддингов. Схема из этого урока используется дальше в уроках 37 и 38.

## Что такое knowledge graph

До сих пор граф курса собирался из структурированных данных: у заказа есть покупатель, у товара — категория. Всё это уже лежало в таблицах, задача сводилась к переносу.

Knowledge graph строится из **текста**, в котором структуры нет. Инструкция, обзор, тикет поддержки, договор — там те же сущности и связи, но выражены словами. Извлечь их и уложить в граф — задача этого урока.

Зачем это нужно, если есть векторный поиск. Векторный индекс находит похожие куски текста и на этом останавливается. Он не ответит на вопрос «какие товары этого бренда упоминаются вместе с проблемой протечки», потому что в отдельно взятом чанке нет ни слова «бренд», ни связи между чанками. Граф отвечает, потому что связь между сущностями в нём материализована.

## Схема

Минимальная рабочая схема состоит из трёх слоёв.

```
(:Document)-[:HAS_CHUNK]->(:Chunk)-[:MENTIONS]->(:Entity)
                                        │
                                        ├─[:RELATES_TO {type, mentions, evidence}]─▶(:Entity)
                                        └─[:RESOLVED_TO]──────────────────────────▶(:Product)
```

**Документы и чанки** — слой хранения текста. Чанк несёт `text` и эмбеддинг, по нему работает векторный поиск.

**Сущности** — слой смысла. Один узел на одну реальную вещь, независимо от того, в скольких чанках она упомянута.

**`RESOLVED_TO`** — мост в основной граф. Извлечённая из текста «Aroma Pro» связывается с товаром `Кофеварка Aroma Pro`, который уже был в каталоге. Это и есть главная ценность схемы: текст и структурированные данные оказываются в одном графе.

Связь `MENTIONS` между чанком и сущностью — не украшение. Она обеспечивает **прослеживаемость**: по любому утверждению графа можно вернуться к исходному предложению. Без неё knowledge graph превращается в набор непроверяемых фактов, а ответы LLM — в галлюцинации без источника.

## Ограничения

```cypher
CREATE CONSTRAINT document_id IF NOT EXISTS FOR (d:Document) REQUIRE d.docId IS UNIQUE;
CREATE CONSTRAINT chunk_id    IF NOT EXISTS FOR (c:Chunk)    REQUIRE c.chunkId IS UNIQUE;
CREATE CONSTRAINT entity_key  IF NOT EXISTS FOR (e:Entity)   REQUIRE e.key IS UNIQUE;
```

Ограничение уникальности на `Entity.key` — центральный элемент всей конструкции. Оно гарантирует, что `MERGE` по ключу не создаст дубль сущности, сколько бы раз она ни встретилась в текстах. Ключ — нормализованное имя, а не сырое: регистр, лишние пробелы и знаки препинания снимаются заранее.

## Загрузка документов

Чанкинг — разбиение документа на куски — делается вне базы. Практическое правило: 300–800 токенов на чанк с перекрытием 10–20%, границы по абзацам, а не по символам.

```cypher
WITH [
  {docId: 'doc-1', title: 'Инструкция: кофеварка Aroma Pro', source: 'manual',
   chunks: [
     {n: 0, text: 'Кофеварка Aroma Pro относится к капельным кофеваркам. Производитель — компания Aroma. Гарантия составляет 24 месяца.'},
     {n: 1, text: 'Для приготовления используйте кофемолку Aroma Compact. Помол средней грубости обеспечивает лучший вкус.'}
   ]},
  {docId: 'doc-2', title: 'Обзор: сравнение Aroma Pro и Crema S', source: 'blog',
   chunks: [
     {n: 0, text: 'Рожковая кофеварка Crema S дороже, чем Aroma Pro, но даёт более плотный эспрессо.'},
     {n: 1, text: 'Компания Crema выпускает технику для эспрессо с 2015 года и конкурирует с Aroma.'}
   ]}
] AS docs
UNWIND docs AS d
MERGE (doc:Document {docId: d.docId})
SET doc.title = d.title, doc.source = d.source
WITH doc, d
UNWIND d.chunks AS ch
MERGE (c:Chunk {chunkId: d.docId + '-' + ch.n})
SET c.text = ch.text, c.position = ch.n
MERGE (doc)-[:HAS_CHUNK]->(c);
```

Идентификатор чанка составной — `docId + позиция`. Это делает загрузку идемпотентной: повторный прогон того же документа обновит тексты, а не создаст вторую копию.

## Извлечение сущностей

Извлечением занимается LLM, база принимает готовый результат. Промпт должен требовать строго заданный JSON и **закрытый список** типов.

```
Извлеки из текста сущности и связи между ними.

Допустимые типы сущностей: Product, Brand, Category, Problem, Feature.
Допустимые типы связей: IN_CATEGORY, MADE_BY, USED_WITH, COMPETES_WITH, HAS_PROBLEM.

Правила:
- используй только типы из списков выше;
- имя сущности приводи к форме из текста, без склонения;
- не выдумывай связи, которых в тексте нет;
- если ничего не найдено, верни пустые массивы.

Ответ строго в формате:
{"entities": [{"name": "...", "type": "..."}],
 "relations": [{"source": "...", "type": "...", "target": "..."}]}

Текст:
<чанк>
```

> **Важно**: закрытый список типов — не формальность. Без него LLM изобретёт `PRODUCED_BY`, `MANUFACTURED_BY` и `MADE_BY` для одного и того же отношения, и граф станет неприменим: запросы придётся писать под каждый вариант. Онтология проектируется **до** извлечения, а не выводится из результатов.

Второе правило той же природы: типов должно быть мало. Пять-десять типов сущностей и десяток типов связей покрывают большинство задач. Онтология на сорок типов не наполняется — LLM начинает путать близкие категории, и качество падает быстрее, чем растёт выразительность.

### Гарантированный формат ответа

Просить JSON в тексте промпта — ненадёжно: модель добавит пояснение до или после, обернёт ответ в markdown-блок, оборвётся на середине. Ollama и большинство провайдеров умеют принимать JSON Schema и ограничивать генерацию ею:

```json
{
  "model": "qwen3:8b",
  "messages": [{"role": "user", "content": "<промпт с текстом чанка>"}],
  "stream": false,
  "format": {
    "type": "object",
    "properties": {
      "entities": {"type": "array", "items": {"type": "object", "properties": {
        "name": {"type": "string"},
        "type": {"type": "string",
                 "enum": ["Product", "Brand", "Category", "Problem", "Feature"]}},
        "required": ["name", "type"]}},
      "relations": {"type": "array", "items": {"type": "object", "properties": {
        "source": {"type": "string"},
        "type": {"type": "string",
                 "enum": ["IN_CATEGORY", "MADE_BY", "USED_WITH", "COMPETES_WITH", "HAS_PROBLEM"]},
        "target": {"type": "string"}},
        "required": ["source", "type", "target"]}}
    },
    "required": ["entities", "relations"]
  }
}
```

Схема даёт две гарантии механически, а не уговорами: ответ разбирается как JSON, и типы принадлежат онтологии. Список `enum` дублирует то, что уже написано в промпте, и это правильно — промпт влияет на выбор, схема запрещает выход за границы.

Чего схема **не** гарантирует — осмысленности содержимого. Ниже видно, что именно с ним и происходит.

## Загрузка результата извлечения

Приложение отдаёт массив разборов, база раскладывает его по узлам и связям.

```cypher
WITH [
  {chunkId: 'doc-1-0',
   entities: [{name: 'Aroma Pro', type: 'Product'},
              {name: 'капельные кофеварки', type: 'Category'},
              {name: 'Aroma', type: 'Brand'}],
   relations: [{source: 'Aroma Pro', type: 'IN_CATEGORY', target: 'капельные кофеварки'},
               {source: 'Aroma Pro', type: 'MADE_BY', target: 'Aroma'}]},
  {chunkId: 'doc-1-1',
   entities: [{name: 'Aroma Compact', type: 'Product'}, {name: 'Aroma Pro', type: 'Product'}],
   relations: [{source: 'Aroma Pro', type: 'USED_WITH', target: 'Aroma Compact'}]},
  {chunkId: 'doc-2-0',
   entities: [{name: 'Crema S', type: 'Product'}, {name: 'Aroma Pro', type: 'Product'}],
   relations: [{source: 'Crema S', type: 'COMPETES_WITH', target: 'Aroma Pro'}]},
  {chunkId: 'doc-2-1',
   entities: [{name: 'Crema', type: 'Brand'}, {name: 'Aroma', type: 'Brand'}],
   relations: [{source: 'Crema', type: 'COMPETES_WITH', target: 'Aroma'}]}
] AS extracted
UNWIND extracted AS ex
MATCH (c:Chunk {chunkId: ex.chunkId})
CALL (c, ex) {
  UNWIND ex.entities AS e
  MERGE (n:Entity {key: toLower(e.name)})
  SET n.name = e.name, n.type = e.type
  MERGE (c)-[:MENTIONS]->(n)
}
CALL (c, ex) {
  UNWIND ex.relations AS r
  MATCH (s:Entity {key: toLower(r.source)}), (t:Entity {key: toLower(r.target)})
  MERGE (s)-[rel:RELATES_TO {type: r.type}]->(t)
  ON CREATE SET rel.mentions = 1, rel.evidence = [c.chunkId]
  ON MATCH  SET rel.mentions = rel.mentions + 1, rel.evidence = rel.evidence + c.chunkId
}
RETURN count(*) AS processed;
```

Разбор конструкции:

- два отдельных `CALL (c, ex) { ... }` вместо одного: сущности обязаны быть созданы полностью до того, как начнётся сопоставление связей, иначе `MATCH` не найдёт вторую сторону;
- `MERGE (n:Entity {key: toLower(e.name)})` — нормализация ключа прямо в запросе; в реальном пайплайне нормализация сложнее и делается до загрузки;
- `mentions` считает, сколько раз связь подтверждена разными чанками, `evidence` хранит их идентификаторы — это опора для проверки качества и для ссылок в ответе LLM.

Результат:

```cypher
MATCH (a:Entity)-[r:RELATES_TO]->(b:Entity)
RETURN a.name AS source, r.type AS type, b.name AS target, r.mentions AS support, r.evidence;
```

```
╒═════════════╤══════════════════╤═══════════════════════╤═══════════╤═══════════════╕
│source       │type              │target                 │support    │r.evidence     │
╞═════════════╪══════════════════╪═══════════════════════╪═══════════╪═══════════════╡
│"Aroma Pro"  │"USED_WITH"       │"Aroma Compact"        │1          │["doc-1-1"]    │
│"Aroma Pro"  │"IN_CATEGORY"     │"капельные кофеварки"  │1          │["doc-1-0"]    │
│"Aroma Pro"  │"MADE_BY"         │"Aroma"                │1          │["doc-1-0"]    │
│"Crema S"    │"COMPETES_WITH"   │"Aroma Pro"            │1          │["doc-2-0"]    │
│"Crema"      │"COMPETES_WITH"   │"Aroma"                │1          │["doc-2-1"]    │
└─────────────┴──────────────────┴───────────────────────┴───────────┴───────────────┘
```

Это результат на **вычищенном вручную** разборе — так выглядит правильный ответ. Дальше то же самое с настоящей моделью.

## Что возвращает реальная модель

Те же четыре чанка, тот же промпт со схемой, `qwen3:8b` при `temperature: 0`. Результат:

| Чанк | Сущности | Связи |
|---|---|---|
| doc-1-0 | `Кофеварка Aroma Pro` Product, `Aroma` Brand, `капельные кофеварки` Category | `Кофеварка Aroma Pro` IN_CATEGORY `капельные кофеварки`; `Кофеварка Aroma Pro` MADE_BY `Aroma` |
| doc-1-1 | `кофемолка Aroma Compact` Product, `Aroma Compact` **Brand**, `средней грубости` Feature | `кофемолка Aroma Compact` USED_WITH `средней грубости` |
| doc-2-0 | `Рожковая кофеварка Crema S` Product, `Aroma Pro` Product | `Рожковая кофеварка Crema S` COMPETES_WITH `Aroma Pro` |
| doc-2-1 | `Crema` Brand, `Aroma` Brand, `эспрессо` **Product** | `Crema` COMPETES_WITH `Aroma` |

Два чанка из четырёх разобраны идеально. В двух других — четыре ошибки, и все они типовые.

**Одна вещь под двумя именами.** `Кофеварка Aroma Pro` из первого чанка и `Aroma Pro` из третьего — один товар, два узла. Модель воспроизводит форму из текста, как её и просили, а форма в текстах разная.

**Одна вещь под двумя типами.** В doc-1-1 модель извлекла и `кофемолка Aroma Compact` как Product, и `Aroma Compact` как Brand. Это не два объекта, а один, разобранный дважды.

**Выдуманная связь.** `кофемолка Aroma Compact USED_WITH средней грубости` — «используется с помолом средней грубости» связью не является, это характеристика. При этом настоящая связь чанка — что кофемолка применяется с `Aroma Pro` — **не** извлечена: в самом чанке `Aroma Pro` не назван, он остался в предыдущем. Прямой аргумент за перекрытие чанков, и он же объясняет, почему перекрытие не роскошь.

**Слишком общая сущность.** `эспрессо` попал в Product, хотя это напиток. Схема с `enum` тут не спасает: тип из списка, а содержание неверное.

> **Важно**: схема ответа гарантирует форму, а не смысл. Прогон того же промпта на `qwen3:0.6b` дал безупречно валидный JSON, в котором именами сущностей были строки `Product` и `Brand`, а типами — `IN_CATEGORY` и `MADE_BY`. Модель перепутала местами онтологию и данные, но формально ответ соответствовал схеме. Размер модели на извлечении структуры значит больше, чем кажется: 0.6B не работает вовсе, 8B работает с ошибками, которые ловятся проверками.

Вывод для пайплайна: результат извлечения **всегда** проходит через дедупликацию и контроль качества, даже когда на глаз выглядит хорошо. Обе процедуры разбираются ниже уже на этих реальных данных — значит, их нужно загрузить в граф вместо вычищенного набора:

```cypher
// Сначала убираем вычищенный разбор, чтобы не смешивать два набора
MATCH (e:Entity) DETACH DELETE e;

WITH [
  {chunkId: 'doc-1-0',
   entities: [{name: 'Кофеварка Aroma Pro', type: 'Product'}, {name: 'Aroma', type: 'Brand'},
              {name: 'капельные кофеварки', type: 'Category'}],
   relations: [{source: 'Кофеварка Aroma Pro', type: 'IN_CATEGORY', target: 'капельные кофеварки'},
               {source: 'Кофеварка Aroma Pro', type: 'MADE_BY', target: 'Aroma'}]},
  {chunkId: 'doc-1-1',
   entities: [{name: 'кофемолка Aroma Compact', type: 'Product'}, {name: 'Aroma Compact', type: 'Brand'},
              {name: 'средней грубости', type: 'Feature'}],
   relations: [{source: 'кофемолка Aroma Compact', type: 'USED_WITH', target: 'средней грубости'}]},
  {chunkId: 'doc-2-0',
   entities: [{name: 'Рожковая кофеварка Crema S', type: 'Product'}, {name: 'Aroma Pro', type: 'Product'}],
   relations: [{source: 'Рожковая кофеварка Crema S', type: 'COMPETES_WITH', target: 'Aroma Pro'}]},
  {chunkId: 'doc-2-1',
   entities: [{name: 'Crema', type: 'Brand'}, {name: 'Aroma', type: 'Brand'}, {name: 'эспрессо', type: 'Product'}],
   relations: [{source: 'Crema', type: 'COMPETES_WITH', target: 'Aroma'}]}
] AS extracted
UNWIND extracted AS ex
MATCH (c:Chunk {chunkId: ex.chunkId})
CALL (c, ex) {
  UNWIND ex.entities AS e
  MERGE (n:Entity {key: toLower(e.name)})
  SET n.name = e.name, n.type = e.type
  MERGE (c)-[:MENTIONS]->(n)
}
CALL (c, ex) {
  UNWIND ex.relations AS r
  MATCH (s:Entity {key: toLower(r.source)}), (t:Entity {key: toLower(r.target)})
  MERGE (s)-[rel:RELATES_TO {type: r.type}]->(t)
  ON CREATE SET rel.mentions = 1, rel.evidence = [c.chunkId]
  ON MATCH  SET rel.mentions = rel.mentions + 1, rel.evidence = rel.evidence + c.chunkId
}
RETURN count(*) AS processed;
```

Это тот же загрузчик, что и выше, — изменились только данные. Дальше по уроку граф содержит десять сущностей с задвоениями и мусором, и именно на них имеет смысл смотреть, как работают проверки. Разрешение в каталог (раздел ниже) выполняется уже после этой загрузки.

### Тип в свойстве или в типе связи

Выше все связи имеют один тип `RELATES_TO`, а смысл лежит в свойстве. Альтернатива — настоящий тип связи, который в Cypher 25 подставляется динамически:

```cypher
MATCH (a:Entity {key: 'crema s'}), (b:Entity {key: 'crema'})
WITH a, b, 'MADE_BY' AS t
MERGE (a)-[r:$(t)]->(b)
RETURN type(r);
```

Синтаксис `$(выражение)` в позиции типа связи — нововведение Cypher 25. До него ту же задачу решала `apoc.merge.relationship`, и она по-прежнему работает.

| | Тип в свойстве | Настоящий тип связи |
|---|---|---|
| Обход по конкретному типу | Фильтр по свойству | Индексируется движком, быстрее |
| Новый тип из извлечения | Ничего не ломает | Нужна валидация против онтологии |
| Читаемость запросов | Хуже | Лучше |
| `SHOW` схемы базы | Ничего не покажет | Все типы видны |

Практика: на этапе прототипирования удобнее свойство — схема не засоряется мусором от неудачных промптов. В продакшене, где онтология зафиксирована, лучше настоящие типы.

## Связь с основным графом

Извлечённая «Aroma Pro» и товар `Кофеварка Aroma Pro` из каталога — одна и та же вещь. Связываются они отдельным шагом.

```cypher
MATCH (e:Entity {type: 'Product'})
MATCH (p:Product) WHERE toLower(p.title) CONTAINS toLower(e.name)
MERGE (e)-[:RESOLVED_TO]->(p)
RETURN count(*) AS linked;
```

Сопоставление по подстроке — самый грубый вариант, годный для учебного графа. В реальном пайплайне это задача identity resolution из урока 34: блокировка кандидатов, скоринг по нескольким признакам, порог. Только вместо аккаунтов пользователей — сущности из текста и записи каталога.

После этого шага граф отвечает на вопросы, невозможные ни для векторного поиска, ни для каталога по отдельности:

```cypher
MATCH (p:Product)<-[:RESOLVED_TO]-(e:Entity)<-[:MENTIONS]-(c:Chunk)<-[:HAS_CHUNK]-(d:Document)
MATCH (p)<-[:ABOUT]-(r:Review)
RETURN p.title AS product, round(avg(r.rating), 2) AS rating,
       collect(DISTINCT d.title) AS documents;
```

Товар, его реальный рейтинг из отзывов покупателей и документы, где он упоминается, — в одном ответе.

## Дедупликация сущностей

Главная болезнь извлечения — та самая, что видна в прогоне выше: одна вещь приезжает под разными именами и даже под разными типами.

Нормализация ключа снимает разницу в регистре, но не в формулировке. Дальше нужны те же приёмы, что в уроке 34.

**Строковая похожесть внутри одного типа.** Фильтр `a.type = b.type` обязателен: без него метрика выдаёт пару `Aroma` (Brand) и `Aroma Pro` (Product) с оценкой 0.8 — самой высокой в выборке и при этом заведомо неверной.

```cypher
MATCH (a:Entity), (b:Entity)
WHERE elementId(a) < elementId(b) AND a.type = b.type
WITH a, b, apoc.text.sorensenDiceSimilarity(toLower(a.name), toLower(b.name)) AS sim
WHERE sim > 0.5
RETURN a.name AS a, b.name AS b, a.type AS type, round(sim, 3) AS sim
ORDER BY sim DESC;
```

```
╒═══════════════════════════╤═══════════════════════════════╤═══════════╤═══════╕
│a                          │b                              │type       │sim    │
╞═══════════════════════════╪═══════════════════════════════╪═══════════╪═══════╡
│"Кофеварка Aroma Pro"      │"Aroma Pro"                    │"Product"  │0.6    │
│"Aroma"                    │"Aroma Compact"                │"Brand"    │0.571  │
│"Кофеварка Aroma Pro"      │"Рожковая кофеварка Crema S"   │"Product"  │0.545  │
└───────────────────────────┴───────────────────────────────┴───────────┴───────┘
```

Верна здесь только первая строка. Вторая — два разных бренда, третья — два разных товара, у которых совпало слово «кофеварка». Одна попавшая пара из трёх при пороге 0.5 — реалистичная точность строковой метрики, и повышение порога не спасает: верная пара имеет оценку **ниже**, чем неверная во второй строке была бы при других формулировках. Строковая похожесть годится, чтобы сузить круг кандидатов, но не чтобы принимать решение.

**Совпадение по разрешению в каталог** — сигнал сильнее строкового: если две сущности указывают на один товар, это точно одна вещь.

```cypher
MATCH (a:Entity)-[:RESOLVED_TO]->(p:Product)<-[:RESOLVED_TO]-(b:Entity)
WHERE elementId(a) < elementId(b)
RETURN a.name AS a, b.name AS b, p.title AS product;
```

```
╒═══════════════════════════╤═══════════════╤═══════════════════════════╕
│a                          │b              │product                    │
╞═══════════════════════════╪═══════════════╪═══════════════════════════╡
│"Кофеварка Aroma Pro"      │"Aroma Pro"    │"Кофеварка Aroma Pro"      │
└───────────────────────────┴───────────────┴───────────────────────────┘
```

Ровно та пара, которая нужна, и без ложных срабатываний. Порядок работы отсюда очевиден: сначала разрешение в каталог, потом дедупликация по нему, и только для оставшихся — строковая похожесть с ручной проверкой.

**Слияние** выполняется процедурой APOC, которая переносит все связи на оставшийся узел:

```cypher
MATCH (a:Entity {key: 'кофеварка aroma pro'}), (b:Entity {key: 'aroma pro'})
CALL apoc.refactor.mergeNodes([a, b], {properties: 'discard', mergeRels: true})
YIELD node
RETURN node.key AS key, node.name AS name;
```

Первый узел списка — победитель, его свойства сохраняются. `mergeRels: true` схлопывает дублирующиеся связи вместо того, чтобы оставить две одинаковые.

> **Внимание**: `mergeNodes` необратима. Перед массовым слиянием результат сопоставления просматривают глазами или сохраняют кандидатов отдельными связями `SAME_AS` и сливают только те, что прошли проверку. Схема из урока 34 применима здесь целиком.

## Контроль качества

Извлечение LLM — вероятностный процесс, и граф после него нужно проверять. Четыре запроса, которые стоит гонять после каждой загрузки.

**Сущности без связей** — извлеклись, но ни с чем не соединились. Обычно это шум: общие слова, попавшие в тип `Product`.

```cypher
MATCH (e:Entity) WHERE NOT EXISTS { (e)-[:RELATES_TO]-() }
RETURN e.name AS orphan, e.type AS type;
```

```
╒═══════════════════╤═════════════╕
│orphan             │type         │
╞═══════════════════╪═════════════╡
│"Aroma Compact"    │"Brand"      │
│"эспрессо"         │"Product"    │
└───────────────────┴─────────────┘
```

Обе сироты — из разбора реальной моделью, и обе диагностичны. `Aroma Compact` как Brand — половина задвоенной сущности, которую дедупликация не свела, потому что типы разные. `эспрессо` — слишком общее понятие, попавшее в Product. Проверка отработала: оба узла требуют вмешательства.

**Неразрешённые сущности** — не нашли пары в каталоге. Часть из них законна (бренды и категории отдельными узлами в нашем каталоге не лежат), часть — ошибки нормализации.

```cypher
MATCH (e:Entity) WHERE NOT EXISTS { (e)-[:RESOLVED_TO]->() }
RETURN e.name AS unresolved, e.type AS type;
```

```
╒═══════════════════════╤═════════════╕
│unresolved             │type         │
╞═══════════════════════╪═════════════╡
│"Aroma"                │"Brand"      │
│"капельные кофеварки"  │"Category"   │
│"Aroma Compact"        │"Brand"      │
│"средней грубости"     │"Feature"    │
│"Crema"                │"Brand"      │
└───────────────────────┴─────────────┘
```

> **Внимание**: обратная проверка не менее важна — разрешение бывает **ложным**. Сущность `эспрессо` в этот список не попала, потому что подстрочное сопоставление привязало её сразу к двум товарам: «Эспрессо-машина Barista One» и «Эспрессо-машина Barista Duo». Сущность, разрешённую больше чем в один объект каталога, нужно отправлять на разбор, а не считать успехом:
>
> ```cypher
> MATCH (e:Entity)-[:RESOLVED_TO]->(p:Product)
> WITH e, count(p) AS targets WHERE targets > 1
> RETURN e.name AS ambiguous, targets;
> ```

**Распределение поддержки связей.** Связь, подтверждённая одним чанком, ненадёжна: это может быть галлюцинация. Связь из пяти источников почти наверняка верна.

```cypher
MATCH ()-[r:RELATES_TO]->()
RETURN r.mentions AS support, count(*) AS relations
ORDER BY support;
```

На учебном наборе из четырёх чанков поддержка везде равна единице. На реальном корпусе распределение — основной инструмент отсечения мусора: порог `mentions >= 2` убирает большую часть ошибок извлечения.

**Степень сущностей.** Узел, связанный со всем подряд, — почти всегда результат того, что LLM извлекла слишком общее понятие («устройство», «пользователь»). Такие сущности исключают из онтологии.

```cypher
MATCH (e:Entity)
RETURN e.name AS entity,
       size([(e)-[:RELATES_TO]-() | 1]) AS degree,
       size([(e)<-[:MENTIONS]-() | 1]) AS mentions
ORDER BY mentions DESC, entity;
```

```
╒═══════════════════════════════╤═══════════╤═════════════╕
│entity                         │degree     │mentions     │
╞═══════════════════════════════╪═══════════╪═════════════╡
│"Aroma"                        │2          │2            │
│"Кофеварка Aroma Pro"          │3          │2            │
│"Aroma Compact"                │0          │1            │
│"Crema"                        │1          │1            │
│"Рожковая кофеварка Crema S"   │1          │1            │
│"капельные кофеварки"          │1          │1            │
│"кофемолка Aroma Compact"      │1          │1            │
│"средней грубости"             │1          │1            │
│"эспрессо"                     │0          │1            │
└───────────────────────────────┴───────────┴─────────────┘
```

Нулевая степень при ненулевых упоминаниях — тот же сигнал, что и в проверке на сирот, только видно масштаб проблемы разом. На корпусе из тысяч чанков этот запрос дополняют порогом сверху: узел со степенью в сотни связей — почти наверняка слишком общее понятие.

## Процесс целиком

```
     тексты
        │
        ▼
   ┌──────────┐
   │ чанкинг  │  вне базы: 300-800 токенов, перекрытие 10-20%
   └────┬─────┘
        ▼
   ┌──────────┐
   │ эмбеддинг│  модель эмбеддингов → вектор на чанк
   └────┬─────┘
        ▼
   ┌──────────┐
   │ загрузка │  Document, Chunk, векторный индекс (урок 35)
   └────┬─────┘
        ▼
   ┌──────────┐
   │извлечение│  LLM + закрытая онтология → JSON
   └────┬─────┘
        ▼
   ┌──────────┐
   │ загрузка │  Entity, RELATES_TO, MENTIONS, evidence
   └────┬─────┘
        ▼
   ┌──────────┐
   │ дедуп    │  нормализация, похожесть, mergeNodes
   └────┬─────┘
        ▼
   ┌──────────┐
   │разрешение│  RESOLVED_TO в основной граф
   └────┬─────┘
        ▼
   ┌──────────┐
   │ проверка │  сироты, поддержка, степени
   └──────────┘
```

Практические замечания по каждому шагу:

**Стоимость.** Один вызов LLM на чанк. Корпус из 100 000 чанков — 100 000 вызовов, и это основная статья расходов. Дешёвая модель на извлечении структуры часто работает не хуже дорогой: задача формальная.

**Идемпотентность.** Весь пайплайн должен переживать повторный запуск. Достигается составными ключами и `MERGE` вместо `CREATE` — тогда падение на середине корпуса лечится перезапуском.

**Инкрементальность.** Новый документ обрабатывается один, а не весь корпус заново. `mentions` и `evidence` при этом накапливаются, что и делает поддержку связей осмысленной со временем.

**Версионирование онтологии.** Изменение списка типов означает переизвлечение. Список типов хранят рядом с графом и записывают версию в документ — иначе через полгода нельзя понять, каким промптом получена та или иная связь.

## Практика

1. Создай ограничения уникальности на `Document`, `Chunk` и `Entity`.
2. Загрузи два документа с чанками и убедись, что повторный запуск не создаёт дублей.
3. Загрузи результат извлечения и проверь, что сущности и связи появились.
4. Объедини два `CALL` в один и объясни, почему часть связей перестала создаваться.
5. Создай одну связь настоящим типом через `$(t)` и сравни с вариантом `RELATES_TO {type}` по читаемости запроса-обхода.
6. Прогони промпт на реальной модели через Ollama и сравни свой результат с приведённым в уроке. Совпадения не жди — это вероятностный процесс.
7. Повтори прогон без `format`-схемы и посмотри, всегда ли ответ разбирается как JSON.
8. Свяжи извлечённые сущности с товарами каталога через `RESOLVED_TO`.
9. Собери запрос «товар, его рейтинг из отзывов и документы, где он упоминается».
10. Найди дубли по строковой похожести без фильтра `a.type = b.type` и объясни, почему самая высокая оценка досталась неверной паре.
11. Найди дубли по общему разрешению в каталог и сравни точность с предыдущим способом.
12. Слей дубли через `apoc.refactor.mergeNodes` и проверь, что связь `COMPETES_WITH` теперь указывает на объединённый узел.
13. Прогони все проверки качества и объясни, почему бренды остались неразрешёнными.
14. Найди сущности, разрешённые больше чем в один товар каталога.
15. Загрузи тот же результат извлечения повторно и посмотри, как изменились `mentions` и `evidence`.
16. Напиши запрос, который удаляет связи с поддержкой ниже двух.
17. Удали граф урока: `Document`, `Chunk`, `Entity` со всеми связями.

## Итоги урока

- Knowledge graph строится из текста, где структуры нет, и отвечает на вопросы, охватывающие несколько документов, — векторный поиск на них не отвечает.
- Схема состоит из трёх слоёв: документы с чанками, сущности, и мост `RESOLVED_TO` в основной граф.
- Связь `MENTIONS` обеспечивает прослеживаемость: по любому факту графа можно вернуться к исходному предложению.
- Ограничение уникальности на нормализованный ключ сущности — то, что не даёт графу распасться на дубли.
- Онтология проектируется до извлечения и передаётся LLM закрытым списком типов, иначе одно отношение приедет под тремя именами.
- Типов должно быть немного: онтология на сорок типов не наполняется, LLM начинает их путать.
- JSON Schema в поле `format` гарантирует разбираемость ответа и принадлежность типов онтологии механически, но не гарантирует осмысленности: маленькая модель выдаёт валидный JSON, в котором именами сущностей стоят названия типов.
- Реальный прогон даёт типовой набор ошибок: одна вещь под двумя именами, одна вещь под двумя типами, выдуманная связь вместо настоящей и слишком общая сущность.
- Связь, для которой одна из сторон осталась в предыдущем чанке, не извлекается вовсе — это прямой аргумент за перекрытие чанков.
- Сущности и связи загружаются отдельными подзапросами: связи нельзя сопоставлять, пока не созданы все сущности.
- `mentions` и `evidence` на связи дают поддержку факта и ссылку на источник — основу и для отсечения галлюцинаций, и для цитирования в ответе.
- Тип связи можно держать в свойстве или подставлять динамически через `$(t)`; первое удобно при прототипировании, второе — в зафиксированной онтологии.
- Дедупликация сущностей — это identity resolution из урока 34: нормализация, блокировка, похожесть, слияние через `apoc.refactor.mergeNodes`.
- Строковая похожесть без фильтра по типу ставит неверной паре оценку выше, чем верной; даже с фильтром на реальных данных верной оказалась одна пара из трёх.
- Общее разрешение в каталог — более сильный признак дубля, чем похожесть имён, поэтому порядок такой: сначала разрешение, потом дедупликация по нему, и лишь затем строковые метрики с ручной проверкой.
- Слияние узлов необратимо, поэтому кандидатов сначала помечают связями и проверяют.
- Качество графа проверяется запросами: сироты, неразрешённые сущности, неоднозначно разрешённые, распределение поддержки связей, аномальные степени.
- Успешное разрешение тоже бывает ошибкой: сущность, привязанная сразу к нескольким объектам каталога, требует разбора, а не считается результатом.
- Пайплайн обязан быть идемпотентным и инкрементальным: составные ключи и `MERGE` делают перезапуск после сбоя безопасным.
