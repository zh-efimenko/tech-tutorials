# Урок 37. Паттерны GraphRAG

Предполагается, что пройдены уроки 35 и 36: векторный индекс на чанках и knowledge graph со связями `MENTIONS`, `RELATES_TO`, `RESOLVED_TO`. Для раздела про global retrieval нужен урок 27 — выделение сообществ.

## Чего не может обычный RAG

Классический пайплайн: вопрос → эмбеддинг → k ближайших чанков → всё это в промпт → ответ. Работает, пока ответ целиком лежит внутри одного-двух кусков текста.

Три класса вопросов, на которых схема ломается:

**Вопросы, требующие соединения фактов из разных документов.** «Какие проблемы у товаров бренда Aroma» — бренд назван в инструкции, проблема описана в FAQ поддержки. Ни один чанк не содержит обе части.

**Вопросы про весь корпус.** «Какие основные темы обсуждаются в отзывах» — ответ не в топ-5 чанков, он во всей коллекции.

**Вопросы, где нужны структурированные данные.** «Стоит ли брать эту кофеварку» — текст расскажет про протечку, но цену и рейтинг знает каталог, а не документы.

GraphRAG закрывает все три, потому что после векторного поиска идёт обход графа.

## Наивный retrieval как точка отсчёта

Дальше в примерах вектор запроса записан прямо в тексте запроса — `[0.9, 0.1, 0.9]`. Это учебные трёхмерные векторы, где компоненты означают «про кофе», «про звук» и «про проблему»: так примеры воспроизводимы без вызова модели. Настоящий эмбеддинг вопроса считается вне базы и приходит параметром — это делается в уроке 38.

Корпус урока 36 состоял из двух документов про кофеварки — этого мало: примеры ниже показывают, как граф соединяет проблему из поддержки с товаром из инструкции, а текстов про проблемы там нет. Достроим корпус до пяти документов, заодно проставив чанкам учебные векторы.

```cypher
WITH [
  {docId: 'doc-3', title: 'Каталог: наушники Echo Light', source: 'catalog',
   chunks: [{n: 0, text: 'Наушники Echo Light выпускает компания Echo. Модель относится к беспроводным наушникам.', vec: [0.05, 0.9, 0.1]}]},
  {docId: 'doc-4', title: 'FAQ поддержки: протечки', source: 'support',
   chunks: [
     {n: 0, text: 'Протечка воды — известная проблема Aroma Mini. Причина в уплотнителе резервуара.', vec: [0.9, 0.05, 0.9]},
     {n: 1, text: 'У Aroma Pro протечка встречается реже, но при засоре фильтра возможна.', vec: [0.9, 0.05, 0.85]}
   ]},
  {docId: 'doc-5', title: 'FAQ поддержки: батарея', source: 'support',
   chunks: [
     {n: 0, text: 'Echo Light быстро разряжается при активном шумоподавлении.', vec: [0.05, 0.9, 0.9]},
     {n: 1, text: 'Полный заряд Echo Light держится около шести часов.', vec: [0.05, 0.85, 0.5]}
   ]}
] AS docs
UNWIND docs AS d
MERGE (doc:Document {docId: d.docId})
SET doc.title = d.title, doc.source = d.source
WITH doc, d
UNWIND d.chunks AS ch
MERGE (c:Chunk {chunkId: d.docId + '-' + ch.n})
SET c.text = ch.text, c.position = ch.n, c.embedding = ch.vec
MERGE (doc)-[:HAS_CHUNK]->(c);
```

Теперь векторный индекс и векторы для чанков урока 36 — компоненты означают «про кофе», «про звук», «про проблему»:

```cypher
CREATE VECTOR INDEX chunk_embedding IF NOT EXISTS
FOR (c:Chunk) ON (c.embedding)
OPTIONS {indexConfig: {
  `vector.dimensions`: 3,
  `vector.similarity_function`: 'cosine'
}};

MATCH (c:Chunk {chunkId: 'doc-1-0'}) SET c.embedding = [0.9, 0.05, 0.25];
MATCH (c:Chunk {chunkId: 'doc-1-1'}) SET c.embedding = [0.85, 0.05, 0.2];
MATCH (c:Chunk {chunkId: 'doc-2-0'}) SET c.embedding = [0.8, 0.1, 0.1];
MATCH (c:Chunk {chunkId: 'doc-2-1'}) SET c.embedding = [0.7, 0.05, 0.1];
```

Сущности и связи для новых документов извлекаются тем же способом, что в уроке 36. Для примеров ниже достаточно вот этих:

```cypher
// Ключ товара — тот, что остался после слияния в уроке 36: 'кофеварка aroma pro'
MERGE (leak:Entity {key: 'протечка'})       SET leak.name = 'протечка', leak.type = 'Problem'
MERGE (mini:Entity {key: 'aroma mini'})     SET mini.name = 'Aroma Mini', mini.type = 'Product'
MERGE (echo:Entity {key: 'echo light'})     SET echo.name = 'Echo Light', echo.type = 'Product'
MERGE (echoBrand:Entity {key: 'echo'})      SET echoBrand.name = 'Echo', echoBrand.type = 'Brand'
MERGE (batt:Entity {key: 'разряд батареи'}) SET batt.name = 'разряд батареи', batt.type = 'Problem'
WITH leak, mini, echo, echoBrand, batt
MATCH (pro:Entity {key: 'кофеварка aroma pro'})
MERGE (mini)-[r1:RELATES_TO {type: 'HAS_PROBLEM'}]->(leak) ON CREATE SET r1.mentions = 1, r1.evidence = ['doc-4-0']
MERGE (pro)-[r2:RELATES_TO {type: 'HAS_PROBLEM'}]->(leak)  ON CREATE SET r2.mentions = 1, r2.evidence = ['doc-4-1']
MERGE (echo)-[r3:RELATES_TO {type: 'MADE_BY'}]->(echoBrand) ON CREATE SET r3.mentions = 1, r3.evidence = ['doc-3-0']
MERGE (echo)-[r4:RELATES_TO {type: 'HAS_PROBLEM'}]->(batt)  ON CREATE SET r4.mentions = 1, r4.evidence = ['doc-5-0']
WITH leak, mini, echo, batt, pro
MATCH (c40:Chunk {chunkId: 'doc-4-0'}) MERGE (c40)-[:MENTIONS]->(mini) MERGE (c40)-[:MENTIONS]->(leak)
WITH leak, echo, batt, pro
MATCH (c41:Chunk {chunkId: 'doc-4-1'}) MERGE (c41)-[:MENTIONS]->(pro) MERGE (c41)-[:MENTIONS]->(leak)
WITH echo, batt
MATCH (c30:Chunk {chunkId: 'doc-3-0'}) MERGE (c30)-[:MENTIONS]->(echo)
WITH echo, batt
MATCH (c50:Chunk {chunkId: 'doc-5-0'}) MERGE (c50)-[:MENTIONS]->(echo) MERGE (c50)-[:MENTIONS]->(batt)
WITH echo
MATCH (c51:Chunk {chunkId: 'doc-5-1'}) MERGE (c51)-[:MENTIONS]->(echo);
```

Новые сущности тоже нужно разрешить в каталог — тем же запросом, что в уроке 36. Без этого local retrieval ниже не покажет ни цену, ни рейтинг:

```cypher
MATCH (e:Entity {type: 'Product'})
MATCH (p:Product) WHERE toLower(p.title) CONTAINS toLower(e.name)
MERGE (e)-[:RESOLVED_TO]->(p)
RETURN count(*) AS linked;
```

> **Внимание**: имя `chunk_embedding` занято этим учебным индексом на три измерения. В уроке 38 то же имя займёт `VectorStore` из Spring AI с размерностью 768, и старый индекс придётся удалить — там про это сказано отдельно. Пока держи в голове, что размерность индекса и длина вектора в запросе обязаны совпадать, иначе будет `51N65`.

```cypher
CALL db.index.vector.queryNodes('chunk_embedding', 3, [0.9, 0.1, 0.9])
YIELD node, score
RETURN node.chunkId AS chunk, round(score, 3) AS score, left(node.text, 60) AS text;
```

```

│chunk        │score    │text                                                            │
╞═════════════╪═════════╪════════════════════════════════════════════════════════════════╡
```

Вопрос «у какой кофеварки проблема с протечкой и что взять вместо неё» получил два релевантных чанка. Про протечку модель ответит. Про «что взять вместо» — нет: в этих текстах нет ни цен, ни рейтингов, ни альтернатив.

## Local retrieval

Идея: чанки из векторного поиска — не ответ, а **точка входа** в граф. От них идут переходы к сущностям, от сущностей — к соседям и к каталогу.

```
   вопрос
     │ эмбеддинг
     ▼
 ┌──────────┐   MENTIONS   ┌──────────┐  RELATES_TO  ┌──────────┐
 │  Chunk   │─────────────▶│  Entity  │─────────────▶│  Entity  │
 └────┬─────┘              └────┬─────┘              └──────────┘
      │ HAS_CHUNK               │ RESOLVED_TO
      ▼                         ▼
 ┌──────────┐              ┌──────────┐   ABOUT   ┌──────────┐
 │ Document │              │ Product  │◀──────────│  Review  │
 └──────────┘              └──────────┘           └──────────┘
```

```cypher
CALL db.index.vector.queryNodes('chunk_embedding', 2, [0.9, 0.1, 0.9])
YIELD node AS c, score
MATCH (c)-[:MENTIONS]->(e:Entity)
OPTIONAL MATCH (e)-[r:RELATES_TO]-(n:Entity)
OPTIONAL MATCH (e)-[:RESOLVED_TO]->(p:Product)
OPTIONAL MATCH (p)<-[:ABOUT]-(rev:Review)
RETURN c.chunkId AS seed, e.name AS entity,
       collect(DISTINCT r.type + ':' + n.name) AS related,
       p.title AS catalogProduct, round(avg(rev.rating), 2) AS rating;
```

```
╒═════════════╤═══════════════╤═══════════════════════════════════════════════════════════╤═══════════════════════════╤═════════╕
│seed         │entity         │related                                                    │catalogProduct             │rating   │
╞═════════════╪═══════════════╪═══════════════════════════════════════════════════════════╪═══════════════════════════╪═════════╡
│"doc-4-0"    │"Aroma Mini"   │["HAS_PROBLEM:протечка"]                                   │"Кофеварка Aroma Mini"     │1.0      │
│"doc-4-0"    │"протечка"     │["HAS_PROBLEM:Aroma Mini",                                 │NULL                       │NULL     │
│             │               │ "HAS_PROBLEM:Кофеварка Aroma Pro"]                        │                           │         │
│"doc-4-1"    │"протечка"     │["HAS_PROBLEM:Aroma Mini",                                 │NULL                       │NULL     │
│             │               │ "HAS_PROBLEM:Кофеварка Aroma Pro"]                        │                           │         │
│"doc-4-1"    │"Кофеварка     │["HAS_PROBLEM:протечка",                                   │"Кофеварка Aroma Pro"      │5.0      │
│             │ Aroma Pro"    │ "COMPETES_WITH:Рожковая кофеварка Crema S",               │                           │         │

```

Из тех же двух чанков получено то, чего в них не было: рейтинг 5.0 у одной кофеварки против 1.0 у другой и конкурент `Crema S`. Теперь на «что взять вместо» есть чем ответить.

Ключевое наблюдение: векторный индекс дал два узла, дальше работал обычный Cypher. Никакого второго обращения к внешнему хранилищу, никакой синхронизации метаданных.

### Сборка контекста

Промпт удобнее собирать структурированно, отдельными блоками: тексты, факты графа, данные каталога.

```cypher
CALL db.index.vector.queryNodes('chunk_embedding', 2, [0.9, 0.1, 0.9])
YIELD node AS c, score
WITH collect(c) AS seeds
UNWIND seeds AS c
MATCH (c)-[:MENTIONS]->(e:Entity)
WITH seeds, collect(DISTINCT e) AS entities
CALL (seeds) {
  UNWIND seeds AS c
  MATCH (d:Document)-[:HAS_CHUNK]->(c)
  RETURN collect(DISTINCT d.title + ' :: ' + c.text) AS texts
}
CALL (entities) {
  UNWIND entities AS e
  MATCH (e)-[r:RELATES_TO]-(n:Entity)
  RETURN collect(DISTINCT e.name + ' -[' + r.type + ']- ' + n.name) AS facts
}
CALL (entities) {
  UNWIND entities AS e
  MATCH (e)-[:RESOLVED_TO]->(p:Product)
  OPTIONAL MATCH (p)<-[:ABOUT]-(rv:Review)
  WITH p, avg(rv.rating) AS r
  RETURN collect(p.title + ': цена ' + toString(p.price) +
                 ', рейтинг ' + toString(round(coalesce(r, 0.0), 1))) AS catalog
}
RETURN texts, facts, catalog;
```

```
texts:   ["FAQ поддержки: протечки :: Протечка воды — известная проблема Aroma Mini. Причина в уплотнителе резервуара.",
          "FAQ поддержки: протечки :: У Aroma Pro протечка встречается реже, но при засоре фильтра возможна."]

facts:   ["Aroma Mini -[HAS_PROBLEM]- протечка", "протечка -[HAS_PROBLEM]- Aroma Mini",
          "протечка -[HAS_PROBLEM]- Кофеварка Aroma Pro", "Кофеварка Aroma Pro -[HAS_PROBLEM]- протечка",
          "Кофеварка Aroma Pro -[COMPETES_WITH]- Рожковая кофеварка Crema S",
          "Кофеварка Aroma Pro -[IN_CATEGORY]- капельные кофеварки",
          "Кофеварка Aroma Pro -[MADE_BY]- Aroma"]

catalog: ["Кофеварка Aroma Mini: цена 3290.0, рейтинг 1.0",
          "Кофеварка Aroma Pro: цена 4990.0, рейтинг 5.0"]
```

Три блока с заголовками в промпте работают лучше, чем один слипшийся текст: модель различает «вот что написано в документах», «вот что известно про связи» и «вот текущие данные каталога». Последнее особенно важно — цены и рейтинги меняются, а тексты нет, и модель должна понимать, чему верить.

> **Важно**: обход обязан быть ограничен. `-[:RELATES_TO]-` без квантификатора берёт один шаг — этого достаточно в большинстве случаев. Два шага уже приносят десятки лишних фактов, три на реальном графе — сотни, и контекстное окно заполняется мусором. Больше контекста не значит лучше ответ: качество падает после определённого объёма.

## Global retrieval

Local retrieval начинается с векторного поиска и потому не отвечает на вопросы про корпус целиком: «какие проблемы вообще встречаются», «какие темы обсуждаются». Для них нужен другой заход — снизу вверх, от структуры графа.

Схема, предложенная в оригинальной работе про GraphRAG:

1. разбить граф сущностей на сообщества;
2. по каждому сообществу собрать факты и сгенерировать краткое описание;
3. на вопрос отвечать по описаниям, а не по чанкам.

**Шаг 1 — сообщества.**

```cypher
CALL gds.graph.drop('kg', false) YIELD graphName RETURN graphName;

MATCH (a:Entity)-[:RELATES_TO]->(b:Entity)
RETURN gds.graph.project('kg', a, b, {}, {undirectedRelationshipTypes: ['*']}) AS g;

CALL gds.louvain.write('kg', {writeProperty: 'community', consecutiveIds: true})
YIELD communityCount, modularity
RETURN communityCount, round(modularity, 4) AS modularity;
```

```
╒════════════════╤════════════╕
│communityCount  │modularity  │
╞════════════════╪════════════╡
│5               │0.5494      │
└────────────────┴────────────┘
```

Модулярность 0.549 — структура выраженная. Стоит сравнить с WCC:

```cypher
CALL gds.wcc.stream('kg')
YIELD nodeId, componentId
RETURN componentId, count(*) AS members, collect(gds.util.asNode(nodeId).name) AS entities
ORDER BY members DESC;
```

WCC даёт три компоненты — большой «кофейный» кластер, отдельный «звуковой» и пару из кофемолки с её характеристикой, между которыми нет ни одной связи. Louvain дробит их дальше на пять. Выбор зернистости — это выбор между «четыре подробных описания» и «два общих», и он зависит от объёма корпуса: на тысячах сущностей нужны оба уровня, потому что Louvain строит иерархию (урок 27).

**Шаг 2 — материал для описаний.**

```cypher
MATCH (e:Entity)
WITH e.community AS community, collect(e) AS members
CALL (members) {
  UNWIND members AS m
  MATCH (m)-[r:RELATES_TO]->(t:Entity)
  RETURN collect(DISTINCT m.name + ' -[' + r.type + ']-> ' + t.name) AS facts
}
CALL (members) {
  UNWIND members AS m
  MATCH (c:Chunk)-[:MENTIONS]->(m)
  RETURN count(DISTINCT c) AS chunks
}
RETURN community, [x IN members | x.name] AS entities, chunks, facts
ORDER BY community;
```

**Шаг 3 — хранение описаний.**

```cypher
// Фильтр обязателен: сущности без связей RELATES_TO в проекцию не попали,
// community у них остался null, а MERGE по null-ключу падает с 22N31
MATCH (e:Entity) WHERE e.community IS NOT NULL
WITH e.community AS cid, collect(e.name) AS names
MERGE (s:CommunitySummary {communityId: cid})
SET s.entities = names, s.size = size(names)
RETURN s.communityId AS id, s.size AS size;
```

В реальном пайплайне сюда же пишется `s.summary` — текст от LLM — и его эмбеддинг. Тогда на вопрос про корпус сначала ищутся релевантные описания векторным поиском по `CommunitySummary`, и только их тексты идут в промпт. Вместо тысяч чанков модель видит десятки сводок.

Стоимость: один вызов LLM на сообщество при построении. Для корпуса из 100 000 чанков это порядка сотен вызовов вместо ста тысяч — построение сводок дешевле, чем кажется, а вот пересчёт при добавлении документов затрагивает только изменившиеся сообщества.

## Обход как основной retriever

Есть третий паттерн, где векторный поиск не нужен вовсе. Если вопрос удалось разобрать в структуру, ответ берётся прямым обходом.

```cypher
MATCH (b:Entity {type: 'Brand'})<-[:RELATES_TO {type: 'MADE_BY'}]-(p:Entity)
      -[:RELATES_TO {type: 'HAS_PROBLEM'}]->(pr:Entity)
RETURN b.name AS brand, collect(DISTINCT p.name + ': ' + pr.name) AS problems;
```

```
╒═════════╤═══════════════════════════════════╕
│brand    │problems                           │
╞═════════╪═══════════════════════════════════╡
│"Aroma"  │["Aroma Pro: протечка"]            │
│"Echo"   │["Echo Light: разряд батареи"]     │
└─────────┴───────────────────────────────────┘
```

Ни один чанк не содержит связку «бренд — товар — проблема»: бренд назван в инструкции, проблема в FAQ. Векторный поиск такой ответ не соберёт ни при каком `k`. Обход собирает точно и без галлюцинаций.

Разбор вопроса в запрос делает LLM — это text-to-Cypher. Схема передаётся в промпт, модель возвращает запрос, приложение его выполняет.

> **Внимание**: сгенерированный LLM Cypher нельзя выполнять от пользователя с правами на запись. Минимум — отдельная роль только на чтение и таймаут транзакции. В Community ролей нет (урок 08), поэтому изоляция делается на уровне приложения: белый список шаблонов запросов вместо свободной генерации. Свободный text-to-Cypher в проде без песочницы — прямой путь к `MATCH (n) DETACH DELETE n`.

## Сравнение паттернов

| Паттерн | Вход | Когда работает | Стоимость |
|---|---|---|---|
| Naive vector RAG | Эмбеддинг вопроса | Ответ в одном-двух чанках | Один поиск |
| Local GraphRAG | Эмбеддинг плюс обход на 1-2 шага | Нужен контекст вокруг найденного | Поиск плюс обход |
| Global GraphRAG | Сообщества и их описания | Вопрос про весь корпус | Дорогое построение, дешёвый ответ |
| Обход по схеме | Разбор вопроса в Cypher | Вопрос ложится на структуру | Один запрос |

На практике их комбинируют: маршрутизатор определяет тип вопроса и выбирает стратегию. Конкретный вопрос про товар — local. «Что вообще пишут про» — global. «Сколько», «список», «у каких» — обход.

## Что идёт не так

**Слишком широкий обход.** Два-три шага от seed-узлов забивают контекст фактами, не относящимися к вопросу. Ограничение глубины и `LIMIT` на каждом шаге обязательны — это та же проблема, что в уроке 32.

**Хабы в графе.** Сущность вроде «пользователь» или «устройство», связанная со всем, притягивает в контекст половину графа. Лечится ограничением по степени: узлы со степенью выше порога исключаются из расширения.

**Устаревшие сводки.** Описания сообществ генерируются один раз. Добавили документы — сообщества изменились, а тексты остались. Нужен пересчёт хотя бы для затронутых сообществ.

**Неотличимость источников.** Если в контексте не видно, что факт пришёл из документа, а цена — из каталога, модель смешивает их и цитирует цену «согласно инструкции». Блоки в промпте должны быть подписаны.

**Дублирование.** Один и тот же факт приходит и из текста чанка, и из графа. Это не ошибка, но расход контекста: `DISTINCT` на всех уровнях сборки обязателен.

## Практика

1. Сделай наивный векторный поиск по чанкам и оцени, какой части ответа не хватает.
2. Расширь результат до сущностей через `MENTIONS` и посмотри, что добавилось.
3. Добавь переход в каталог через `RESOLVED_TO` и подтяни рейтинг из отзывов. Найди два товара с одинаковой проблемой и разным рейтингом.
4. Собери контекст тремя блоками: тексты, факты, каталог.
5. Увеличь глубину обхода `RELATES_TO` до двух шагов и посчитай, во сколько раз вырос список фактов.
6. Разбей граф сущностей на сообщества через Louvain и сравни с WCC по числу групп.
7. Собери для каждого сообщества список сущностей, число чанков и список фактов.
8. Создай узлы `CommunitySummary` и объясни, зачем им собственный эмбеддинг.
9. Ответь обходом на вопрос «какие проблемы у товаров каждого бренда» и убедись, что ни один чанк не содержит всей цепочки.
10. Найди сущность с наибольшей степенью и объясни, чем она опасна при расширении контекста.
11. Напиши запрос, который исключает из расширения сущности со степенью выше трёх.
12. Придумай три вопроса — по одному под каждый паттерн — и объясни выбор.

## Итоги урока

- Наивный RAG не отвечает на вопросы, требующие соединения фактов из разных документов, охвата всего корпуса или структурированных данных.
- В local GraphRAG чанки из векторного поиска — точка входа в граф, а не готовый ответ.
- Обход от seed-чанков достаёт то, чего в них нет: рейтинги, цены, конкурентов, связанные сущности.
- После векторного поиска работает обычный Cypher — без второго хранилища и синхронизации метаданных.
- Контекст собирается тремя подписанными блоками — тексты, факты графа, данные каталога, — чтобы модель различала источники и понимала, что актуальнее.
- Обход ограничивается одним-двумя шагами: больше контекста не значит лучше ответ, качество падает после определённого объёма.
- Global retrieval идёт от структуры: сообщества сущностей, сводка по каждому, ответ по сводкам вместо чанков.
- Модулярность и сравнение с WCC помогают выбрать зернистость сообществ; иерархия Louvain даёт несколько уровней сводок.
- Сводки строятся одним вызовом LLM на сообщество — это сотни вызовов вместо сотен тысяч, но требует пересчёта при добавлении документов.
- Третий паттерн — прямой обход по схеме: он отвечает точно там, где вопрос ложится на структуру графа, и не галлюцинирует.
- Сгенерированный LLM Cypher выполняется только с правами на чтение и таймаутом; в Community ролей нет, поэтому нужен белый список шаблонов.
- Хабы графа притягивают в контекст половину графа, поэтому расширение ограничивают по степени узла.
