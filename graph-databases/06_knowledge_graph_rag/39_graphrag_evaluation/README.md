# Урок 39. Оценка качества и внедрение

Завершающий урок программы. Предполагается, что пройден весь трек 6, а для итогового проекта — вся программа целиком.

## Почему без измерения нельзя

GraphRAG выглядит убедительно на демонстрации и разваливается на реальных вопросах. Причина в том, что ответ LLM всегда звучит уверенно — независимо от того, был ли в контексте нужный факт. Ошибка не проявляется как исключение или пустой результат, она проявляется как правдоподобный неверный ответ.

Отсюда правило: без набора вопросов с известными ответами любое утверждение об улучшении качества — вымысел. «Добавили граф, стало лучше» проверяется числами или не проверяется вовсе.

Второе соображение — стоимость. Построение knowledge graph дороже обычной векторной индексации в десятки раз: вызов LLM на каждый чанк вместо вызова модели эмбеддингов. Если выигрыш в качестве не измерен, платить не за что.

## Где ломается конвейер

Ответ проходит четыре стадии, и провалиться может любая. Смысл раздельного измерения в том, чтобы понимать, какую именно чинить.

```
 вопрос ──▶ retrieval ──▶ расширение графом ──▶ сборка контекста ──▶ генерация ──▶ ответ
              │                │                     │                   │
        не нашли нужный   не дошли до факта    вытеснили из окна   не использовали
```

| Стадия | Метрика | Что означает провал |
|---|---|---|
| Retrieval | Recall@k | Нужного чанка нет среди найденных — дальше уже неважно |
| Расширение | Покрытие сущностями | Чанк найден, но из него нет выхода в граф |
| Контекст | Доля релевантного | Окно забито фактами не по делу |
| Генерация | Faithfulness | Факт был в контексте, модель его не использовала или переврала |

Измерять сквозное качество без разбивки бесполезно: падение на 10% может означать и плохой retriever, и слишком широкий обход, и смену модели.

## Golden set

Набор вопросов с эталонными ответами и списком чанков, которые обязаны найтись. Собирается вручную, и это единственная честная его форма.

Требования:

**Не менее 50 вопросов** для первой версии. На двадцати разница между конфигурациями теряется в шуме.

**Все классы вопросов из урока 37.** Однохоповые (ответ в одном чанке), многохоповые (факты из разных документов), корпусные («какие темы»), структурные («сколько», «список»). Набор только из первого класса покажет, что граф ничего не даёт, — на однохоповых вопросах он и правда не нужен.

**Реальные формулировки.** Вопросы, придуманные разработчиком, отличаются от вопросов пользователей: у первых лексика совпадает с документами, у вторых нет.

**Негативные примеры.** Вопросы, ответа на которые в корпусе нет. Правильное поведение — «не знаю», и это тоже измеряется. Без таких примеров система оптимизируется в сторону уверенных выдумок.

## Метрики retrieval в Cypher

Retrieval измеряется без всякой LLM — сравнением списков идентификаторов. Это самая дешёвая и самая полезная часть оценки.

> **Важно**: запросы ниже работают на учебных трёхмерных векторах из урока 37. Если ты проходил урок 38, векторный индекс сейчас другой — на 768 измерений, под `nomic-embed-text`, а свойства `embedding` у чанков стёрты. Верни учебное состояние:
>
> ```cypher
> DROP INDEX chunk_embedding IF EXISTS;
>
> CREATE VECTOR INDEX chunk_embedding IF NOT EXISTS
> FOR (c:Chunk) ON (c.embedding)
> OPTIONS {indexConfig: {`vector.dimensions`: 3, `vector.similarity_function`: 'cosine'}};
>
> MATCH (c:Chunk {chunkId: 'doc-1-0'}) SET c.embedding = [0.9, 0.05, 0.25];
> MATCH (c:Chunk {chunkId: 'doc-1-1'}) SET c.embedding = [0.85, 0.05, 0.2];
> MATCH (c:Chunk {chunkId: 'doc-2-0'}) SET c.embedding = [0.8, 0.1, 0.1];
> MATCH (c:Chunk {chunkId: 'doc-2-1'}) SET c.embedding = [0.7, 0.05, 0.1];
> MATCH (c:Chunk {chunkId: 'doc-3-0'}) SET c.embedding = [0.05, 0.9, 0.1];
> MATCH (c:Chunk {chunkId: 'doc-4-0'}) SET c.embedding = [0.9, 0.05, 0.9];
> MATCH (c:Chunk {chunkId: 'doc-4-1'}) SET c.embedding = [0.9, 0.05, 0.85];
> MATCH (c:Chunk {chunkId: 'doc-5-0'}) SET c.embedding = [0.05, 0.9, 0.9];
> MATCH (c:Chunk {chunkId: 'doc-5-1'}) SET c.embedding = [0.05, 0.85, 0.5];
> ```
>
> Это ровно то ограничение, о котором говорил урок 35: две модели эмбеддингов в одном индексе не живут, переключение между ними — всегда пересоздание.

```cypher
WITH [
  {q: 'протечка кофеварки',                vec: [0.9, 0.1, 0.9], expected: ['doc-4-0', 'doc-4-1']},
  {q: 'кто выпускает Echo Light',           vec: [0.1, 0.9, 0.1], expected: ['doc-3-0']},
  {q: 'чем Crema S отличается от Aroma Pro',vec: [0.9, 0.1, 0.1], expected: ['doc-2-0']}
] AS golden
UNWIND golden AS g
CALL (g) {
  CALL db.index.vector.queryNodes('chunk_embedding', 3, g.vec) YIELD node
  RETURN collect(node.chunkId) AS retrieved
}
WITH g, retrieved, [x IN g.expected WHERE x IN retrieved] AS hits
RETURN g.q AS question, size(hits) AS hits, size(g.expected) AS expected,
       round(1.0 * size(hits) / size(g.expected), 2) AS recall, retrieved;
```

```
╒═══════════════════════════════════════╤═════════╤═══════════╤═════════╤═══════════════════════════════════════╕
│question                               │hits     │expected   │recall   │retrieved                              │
╞═══════════════════════════════════════╪═════════╪═══════════╪═════════╪═══════════════════════════════════════╡
│"протечка кофеварки"                   │2        │2          │1.0      │["doc-4-0","doc-4-1","doc-1-0"]        │
│"кто выпускает Echo Light"             │1        │1          │1.0      │["doc-3-0","doc-5-1","doc-5-0"]        │
│"чем Crema S отличается от Aroma Pro"  │1        │1          │1.0      │["doc-2-0","doc-2-1","doc-1-1"]        │
└───────────────────────────────────────┴─────────┴───────────┴─────────┴───────────────────────────────────────┘
```

Recall везде 1.0 — на учебном корпусе с тремя вопросами retrieval отрабатывает идеально, каждый эталонный чанк оказался первым. Но recall сам по себе слеп к позиции: он не отличит «нашли первым» от «нашли третьим», а при `k = 2` второй случай уже был бы провалом. Поэтому считают ещё две метрики.

```cypher
// Подставь сюда тот же список golden, что и в запросе выше:
// с пустым списком запрос отработает, но вернёт NULL во всех метриках
WITH [ /* golden set из предыдущего запроса */ ] AS golden
UNWIND golden AS g
CALL (g) {
  CALL db.index.vector.queryNodes('chunk_embedding', 3, g.vec) YIELD node, score
  WITH node, score ORDER BY score DESC
  RETURN collect(node.chunkId) AS retrieved
}
WITH g, retrieved,
     [x IN g.expected WHERE x IN retrieved] AS hits,
     [i IN range(0, size(retrieved) - 1) WHERE retrieved[i] IN g.expected | i + 1] AS ranks
WITH size(hits) AS h, size(g.expected) AS e, size(retrieved) AS r,
     CASE WHEN size(ranks) = 0 THEN 0.0 ELSE 1.0 / head(ranks) END AS rr
RETURN round(avg(1.0 * h / e), 3) AS recallAt3,
       round(avg(1.0 * h / r), 3) AS precisionAt3,
       round(avg(rr), 3) AS mrr;
```

```
╒═════════════╤════════════════╤═════════╕
│recallAt3    │precisionAt3    │mrr      │
╞═════════════╪════════════════╪═════════╡
│1.0          │0.444           │1.0      │
└─────────────┴────────────────┴─────────┘
```

**Recall@k** — доля нужного, которое нашлось. Главная метрика: чего не нашли, того в ответе не будет.

**Precision@k** — доля найденного, которое нужно. 0.444 означает, что больше половины контекста — мусор. Это прямой расход окна и источник отвлечения модели.

**MRR** — средняя обратная позиция первого правильного результата. Здесь 1.0: все эталонные чанки на первой позиции. Значение 0.611 при том же recall означало бы ранги 1, 3 и 2 — то есть «находим, но не первым», и именно это различие recall не показывает.

Как этим пользоваться: увеличение `k` всегда поднимает recall и всегда роняет precision. Оптимум — минимальное `k`, при котором recall выходит на плато. Дальше растёт только мусор.

## Метрики графового слоя

Специфичные для GraphRAG проверки, которых нет в обычном RAG.

**Покрытие сущностями** — доля чанков, из которых вообще есть выход в граф. Чанк без `MENTIONS` в GraphRAG ведёт себя как в обычном RAG.

```cypher
MATCH (c:Chunk) WITH count(c) AS chunks
MATCH (c2:Chunk) WHERE EXISTS { (c2)-[:MENTIONS]->() }
RETURN chunks, count(c2) AS withEntities,
       round(100.0 * count(c2) / chunks, 1) AS coveragePct;
```

```
╒═════════╤═══════════════╤═══════════════╕
│chunks   │withEntities   │coveragePct    │
╞═════════╪═══════════════╪═══════════════╡
│9        │9              │100.0          │
└─────────┴───────────────┴───────────────┘
```

На реальном корпусе 100% не бывает: часть чанков — оглавления, служебный текст, куски таблиц. Покрытие ниже 60% означает, что либо онтология не подходит корпусу, либо чанки слишком мелкие.

**Плотность извлечения** — сколько сущностей приходится на чанк.

```cypher
MATCH (c:Chunk)
OPTIONAL MATCH (c)-[:MENTIONS]->(e)
WITH c, count(e) AS n
RETURN round(avg(n), 2) AS avgEntities, min(n) AS minEntities, max(n) AS maxEntities;
```

```
╒═══════════════╤═══════════════╤═══════════════╕
│avgEntities    │minEntities    │maxEntities    │
╞═══════════════╪═══════════════╪═══════════════╡
│2.11           │1              │3              │
└───────────────┴───────────────┴───────────────┘
```

Меньше единицы в среднем — извлечение не работает. Больше десяти — LLM тащит в сущности всё подряд, и граф зашумлён.

**Поддержка связей** — распределение `mentions`, введённое в уроке 36.

```cypher
MATCH ()-[r:RELATES_TO]->()
RETURN r.mentions AS support, count(*) AS relations
ORDER BY support;
```

На учебном корпусе все 9 связей имеют поддержку 1 — набор слишком мал. На реальном корпусе распределение должно иметь хвост: если все связи по-прежнему единичны, значит документы не пересекаются по темам и граф не даёт связности, ради которой строился.

**Разрешение в основной граф** — доля сущностей, нашедших пару в каталоге.

```cypher
MATCH (e:Entity {type: 'Product'}) WITH count(e) AS total
MATCH (e2:Entity {type: 'Product'}) WHERE EXISTS { (e2)-[:RESOLVED_TO]->() }
RETURN total, count(e2) AS resolved;
```

Низкое разрешение означает, что мост между текстом и структурированными данными не работает, и половина ценности GraphRAG теряется.

## Оценка генерации

Здесь без LLM не обойтись: оценивает модель. Spring AI даёт два готовых оценщика.

```java
@Service
class EvaluationService {

    private final RelevancyEvaluator relevancy;
    private final FactCheckingEvaluator factChecking;

    EvaluationService(ChatClient.Builder builder) {
        this.relevancy = RelevancyEvaluator.builder().chatClientBuilder(builder).build();
        this.factChecking = FactCheckingEvaluator.builder(builder).build();
    }

    boolean isRelevant(String question, List<Document> context, String answer) {
        EvaluationResponse response =
                relevancy.evaluate(new EvaluationRequest(question, context, answer));
        return response.isPass();
    }

    boolean isGrounded(String question, List<Document> context, String answer) {
        return factChecking.evaluate(new EvaluationRequest(question, context, answer)).isPass();
    }
}
```

> **Внимание**: API двух оценщиков различаются. У `RelevancyEvaluator` строитель без аргументов и `chatClientBuilder(...)` отдельным вызовом, у `FactCheckingEvaluator` — `builder(chatClientBuilder)` с аргументом. Компилятор это поймает, но искать причину в документации придётся.

`RelevancyEvaluator` отвечает на вопрос «относится ли ответ к вопросу», `FactCheckingEvaluator` — «следует ли ответ из контекста». Второй важнее: он ловит галлюцинации, то есть утверждения, которых в контексте не было.

Ограничение метода очевидно: судья — та же технология, что и подсудимый. Модель-оценщик ошибается, причём коррелированно с моделью-генератором. Поэтому оценки LLM используют для отслеживания динамики между версиями, а абсолютные значения проверяют ручной разметкой на подвыборке.

## Типовые провалы

**Слишком мелкие чанки.** Предложение вырвано из контекста, местоимения не разрешены, извлечение сущностей работает плохо. Лечится увеличением чанка и перекрытием.

**Слишком крупные чанки.** Один чанк про всё, вектор усреднён и не похож ни на что конкретное. Recall падает при формально высоком покрытии.

**Онтология не под корпус.** Типы придуманы до чтения документов. Симптом — низкое покрытие сущностями и много сущностей-сирот.

**Хабы.** Одна сущность связана с половиной графа и тянет в контекст всё подряд. Симптом — precision падает при росте recall сильнее обычного. Лечение — ограничение по степени при расширении.

**Устаревшие сводки сообществ.** Корпус пополнился, сводки не пересчитаны, global retrieval отвечает по старому. Симптом — противоречия между local и global ответами на один вопрос.

**Дубли сущностей.** Дедупликация не отработала, `Aroma Pro` и `Кофеварка Aroma Pro` — два узла. Симптом — обход находит половину фактов. Проверка — запросы из урока 36.

**Утечка структуры в ответ.** Модель начинает цитировать `Aroma Pro -[HAS_PROBLEM]- протечка` дословно. Лечится инструкцией в системном промпте: «факты графа даны для справки, отвечай обычным языком».

## Стоимость

Считать нужно три статьи отдельно.

**Построение.** Один вызов LLM на чанк для извлечения плюс один вызов модели эмбеддингов. Корпус в 100 000 чанков — 100 000 вызовов LLM. Это разовая, но крупная сумма, и она диктует выбор модели: на извлечении структуры дешёвая модель работает почти так же, как дорогая, потому что задача формальная.

**Обновление.** Новый документ — только его чанки. Но добавление документов меняет сообщества, и сводки для затронутых нужно пересчитать. Полный пересчёт сообществ на большом графе — задача на часы, поэтому его делают по расписанию, а не на каждый документ.

**Запрос.** Эмбеддинг вопроса плюс генерация ответа. Граф добавляет к этому только Cypher-обход — доли миллисекунды. Основная стоимость запроса — токены контекста, и здесь GraphRAG может оказаться **дешевле** наивного RAG: точные факты из графа занимают меньше места, чем пять чанков текста.

**Память.** Векторы плюс HNSW плюс сам граф. Оценка из урока 35: 1536-мерный вектор — 6 КБ на узел до квантизации.

## Когда GraphRAG не нужен

Отдельный пункт, потому что честный ответ здесь экономит месяцы.

Граф не нужен, если корпус небольшой и однородный, вопросы однохоповые, а ответы целиком лежат внутри одного документа. FAQ, документация одного продукта, база из тысячи страниц — обычный векторный RAG справится, а построение графа только добавит стоимости и точек отказа.

Граф оправдан, когда: документы ссылаются друг на друга и на общие сущности; нужны ответы, соединяющие факты из разных источников; требуется прослеживаемость каждого утверждения до источника; текст нужно соединить со структурированными данными — каталогом, справочниками, транзакциями.

Последний пункт — самый сильный аргумент и самый недооценённый. Если структурированные данные уже лежат в Neo4j, добавление к ним текстового слоя дешевле, чем построение графа с нуля, а выигрыш больше.

## Итоговый проект

Задача, использующая материал всех шести треков. Тема — «Ассистент по каталогу магазина».

**Требования**

1. Граф магазина из треков 1–2 со всеми индексами и ограничениями.
2. Слой документов: не менее 10 документов по товарам (описания, инструкции, FAQ), разбитых на чанки, с эмбеддингами и векторным индексом.
3. Knowledge graph по урокам 36: сущности, связи с поддержкой и evidence, разрешение в каталог.
4. Рекомендации из урока 30, доступные как метод сервиса.
5. Выделение сообществ из урока 27 на графе сущностей плюс сводки.
6. Приложение на Spring Boot 4.1 и Spring AI 2.0 с двумя ретриверами: наивным и графовым.
7. Golden set из 20 вопросов, включающий все четыре класса и негативные примеры.
8. Отчёт: таблица сравнения двух конфигураций по recall, precision, латентности.

**Критерии готовности**

- Пайплайн загрузки переживает повторный запуск без дублей
- Каждый ответ ассистента содержит ссылки на исходные чанки
- На многохоповом вопросе графовая конфигурация измеримо лучше наивной
- Все обходы ограничены по глубине, все запросы к базе — через параметры
- Есть тест на Testcontainers, проверяющий retrieval на трёх вопросах golden set

**Что проверять на защите**

Не «работает ли», а «на сколько лучше и какой ценой». Ответ «граф дал плюс 15% recall на многохоповых вопросах при росте латентности на 40 мс» — законченная работа. Ответ «выглядит умнее» — нет.

## Практика

1. Собери golden set из десяти вопросов по четырём классам, включая два негативных.
2. Посчитай recall@3 по golden set запросом на Cypher.
3. Посчитай precision@3 и MRR, объясни, почему recall может быть равен единице при MRR 0.6.
4. Меняй `k` от 1 до 10 и найди значение, после которого recall перестаёт расти.
5. Посчитай покрытие чанков сущностями и найди чанки без выхода в граф.
6. Посчитай плотность извлечения и определи, есть ли чанки с аномально большим числом сущностей.
7. Посмотри распределение поддержки связей и объясни, о чём говорит отсутствие хвоста.
8. Посчитай долю сущностей, разрешённых в каталог, отдельно по каждому типу.
9. Подключи `FactCheckingEvaluator` и прогони через него три ответа, один из которых заведомо содержит выдумку.
10. Сравни наивную и графовую конфигурации по всем метрикам, включая латентность, и заполни таблицу.
11. Найди в своей системе два вопроса: один, где граф помогает, и один, где мешает. Объясни разницу.
12. Пройди чеклист внедрения и выпиши пункты, которые в твоём проекте не выполнены.
13. Удали учебные данные трека 6: `Document`, `Chunk`, `Entity`, `CommunitySummary`, векторные и полнотекстовые индексы.

## Итоги урока

- Ошибка GraphRAG не выглядит как ошибка: ответ звучит уверенно независимо от того, был ли нужный факт в контексте.
- Без golden set любое утверждение об улучшении качества недоказуемо, а построение графа стоит в десятки раз дороже векторной индексации.
- Конвейер измеряется по стадиям: retrieval, расширение графом, сборка контекста, генерация — сквозная метрика не показывает, что чинить.
- Golden set нужен от 50 вопросов, со всеми классами из урока 37, реальными формулировками и негативными примерами.
- Метрики retrieval считаются в Cypher сравнением списков идентификаторов и не требуют LLM — это самая дешёвая часть оценки.
- Recall без учёта позиции скрывает случаи, когда нужный чанк найден последним; для этого считают precision и MRR.
- Рост `k` всегда поднимает recall и роняет precision: оптимум — минимальное `k`, при котором recall выходит на плато.
- Графовый слой измеряется своими метриками: покрытие чанков сущностями, плотность извлечения, распределение поддержки связей, доля разрешения в каталог.
- Отсутствие хвоста в распределении поддержки означает, что документы не пересекаются по темам и граф не даёт связности.
- Оценка генерации делается LLM-судьёй, который ошибается коррелированно с генератором, поэтому его выводы годятся для динамики, а не для абсолютных значений.
- Таблица сравнения конфигураций обязана включать латентность и стоимость: плюс два процента качества ценой удвоения времени ответа в прод не идут.
- Граф обычно не помогает на однохоповых вопросах и даёт кратный выигрыш на многохоповых — отсюда маршрутизация важнее выбора одной конфигурации.
- GraphRAG не нужен на небольшом однородном корпусе с однохоповыми вопросами; сильнее всего он оправдан, когда структурированные данные уже лежат в графе и к ним добавляется текстовый слой.
