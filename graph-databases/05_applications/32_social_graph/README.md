# Урок 32. Социальный граф

Предполагается, что пройдены треки 1 и 2, а для разделов про влияние — урок 26. Все запросы работают на сети подписок `FOLLOWS` из графа магазина: 30 пользователей, 77 связей.

> **Важно**: приведённые числа относятся к базовому датасету из урока 9, без синтетики. Генератор из того же урока добавляет двадцать тысяч пользователей с восемью подписками у каждого, и абсолютные значения меняются кардинально: например, взаимных пар вместо 4 станет несколько десятков. Выводы урока от этого не меняются, но сверять имеет смысл структуру результата, а не цифры. Если хочешь получить ровно те числа, что в тексте, удали синтетику: `MATCH (n:Synthetic) CALL (n) { DETACH DELETE n } IN TRANSACTIONS OF 10000 ROWS`.

## Что делает социальный граф особенным

Заказы, товары и категории образуют дерево или почти дерево: у заказа один покупатель, у товара одна категория. Социальный граф устроен иначе — он **однородный** (пользователи связаны с пользователями) и содержит циклы. Отсюда два следствия, которых нет в остальной модели.

Первое: обход растёт экспоненциально. Друзья друзей — это не «в два раза больше», а «в квадрат раз больше».

Второе: степень узлов распределена крайне неравномерно. У большинства пользователей десяток подписок, у нескольких — десятки тысяч. Запрос, отлично работающий на среднем пользователе, на таком узле встаёт.

## Рекомендация друзей

Базовая задача любой соцсети: «вы можете знать». Кандидаты — друзья друзей, сила сигнала — число общих знакомых.

```cypher
MATCH (u:User {email: 'sergey@shop.io'})-[:FOLLOWS]->(m:User)-[:FOLLOWS]->(fof:User)
WHERE fof <> u AND NOT EXISTS { (u)-[:FOLLOWS]->(fof) }
RETURN fof.email AS suggestion, count(DISTINCT m) AS mutual,
       collect(DISTINCT m.email) AS via
ORDER BY mutual DESC, suggestion LIMIT 5;
```

```
╒══════════════════╤═════════╤══════════════════════════════════════════╕
│suggestion        │mutual   │via                                       │
╞══════════════════╪═════════╪══════════════════════════════════════════╡
│"alina@shop.io"   │2        │["daria@shop.io","vera@shop.io"]          │
│"timur@shop.io"   │2        │["petr@shop.io","mult2@shop.io"]          │
│"egor@shop.io"    │1        │["mult2@shop.io"]                         │
│"gleb@shop.io"    │1        │["daria@shop.io"]                         │
│"ivan@shop.io"    │1        │["mult2@shop.io"]                         │
└──────────────────┴─────────┴──────────────────────────────────────────┘
```

Три обязательных элемента запроса:

- `fof <> u` — иначе пользователь окажется в собственных рекомендациях через взаимную подписку;
- `NOT EXISTS { (u)-[:FOLLOWS]->(fof) }` — отсекает тех, на кого уже подписан;
- `count(DISTINCT m)` — считает общих знакомых, а не пути.

Колонка `via` — та же логика объяснимости, что и в уроке 30: «вас связывают Дарья и Вера» понятнее, чем число 2.

### Взаимность

Направленная подписка и взаимная дружба — разные отношения, и путать их дорого.

```cypher
MATCH (a:User)-[:FOLLOWS]->(b:User)
WHERE EXISTS { (b)-[:FOLLOWS]->(a) } AND elementId(a) < elementId(b)
RETURN count(*) AS mutualPairs;
```

```
╒═══════════════╕
│mutualPairs    │
╞═══════════════╡
│4              │
└───────────────┘
```

Четыре взаимные пары на 77 подписок — граф преимущественно односторонний, как лента блогов, а не как список друзей. Для рекомендаций это важно: сигнал «подписан на того же, на кого и ты» слабее сигнала «дружит с тем, с кем дружишь ты».

## Охват

«До скольких людей дойдёт репост» — вопрос о достижимости на разной глубине.

```cypher
MATCH (u:User {email: 'sergey@shop.io'})
MATCH p = SHORTEST 1 (u)-[:FOLLOWS]->+(other:User)
RETURN length(p) AS depth, count(*) AS reachable
ORDER BY depth;
```

```
╒═════════╤═════════════╕
│depth    │reachable    │
╞═════════╪═════════════╡
│1        │4            │
│2        │10           │
│3        │6            │
│4        │3            │
│5        │1            │
└─────────┴─────────────┘
```

`SHORTEST 1` здесь принципиален: он даёт **кратчайшее** расстояние до каждого достижимого узла, поэтому каждый человек считается ровно один раз, на своей минимальной глубине. Без него один и тот же пользователь попал бы в несколько строк — по одной на каждый ведущий к нему путь.

Читается таблица так: четыре прямые подписки, ещё десять человек в двух шагах, всего 24 достижимых из 29 возможных. Классическая картина малого мира: основная масса охвата набирается на втором и третьем шаге, дальше остаются единицы.

## Стоимость глубины

Главная ловушка социального графа — обход без ограничения глубины. Посмотрим, как растёт работа с каждым шагом:

```cypher
PROFILE MATCH (u:User {email: 'sergey@shop.io'})-[:FOLLOWS]->{4}(x:User)
RETURN count(x) AS paths;
```

| Глубина | Путей | DbHits |
|---|---|---|
| 1 | 4 | 11 |
| 2 | 14 | 39 |
| 3 | 28 | 97 |
| 4 | 82 | 264 |
| 5 | 196 | 670 |
| 6 | 398 | 1507 |
| 8 | 2050 | 7892 |

Восьмой шаг стоит в 700 раз дороже первого — и это на графе, где всего 30 пользователей и 77 связей. При средней степени `d` число путей растёт как `d^k`: на реальной сети с двумя сотнями подписок у среднего пользователя четвёртый шаг — это порядка полутора миллиардов путей.

Практические правила:

**Ограничивай глубину явно.** `-[:FOLLOWS]->{1,3}` вместо `-[:FOLLOWS]->+`. Верхняя граница обязана быть в запросе, а не в надежде на данные.

**Считай узлы, а не пути.** `count(DISTINCT x)` вместо `count(x)`: на глубине 4 это 21 против 82. Ещё лучше — `SHORTEST 1`, который вообще не строит лишние пути.

**Смотри на режим обхода.** В Cypher 25 путь по умолчанию `TRAIL`: связь не повторяется, и обход конечен даже на графе с циклами. Но конечность не означает дешевизну.

**Выноси тяжёлое в GDS.** Влияние, сообщества, похожесть считаются пакетно и пишутся свойствами — уроки 26–28. В онлайне остаются обходы на один-два шага.

## Формирование ленты

Лента — это активность тех, на кого подписан пользователь, слитая в один поток по времени. Разные типы активности собираются через `UNION` внутри вызываемого подзапроса.

```cypher
MATCH (u:User {email: 'sergey@shop.io'})-[:FOLLOWS]->(f:User)
CALL (f) {
  MATCH (f)-[:WROTE]->(r:Review)-[:ABOUT]->(p:Product)
  RETURN f.email AS author, 'review' AS kind, p.title AS subject, r.createdAt AS at
UNION
  MATCH (f)-[:PLACED]->(o:Order)-[:CONTAINS]->(p:Product)
  RETURN f.email AS author, 'purchase' AS kind, p.title AS subject, o.createdAt AS at
}
RETURN author, kind, subject, at
ORDER BY at DESC LIMIT 6;
```

```

│author            │kind        │subject                          │at           │
╞══════════════════╪════════════╪═════════════════════════════════╪═════════════╡
│"mult2@shop.io"   │"purchase"  │"Комплект полотенец Cozy Soft"   │2026-03-31   │
│"mult2@shop.io"   │"review"    │"Комплект полотенец Cozy Soft"   │2026-03-31   │
│"mult2@shop.io"   │"purchase"  │"Кофеварка Aroma Pro"            │2026-03-25   │
│"mult2@shop.io"   │"purchase"  │"Колонка Echo Mini"              │2026-03-25   │
│"mult2@shop.io"   │"purchase"  │"Комплект полотенец Cozy Soft"   │2026-03-25   │
│"mult2@shop.io"   │"purchase"  │"Эспрессо-машина Barista One"    │2026-03-24   │
└──────────────────┴────────────┴─────────────────────────────────┴─────────────┘
```

Выдача сразу показывает проблему любой ленты: один активный автор занял её целиком. Лечится это на уровне запроса — ограничением на автора:

```cypher
MATCH (u:User {email: 'sergey@shop.io'})-[:FOLLOWS]->(f:User)
CALL (f) {
  MATCH (f)-[:PLACED]->(o:Order)-[:CONTAINS]->(p:Product)
  RETURN p.title AS subject, o.createdAt AS at
  ORDER BY o.createdAt DESC LIMIT 2
}
RETURN f.email AS author, subject, at
ORDER BY at DESC LIMIT 6;
```

```
╒══════════════════╤═════════════════════════════════╤═════════════╕
│author            │subject                          │at           │
╞══════════════════╪═════════════════════════════════╪═════════════╡
│"mult2@shop.io"   │"Комплект полотенец Cozy Soft"   │2026-03-31   │
│"mult2@shop.io"   │"Колонка Echo Mini"              │2026-03-25   │
│"daria@shop.io"   │"Плед Cozy Wool"                 │2026-03-22   │
│"daria@shop.io"   │"Наушники Wave TWS Pro"          │2026-03-10   │
│"vera@shop.io"    │"Торшер Lumen Floor"             │2026-03-04   │
│"vera@shop.io"    │"Чайник Steam Classic"           │2026-02-11   │
└──────────────────┴─────────────────────────────────┴─────────────┘
```

Теперь в выдаче три автора вместо одного, а если поднять внешний `LIMIT`, появятся и остальные. Подзапрос с `LIMIT` внутри выполняется **для каждого** значения `f`, поэтому лимит применяется к каждому автору отдельно. Это ключевое отличие от `LIMIT` снаружи, который режет уже объединённый список.

### Fan-out против fan-in

Есть два способа построить ленту, и выбор между ними — архитектурное решение, а не деталь запроса.

| | Fan-in (на чтение) | Fan-out (на запись) |
|---|---|---|
| Как | Запрос собирает ленту при открытии | Событие рассылается в ленты подписчиков |
| Стоимость чтения | Обход по всем подпискам | Чтение готового списка |
| Стоимость записи | Нулевая | Пропорциональна числу подписчиков |
| Больно на | Пользователе с тысячей подписок | Авторе с миллионом подписчиков |

Граф естественно даёт fan-in: подписки уже лежат связями, обход дешёвый. Fan-out обычно реализуют не в графе, а в очереди и кеше, оставляя графу роль источника истины о том, кому рассылать.

Гибрид, к которому приходит большинство систем: fan-in для обычных авторов, fan-in по расписанию с кешированием для популярных. Граф в обеих схемах отвечает на один вопрос — «кто подписан», — и отвечает на него за один переход.

## Влияние

Число подписчиков — плохая метрика влияния, и это разбиралось в уроке 26: PageRank учитывает, кто именно подписан, betweenness находит мосты между группами. Здесь важно, как этим пользоваться в приложении.

```cypher
MATCH (u:User)-[:FOLLOWS]->(v:User)
RETURN gds.graph.project('social', u, v) AS g;

CALL gds.pageRank.write('social', {writeProperty: 'influence', maxIterations: 100})
YIELD nodePropertiesWritten RETURN nodePropertiesWritten;

CALL gds.graph.drop('social') YIELD graphName RETURN graphName;
```

После этого влияние — обычное свойство, и приложение читает его без всякого GDS:

```cypher
MATCH (u:User)-[:FOLLOWS]->(f:User)
WHERE u.email = 'sergey@shop.io'
RETURN f.email AS following, round(f.influence, 2) AS influence
ORDER BY influence DESC;
```

Так строится сортировка ленты по авторитету автора, приоритет в модерации, отбор для посева рекламы. Пересчёт — ночная задача: PageRank на миллионах узлов занимает минуты, и в обработке HTTP-запроса ему места нет.

## Проблема супернодов

Узел с огромным числом связей ломает планировщик. Запрос «на кого подписаны мои подписки» на обычном пользователе трогает сотню связей, а на узле с миллионом подписчиков — миллион.

Симптомы: запрос, который на 99% пользователей отрабатывает за 5 мс, на оставшемся проценте занимает секунды и выбивает таймаут.

Что с этим делают:

**Ограничивать на входе.** Брать не всех соседей, а срез: `ORDER BY ... LIMIT` в подзапросе, как в примере с лентой.

**Не начинать обход с суперноды.** Идти от малого узла к большому: планировщик выбирает направление по статистике, но подсказать порядком `MATCH` можно и нужно.

**Разделять связи по типам.** Вместо одного `FOLLOWS` на всё — `FOLLOWS_ACTIVE` и `FOLLOWS_ARCHIVED`, или разбиение по времени. Тогда обход трогает только нужную часть. Приём разбирался в уроке 12.

**Проверять на реальном распределении.** Тест на равномерном синтетическом графе супернодов не создаёт и проблему не покажет. Генератор из урока 09 нужен именно для этого.

## Реализация

Рекомендация друзей возвращается DTO с объяснением:

```java
public interface SocialRepository extends Neo4jRepository<UserEntity, String> {

    @Query("""
           MATCH (u:User {email: $email})-[:FOLLOWS]->(m:User)-[:FOLLOWS]->(fof:User)
           WHERE fof <> u AND NOT EXISTS { (u)-[:FOLLOWS]->(fof) }
           RETURN fof.email AS email,
                  fof.name AS name,
                  count(DISTINCT m) AS mutual,
                  collect(DISTINCT m.name)[0..3] AS via
           ORDER BY mutual DESC
           LIMIT $limit
           """)
    List<FriendSuggestion> suggest(String email, int limit);
}

public record FriendSuggestion(String email, String name, Long mutual, List<String> via) {}
```

`collect(...)` внутри `RETURN` в DTO работает: список строк SDN разбирает без конвертера. Ограничение из урока 19 касается map-проекций на верхнем уровне, а не коллекций скаляров.

Лента с лимитом на автора:

```java
@Query("""
       MATCH (u:User {email: $email})-[:FOLLOWS]->(f:User)
       CALL (f) {
         MATCH (f)-[:PLACED]->(o:Order)-[:CONTAINS]->(p:Product)
         RETURN p.title AS subject, o.createdAt AS at
         ORDER BY o.createdAt DESC
         LIMIT 2
       }
       RETURN f.name AS author, subject, at
       ORDER BY at DESC
       LIMIT $limit
       """)
List<FeedItem> feed(String email, int limit);

public record FeedItem(String author, String subject, LocalDate at) {}
```

> **Важно**: любой запрос к социальному графу, который уходит глубже двух шагов, должен иметь явный `LIMIT` и таймаут. Обход глубины 5 на пользователе с большой аудиторией — это не медленный запрос, это отказ сервиса. Настройка таймаутов транзакций разбиралась в уроке 24.

## Практика

1. Собери рекомендации друзей для `sergey@shop.io` с числом общих знакомых и списком, через кого.
2. Убери условие `fof <> u` и объясни, кто появился в выдаче.
3. Замени `count(DISTINCT m)` на `count(m)` и объясни разницу.
4. Посчитай число взаимных пар подписок и долю от общего числа связей.
5. Посчитай охват `sergey@shop.io` по глубине через `SHORTEST 1`. Убери `SHORTEST 1` и объясни, почему суммы перестали сходиться.
6. Сними профиль обхода фиксированной глубины от 1 до 6 и построй таблицу числа путей и DbHits.
7. Сравни `count(x)` и `count(DISTINCT x)` на глубине 4.
8. Собери ленту из покупок и отзывов подписок, отсортированную по дате.
9. Добавь в ленту ограничение «не более двух событий на автора» через подзапрос с `LIMIT` и убедись, что один активный автор больше не занимает всю выдачу.
10. Посчитай PageRank, запиши свойством `influence` и отсортируй подписки `sergey@shop.io` по влиянию.
11. Найди пользователя с максимальным числом входящих подписок и оцени, во сколько раз обход от него дороже обхода от среднего пользователя.
12. Оформи рекомендацию друзей методом репозитория с record-DTO, включающим список общих знакомых.

## Итоги урока

- Социальный граф однороден и содержит циклы, поэтому обход растёт экспоненциально, а степень узлов распределена крайне неравномерно.
- В рекомендации друзей обязательны три условия: исключить самого пользователя, исключить уже имеющиеся подписки, считать общих знакомых через `DISTINCT`.
- Направленная подписка и взаимная дружба — разные отношения; в нашем графе взаимны лишь 4 пары из 77 связей.
- `SHORTEST 1` при подсчёте охвата даёт каждому достижимому узлу его минимальную глубину и не строит лишние пути.
- Восьмой шаг обхода на графе из 30 узлов стоит в 700 раз дороже первого — верхняя граница глубины обязана быть в запросе.
- `count(DISTINCT x)` вместо `count(x)` резко снижает стоимость: на глубине 4 это 21 узел против 82 путей.
- Режим `TRAIL` в Cypher 25 гарантирует конечность обхода на графе с циклами, но не его дешевизну.
- `LIMIT` внутри вызываемого подзапроса применяется к каждому значению импортированной переменной отдельно — так делается ограничение «не более N событий на автора».
- Fan-in собирает ленту на чтении и естественен для графа; fan-out переносит стоимость на запись и живёт вне графа, оставляя графу ответ на вопрос «кто подписан».
- Влияние считается пакетно через GDS и пишется свойством узла; в онлайне остаётся чтение свойства и обход на один-два шага.
- Суперноды делают запрос непредсказуемым: срез соседей, обход от малого узла к большому и разделение связей по типам — стандартные приёмы против них.
- Тест на равномерном синтетическом графе супернодов не создаёт и проблему не выявляет.
