# Урок 34. Identity resolution

Предполагается, что пройдены треки 1 и 2. Урок 31 полезен — там тот же граф общих идентификаторов использовался для другой цели, и разница между задачами важна. Для раздела про WCC пригодится урок 27.

## Задача

Identity resolution — сведение нескольких записей к одному реальному объекту. Один человек завёл три аккаунта: с рабочей почты, с личной и через вход по телефону. Формально это три пользователя. Фактически — один клиент, у которого одна история покупок, одна корзина и одно право на удаление данных.

Смежные названия: entity resolution, record linkage, дедупликация, master data management. Различаются акценты, техника одна.

Задача не решается точным совпадением. `Андрей Смирнов`, `А. Смирнов`, `Андрей С.` и `Смирнов А. В.` — это четыре разные строки. Требуется вероятностное сопоставление: набор признаков, каждый из которых сам по себе слаб, вместе дают уверенность.

## Отличие от антифрода

Урок 31 работал с тем же графом общих устройств, карт и адресов, но искал другое.

| | Антифрод (урок 31) | Identity resolution |
|---|---|---|
| Вопрос | Действуют ли эти аккаунты сообща | Один ли это человек |
| Результат | Оценка риска, блокировка | Кластер и золотая запись |
| Ошибка первого рода | Потерянный клиент | Склеенные истории двух людей |
| Ошибка второго рода | Пропущенное мошенничество | Раздвоенный клиент |

Разница не академическая. В нашем графе `banned1@shop.io` («Виктор Грачёв») делит устройство, карту и адрес с четырьмя аккаунтами Смирнова. Для антифрода это одна группа. Для identity resolution — нет: имя другое, и склеивать их истории нельзя. Один и тот же граф, два разных ответа.

## Почему строковой похожести недостаточно

Первый порыв — сравнить имена метрикой расстояния. APOC даёт несколько:

```cypher
MATCH (a:User {email: 'mult2@shop.io'}), (b:User {email: 'mult3@shop.io'})
RETURN a.name, b.name,
       round(apoc.text.sorensenDiceSimilarity(a.name, b.name), 3) AS dice,
       round(apoc.text.jaroWinklerDistance(a.name, b.name), 3) AS jaroWinkler,
       round(apoc.text.levenshteinSimilarity(a.name, b.name), 3) AS levenshtein;
```

`А. Смирнов` и `Андрей С.` — один человек, а коэффициент Дайса между ними равен 0.0: общих биграмм нет вовсе. При этом `А. Смирнов` и `Смирнов А. В.` дают 0.933 — тоже верно, но по случайности порядка слов.

Вывод: любой порог по строковой метрике либо пропустит первую пару, либо соберёт в кластер посторонних. Строковая похожесть — один слабый признак, а не решение.

| Метрика | Что ловит | Где промахивается |
|---|---|---|
| Левенштейн | Опечатки, лишние символы | Перестановка слов |
| Жаро-Винклер | Совпадение начала строки | Фамилия вперёд имени |
| Сёренсен-Дайс | Общие биграммы | Сокращения до инициала |
| Метафон, `apoc.text.phonetic` | Созвучные написания | Настроен на английский |

## Признаки

Работающая схема складывает независимые признаки. В нашем графе доступны:

| Признак | Сила | Почему |
|---|---|---|
| Общая карта | Очень высокая | Реквизиты не одалживают |
| Общий адрес доставки | Средняя | Семья, офис, пункт выдачи |
| Общее устройство | Средняя | Семейный компьютер, публичный wi-fi |
| Совпадение токена в имени | Средняя | Фамилия совпадает у однофамильцев |
| Один город | Низкая | Слишком много совпадений |
| Близкие даты регистрации | Низкая | Сам по себе ничего не значит |

Правило: одного признака не хватает никогда. Комбинация «общая карта плюс совпадающая фамилия» уже почти доказательство.

## Блокировка кандидатов

Наивное сравнение каждого с каждым — это `n²`. На миллионе пользователей — 500 миллиардов пар, что неприемлемо.

**Блокировка** (blocking) — предварительный отбор кандидатов по дешёвому признаку, после которого дорогое сравнение делается только внутри блоков. Граф даёт естественную блокировку: сравнивать имеет смысл только тех, кто уже связан общим идентификатором.

```cypher
MATCH (a:User)-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]->(x)
      <-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]-(b:User)
WHERE elementId(a) < elementId(b)
WITH a, b, count(DISTINCT x) AS shared
RETURN count(*) AS candidatePairs;
```

Одиннадцать пар вместо 435 возможных сочетаний из 30 пользователей. На миллионе записей эффект тот же по природе: перебор заменяется обходом от узла-идентификатора, стоимость становится линейной по числу связей.

> **Важно**: блокировка — компромисс. Дубли, не имеющие ни одного общего идентификатора, в кандидаты не попадут и останутся ненайденными. Поэтому блоков делают несколько и по разным признакам: общий идентификатор, нормализованный телефон, префикс фамилии, эмбеддинг имени с векторным поиском (урок 35).

## Сравнение имён по токенам

Вместо расстояния между строками — разбор имени на слова и поиск общих. Инициалы отбрасываются как неинформативные.

```cypher
MATCH (a:User)-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]->(x)
      <-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]-(b:User)
WHERE elementId(a) < elementId(b)
WITH a, b, count(DISTINCT x) AS shared
WITH a, b, shared,
     [w IN split(replace(a.name, '.', ''), ' ') WHERE size(w) > 2] AS ta,
     [w IN split(replace(b.name, '.', ''), ' ') WHERE size(w) > 2] AS tb
WITH a, b, shared, [w IN ta WHERE w IN tb] AS common
RETURN a.name AS a, b.name AS b, shared, common, size(common) AS overlap
ORDER BY overlap DESC, shared DESC LIMIT 8;
```

```

│a                  │b                  │shared   │common         │overlap    │

│"Андрей Смирнов"   │"А. Смирнов"       │3        │["Смирнов"]    │1          │
│"Андрей Смирнов"   │"Андрей С."        │3        │["Андрей"]     │1          │

```

Токены дают то, чего не дала строковая метрика: `Андрей Смирнов` связывается со всеми тремя вариантами. Пары `А. Смирнов`–`Андрей С.` в списке нет, и это правильный результат попарного сравнения: у двух строк действительно нет ни одного общего слова. Соберёт их вместе следующий шаг.

`Виктор Грачёв` при трёх общих идентификаторах получает нулевое совпадение имени — та самая граница между антифродом и identity resolution.

## Скоринг и запись связей

```cypher
MATCH (a:User)-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]->(x)
      <-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]-(b:User)
WHERE elementId(a) < elementId(b)
WITH a, b, count(DISTINCT x) AS shared
WITH a, b, shared,
     [w IN split(replace(a.name, '.', ''), ' ') WHERE size(w) > 2] AS ta,
     [w IN split(replace(b.name, '.', ''), ' ') WHERE size(w) > 2] AS tb
WITH a, b, shared, size([w IN ta WHERE w IN tb]) AS overlap
WITH a, b, shared * 2 + overlap * 5 AS score
WHERE score >= 11
MERGE (a)-[r:SAME_AS]->(b)
SET r.score = score
RETURN count(r) AS links;
```

```
╒═════════╕
│links    │
╞═════════╡
│4        │
└─────────┘
```

Порог 11 подобран так, чтобы три общих идентификатора без совпадения имени (6 баллов) не проходили, а три идентификатора плюс общий токен (11 баллов) проходили. `MERGE` вместо `CREATE` делает пересчёт идемпотентным: повторный запуск обновит `score`, а не наплодит дубликаты связей.

Три уровня решения вместо одного порога — стандартная практика:

| Диапазон | Действие |
|---|---|
| Высокий балл | Автоматическое слияние |
| Средний балл | Очередь на ручную проверку |
| Низкий балл | Игнорировать |

Границы калибруются на размеченной выборке: берут известные дубли, смотрят распределение баллов, ставят пороги по допустимой доле ошибок. Ошибка склейки двух разных людей дороже пропуска дубля — история покупок, адрес и платёжные данные чужого человека попадают не туда.

## Транзитивное замыкание

Попарное сравнение даёт неполный граф: `А. Смирнов` и `Андрей С.` напрямую не связаны. Кластер получается обходом по связности.

```cypher
MATCH p = (u:User)-[:SAME_AS]-{0,5}(v:User)
WITH u, collect(DISTINCT v.email) AS cluster
WHERE size(cluster) > 1
RETURN u.email AS anchor, size(cluster) AS members, cluster
ORDER BY members DESC LIMIT 4;
```

```
╒══════════════════╤═══════════╤══════════════════════════════════════════════════════════════════╕
│anchor            │members    │cluster                                                           │
╞══════════════════╪═══════════╪══════════════════════════════════════════════════════════════════╡
│"mult1@shop.io"   │4          │["mult1@shop.io","mult2@shop.io","mult3@shop.io","mult4@shop.io"] │
│"mult2@shop.io"   │4          │["mult2@shop.io","mult1@shop.io","mult4@shop.io","mult3@shop.io"] │
│"mult3@shop.io"   │4          │["mult3@shop.io","mult1@shop.io","mult2@shop.io","mult4@shop.io"] │
│"mult4@shop.io"   │4          │["mult4@shop.io","mult1@shop.io","mult2@shop.io","mult3@shop.io"] │
└──────────────────┴───────────┴══════════════════════════════════════════════════════════════════┘
```

`-{0,5}` включает нулевую длину, поэтому сам узел попадает в свой кластер. Все четыре аккаунта собрались вместе, хотя прямых связей между ними всего четыре из шести возможных. `banned1` не попал — его никто с ними не связал.

То же самое пакетно через WCC:

```cypher
MATCH (a:User)-[:SAME_AS]-(b:User)
RETURN gds.graph.project('identities', a, b, {}, {undirectedRelationshipTypes: ['*']}) AS g;

CALL gds.wcc.stream('identities')
YIELD nodeId, componentId
RETURN componentId, collect(gds.util.asNode(nodeId).email) AS cluster;

CALL gds.graph.drop('identities') YIELD graphName RETURN graphName;
```

Выбор между обходом и WCC — тот же, что в остальных уроках: Cypher отвечает про одного пользователя в момент запроса, GDS размечает весь граф за один проход.

> **Внимание**: транзитивность — самая опасная часть схемы. Одна ошибочная связь склеивает два кластера в один, и восстановить границу потом нельзя — исходные пары уже слиты. Поэтому связи `SAME_AS` хранят балл и происхождение, а слияние остаётся обратимым: аккаунты не удаляются, а помечаются.

## Золотая запись

Кластер — это ещё не ответ. Приложению нужна одна запись с лучшими значениями полей. Заводится отдельный узел `:Identity`, аккаунты к нему подшиваются.

```cypher
MATCH (u:User)
CALL (u) {
  MATCH (u)-[:SAME_AS]-{0,5}(v:User)
  RETURN collect(DISTINCT v) AS cluster
}
WITH u, cluster WHERE size(cluster) > 1
WITH apoc.coll.sort([x IN cluster | x.email]) AS key, cluster
WITH DISTINCT key, head(collect(cluster)) AS members
MERGE (i:Identity {identityId: head(key)})
WITH i, members
CALL (members) {
  UNWIND members AS m
  WITH m ORDER BY size(m.name) DESC LIMIT 1
  RETURN m.name AS bestName
}
CALL (members) {
  UNWIND members AS m
  RETURN min(m.registeredAt) AS firstSeen, count(*) AS accounts
}
SET i.name = bestName, i.firstSeen = firstSeen, i.accounts = accounts
WITH i, members
UNWIND members AS m
MERGE (m)-[:IS_IDENTITY]->(i)
// DISTINCT обязателен: UNWIND размножил строку по числу аккаунтов в кластере,
// и без него та же золотая запись вернётся четыре раза
RETURN DISTINCT i.identityId AS id, i.name AS name, i.firstSeen AS firstSeen, i.accounts AS accounts;
```

```
╒══════════════════╤═══════════════════╤═════════════╤═══════════╕
│id                │name               │firstSeen    │accounts   │
╞══════════════════╪═══════════════════╪═════════════╪═══════════╡
│"mult1@shop.io"   │"Андрей Смирнов"   │2026-03-20   │4          │
└──────────────────┴───────────────────┴─────────────┴───────────┘
```

Разбор ключевых мест:

- отсортированный список почт кластера служит устойчивым ключом: один и тот же набор аккаунтов всегда даёт один `identityId`, и `MERGE` не создаёт дубли при пересчёте;
- `head(collect(cluster))` после `DISTINCT key` берёт кластер один раз, а не по разу от каждого участника;
- правило выбора имени — «самое длинное» — эвристика: `Андрей Смирнов` информативнее, чем `Андрей С.`;
- дата регистрации берётся минимальная: клиент существует с первого аккаунта.

Правила выбора для каждого поля свои: имя — самое полное, адрес — из последнего заказа, телефон — подтверждённый, статус — худший из всех (если один аккаунт заблокирован, вся личность под подозрением).

**Аккаунты не удаляются.** Узлы `:User` остаются, `:Identity` лежит слоем поверх. Это позволяет откатить неверное слияние и сохраняет ссылки из заказов.

## Практическая сторона

**Инкрементальность.** Полный пересчёт на каждой регистрации не нужен: новый пользователь сравнивается только со своим блоком кандидатов. Это несколько десятков сравнений вместо миллиона.

**Обратимость.** Связи `SAME_AS` хранят балл и — в продакшене — признак того, чем именно они порождены. Разбор жалобы «мне показывают чужие заказы» начинается с вопроса, какая связь склеила кластеры.

**Отдельный слой.** `:Identity` не заменяет `:User`, а надстраивается. Заказы остаются на аккаунтах, витрина ходит через `IS_IDENTITY`.

**Пороги на данных.** Веса и границы подбираются на размеченной выборке. Числа из этого урока подогнаны под учебный граф и в другой системе будут другими.

**Стоимость ошибки несимметрична.** Пропущенный дубль — потеря выручки. Ошибочное слияние — утечка персональных данных между людьми. Пороги смещают в сторону осторожности.

```java
@Service
public class IdentityService {

    private final Neo4jClient client;

    public IdentityService(Neo4jClient client) {
        this.client = client;
    }

    public List<String> clusterOf(String email) {
        return client.query("""
                MATCH (u:User {email: $email})-[:SAME_AS]-{0,5}(v:User)
                RETURN DISTINCT v.email AS email
                ORDER BY email
                """)
            .bind(email).to("email")
            .fetchAs(String.class)
            .mappedBy((types, record) -> record.get("email").asString())
            .all()
            .stream().toList();
    }

    public Optional<IdentityView> identityOf(String email) {
        return client.query("""
                MATCH (:User {email: $email})-[:IS_IDENTITY]->(i:Identity)
                MATCH (i)<-[:IS_IDENTITY]-(u:User)
                OPTIONAL MATCH (u)-[:PLACED]->(o:Order)
                RETURN i.identityId AS id,
                       i.name AS name,
                       i.accounts AS accounts,
                       count(o) AS orders,
                       coalesce(sum(o.total), 0.0) AS lifetimeValue
                """)
            .bind(email).to("email")
            .fetchAs(IdentityView.class)
            .mappedBy((types, record) -> new IdentityView(
                record.get("id").asString(),
                record.get("name").asString(),
                record.get("accounts").asInt(),
                record.get("orders").asInt(),
                record.get("lifetimeValue").asDouble()))
            .one();
    }
}

public record IdentityView(String id, String name, int accounts,
                           int orders, double lifetimeValue) {}
```

## Итоги урока

- Identity resolution сводит несколько записей к одному реальному объекту и не решается точным совпадением: требуется набор слабых признаков.
- Тот же граф общих идентификаторов отвечает на разные вопросы: антифрод спрашивает «действуют ли сообща», identity resolution — «один ли это человек».
- Строковые метрики между собой не согласованы: пара с нулевым коэффициентом Дайса может оказаться одним человеком, а высокий балл — совпадением порядка слов.
- Сравнение имён по токенам с отбрасыванием инициалов работает там, где метрики расстояния промахиваются.
- Блокировка по общим идентификаторам превращает квадратичное сравнение в обход графа, но не находит дубли без единого общего признака — блоков нужно несколько.
- Один признак не доказывает ничего; комбинация «общая карта плюс совпадающая фамилия» — почти доказательство.
- Порог заменяется тремя диапазонами: автоматическое слияние, ручная проверка, игнорирование.
- Ошибочное слияние дороже пропущенного дубля: разным людям становятся видны чужие заказы и адреса.
- Попарное сравнение даёт неполный граф, кластер собирается транзитивным обходом или WCC; одна ошибочная связь склеивает два кластера необратимо.
- `MERGE` вместо `CREATE` делает пересчёт связей идемпотентным.
- Золотая запись живёт отдельным узлом `:Identity`, аккаунты не удаляются — слияние остаётся обратимым, а ссылки из заказов сохраняются.
- Правило выбора значения своё для каждого поля: имя — самое полное, дата — самая ранняя, статус — худший из всех.
- Консолидация меняет бизнес-картину: четыре незаметных аккаунта складываются в одного из крупнейших клиентов.
