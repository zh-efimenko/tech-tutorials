# Урок 31. Антифрод

Предполагается, что пройдены треки 1 и 2. Раздел про сообщества опирается на урок 27 — там разбирались WCC и порог по весу на том же графе общих идентификаторов.

## Почему мошенничество — графовая задача

Одиночная запись о мошеннике выглядит как обычная запись. Мошенничество проявляется **в связях**: один и тот же телефон у пяти «разных» людей, один адрес доставки у аккаунтов из разных городов, кольцо взаимных приглашений ради реферального бонуса.

Реляционная модель такие связи находит плохо. «Все аккаунты, связанные с забаненным через любую цепочку общих устройств, карт и адресов» — это рекурсивный запрос неизвестной глубины по нескольким таблицам. В графе это один `MATCH` переменной длины.

Второй аргумент — время реакции. Проверка «связан ли этот аккаунт с известным мошенником» должна укладываться в момент оформления заказа. Обход двух-трёх шагов от одного узла — единицы миллисекунд независимо от размера базы.

## Что в графе магазина

Модель уже содержит всё нужное:

```
(:User)-[:LOGGED_IN_FROM]->(:Device)
(:User)-[:PAID_WITH]->(:PaymentMethod)
(:User)-[:SHIPPED_TO]->(:Address)
(:User)-[:REFERRED]->(:User)
(:User)-[:PLACED]->(:Order)
```

Устройство, карта и адрес — это **общие идентификаторы**. Они не принадлежат пользователю монопольно, и именно поэтому по ним можно связывать аккаунты.

В датасете заложены две группы, которые дальше служат проверкой качества правил:

- `mult1..4@shop.io` и `banned1@shop.io` делят `dev-999`, `card-999` и `addr-999`; у `banned1` статус `banned`;
- `ivan@shop.io` и `petr@shop.io` делят `dev-002` и `addr-002` — это семья, а не кольцо.

Правило, которое ловит первую группу и не задевает вторую, — рабочее. Правило, которое банит обеих, — вредное: ложные срабатывания в антифроде дороже пропусков, потому что за каждым стоит потерянный клиент.

## Первый уровень: общие идентификаторы

```cypher
MATCH (d:Device)<-[:LOGGED_IN_FROM]-(u:User)
WITH d, count(u) AS users, collect(u.email) AS who
WHERE users > 1
RETURN d.deviceId AS device, users, who
ORDER BY users DESC;
```

```
╒═════════════╤═════════╤══════════════════════════════════════════════════════════════════════╕
│device       │users    │who                                                                   │
╞═════════════╪═════════╪══════════════════════════════════════════════════════════════════════╡
│"dev-999"    │5        │["mult3@shop.io","mult4@shop.io","mult1@shop.io","mult2@shop.io",     │

```

То же по картам:

```cypher
MATCH (pm:PaymentMethod)<-[:PAID_WITH]-(u:User)
WITH pm, count(DISTINCT u) AS users, collect(DISTINCT u.email) AS who
WHERE users > 1

```

```
╒═════════════╤═════════╤══════════════════════════════════════════════════════════════════════╕
│card         │users    │who                                                                   │
╞═════════════╪═════════╪══════════════════════════════════════════════════════════════════════╡
```

Устройство делят и мошенники, и семья. Карту — только мошенники. Это первый намёк на то, что сигналы неравноценны, и разбирать их поодиночке недостаточно.

## Второй уровень: сколько сигналов совпало

Сила подозрения — не в факте совпадения, а в их количестве и разнообразии.

```cypher
MATCH (a:User)-[r]->(x)<-[]-(b:User)
WHERE type(r) IN ['LOGGED_IN_FROM', 'PAID_WITH', 'SHIPPED_TO']
  AND elementId(a) < elementId(b)
WITH a, b, collect(DISTINCT type(r)) AS signals, count(DISTINCT x) AS shared
RETURN a.email AS a, b.email AS b, shared, signals
ORDER BY shared DESC, a;
```

```
╒══════════════════╤══════════════════╤═════════╤════════════════════════════════════════════════╕
│a                 │b                 │shared   │signals                                         │
╞══════════════════╪══════════════════╪═════════╪════════════════════════════════════════════════╡
│"mult1@shop.io"   │"mult2@shop.io"   │3        │["LOGGED_IN_FROM","SHIPPED_TO","PAID_WITH"]     │
│"mult1@shop.io"   │"mult3@shop.io"   │3        │["LOGGED_IN_FROM","SHIPPED_TO","PAID_WITH"]     │
│"mult1@shop.io"   │"mult4@shop.io"   │3        │["LOGGED_IN_FROM","SHIPPED_TO","PAID_WITH"]     │
│"mult1@shop.io"   │"banned1@shop.io" │3        │["LOGGED_IN_FROM","SHIPPED_TO","PAID_WITH"]     │
│ ... ещё шесть пар внутри той же пятёрки, тоже по три сигнала ...                                │
│"ivan@shop.io"    │"petr@shop.io"    │2        │["SHIPPED_TO","LOGGED_IN_FROM"]                 │
└──────────────────┴──────────────────┴─────────┴────────────────────────────────────────────────┘
```

Всего пар с тремя сигналами получается десять — это все сочетания внутри пятёрки аккаунтов. Ставить здесь `LIMIT 5` бессмысленно: семья до выдачи просто не доберётся, а ради контраста нужен как раз хвост списка.

Условие `elementId(a) < elementId(b)` даёт каждую пару один раз. Без него `MATCH` вернёт и `(a, b)`, и `(b, a)`, и всё удвоится.

Разница между группами видна: три сигнала против двух. Общая карта — то, чего у семьи нет, и это самый весомый признак.

## Третий уровень: связь с известным мошенником

Самый ценный запрос антифрода: расползание от уже подтверждённого нарушителя.

```cypher
MATCH (banned:User {status: 'banned'})
MATCH (banned)-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]->()
      <-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]-(other:User)
RETURN DISTINCT other.email AS linked, other.status AS status;
```

```
╒══════════════════╤═════════╕
│linked            │status   │
╞══════════════════╪═════════╡
│"mult1@shop.io"   │"active" │
│"mult2@shop.io"   │"active" │
│"mult3@shop.io"   │"active" │
│"mult4@shop.io"   │"active" │
└──────────────────┴─────────┘
```

Четыре активных аккаунта в одном шаге от забаненного. `banned1` заблокировали, а кольцо продолжает работать — ровно та ситуация, ради которой антифрод и строится на графе.

Заражение распространяется дальше одного шага. Расстояние считается поиском кратчайшего пути:

```cypher
MATCH (b:User {status: 'banned'})
MATCH p = SHORTEST 1 (b)-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]-+(u:User)
WHERE u.status = 'active'
RETURN u.email AS user, length(p) / 2 AS hops
ORDER BY hops, user;
```

Деление длины пути на два — потому что каждый «шаг между людьми» состоит из двух связей: до общего идентификатора и обратно.

> **Важно**: чем дальше от подтверждённого мошенника, тем слабее сигнал. Аккаунт в одном шаге — почти наверняка тот же человек. В трёх шагах — скорее всего совпадение: где-то по цепочке попался публичный wi-fi или пункт выдачи. Автоматическая блокировка допустима на первом шаге, дальше — только на ручную проверку.

## Правила против сообществ

Правило — это явно записанное условие. Его легко объяснить юристу и легко обойти мошеннику. Соберём правило из двух сигналов: три общих идентификатора и близкие даты регистрации.

```cypher
MATCH (a:User)-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]->(x)
      <-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]-(b:User)
WHERE elementId(a) < elementId(b)
WITH a, b, count(DISTINCT x) AS shared,
     abs(duration.inDays(a.registeredAt, b.registeredAt).days) AS daysApart
WHERE shared >= 3 AND daysApart <= 7
RETURN a.email AS a, b.email AS b, shared, daysApart
ORDER BY a, b;
```

```
╒══════════════════╤══════════════════╤═════════╤════════════╕
│a                 │b                 │shared   │daysApart   │
╞══════════════════╪══════════════════╪═════════╪════════════╡
│"mult1@shop.io"   │"mult2@shop.io"   │3        │1           │
│"mult1@shop.io"   │"mult3@shop.io"   │3        │2           │
│"mult1@shop.io"   │"mult4@shop.io"   │3        │3           │
│"mult2@shop.io"   │"mult3@shop.io"   │3        │1           │
│"mult2@shop.io"   │"mult4@shop.io"   │3        │2           │
│"mult3@shop.io"   │"mult4@shop.io"   │3        │1           │
└──────────────────┴──────────────────┴─────────┴────────────┘
```

Правило отработало: `ivan` и `petr` не попали. Но обрати внимание, кого в списке **нет**: `banned1` зарегистрирован 14 февраля, а мультиаккаунты — 20–23 марта, разрыв больше месяца. Условие по времени выбросило именно тот аккаунт, вокруг которого всё строится.

Это типовой отказ правил: каждое по отдельности разумно, вместе они вырезают часть картины. Лечение — не ужесточать условия, а перейти от пар к связной группе. WCC на графе общих идентификаторов из урока 27 находит все пять аккаунтов, включая `banned1`, потому что смотрит на связность, а не на попарные условия.

Рабочая схема — две ступени: сообщества дают кандидатов, правила расставляют приоритет внутри них.

| | Правила | Сообщества |
|---|---|---|
| Объяснимость | Полная | Требует интерпретации |
| Реакция на новую схему | Нужно писать новое правило | Часто ловит без изменений |
| Ложные срабатывания | Управляемы порогами | Выше, нужна ручная проверка |
| Когда применять | Блокировка в реальном времени | Ночная пакетная разметка |

## Скоринг

Вместо бинарного «мошенник или нет» практичнее числовая оценка риска: она позволяет двигать порог, не переписывая запросы.

```cypher
MATCH (u:User) WHERE u.status = 'active'
OPTIONAL MATCH (u)-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]->(x)
      <-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]-(o:User)
WITH u, count(DISTINCT o) AS neighbours, count(DISTINCT x) AS sharedItems
OPTIONAL MATCH (u)-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]->(y)
      <-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]-(bad:User {status: 'banned'})
WITH u, neighbours, sharedItems, count(DISTINCT bad) AS bannedLinks
WITH u, neighbours, sharedItems, bannedLinks,
     neighbours * 2 + sharedItems + bannedLinks * 10 AS score
WHERE score > 0
RETURN u.email AS user, neighbours, sharedItems, bannedLinks, score
ORDER BY score DESC;
```

```
╒══════════════════╤═════════════╤══════════════╤══════════════╤═════════╕
│user              │neighbours   │sharedItems   │bannedLinks   │score    │
╞══════════════════╪═════════════╪══════════════╪══════════════╪═════════╡
│"mult1@shop.io"   │4            │3             │1             │21       │
│"mult2@shop.io"   │4            │3             │1             │21       │
│"mult3@shop.io"   │4            │3             │1             │21       │
│"mult4@shop.io"   │4            │3             │1             │21       │
│"ivan@shop.io"    │1            │2             │0             │4        │
│"petr@shop.io"    │1            │2             │0             │4        │
└──────────────────┴─────────────┴──────────────┴──────────────┴─────────┘
```

21 против 4 — разрыв в пять раз, порог ставится где угодно между ними. Вес 10 у связи с забаненным аккаунтом отражает, что это сигнал другого порядка по сравнению с числом соседей.

`OPTIONAL MATCH` здесь обязателен: с обычным `MATCH` пользователи без единого общего идентификатора выпали бы из выдачи вместо того, чтобы получить нулевой балл. На практике оценка пишется свойством узла ночным пересчётом и читается на оформлении заказа одним обращением по индексу.

Веса — предмет калибровки на размеченных данных: берётся история подтверждённых блокировок, подбираются коэффициенты, замеряется доля ложных срабатываний. Числа, подобранные «на глаз», не работают.

## Реферальные схемы

Реферальный бонус — отдельный класс злоупотреблений: пользователь приглашает сам себя под другими аккаунтами.

```cypher
MATCH (a:User)-[:REFERRED]->(b:User)
WHERE EXISTS { (a)-[:LOGGED_IN_FROM]->(:Device)<-[:LOGGED_IN_FROM]-(b) }
RETURN a.email AS referrer, b.email AS invited;
```

```
╒══════════════════╤══════════════════╕
│referrer          │invited           │
╞══════════════════╪══════════════════╡
│"mult1@shop.io"   │"mult3@shop.io"   │
│"mult1@shop.io"   │"mult2@shop.io"   │
│"mult2@shop.io"   │"mult4@shop.io"   │
└──────────────────┴──────────────────┘
```

Пригласивший и приглашённый заходят с одного устройства — самостоятельное правило, не требующее ни порогов, ни сообществ. Именно так кольцо и разрослось: `mult1` привёл `mult2` и `mult3`, `mult2` привёл `mult4`.

Глубина реферальных цепочек — ещё один сигнал:

```cypher
MATCH p = (a:User)-[:REFERRED]->+(b:User)
RETURN length(p) AS depth, count(*) AS chains
ORDER BY depth;
```

```
╒═════════╤═════════╕
│depth    │chains   │
╞═════════╪═════════╡
│1        │24       │
│2        │15       │
│3        │9        │
│4        │4        │
│5        │2        │
└─────────┴─────────┘
```

Длинные цепочки сами по себе законны — так работает любая реферальная программа. Подозрительна цепочка, в которой все участники делят устройство или карту.

> **Внимание**: `-[:REFERRED]->+` без ограничения глубины на графе с циклом не завершится. В Cypher 25 путь по умолчанию `TRAIL` — связи не повторяются, поэтому запрос конечен, но на большом графе всё равно дорог. В продакшене глубина ограничивается явно: `-[:REFERRED]->{1,5}(b:User)`.

## Оценка ущерба

Когда кольцо найдено, следующий вопрос — что именно затронуто.

```cypher
MATCH (b:User {status: 'banned'})-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]->(x)
      <-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]-(u:User)
WITH collect(DISTINCT u) + collect(DISTINCT b) AS ring
UNWIND ring AS m
OPTIONAL MATCH (m)-[:PLACED]->(o:Order)
RETURN count(DISTINCT m) AS accounts, count(o) AS orders, sum(o.total) AS money;
```

```
╒═══════════╤═════════╤═══════════╕
│accounts   │orders   │money      │
╞═══════════╪═════════╪═══════════╡
│5          │15       │146000.0   │
└───────────┴─────────┴───────────┘
```

Пять аккаунтов, пятнадцать заказов, 146 000 — это и цена вопроса, и оценка того, сколько придётся отменять.

Отзывы кольца заслуживают отдельного внимания: накрутка рейтинга — обычная сопутствующая активность.

```cypher
MATCH (b:User {status: 'banned'})-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]->(x)
      <-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]-(u:User)
WITH collect(DISTINCT u) AS ring
UNWIND ring AS m
MATCH (m)-[:WROTE]->(r:Review)-[:ABOUT]->(p:Product)
RETURN p.title AS product, count(r) AS reviews, round(avg(r.rating), 2) AS avgRating
ORDER BY reviews DESC LIMIT 3;
```

```
╒═════════════════════════════════╤═══════════╤═════════════╕
│product                          │reviews    │avgRating    │
╞═════════════════════════════════╪═══════════╪═════════════╡
│"Наушники Wave Studio"           │3          │3.67         │
│"Кофемолка Fine Burr Pro"        │2          │3.0          │
│"Комплект полотенец Cozy Soft"   │1          │5.0          │
└─────────────────────────────────┴───────────┴─────────────┘
```

Три отзыва на один товар от связанных аккаунтов — повод пересчитать его рейтинг без них. Здесь оценки средние, накрутки не видно, и это тоже результат: не всякая связанная группа занимается всем сразу.

## Проверка в момент заказа

Тяжёлые вещи считаются ночью, в онлайне остаётся один дешёвый обход.

```java
@Service
public class FraudCheckService {

    private final Neo4jClient client;

    public FraudCheckService(Neo4jClient client) {
        this.client = client;
    }

    public FraudVerdict check(String email) {
        return client.query("""
                MATCH (u:User {email: $email})
                OPTIONAL MATCH (u)-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]->(x)
                      <-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]-(bad:User {status: 'banned'})
                WITH u, count(DISTINCT bad) AS bannedLinks
                OPTIONAL MATCH (u)-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]->(y)
                      <-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]-(o:User)
                RETURN bannedLinks AS bannedLinks,
                       count(DISTINCT o) AS neighbours,
                       coalesce(u.riskScore, 0) AS storedScore
                """)
            .bind(email).to("email")
            .fetchAs(FraudVerdict.class)
            .mappedBy((types, record) -> new FraudVerdict(
                record.get("bannedLinks").asInt(),
                record.get("neighbours").asInt(),
                record.get("storedScore").asInt()))
            .one()
            .orElse(new FraudVerdict(0, 0, 0));
    }
}

public record FraudVerdict(int bannedLinks, int neighbours, int storedScore) {

    public boolean block() {
        return bannedLinks > 0;
    }

    public boolean review() {
        return !block() && (neighbours >= 3 || storedScore >= 15);
    }
}
```

Запрос стартует от одного узла по индексу на `email` и делает два перехода. Стоимость не зависит от размера базы — только от числа устройств и карт конкретного пользователя.

Ночной пересчёт скоринга оформляется отдельно и не должен идти внутри `@Transactional`:

```java
@Scheduled(cron = "0 0 3 * * *")
public void recalculateRiskScores() {
    client.query("""
            MATCH (u:User) WHERE u.status = 'active'
            CALL (u) {
              OPTIONAL MATCH (u)-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]->(x)
                    <-[:LOGGED_IN_FROM|PAID_WITH|SHIPPED_TO]-(o:User)
              WITH count(DISTINCT o) AS neighbours, count(DISTINCT x) AS items
              SET u.riskScore = neighbours * 2 + items
            } IN TRANSACTIONS OF 1000 ROWS
            """).run();
}
```

Пакетная запись через `CALL {} IN TRANSACTIONS` разбиралась в уроке 21 — без неё пересчёт на миллионах пользователей упрётся в размер транзакции.

## Что легко сделать неправильно

**Считать любой шеринг мошенничеством.** Семья, общий компьютер, пункт выдачи, корпоративный NAT — законные причины совпадения. Одного сигнала недостаточно никогда.

**Забыть про `DISTINCT`.** Пользователь с пятью заказами по одному адресу даст пять «совпадений» вместо одного, и скоринг превратится в счётчик активности.

**Не ограничивать глубину обхода.** Через 4–5 шагов по общим идентификаторам связан весь граф. Такой запрос не только медленный — он бессмысленный.

**Блокировать автоматически по слабому сигналу.** Стоимость ложного срабатывания — ушедший клиент и обращение в поддержку. На слабых сигналах — очередь на ручную проверку, а не блокировка.

**Держать признаки только в графе.** Граф отвечает на вопросы о связях. Сумма заказа, частота попыток оплаты, поведение в сессии — это соседние сигналы, и итоговое решение принимается по всем сразу.

## Практика

1. Найди все устройства, с которых заходило больше одного пользователя, и отдельно — все карты.
2. Собери пары пользователей с общими идентификаторами и посчитай, сколько сигналов совпало у каждой пары.
3. Убери условие `elementId(a) < elementId(b)` и объясни, как изменился результат.
4. Найди всех активных пользователей в одном шаге от забаненного аккаунта.
5. Посчитай расстояние в шагах от забаненного аккаунта до каждого активного и объясни деление длины пути на два.
6. Примени правило «три общих идентификатора и не больше семи дней между регистрациями». Объясни, почему `banned1@shop.io` в результат не попал.
7. Сравни результат этого правила с компонентами связности из урока 27 на том же графе.
8. Посчитай скоринг риска и подбери порог, разделяющий кольцо и семью. Замени `OPTIONAL MATCH` на `MATCH` и объясни, кто пропал из выдачи.
9. Найди случаи, когда пригласивший и приглашённый заходят с одного устройства.
10. Посчитай распределение реферальных цепочек по глубине и ограничь обход пятью шагами.
11. Оцени ущерб от кольца: число аккаунтов, заказов и сумму.
12. Найди товары, на которые кольцо оставило больше одного отзыва, и пересчитай их средний рейтинг без этих отзывов.
13. Реализуй онлайновую проверку как метод сервиса на `Neo4jClient` и убедись, что запрос стартует от индекса по `email`.

## Итоги урока

- Мошенничество видно не в отдельной записи, а в связях: общие устройства, карты и адреса связывают аккаунты, которые по отдельности выглядят нормально.
- Ложное срабатывание в антифроде дороже пропуска, поэтому правило проверяется не только на том, кого оно ловит, но и на том, кого не задевает.
- Один общий идентификатор ничего не доказывает: семья делит устройство и адрес, но не карту — разнообразие сигналов важнее их количества.
- `elementId(a) < elementId(b)` берёт каждую пару один раз; без него результат удваивается.
- Связь с уже забаненным аккаунтом — самый сильный сигнал; сила падает с каждым шагом, и автоматическая блокировка оправдана только на первом.
- Каждый «шаг между людьми» через общий идентификатор состоит из двух связей, поэтому длина пути делится на два.
- Набор попарных правил может вырезать ключевой аккаунт из группы: связность находит кольцо целиком там, где условие по времени регистрации его разрывает.
- Рабочая схема двухступенчатая: сообщества дают кандидатов пакетно, правила расставляют приоритеты и объясняют решение.
- Числовой скоринг вместо бинарного вердикта позволяет двигать порог без переписывания запросов; `OPTIONAL MATCH` нужен, чтобы чистые пользователи получали ноль, а не выпадали.
- Совпадение устройства у пригласившего и приглашённого — самостоятельное правило против накрутки реферальных бонусов.
- Обход по общим идентификаторам обязательно ограничивается по глубине: через несколько шагов связан весь граф.
- Онлайновая проверка — это два перехода от узла, найденного по индексу; тяжёлый скоринг считается ночью и пишется свойством.
