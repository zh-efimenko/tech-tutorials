После генератора коллаборативные запросы вернут те же товары, но счётчик `buyers` вырастет до тысяч — похожими окажутся двадцать тысяч синтетических покупателей. ## Почему граф

Рекомендация — это всегда обход: от пользователя к его покупкам, от покупок к другим покупателям, от них к их покупкам. В реляционной модели это три соединения таблицы заказов саму с собой, и каждое из них умножает промежуточный результат. В графе это три перехода по указателям, и стоимость зависит от числа связей конкретного пользователя, а не от размера таблицы.

Второе преимущество важнее производительности: рекомендацию можно **объяснить**. Матричная факторизация выдаёт число, граф выдаёт путь — «этот товар покупали трое, у кого совпали с тобой две покупки». Такое объяснение показывают пользователю и разбирают, когда рекомендация оказалась нелепой.

## Три источника сигнала

| Подход | Основа | Сильная сторона | Слабость |
|---|---|---|---|
| Collaborative filtering | Поведение похожих пользователей | Находит неочевидное | Не работает без истории |
| Content-based | Атрибуты товара: категория, бренд | Работает с первой покупки | Замыкает в пузырь |
| Social | Связи между пользователями | Понятное объяснение | Нужен социальный граф |

Рабочая система комбинирует все три. Начнём по отдельности.

## Collaborative filtering

Классическая формулировка: найти пользователей, купивших то же, что и наш, и предложить остальные их покупки.

```cypher
MATCH (u:User {email: 'anna@shop.io'})-[:PLACED]->(:Order)-[:CONTAINS]->(p:Product)
MATCH (p)<-[:CONTAINS]-(:Order)<-[:PLACED]-(other:User)
WHERE other <> u
MATCH (other)-[:PLACED]->(:Order)-[:CONTAINS]->(rec:Product)
WHERE NOT EXISTS { (u)-[:PLACED]->(:Order)-[:CONTAINS]->(rec) }
RETURN rec.title AS product, count(DISTINCT other) AS buyers
ORDER BY buyers DESC LIMIT 5;
```

```
╒═════════════════════════════════╤═════════╕
│product                          │buyers   │
╞═════════════════════════════════╪═════════╡
│"Термопот Steam Keep"            │4        │
│"Наушники Wave Studio"           │4        │
│"Плед Cozy Wool"                 │4        │
│"Стационарный блендер Crema Pro" │4        │
│"Кофеварка Aroma Pro"            │3        │
└─────────────────────────────────┴─────────┘
```

Два момента, без которых запрос неверен.

`NOT EXISTS { ... }` отсекает уже купленное. Без этого фильтра в топе окажутся собственные покупки пользователя: они гарантированно есть у всех, кто на него похож.

`count(DISTINCT other)` считает **людей**, а не пути. Без `DISTINCT` пользователь, у которого пять заказов с этим товаром, даст пять очков вместо одного, и рейтинг перекосится в сторону товаров, которые покупают часто и помногу.

### Учёт силы совпадения

Все «похожие» пользователи в запросе выше равноправны, хотя один совпал с `anna` по одной покупке, а другой — по трём. Взвесим:

```cypher
MATCH (u:User {email: 'anna@shop.io'})-[:PLACED]->(:Order)-[:CONTAINS]->(p:Product)
MATCH (p)<-[:CONTAINS]-(:Order)<-[:PLACED]-(other:User)
WHERE other <> u
WITH u, other, count(DISTINCT p) AS overlap
MATCH (other)-[:PLACED]->(:Order)-[:CONTAINS]->(rec:Product)
WHERE NOT EXISTS { (u)-[:PLACED]->(:Order)-[:CONTAINS]->(rec) }
RETURN rec.title AS product, sum(overlap) AS score, count(DISTINCT other) AS buyers
ORDER BY score DESC LIMIT 5;
```

Промежуточный `WITH` схлопывает пути в пару «пользователь — размер пересечения», и дальше каждый сосед вносит вклад пропорционально сходству. Это тот же коэффициент, что считает `gds.nodeSimilarity` из урока 28, только вычисленный на лету и без проекции.

Выбор между Cypher и GDS здесь такой: Cypher считает для одного пользователя в момент запроса, GDS — для всех сразу в фоне. Для витрины «похожие товары», которая одинакова для всех посетителей, дешевле GDS с записью связей `SIMILAR_TO`. Для персональной ленты, зависящей от только что сделанной покупки, — Cypher.

## Content-based

Здесь сигнал берётся из атрибутов товара, а не из чужого поведения. Категория — самый сильный из них.

```cypher
MATCH (u:User {email: 'kirill@shop.io'})-[:PLACED]->(:Order)-[:CONTAINS]->(:Product)
      -[:IN_CATEGORY]->(c:Category)
WITH u, c, count(*) AS affinity
MATCH (rec:Product)-[:IN_CATEGORY]->(c)
WHERE NOT EXISTS { (u)-[:PLACED]->(:Order)-[:CONTAINS]->(rec) }
RETURN rec.title AS product, c.name AS category, affinity
ORDER BY affinity DESC, product LIMIT 5;
```

```
╒═════════════════════════════════╤═════════════════════════╤═══════════╕
│product                          │category                 │affinity   │
╞═════════════════════════════════╪═════════════════════════╪═══════════╡
│"Кофемолка Fine Burr Pro"        │"Кофемолки"              │4          │
│"Комплект полотенец Cozy Soft"   │"Текстиль"               │2          │
│"Наушники Wave TWS"              │"Беспроводные наушники"  │2          │
└─────────────────────────────────┴─────────────────────────┴───────────┘
```

`kirill` купил четыре кофемолки — предложить пятую логично. Но список из трёх позиций показывает и проблему подхода: он не выходит за пределы уже освоенных категорий. Это и есть пузырь фильтров, и лечится он только смешиванием с другими сигналами.

Иерархия категорий даёт способ немного расширить охват: подниматься не к точной категории, а к родительской.

```cypher
MATCH (u:User {email: 'kirill@shop.io'})-[:PLACED]->(:Order)-[:CONTAINS]->(:Product)
      -[:IN_CATEGORY]->(:Category)-[:SUBCATEGORY_OF]->(parent:Category)
WITH u, parent, count(*) AS affinity
MATCH (rec:Product)-[:IN_CATEGORY]->(:Category)-[:SUBCATEGORY_OF]->(parent)
WHERE NOT EXISTS { (u)-[:PLACED]->(:Order)-[:CONTAINS]->(rec) }
RETURN parent.name AS parentCategory, collect(DISTINCT rec.title)[0..4] AS products, affinity
ORDER BY affinity DESC;
```

Один переход вверх по дереву — и вместо трёх товаров в выдаче восемь: к кофемолкам добавляются блендеры и термопот из той же «Кухни», а к полотенцам — лампы и торшер из «Дома». Насколько высоко подниматься — вопрос настройки: на верхнем уровне рекомендация вырождается в «весь каталог».

Бренд работает так же:

```cypher
MATCH (u:User {email: 'anna@shop.io'})-[:PLACED]->(:Order)-[:CONTAINS]->(:Product)
      -[:MADE_BY]->(b:Brand)
WITH u, b, count(*) AS n
MATCH (rec:Product)-[:MADE_BY]->(b)
WHERE NOT EXISTS { (u)-[:PLACED]->(:Order)-[:CONTAINS]->(rec) }
RETURN b.name AS brand, n, collect(rec.title)[0..3] AS products
ORDER BY n DESC;
```

```
╒═════════╤═════╤══════════════════════════════════════════════════╕
│brand    │n    │products                                          │
╞═════════╪═════╪══════════════════════════════════════════════════╡
│"Echo"   │1    │["Колонка Echo Mini", "Колонка Echo Room"]        │
│"Aroma"  │1    │["Кофемолка Aroma Compact", "Кофеварка Aroma Pro"]│
│"Lumen"  │1    │["Торшер Lumen Floor"]                            │
│"Turbo"  │1    │["Блендер Turbo Hand"]                            │
└─────────┴─────┴──────────────────────────────────────────────────┘
```

## Просмотры без покупки

Самый недооценённый сигнал живёт на связи `VIEWED` со свойством `views`. Товар, который смотрели много раз и не купили, — это либо цена, либо сомнение, и в обоих случаях повод для рекомендации.

```cypher
MATCH (u:User {email: 'anna@shop.io'})-[v:VIEWED]->(p:Product)
WHERE NOT EXISTS { (u)-[:PLACED]->(:Order)-[:CONTAINS]->(p) }
RETURN p.title AS product, v.views AS views
ORDER BY views DESC;
```

```
╒═════════════════════════╤═════════╕
│product                  │views    │
╞═════════════════════════╪═════════╡
│"Кофеварка Aroma Pro"    │4        │
│"Наушники Wave TWS"      │2        │
└─────────────────────────┴─────────┘
```

Сигнал сильный и дешёвый: запрос делает один переход от пользователя, никаких обходов вглубь.

## Социальные рекомендации

```cypher
MATCH (u:User {email: 'anna@shop.io'})-[:FOLLOWS]->(f:User)
      -[:PLACED]->(:Order)-[:CONTAINS]->(rec:Product)
WHERE NOT EXISTS { (u)-[:PLACED]->(:Order)-[:CONTAINS]->(rec) }
RETURN rec.title AS product, count(DISTINCT f) AS friends,
       collect(DISTINCT f.email)[0..2] AS who
ORDER BY friends DESC LIMIT 3;
```

```
╒═════════════════════════════════╤═══════════╤══════════════════════════════════════╕
│product                          │friends    │who                                   │
╞═════════════════════════════════╪═══════════╪══════════════════════════════════════╡
│"Наушники Wave Studio"           │3          │["artem@shop.io", "sofia@shop.io"]    │
│"Комплект полотенец Cozy Soft"   │2          │["sofia@shop.io", "lidia@shop.io"]    │
│"Эспрессо-машина Barista One"    │1          │["julia@shop.io"]                     │
└─────────────────────────────────┴───────────┴──────────────────────────────────────┘
```

Колонка `who` — готовое объяснение для интерфейса: «купили Артём и София, на которых ты подписана». Именно ради такой строки и стоит держать социальный граф.

## Гибридная схема

Три сигнала соединяются в один рейтинг через `UNION` внутри вызываемого подзапроса. Каждая ветка приносит свой вес.

```cypher
MATCH (u:User {email: 'anna@shop.io'})
CALL (u) {
  MATCH (u)-[:PLACED]->(:Order)-[:CONTAINS]->(:Product)
        <-[:CONTAINS]-(:Order)<-[:PLACED]-(o:User)
  WHERE o <> u
  MATCH (o)-[:PLACED]->(:Order)-[:CONTAINS]->(rec:Product)
  RETURN rec, count(DISTINCT o) * 1.0 AS score, 'collab' AS src
UNION
  MATCH (u)-[:PLACED]->(:Order)-[:CONTAINS]->(:Product)
        -[:IN_CATEGORY]->(c:Category)<-[:IN_CATEGORY]-(rec:Product)
  RETURN rec, count(*) * 2.0 AS score, 'content' AS src
UNION
  MATCH (u)-[:FOLLOWS]->(:User)-[:PLACED]->(:Order)-[:CONTAINS]->(rec:Product)
  RETURN rec, count(*) * 1.5 AS score, 'social' AS src
}
WITH u, rec, sum(score) AS total, collect(src) AS sources
WHERE NOT EXISTS { (u)-[:PLACED]->(:Order)-[:CONTAINS]->(rec) }
RETURN rec.title AS product, round(total, 1) AS score, sources
ORDER BY score DESC LIMIT 6;
```

```
╒═════════════════════════════════╤═════════╤════════════════════════════════╕
│product                          │score    │sources                         │
╞═════════════════════════════════╪═════════╪════════════════════════════════╡
│"Наушники Wave Studio"           │10.5     │["collab","content","social"]   │
│"Стационарный блендер Crema Pro" │7.5      │["collab","content","social"]   │
│"Торшер Lumen Floor"             │7.0      │["collab","content","social"]   │
│"Блендер Turbo Hand"             │6.5      │["collab","content","social"]   │
│"Комплект полотенец Cozy Soft"   │6.0      │["collab","social"]             │
│"Термопот Steam Keep"            │5.5      │["collab","social"]             │
└─────────────────────────────────┴─────────┴────────────────────────────────┘
```

Разбор конструкции:

- `CALL (u) { ... }` — вызываемый подзапрос с явным импортом переменной `u`. Форма с круглыми скобками — синтаксис Cypher 25, старая `WITH u` внутри блока считается устаревшей.
- `UNION` внутри блока объединяет ветки, сохраняя дубликаты: один и тот же товар приходит из нескольких источников отдельными строками, и это нужно для суммирования.
- `sum(score)` складывает вклады, `collect(src)` показывает, какие сигналы сработали.
- Фильтр «уже куплено» вынесен наружу — иначе его пришлось бы повторять в каждой ветке.

Веса 1.0, 2.0 и 1.5 — начальная точка, а не истина. Подбирают их по метрикам: доля кликов по рекомендациям, конверсия, разнообразие выдачи. Начинать разумно с равных весов и двигать по одному.

Столбец `sources` полезен и для отладки, и для продукта. Товар, набравший баллы из всех трёх источников, — надёжная рекомендация. Товар с единственным источником `collab` и высоким баллом — повод посмотреть, не популярный ли это ширпотреб, который «покупали все».

## Качество вместо популярности

Любая схема с подсчётом покупок сползает к бестселлерам. На нашем графе это видно сразу:

```cypher
MATCH (p:Product)<-[:CONTAINS]-(:Order)
WITH p, count(*) AS purchases
OPTIONAL MATCH (r:Review)-[:ABOUT]->(p)
RETURN p.title AS product, purchases, round(avg(r.rating), 2) AS rating
ORDER BY purchases DESC LIMIT 5;
```

```
╒═════════════════════════════════╤═══════════╤═════════╕
│product                          │purchases  │rating   │
╞═════════════════════════════════╪═══════════╪═════════╡
│"Наушники Wave Studio"           │9          │3.67     │
│"Наушники Echo Light"            │9          │4.67     │
│"Кофеварка Aroma Mini"           │9          │1.0      │
│"Блендер Turbo Max"              │9          │4.0      │
│"Плед Cozy Wool"                 │8          │3.67     │
└─────────────────────────────────┴───────────┴─────────┘
```

«Кофеварка Aroma Mini» — девять покупок и средняя оценка 1.0. Рекомендовать её по популярности означает гарантированный возврат. Фильтр по рейтингу обязателен:

```cypher
MATCH (p:Product)<-[:CONTAINS]-(:Order)
WITH p, count(*) AS purchases
MATCH (r:Review)-[:ABOUT]->(p)
WITH p, purchases, avg(r.rating) AS rating, count(r) AS reviews
WHERE rating >= 4.0
RETURN p.title AS product, purchases, round(rating, 2) AS rating, reviews
ORDER BY purchases DESC LIMIT 5;
```

```
╒═════════════════════════════════╤═══════════╤═════════╤═══════════╕
│product                          │purchases  │rating   │reviews    │
╞═════════════════════════════════╪═══════════╪═════════╪═══════════╡
│"Наушники Echo Light"            │9          │4.67     │3          │
│"Блендер Turbo Max"              │9          │4.0      │2          │
│"Комплект полотенец Cozy Soft"   │8          │4.67     │3          │
│"Наушники Wave TWS Pro"          │6          │5.0      │1          │
│"Наушники Wave TWS"              │5          │5.0      │2          │
└─────────────────────────────────┴───────────┴─────────┴───────────┘
```

Обрати внимание на «Наушники Wave TWS Pro»: оценка 5.0 по **одному** отзыву. Без минимального порога по числу отзывов средний рейтинг — шум. На практике порог ставят от 5–10 отзывов либо применяют байесовское сглаживание к среднему по каталогу.

## Холодный старт

У нового пользователя нет покупок, и всё, что построено выше, для него не работает. Граф даёт три обходных пути, и они располагаются по убыванию качества.

**Просмотры текущей сессии.** Даже без покупок пользователь уже что-то смотрел.

```cypher
MATCH (u:User {email: 'gleb@shop.io'})-[v:VIEWED]->(p:Product)
RETURN p.title AS product, v.views AS views
ORDER BY views DESC LIMIT 4;
```

```
╒═════════════════════════════╤═════════╕
│product                      │views    │
╞═════════════════════════════╪═════════╡
│"Рожковая кофеварка Crema S" │10       │
│"Кофеварка Aroma Mini"       │8        │
│"Эспрессо-машина Barista Duo"│5        │
│"Кофемолка Fine Burr Pro"    │3        │
└─────────────────────────────┴─────────┘
```

Интерес очевиден: человек выбирает кофеварку. Категория этих просмотров — готовый вход в content-based схему.

**Тот, кто привёл.** Связь `REFERRED` работает как первичный сигнал: люди приводят похожих на себя.

```cypher
MATCH (u:User {email: 'gleb@shop.io'})<-[:REFERRED]-(ref:User)
      -[:PLACED]->(:Order)-[:CONTAINS]->(rec:Product)
RETURN ref.email AS referrer, collect(DISTINCT rec.title)[0..3] AS products;
```

```
╒═════════════════╤═════════════════════════════════════════════════════════════════════════╕
│referrer         │products                                                                 │
╞═════════════════╪═════════════════════════════════════════════════════════════════════════╡
│"egor@shop.io"   │["Стационарный блендер Crema Pro","Блендер Turbo Max",                  │
│                 │ "Кофеварка Aroma Mini"]                                                │
└─────────────────┴─────────────────────────────────────────────────────────────────────────┘
```

**Популярное с фильтром по качеству** — последний рубеж, когда о пользователе не известно вообще ничего. Запрос из предыдущего раздела.

Важно, что все три варианта — это те же обходы по тому же графу. В матричных подходах холодный старт требует отдельной подсистемы; в графовых это ещё один `MATCH`.

## Реализация в приложении

Рекомендации возвращаются как DTO, а не как сущности: собирать граф объектов ради списка из пяти товаров незачем.

```java
public interface RecommendationRepository extends Neo4jRepository<UserEntity, String> {

    @Query("""
           MATCH (u:User {email: $email})-[:PLACED]->(:Order)-[:CONTAINS]->(p:Product)
           MATCH (p)<-[:CONTAINS]-(:Order)<-[:PLACED]-(other:User)
           WHERE other <> u
           WITH u, other, count(DISTINCT p) AS overlap
           MATCH (other)-[:PLACED]->(:Order)-[:CONTAINS]->(rec:Product)
           WHERE NOT EXISTS { (u)-[:PLACED]->(:Order)-[:CONTAINS]->(rec) }
           RETURN rec.sku AS sku,
                  rec.title AS title,
                  rec.price AS price,
                  sum(overlap) AS score
           ORDER BY score DESC
           LIMIT $limit
           """)
    List<ProductRecommendation> collaborative(String email, int limit);
}

public record ProductRecommendation(String sku, String title, Double price, Long score) {}
```

> **Важно**: каждое поле возвращается отдельной колонкой через `AS`. Map-проекция `rec {.sku, .title}` на верхнем уровне для DTO не годится: SDN разрешает компоненты record по свойствам сущности, и поля из соседних узлов приходят `null`. Это разбиралось в уроке 19.

Сервис с объяснением рекомендации:

```java
@Service
public class RecommendationService {

    private final Neo4jClient client;

    public RecommendationService(Neo4jClient client) {
        this.client = client;
    }

    public List<SocialRecommendation> fromFriends(String email, int limit) {
        return client.query("""
                MATCH (u:User {email: $email})-[:FOLLOWS]->(f:User)
                      -[:PLACED]->(:Order)-[:CONTAINS]->(rec:Product)
                WHERE NOT EXISTS { (u)-[:PLACED]->(:Order)-[:CONTAINS]->(rec) }
                RETURN rec.title AS title,
                       count(DISTINCT f) AS friends,
                       collect(DISTINCT f.name)[0..3] AS who
                ORDER BY friends DESC
                LIMIT $limit
                """)
            .bindAll(Map.of("email", email, "limit", limit))
            .fetchAs(SocialRecommendation.class)
            .mappedBy((typeSystem, record) -> new SocialRecommendation(
                record.get("title").asString(),
                record.get("friends").asInt(),
                record.get("who").asList(Value::asString)))
            .all()
            .stream().toList();
    }
}

public record SocialRecommendation(String title, int friends, List<String> who) {}
```

Список строк проще собрать вручную через `Neo4jClient`, чем описывать конвертер для репозитория.

### Что считать заранее

| Что | Как | Почему |
|---|---|---|
| «С этим товаром покупают» | GDS Node Similarity `.write` ночью | Одинаково для всех, считается долго |
| Топ популярного с фильтром | Материализованное свойство или кеш | Меняется раз в сутки |
| Персональная лента | Cypher в момент запроса | Зависит от последнего действия |
| Похожие пользователи | GDS KNN на эмбеддингах | Квадратичная стоимость на лету |

Правило простое: если результат не зависит от текущего пользователя — считать заранее. Если зависит и должен учитывать только что сделанное действие — считать запросом, и тогда обход обязан укладываться в десятки миллисекунд. Профилирование таких запросов — урок 13.

## Практика

1. Собери collaborative-рекомендации для `anna@shop.io` и убери фильтр `NOT EXISTS`. Объясни, что появилось в топе.
2. Убери `DISTINCT` из `count(DISTINCT other)` и сравни результат. Объясни расхождение.
3. Добавь взвешивание по размеру пересечения покупок и найди товар, который поднялся в рейтинге.
4. Сделай content-based рекомендации для `kirill@shop.io` по точной категории, затем по родительской. Сравни охват.
5. Найди товары, которые `anna@shop.io` смотрела больше двух раз и не купила.
6. Собери социальные рекомендации с объяснением «кто из друзей купил».
7. Запусти гибридный запрос и поменяй веса так, чтобы «Комплект полотенец Cozy Soft» поднялся на первое место.
8. Добавь в гибридный запрос четвёртую ветку — по просмотрам с весом, пропорциональным `views`.
9. Найди товары с максимальным числом покупок и средним рейтингом ниже 2.0.
10. Добавь к фильтру по рейтингу порог по числу отзывов и посмотри, кто выпал из топа.
11. Найди пользователя без единого заказа и собери для него рекомендации тремя способами: по просмотрам, по пригласившему, по популярному.
12. Оформи collaborative-запрос как метод репозитория с `@Query` и record-DTO, где каждое поле возвращается отдельной колонкой.

## Итоги урока

- Рекомендация в графе — это обход, и его стоимость зависит от связей конкретного пользователя, а не от размера таблицы заказов.
- Главное преимущество графа перед матричными методами — объяснимость: вместе с товаром возвращается путь, по которому он найден.
- В collaborative-запросе обязательны два элемента: `NOT EXISTS` против уже купленного и `count(DISTINCT ...)` против задвоения по числу заказов.
- Взвешивание по размеру пересечения покупок превращает грубый подсчёт соседей в аналог коэффициента Жаккара, посчитанный на лету.
- Content-based рекомендации работают с первой покупки, но замыкают пользователя в уже освоенных категориях; подъём к родительской категории расширяет охват.
- Просмотры без покупки — сильный и дешёвый сигнал в один переход от пользователя.
- Гибридная схема собирается через `CALL (u) { ... UNION ... }`: ветки дают взвешенные вклады, `sum` их складывает, `collect(src)` объясняет результат.
- Фильтр «уже куплено» выносится за пределы подзапроса, чтобы не повторять его в каждой ветке.
- Подсчёт покупок без фильтра по рейтингу выводит наверх товары с оценкой 1.0 — популярность и качество нужно проверять вместе.
- Средний рейтинг по одному-двум отзывам — шум; нужен минимальный порог по числу отзывов или сглаживание.
- Холодный старт в графе решается теми же обходами: просмотры сессии, покупки пригласившего, популярное с фильтром по качеству.
- Всё, что не зависит от конкретного пользователя, считается заранее через GDS; персональная лента — запросом в момент обращения.
- DTO рекомендаций собирается из отдельных колонок с `AS`: map-проекция на верхнем уровне даёт `null` в полях из соседних узлов.
