# Урок 12. Индексы и ограничения

## Зачем индекс в графе

В реляционной СУБД индекс ускоряет всё: поиск, соединения, сортировку. В графе роль индекса уже — он нужен **только для входа в граф**.

```
   MATCH (u:User {email: 'anna@shop.io'})-[:PLACED]->(o:Order)-[:CONTAINS]->(p:Product)
          └────────────┬────────────┘   └──────────────┬──────────────────┘
             индекс работает здесь           здесь работает обход,
             (найти стартовый узел)          индекс не участвует
```

Дальше движок идёт по физическим ссылкам — index-free adjacency из урока 1. Отсюда практическое правило: индексы нужны на свойства, по которым **начинают** запросы, и не нужны на всё подряд. Индекс на `p.title`, если по названию никогда не ищут, — чистые накладные расходы на запись.

## Типы индексов

```cypher
SHOW INDEXES YIELD name, type, entityType, labelsOrTypes, properties;
```

| Тип | Что ускоряет | Синтаксис |
|---|---|---|
| **RANGE** | Равенство, диапазоны, `STARTS WITH`, сортировка | `ON (p.price)` |
| **TEXT** | `CONTAINS`, `ENDS WITH` по строкам | `CREATE TEXT INDEX` |
| **POINT** | Геозапросы: расстояние, попадание в область | `CREATE POINT INDEX` |
| **FULLTEXT** | Полнотекстовый поиск с релевантностью | `CREATE FULLTEXT INDEX` |
| **VECTOR** | Поиск ближайших по эмбеддингу | `CREATE VECTOR INDEX` |
| **LOOKUP** | Поиск узлов по метке, связей по типу | Создаётся автоматически |

### Range — рабочая лошадка

```cypher
CREATE INDEX product_price IF NOT EXISTS FOR (p:Product) ON (p.price);
CREATE INDEX order_created IF NOT EXISTS FOR (o:Order) ON (o.createdAt);

// Составной индекс — порядок свойств важен
CREATE INDEX order_status_date IF NOT EXISTS FOR (o:Order) ON (o.status, o.createdAt);
```

> **Внимание**: составной индекс в Neo4j работает **не так**, как в PostgreSQL. Там индекс по `(a, b)` используется и для запроса по одному `a`; здесь он задействуется, только когда в запросе есть предикаты по **всем** свойствам индекса. Фильтр по одному `status` даст `NodeByLabelScan`, а не поиск по индексу, независимо от селективности значения. Подсказка тоже не спасает: `USING INDEX o:Order(status, createdAt)` отвергается с `42N77 ... The query does not contain a compatible predicate`.

```cypher
// Используется order_status_date: предикаты по обоим свойствам
MATCH (o:Order) WHERE o.status = 'delivered' AND o.createdAt > date('2026-03-01') RETURN count(o);

// НЕ используется — предикат только по первому свойству
MATCH (o:Order) WHERE o.status = 'delivered' RETURN count(o);

// НЕ используется — нет фильтра по первому свойству
MATCH (o:Order) WHERE o.createdAt > date('2026-03-01') RETURN count(o);
```

Практическое следствие: составной индекс заводят под конкретный запрос, где фильтруют сразу по всем его свойствам. Если по `status` тоже ищут отдельно, нужен отдельный однополевой индекс.

### Индексы на связях

Связи тоже индексируются — это нужно, когда фильтр стоит на свойстве связи и она является входом в граф.

```cypher
CREATE INDEX contains_qty IF NOT EXISTS FOR ()-[c:CONTAINS]-() ON (c.qty);
```

> **Важно**: индекс на связи оправдан редко. Если запрос уже пришёл к узлу и оттуда идёт по связям, фильтр по свойству связи применяется при обходе и индекс не нужен. Он полезен только когда обход **начинается** со связи.

### Text против Range

Оба работают со строками, но по-разному.

| Предикат | RANGE | TEXT |
|---|---|---|
| `=` | Да | Да |
| `STARTS WITH` | Да | Да |
| `ENDS WITH` | Нет | Да |
| `CONTAINS` | Нет | Да |
| `<`, `>`, сортировка | Да | Нет |

```cypher
CREATE TEXT INDEX product_title_text IF NOT EXISTS FOR (p:Product) ON (p.title);

// Теперь это использует индекс, а не сканирование всех товаров
MATCH (p:Product) WHERE p.title CONTAINS 'кофеварка' RETURN p.sku;
```

> **Внимание**: `CONTAINS` даже с текстовым индексом остаётся дорогим — индекс сужает выборку, но не даёт точного попадания. Для настоящего поиска по тексту нужен full-text индекс.

### Full-text

Отдельный индекс на движке Lucene: токенизация, стемминг, релевантность, поиск по нескольким свойствам сразу.

```cypher
CREATE FULLTEXT INDEX productSearch IF NOT EXISTS
FOR (p:Product) ON EACH [p.title];

CALL db.index.fulltext.queryNodes('productSearch', 'кофеварка') YIELD node, score
RETURN node.title, score ORDER BY score DESC LIMIT 5;
```

```
╒══════════════════════════════╤════════════════════╕
│node.title                    │score               │
╞══════════════════════════════╪════════════════════╡
│"Кофеварка Aroma Pro"         │0.9318070411682129  │
│"Кофеварка Aroma Mini"        │0.9318070411682129  │
│"Рожковая кофеварка Crema S"  │0.826097846031189   │
└──────────────────────────────┴────────────────────┘
```

Full-text вызывается процедурой, а не участвует в `WHERE` автоматически. Поддерживает синтаксис Lucene: `title:кофе*`, `кофеварка AND aroma`, `"точная фраза"~2`.

Типичный сценарий — гибридный: full-text находит стартовые узлы, дальше идёт обход графа.

```cypher
CALL db.index.fulltext.queryNodes('productSearch', 'кофе*') YIELD node AS p, score
MATCH (p)<-[:CONTAINS]-(:Order)<-[:PLACED]-(u:User)
RETURN p.title, score, count(DISTINCT u) AS buyers
ORDER BY score DESC, buyers DESC LIMIT 5;
```

> **Внимание**: звёздочка здесь обязательна. Lucene ищет целые токены, а не подстроки: запрос `кофе` не найдёт «Кофеварку», потому что в индексе лежит токен `кофеварка`, а не `кофе`. Запрос без звёздочки вернёт пустой результат, и это выглядит как неработающий индекс.

### Point

```cypher
CREATE POINT INDEX address_location IF NOT EXISTS FOR (a:Address) ON (a.location);

MATCH (a:Address)
WHERE point.distance(a.location, point({latitude: 53.9, longitude: 27.56})) < 5000
RETURN a.addressId;
```

### Vector

Индекс для поиска ближайших векторов — основа трека 6. Создаётся сейчас, используется в уроке 35.

```cypher
CREATE VECTOR INDEX productEmbedding IF NOT EXISTS
FOR (p:Product) ON (p.embedding)
OPTIONS {indexConfig: {
  `vector.dimensions`: 384,
  `vector.similarity_function`: 'cosine'
}};
```

Размерность фиксируется при создании и должна совпадать с размерностью модели эмбеддингов. Изменить её потом нельзя — только пересоздать индекс.

## Ограничения

Ограничение — это правило целостности. Уникальность попутно создаёт индекс, поэтому отдельный индекс на то же свойство заводить не нужно.

```cypher
CREATE CONSTRAINT user_email IF NOT EXISTS FOR (u:User) REQUIRE u.email IS UNIQUE;

SHOW CONSTRAINTS YIELD name, type, labelsOrTypes, properties;
```

| Тип ограничения | Что гарантирует | Community |
|---|---|---|
| `IS UNIQUE` | Уникальность значения свойства | Да |
| `IS NOT NULL` | Обязательное наличие свойства | Нет, только Enterprise |
| `IS NODE KEY` | Уникальность и обязательность набора свойств | Нет, только Enterprise |
| `IS :: <TYPE>` | Тип значения свойства | Нет, только Enterprise |

> **Внимание**: в Community доступна только уникальность. Попытка создать остальные даёт ошибку `51N27: not supported in this edition`. Практическое следствие: обязательность полей и типы в Community приходится проверять на стороне приложения — в треке 3 это делается валидацией на уровне сущностей Spring Data.

Синтаксис ограничений Enterprise, чтобы узнавать их в чужом коде:

```cypher
CREATE CONSTRAINT user_name_exists IF NOT EXISTS FOR (u:User) REQUIRE u.name IS NOT NULL;
CREATE CONSTRAINT user_key         IF NOT EXISTS FOR (u:User) REQUIRE (u.email, u.city) IS NODE KEY;
CREATE CONSTRAINT price_type       IF NOT EXISTS FOR (p:Product) REQUIRE p.price IS :: FLOAT;
```

### Уникальность и MERGE

Главная практическая роль ограничения уникальности — не запрет дубликатов, а корректность `MERGE` при параллельной записи.

Без ограничения `MERGE` выполняет чтение и запись без блокировки по ключу: две транзакции одновременно не находят узел и обе его создают. С ограничением движок берёт блокировку на значение ключа, и вторая транзакция ждёт.

```cypher
// Проверка: есть ли дубликаты по бизнес-ключу
MATCH (u:User)
WITH u.email AS email, count(*) AS cnt
WHERE cnt > 1
RETURN email, cnt;
```

Ограничение нельзя создать, если дубликаты уже есть — сначала их придётся слить. Это делается в уроке 34.

## Как проверить, что индекс используется

Единственный надёжный способ — посмотреть план.

```cypher
PROFILE MATCH (u:User {email: 'anna@shop.io'})-[:PLACED]->(o:Order) RETURN count(o);
```

```
| Operator             | Details                                          | Rows | DB Hits | Indexes Used  |
| +NodeUniqueIndexSeek | UNIQUE u:User(email) WHERE email = $autostring_0 |    1 |       2 | user_email: 1 |
```

Оператор `NodeUniqueIndexSeek` и заполненная колонка `Indexes Used` означают, что индекс сработал. Плохие признаки:

| Оператор | Что означает |
|---|---|
| `NodeIndexSeek` | Индекс используется, точечный поиск |
| `NodeIndexScan` | Индекс используется, но сканируется целиком |
| `NodeByLabelScan` | Индекса нет, читаются все узлы метки |
| `AllNodesScan` | В паттерне нет метки, читается вся база |

## Стоимость индексов

| Что дорожает | Насколько |
|---|---|
| `CREATE` и `MERGE` узла | Обновление каждого индекса по затронутым свойствам |
| `SET` свойства | То же, если свойство проиндексировано |
| Место на диске | Обычно единицы процентов от размера графа |
| Создание индекса на живой базе | Фоновая операция, индекс до готовности в состоянии `POPULATING` |

```cypher
// Готовность индексов — при загрузке важно дождаться ONLINE
SHOW INDEXES YIELD name, type, state, populationPercent;
```

Индексы, которые не используются, — чистый убыток. В Enterprise есть статистика использования; в Community остаётся выписать запросы приложения и проверить каждый через `PROFILE`.

## Порядок создания при загрузке

```
1. Ограничения уникальности на бизнес-ключи   ← до загрузки, обязательно
2. Загрузка данных
3. Остальные индексы (range, text, fulltext)  ← после загрузки, быстрее
```

Уникальность создаётся первой, потому что от неё зависит корректность `MERGE`. Остальные индексы после загрузки строятся быстрее, чем обновляются построчно во время неё.

## Практика

1. Выведи все индексы и ограничения текущей базы и определи, какие из них создались автоматически вместе с ограничениями.
2. Создай range-индекс на `Product.price` и проверь через `PROFILE`, что запрос с фильтром по цене использует `NodeIndexSeek`.
3. Создай составной индекс на `(o.status, o.createdAt)` и проверь три запроса: по обоим свойствам, только по `status`, только по `createdAt`. Убедись, что индекс сработал ровно в одном случае из трёх, и объясни, чем это отличается от поведения PostgreSQL.
4. Выполни `MATCH (p:Product) WHERE p.title CONTAINS 'кофе'` без текстового индекса и с ним, сравни операторы и db hits.
5. Создай full-text индекс по названиям товаров и найди товары по запросу `кофе*`. Повтори без звёздочки и объясни пустой результат.
6. Напиши гибридный запрос: full-text по `кофе*` находит товары, обход считает количество купивших их пользователей.
7. Попробуй создать ограничение `IS NOT NULL` и зафиксируй текст ошибки Community.
8. Ограничение `product_sku` создано ещё в уроке 9, поэтому второй `CREATE` с тем же `sku` упадёт сразу — сначала сними его через `DROP CONSTRAINT product_sku`. Создай два узла-дубликата, попробуй вернуть ограничение и зафиксируй ошибку. Почини данные и восстанови ограничение.
9. Создай векторный индекс на `Product.embedding` с размерностью 384 — он понадобится в уроке 35.
10. Выполни `PROFILE` запроса без метки в паттерне и найди в плане `AllNodesScan`.

## Итоги урока

- Индекс в графе нужен только для входа в граф: дальше работает обход по физическим ссылкам, и индексы в нём не участвуют.
- Range-индекс покрывает равенство, диапазоны, `STARTS WITH` и сортировку; составной, в отличие от PostgreSQL, требует предикатов по всем своим свойствам и по префиксу не работает.
- Text-индекс добавляет `CONTAINS` и `ENDS WITH`, но не поддерживает диапазоны и сортировку.
- Full-text — отдельный индекс на Lucene с релевантностью и синтаксисом запросов; вызывается процедурой и хорошо работает как способ найти стартовые узлы для обхода.
- Vector-индекс фиксирует размерность при создании — изменить её можно только пересозданием.
- В Community доступно только ограничение уникальности; existence, node key и типы — Enterprise, их приходится проверять на стороне приложения.
- Ограничение уникальности создаёт индекс автоматически и, что важнее, заставляет `MERGE` брать блокировку по ключу — без него параллельные загрузки создают дубликаты.
- Проверить использование индекса можно только через `PROFILE`: `NodeIndexSeek` — хорошо, `NodeByLabelScan` — индекса нет, `AllNodesScan` — в паттерне забыта метка.
- Ограничения уникальности создаются до загрузки данных, остальные индексы — после: так быстрее и корректнее.
