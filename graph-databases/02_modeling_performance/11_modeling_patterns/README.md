# Урок 11. Паттерны и антипаттерны моделирования

## Supernode

**Supernode** — узел с непропорционально большим количеством связей: десятки и сотни тысяч. Он ломает главное преимущество графа, потому что обход через него перестаёт быть локальным.

```
                       ┌─────────────────┐
   ... 200 000 связей ─┤ (:Category      │
                       │  {name:'Кухня'})├─ ... ещё 200 000
                       └─────────────────┘
```

Проблема не в самом количестве, а в том, что любой запрос, проходящий через такой узел, вынужден прочитать все его связи. Запрос «в какой категории этот товар» дёшев — он идёт от товара. Запрос «товары этой категории дороже 10000» читает все двести тысяч связей и потом фильтрует.

### Как обнаружить

```cypher
// Узлы с наибольшим количеством связей
MATCH (n)
RETURN labels(n) AS label, elementId(n) AS id, count { (n)--() } AS degree
ORDER BY degree DESC LIMIT 10;
```

`count { (n)--() }` — подзапрос-счётчик, он не материализует связи и работает быстро.

### Приём 1: разбиение по типу связи

Самое дешёвое решение — если ветки обхода различимы по типу, supernode перестаёт быть проблемой автоматически, потому что движок читает только связи нужного типа.

```cypher
// Плохо: все товары категории висят на одном типе
(:Product)-[:IN_CATEGORY]->(:Category)

// Лучше: если запросы всегда идут по ценовому сегменту
(:Product)-[:IN_CATEGORY_BUDGET]->(:Category)
(:Product)-[:IN_CATEGORY_PREMIUM]->(:Category)
```

Приём работает, когда сегментов немного и они устойчивы. Плодить сотни типов связей нельзя — каждый тип имеет стоимость в метаданных.

### Приём 2: промежуточные узлы

Supernode разбивается на дерево посредников.

```
   (:Category {name:'Кухня'})
        │           │
   [:BUCKET]   [:BUCKET]
        │           │
   (:CategoryBucket {range:'0-5000'})   (:CategoryBucket {range:'5000+'})
        │                                    │
   ... 20 000 товаров                  ... 15 000 товаров
```

Обход становится двухшаговым, но каждый шаг читает на порядок меньше связей. Цена — усложнение всех запросов и загрузки.

### Приём 3: вынести признак в свойство узла-соседа

Часто supernode вообще не нужен. Категория с двумястами тысячами товаров, через которую никогда не ходят «сверху вниз», может остаться просто свойством товара, а узел `:Category` — существовать только для иерархии.

> **Важно**: supernode — проблема, только если через него **проходят**. Узел с миллионом входящих связей, от которого никогда не идут наружу, безвреден. Прежде чем перестраивать модель, проверь PROFILE: если в плане нет `Expand(All)` от этого узла, оптимизировать нечего.

## Денормализация связей

Штатный приём: если цепочка обходится часто и её концы важнее промежуточных узлов, добавляется прямая связь.

```cypher
// Базовая модель: два шага
(:User)-[:PLACED]->(:Order)-[:CONTAINS]->(:Product)

// Денормализованная прямая связь
MATCH (u:User)-[:PLACED]->(o:Order)-[:CONTAINS]->(p:Product)
MERGE (u)-[r:PURCHASED]->(p)
  ON CREATE SET r.firstAt = o.createdAt, r.times = 1
  ON MATCH  SET r.times = r.times + 1;
```

Теперь коллаборативная рекомендация из урока 1 сокращается вдвое по количеству шагов:

```cypher
// Было: 6 шагов
MATCH (u:User {email: 'anna@shop.io'})-[:PLACED]->(:Order)-[:CONTAINS]->(p:Product)
      <-[:CONTAINS]-(:Order)<-[:PLACED]-(other:User)-[:PLACED]->(:Order)-[:CONTAINS]->(rec:Product)
RETURN DISTINCT rec.title;

// Стало: 3 шага
MATCH (u:User {email: 'anna@shop.io'})-[:PURCHASED]->(:Product)
      <-[:PURCHASED]-(other:User)-[:PURCHASED]->(rec:Product)
WHERE NOT (u)-[:PURCHASED]->(rec)
RETURN DISTINCT rec.title;
```

> **Внимание**: денормализованная связь — это кэш, и у неё те же проблемы, что у любого кэша. Отмена заказа обязана удалить или уменьшить `PURCHASED`, иначе рекомендации начнут ссылаться на несуществующие покупки. Решение — обновлять денормализованную связь в той же транзакции, что и исходные данные, а не отдельным фоновым процессом.

Когда денормализация оправдана:

| Оправдана | Не оправдана |
|---|---|
| Цепочка обходится в горячем пути | Запрос выполняется раз в сутки |
| Промежуточные узлы не нужны в ответе | Из промежуточного узла берутся свойства |
| Исходные данные меняются редко | Данные меняются чаще, чем читаются |

## Временные данные

Проблема: `o.createdAt` как свойство отлично работает для «заказы за март», но не позволяет ходить по времени как по графу.

### Свойство-дата — вариант по умолчанию

```cypher
MATCH (o:Order)
WHERE o.createdAt >= date('2026-03-01') AND o.createdAt < date('2026-04-01')
RETURN count(o);
```

С range-индексом по `createdAt` это быстро и просто. **Начинать нужно с этого варианта.**

### Time-tree

Дерево из узлов года, месяца и дня. Заказы подвешиваются к дню.

```
        (:Year {value: 2026})
              │
        [:HAS_MONTH]
              ▼
        (:Month {value: 3})
              │
        [:HAS_DAY]
              ▼
        (:Day {date: date('2026-03-01')}) ◀──[:ON_DAY]── (:Order)
```

```cypher
// Построение time-tree по существующим заказам
MATCH (o:Order)
WITH o, o.createdAt AS d
MERGE (y:Year  {value: d.year})
MERGE (m:Month {value: d.month, year: d.year})
MERGE (day:Day {date: d})
MERGE (y)-[:HAS_MONTH]->(m)
MERGE (m)-[:HAS_DAY]->(day)
MERGE (o)-[:ON_DAY]->(day);
```

Зачем это нужно: время становится частью обхода, а не фильтром.

```cypher
// Товары, купленные в марте пользователями, которые заходили с этого устройства
MATCH (d:Device {deviceId: 'dev-999'})<-[:LOGGED_IN_FROM]-(u:User)
      -[:PLACED]->(o:Order)-[:ON_DAY]->(:Day)<-[:HAS_DAY]-(:Month {value: 3, year: 2026})
MATCH (o)-[:CONTAINS]->(p:Product)
RETURN p.title, count(*) AS purchases ORDER BY purchases DESC;
```

> **Внимание**: time-tree сдвигает нагрузку на узлы дней. Степень узла месяца остаётся маленькой — это количество дней в нём, три-четыре десятка связей. А вот к каждому узлу дня подвешены все заказы этого дня, и на большом графе это сотни тысяч связей: обход «месяц → дни → заказы» упирается именно в день. Строить time-tree имеет смысл, только если обход по времени реально нужен в середине запроса. Для фильтрации по датам он не даёт ничего, кроме усложнения.

### Интервалы

Когда сущность действует в промежутке времени — цена, скидка, статус — интервал выносится в отдельный узел.

```cypher
// История цен: сама цена становится сущностью с периодом действия.
// Товар уже есть в графе после урока 9, поэтому его ищут, а не создают —
// CREATE здесь нарушил бы ограничение уникальности на sku
MATCH (p:Product {sku: 'CM-100'})
CREATE (p)-[:HAS_PRICE]->
       (:Price {value: 4990.0, from: date('2026-01-01'), to: date('2026-03-01')});

// Цена на конкретную дату
MATCH (p:Product {sku: 'CM-100'})-[:HAS_PRICE]->(pr:Price)
WHERE pr.from <= date('2026-02-15') AND (pr.to IS NULL OR pr.to > date('2026-02-15'))
RETURN pr.value;
```

## Связный список

Когда важен порядок и переход «следующий-предыдущий», элементы связываются в цепочку.

```
(:User)-[:LAST_EVENT]->(:Event {n:5})-[:PREV]->(:Event {n:4})-[:PREV]->(:Event {n:3}) ...
```

```cypher
// Добавление события в голову списка
MATCH (u:User {email: 'anna@shop.io'})
OPTIONAL MATCH (u)-[old:LAST_EVENT]->(prev:Event)
CREATE (e:Event {type: 'login', at: datetime()})
CREATE (u)-[:LAST_EVENT]->(e)
WITH e, prev, old
FOREACH (_ IN CASE WHEN prev IS NULL THEN [] ELSE [1] END | CREATE (e)-[:PREV]->(prev))
DELETE old;
```

Зачем: «последние 10 событий пользователя» становится обходом на 10 шагов от известной точки — стоимость не зависит от общего количества событий. Через свойство-дату с сортировкой пришлось бы читать все события пользователя.

Цена — сложность записи и невозможность вставки в середину без перестройки. Паттерн оправдан для append-only потоков: события, версии, история статусов.

## Промежуточный узел-событие

Самый универсальный паттерн. Когда у отношения появляются собственные вопросы, связь превращается в узел.

```cypher
// Было: факт покупки как связь
(:User)-[:PURCHASED {at: date()}]->(:Product)

// Стало: покупка как сущность
(:User)-[:MADE]->(:Purchase {at: date(), channel: 'mobile'})-[:OF]->(:Product)
(:Purchase)-[:PAID_WITH]->(:PaymentMethod)
(:Purchase)-[:RETURNED_BY]->(:Return)
```

Признак, что пора превращать связь в узел:

- у отношения появляются связи с третьими сущностями;
- одно и то же отношение может повторяться с разными атрибутами;
- по отношению задают собственные вопросы.

Обратный признак — узел с ровно двумя связями и без собственных вопросов — разбирался в уроке 10 как антипаттерн.

Этот же паттерн решает проблему идемпотентности счётчиков из урока 6:

```cypher
// Не идемпотентно: повторная доставка события удвоит счётчик
MERGE (u)-[r:VIEWED]->(p) ON MATCH SET r.views = r.views + 1;

// Идемпотентно: событие с уникальным идентификатором, счётчик считается запросом
MERGE (v:View {eventId: $eventId})
SET v.at = datetime($at)
MERGE (u:User {email: $email})
MERGE (p:Product {sku: $sku})
MERGE (u)-[:GENERATED]->(v)
MERGE (v)-[:ON]->(p);

// Счётчик как агрегат
MATCH (u:User {email: $email})-[:GENERATED]->(v:View)-[:ON]->(p:Product)
RETURN p.sku, count(v) AS views;
```

Цена — на порядок больше узлов. Компромисс: хранить события ограниченное время, а агрегат материализовать в свойство связи фоновой задачей.

## Иерархии

Дерево категорий — самый частый случай. Три варианта.

| Вариант | Модель | Плюсы | Минусы |
|---|---|---|---|
| Прямые связи | `(:Category)-[:SUBCATEGORY_OF]->(:Category)` | Просто, дёшево на запись | Обход глубины N на каждый запрос |
| Материализованный путь | Свойство `path: '/kitchen/coffee/espresso'` | Поиск поддерева одним `STARTS WITH` | Перемещение узла требует обновления всего поддерева |
| Транзитивное замыкание | Дополнительная связь `[:DESCENDANT_OF]` до всех предков | Один шаг до любого предка | Квадратичный рост количества связей |

Для дерева глубины 3-5 достаточно первого варианта — именно он используется в датасете курса. Второй оправдан, когда поддеревья ищут часто, а структура почти не меняется. Третий — когда глубина большая и обход по-настоящему дорог.

```cypher
// Прямые связи: все предки категории
MATCH (c:Category {categoryId: 'c-coffee-espresso'})-[:SUBCATEGORY_OF*]->(parent:Category)
RETURN parent.name;

// Транзитивное замыкание строится один раз
MATCH (c:Category)-[:SUBCATEGORY_OF*]->(anc:Category)
MERGE (c)-[:DESCENDANT_OF]->(anc);
```

## Практика

1. Найди в графе курса узлы с наибольшим количеством связей через `count { (n)--() }`. Определи, есть ли среди них настоящий supernode — то есть тот, через который проходят обходы.
2. Запусти генератор синтетических данных из урока 9 и повтори замер — посмотри, какие узлы стали supernode.
3. Построй денормализованную связь `PURCHASED` между пользователями и товарами.
4. Перепиши коллаборативную рекомендацию на `PURCHASED` и сравни через `PROFILE` количество db hits со старой версией.
5. Напиши запрос, который поддерживает `PURCHASED` в актуальном состоянии при отмене заказа.
6. Построй time-tree по заказам и напиши запрос, который использует обход по месяцу в середине пути.
7. Замерь через `count { (n)--() }` степень узлов `:Month` и `:Day`. Определи, на каком уровне дерева реально возник supernode, и объясни почему.
8. Смоделируй историю цены товара узлами `:Price` с интервалами и напиши запрос цены на произвольную дату.
9. Переведи просмотры товаров с денормализованной связи `VIEWED` на узлы-события `:View` и напиши идемпотентную загрузку.
10. Построй транзитивное замыкание по категориям и сравни количество связей `SUBCATEGORY_OF` и `DESCENDANT_OF`.

## Итоги урока

- Supernode вреден только тогда, когда через него идёт обход: узел с миллионом входящих связей, от которого не расходятся пути, безопасен.
- Supernode лечится разбиением по типам связей, промежуточными узлами-бакетами или отказом от обхода через него.
- `count { (n)--() }` считает степень узла, не материализуя связи, — основной инструмент поиска supernode.
- Денормализованная прямая связь сокращает обход, но является кэшем: её нужно обновлять в той же транзакции, что и исходные данные.
- Свойство-дата с range-индексом — вариант по умолчанию для времени; time-tree строят только когда обход по времени нужен в середине запроса.
- Time-tree сам создаёт supernode на уровне дней, к которым подвешены все события суток, — это осознанный размен, а не побочный эффект.
- Связный список делает «последние N событий» обходом фиксированной стоимости, не зависящей от общего объёма истории.
- Связь превращают в узел, когда у отношения появляются собственные связи, повторяемость или собственные вопросы.
- Узлы-события решают проблему неидемпотентных счётчиков: счётчик становится агрегатом, а не инкрементом.
- Иерархию глубиной до пяти уровней достаточно хранить прямыми связями; материализованный путь и транзитивное замыкание — оптимизации под конкретные сценарии.
