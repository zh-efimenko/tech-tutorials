# Урок 15. Транзакции и конкурентность

## ACID в Neo4j

Neo4j — полноценно транзакционная СУБД, в отличие от многих NoSQL-хранилищ. Это одно из главных отличий от ClickHouse, где транзакций фактически нет.

| Свойство | Как реализовано |
|---|---|
| Atomicity | Транзакция применяется целиком или откатывается целиком |
| Consistency | Ограничения проверяются при коммите, висячих связей не бывает по устройству хранилища |
| Isolation | Read-committed по умолчанию, с явными блокировками записи |
| Durability | Write-ahead log, коммит подтверждается после записи в лог |

Уровень изоляции — **read-committed**. Транзакция видит закоммиченные изменения других транзакций, но не видит незакоммиченные. Это слабее, чем repeatable read в PostgreSQL: два одинаковых чтения внутри одной транзакции могут вернуть разное.

```
Транзакция A                         Транзакция B
─────────────────────────────────────────────────────
MATCH (p:Product {sku:'CM-100'})
RETURN p.price          → 4990
                                     SET p.price = 5490
                                     COMMIT
MATCH (p:Product {sku:'CM-100'})
RETURN p.price          → 5490       ← неповторяющееся чтение
```

Практическое следствие: если внутри транзакции нужна стабильная картина, значение читают один раз и держат в переменной.

## Явные транзакции

В `cypher-shell` транзакция управляется командами оболочки.

```cypher
:begin
MATCH (p:Product {sku: 'CM-100'}) SET p.price = 5490;
MATCH (p:Product {sku: 'CM-101'}) SET p.price = 3690;
:rollback
```

```cypher
:begin
MERGE (b:Brand {name: 'NewBrand'});
:commit
```

Без явного `:begin` каждый запрос выполняется в собственной транзакции — это режим autocommit.

В Java-драйвере есть три режима, они подробно разбираются в уроке 17:

| Режим | Когда применять |
|---|---|
| Autocommit | Одиночные запросы, `CALL {} IN TRANSACTIONS` |
| Transaction function | Основной режим: автоматический retry при откате |
| Explicit transaction | Когда нужно управлять границей вручную |

## Блокировки

Neo4j берёт блокировки **на запись**, автоматически и на самом мелком уровне: узел, связь, значение ключа уникального индекса.

| Операция | Что блокируется |
|---|---|
| `SET` свойства узла | Узел |
| `CREATE` связи | Оба узла на концах |
| `DELETE` связи | Оба узла и сама связь |
| `MERGE` при наличии constraint | Значение ключа в индексе |

Блокировки держатся **до конца транзакции** и не снимаются раньше. Отсюда главное практическое правило: транзакция должна быть короткой. Транзакция, которая читает миллион узлов и потом обновляет один, держит блокировку всё время чтения.

> **Важно**: `CREATE` связи блокирует **оба** узла. Это делает supernode из урока 11 не только проблемой производительности, но и точкой конкуренции: если тысяча параллельных транзакций добавляют связи к одному узлу, они выстраиваются в очередь.

## Deadlock

Взаимная блокировка возникает, когда две транзакции берут одни и те же узлы в разном порядке.

```
Транзакция A                        Транзакция B
─────────────────────────────────────────────────────
блокирует User(anna)
                                    блокирует User(ivan)
ждёт User(ivan)  ←──────────────────┐
                                    │
                                    ждёт User(anna)
                                    └──── deadlock
```

Neo4j обнаруживает deadlock и откатывает одну из транзакций с ошибкой:

```
ForsetiClient[transactionId=42, clientId=3] can't acquire EXCLUSIVE NODE(49)
because it would form this deadlock wait cycle: NODE(49)-[EXCLUSIVE_OWNER]->...
```

Класс ошибки — `Neo.TransientError.Transaction.DeadlockDetected`. Сам класс `cypher-shell` в выводе не печатает, там видно только сообщение; увидеть код можно в драйвере через `exception.code()` или в логах приложения. `TransientError` означает, что запрос имеет смысл повторить: при повторе порядок захвата, скорее всего, окажется другим.

### Профилактика

**1. Единый порядок захвата.** Если транзакция трогает несколько узлов, брать их всегда в одном и том же порядке — например, отсортированными по бизнес-ключу.

```cypher
// Порядок захвата детерминирован сортировкой
UNWIND $emails AS email
WITH email ORDER BY email
MATCH (u:User {email: email})
SET u.processedAt = datetime();
```

**2. Не распараллеливать записи в пересекающиеся области.** Именно поэтому `parallel: true` в `apoc.periodic.iterate` из урока 9 опасен.

**3. Retry на уровне приложения.** Transaction function в Java-драйвере делает это автоматически — это главная причина использовать её, а не явные транзакции.

**4. Короткие транзакции.** Чем меньше блокировок держится одновременно, тем меньше шансов на пересечение.

## Наблюдение за транзакциями

```cypher
// Активные транзакции
SHOW TRANSACTIONS
YIELD transactionId, currentQuery, status, elapsedTime, currentQueryStartTime
RETURN transactionId, status, elapsedTime, currentQuery;

// Убить зависшую транзакцию
TERMINATE TRANSACTION 'neo4j-transaction-42';
```

> **Внимание**: в Cypher 25 колонки `startTime` и `currentQueryStartTime` имеют тип `ZONED DATETIME`, а не строку — это одно из ломающих изменений из урока 8. Скрипты мониторинга, написанные под Cypher 5, придётся поправить.

Заблокированные транзакции видны по статусу:

```cypher
SHOW TRANSACTIONS YIELD transactionId, status, elapsedTime
WHERE status <> 'Running'
RETURN transactionId, status, elapsedTime;
```

## Память транзакции

Транзакция целиком живёт в heap: изменённые узлы, промежуточные результаты, буферы операторов `Eager` и `Sort`.

```cypher
CALL dbms.listConfig() YIELD name, value
WHERE name CONTAINS 'memory.transaction'
RETURN name, value;
```

| Настройка | Что ограничивает |
|---|---|
| `dbms.memory.transaction.total.max` | Суммарная память всех транзакций сервера |
| `db.memory.transaction.total.max` | Суммарная память всех транзакций одной базы |
| `db.memory.transaction.max` | Память одной транзакции |
| `server.memory.heap.max_size` | Общий heap процесса |

Значение `0B` означает «без отдельного лимита» — ограничением остаётся уровень выше.

При превышении транзакция откатывается с ошибкой о нехватке памяти. Три способа не доводить до этого:

1. Батчи через `CALL {} IN TRANSACTIONS`.
2. Убрать `Eager` из плана — см. уроки 13 и 14.
3. Не собирать весь результат в `collect()`, если он не нужен целиком.

## Таймауты

Долгий запрос блокирует ресурсы и удерживает блокировки. Ограничение задаётся глобально или на запрос.

```cypher
CALL dbms.listConfig() YIELD name, value
WHERE name = 'db.transaction.timeout'
RETURN name, value;
```

В драйвере таймаут задаётся на конкретную транзакцию — это разбирается в уроках 17 и 24.

## Идемпотентность и повторы

Раз `TransientError` требует повтора, любой изменяющий запрос обязан быть безопасным при повторном выполнении. Правила из урока 6 становятся здесь требованием, а не рекомендацией:

```cypher
// Опасно при retry: счётчик увеличится дважды
MATCH (p:Product {sku: $sku}) SET p.views = p.views + 1;

// Безопасно: результат не зависит от количества выполнений
MERGE (v:View {eventId: $eventId})
SET v.at = datetime($at)
MERGE (p:Product {sku: $sku})
MERGE (v)-[:ON]->(p);
```

Ошибки делятся на два класса, и обрабатывать их надо по-разному:

| Класс | Примеры | Что делать |
|---|---|---|
| `TransientError` | Deadlock, нехватка памяти, потеря лидера в кластере | Повторить с задержкой |
| `ClientError` | Синтаксическая ошибка, нарушение ограничения, неверный тип | Повторять бесполезно, чинить запрос или данные |

## Транзакции и CALL {} IN TRANSACTIONS

Отдельно стоит зафиксировать: конструкция из уроков 9 и 14 **нарушает атомарность намеренно**.

```
Обычный запрос:            одна транзакция ── всё или ничего
CALL {} IN TRANSACTIONS:   транзакция на батч ── частичный результат возможен
```

Требования к такому коду:

- только идемпотентные операции;
- возможность определить, где остановились, и продолжить;
- `ON ERROR CONTINUE` с `REPORT STATUS` для сбора отчёта об ошибках, а не молчаливого проглатывания.

```cypher
UNWIND $rows AS row
CALL (row) {
  MERGE (p:Product {sku: row.sku}) SET p.price = toFloat(row.price)
} IN TRANSACTIONS OF 5000 ROWS
  ON ERROR CONTINUE
  REPORT STATUS AS status
RETURN status.committed AS ok, status.errorMessage AS err, count(*) AS batches;
```

## Практика

1. Открой две сессии `cypher-shell` к одной базе. В первой начни транзакцию через `:begin` и измени цену товара, не коммитя.
2. Во второй сессии прочитай цену того же товара — убедись, что изменение не видно.
3. Во второй сессии попробуй изменить тот же товар и зафиксируй, что запрос ждёт. Сделай `:commit` в первой и посмотри, что произойдёт со второй.
4. Воспроизведи неповторяющееся чтение: в первой сессии внутри одной транзакции прочитай свойство дважды, между чтениями измени его из второй сессии.
5. Воспроизведи deadlock: две сессии берут двух пользователей в противоположном порядке. Зафиксируй текст ошибки про цикл ожидания. Учти, что код `Neo.TransientError.Transaction.DeadlockDetected` в `cypher-shell` не отображается — он доступен из драйвера.
6. Перепиши обе транзакции так, чтобы узлы захватывались в отсортированном порядке, и убедись, что deadlock исчез.
7. Запусти долгий запрос и найди его через `SHOW TRANSACTIONS`, затем убей через `TERMINATE TRANSACTION`.
8. Проверь текущие лимиты памяти транзакций через `dbms.listConfig`.
9. Попробуй удалить все синтетические узлы одной транзакцией и зафиксируй поведение. Затем сделай это батчами.
10. Напиши загрузку с `ON ERROR CONTINUE` и `REPORT STATUS`, намеренно сломав данные в одной строке, и разбери отчёт. Учти, что не всякие плохие данные дают ошибку: `toFloat('нечисло')` вернёт `null` молча, и батч закоммитится. Рабочий пример сбоя — `MERGE` по ключу, который оказался `null`:

```cypher
UNWIND [{id: '1'}, {id: 'abc'}] AS row
CALL (row) {
  MERGE (t:Tmp {id: toInteger(row.id)})
} IN TRANSACTIONS OF 1 ROWS
  ON ERROR CONTINUE
  REPORT STATUS AS status
RETURN status.committed AS ok, status.errorMessage AS err;
```

```
│ok     │err                                                                        │
╞═══════╪═══════════════════════════════════════════════════════════════════════════╡
│TRUE   │null                                                                       │

```

## Итоги урока

- Neo4j полностью транзакционен: атомарность, проверка ограничений при коммите, WAL и durability.
- Уровень изоляции — read-committed, поэтому два чтения внутри одной транзакции могут вернуть разные значения.
- Блокировки берутся только на запись, автоматически, на уровне узла, связи или значения ключа уникального индекса, и держатся до конца транзакции.
- `CREATE` связи блокирует оба узла на её концах, поэтому supernode становится ещё и точкой конкуренции при параллельной записи.
- Deadlock обнаруживается движком и приводит к откату одной транзакции с ошибкой класса `TransientError`, которую нужно повторять.
- Профилактика deadlock — единый порядок захвата узлов, короткие транзакции, отказ от параллельной записи в пересекающиеся области и retry на уровне приложения.
- Ошибки делятся на `TransientError`, которые надо повторять, и `ClientError`, повтор которых бесполезен.
- Транзакция целиком живёт в heap, поэтому большие изменения делаются батчами, а `Eager` и лишние `collect()` из плана убираются.
- `SHOW TRANSACTIONS` и `TERMINATE TRANSACTION` — штатные инструменты диагностики; в Cypher 25 часть их колонок сменила тип на `ZONED DATETIME`.
- `CALL {} IN TRANSACTIONS` намеренно отказывается от атомарности ради объёма и требует идемпотентных операций и явной обработки ошибок.
