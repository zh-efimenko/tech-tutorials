# Урок 14. Оптимизация запросов

## Параметры и кэш планов

Планирование запроса стоит дорого — разбор, оценка альтернатив, выбор операторов. Neo4j кэширует планы, но ключом кэша служит **текст запроса**.

```cypher
// Три разных ключа кэша, три планирования
MATCH (u:User {email: 'anna@shop.io'}) RETURN u;
MATCH (u:User {email: 'ivan@shop.io'}) RETURN u;
MATCH (u:User {email: 'petr@shop.io'}) RETURN u;

// Один ключ кэша, одно планирование
MATCH (u:User {email: $email}) RETURN u;
```

На приложении с тысячей запросов в секунду разница между этими вариантами — это разница между работающим и лежащим сервисом. Планировщик занимает CPU и вытесняет из кэша полезные планы.

Neo4j частично спасает автопараметризацией: литералы заменяются на `$autostring_0`, что видно в планах из урока 13. Но это работает не всегда, и полагаться на неё нельзя.

```cypher
// Списки тоже параметризуются
:param skus => ['CM-100', 'GR-200', 'KT-300']
MATCH (p:Product) WHERE p.sku IN $skus RETURN p.title;
```

> **Важно**: у параметризации есть обратная сторона. Планировщик не знает значения параметра и планирует по средней селективности. Если распределение сильно неравномерное — `status = 'delivered'` даёт 70% строк, а `status = 'cancelled'` даёт 2% — один план окажется плохим для одного из значений. В таких редких случаях литерал в запросе оправдан.

## Сокращать поток как можно раньше

Самый результативный приём: `LIMIT` и фильтры ставятся до тяжёлых обходов, а не после.

```cypher
// Плохо: обход категорий выполняется для всех товаров
MATCH (p:Product)<-[:CONTAINS]-(o:Order)
MATCH (p)-[:IN_CATEGORY]->(c:Category)
WITH p, c, count(o) AS sales
RETURN p.title, c.name, sales ORDER BY sales DESC LIMIT 3;

// Хорошо: сначала топ-3, потом обход только для них
MATCH (p:Product)<-[:CONTAINS]-(o:Order)
WITH p, count(o) AS sales
ORDER BY sales DESC LIMIT 3
MATCH (p)-[:IN_CATEGORY]->(c:Category)
RETURN p.title, c.name, sales;
```

Тот же принцип для фильтров: условие ставится сразу после `MATCH`, породившего переменную, а не в конце запроса.

> **Внимание**: на простых запросах вроде примера выше современный планировщик сам поднимает агрегацию наверх, и db hits обоих вариантов совпадут — в плане будет один и тот же `OrderedAggregation` с `Top`. Выигрыш проявляется там, где после `LIMIT` идёт дорогой многошаговый обход, который планировщик переставить не может: несколько `MATCH` подряд, обход переменной длины, вызов процедуры. Мерить нужно на своём запросе, а не принимать на веру.

## Ограничивать глубину обхода

```cypher
// Опасно: без верхней границы количество путей растёт экспоненциально
MATCH (u:User {email: $email})-[:FOLLOWS*]->(other:User) RETURN count(other);

// Безопасно
MATCH (u:User {email: $email})-[:FOLLOWS]->{1,3}(other:User) RETURN count(DISTINCT other);
```

На синтетическом графе из урока 9 у каждого пользователя восемь подписок. Обход глубины 3 даёт около 500 путей, глубины 5 — около 32 тысяч, глубины 7 — два миллиона. Три лишних шага превращают запрос в зависание.

Второй приём — `DISTINCT` там, где нужны узлы, а не пути: до одного узла может вести множество путей, и без `DISTINCT` дальнейшие шаги выполняются для каждого из них.

Третий — режим `ACYCLIC` из урока 8: он отсекает пути, ходящие по кругу.

## Expand(Into) вместо Expand(All)

Когда оба конца связи уже известны, проверка связи дешевле её разворачивания.

```cypher
// Плохо: разворачиваем все заказы пользователя и фильтруем
MATCH (u:User {email: $email})-[:PLACED]->(o:Order)
WHERE o.orderId = $orderId
RETURN o;

// Хорошо: находим оба узла по индексам, проверяем связь
MATCH (u:User {email: $email}), (o:Order {orderId: $orderId})
WHERE (u)-[:PLACED]->(o)
RETURN o;
```

Идея приёма: когда оба конца известны, движок проверяет наличие связи (`Expand(Into)`) вместо разворачивания всех связей узла (`Expand(All)`). У пользователя с тысячей заказов это тысяча чтений против одного.

> **Внимание**: приём не универсален, и слепо применять его нельзя. Если оба узла находятся по уникальным индексам, планировщик и в первом варианте начнёт обход с более селективной стороны — от заказа, а не от пользователя, — и `Expand(All)` развернёт всего одну связь. Второй вариант при этом добавит `Apply` и окажется дороже — на датасете курса замер стабильно показывает примерно двукратный проигрыш «правильного» варианта (порядок 10 db hits против 25; точные числа зависят от того, сколько связей накопилось у узлов к этому моменту).
>
> Правило: переписывание оправдано, когда у одной из сторон высокая степень, а фильтр по второй стороне не является уникальным индексом. Проверять нужно `PROFILE` до и после — как и любую другую оптимизацию из этого урока.

## Батчевая запись

### UNWIND вместо цикла в приложении

```java
// Плохо: сетевой round-trip на каждую строку
for (ProductDto p : products) {
    session.run("MERGE (p:Product {sku: $sku}) SET p.price = $price",
                Map.of("sku", p.sku(), "price", p.price()));
}
```

```cypher
// Хорошо: один запрос на всю пачку
UNWIND $rows AS row
MERGE (p:Product {sku: row.sku})
SET p.price = row.price;
```

Тысяча отдельных запросов против одного — разница на два порядка. Это основной приём записи из Java, и в треке 3 он используется везде.

Размер пачки подбирается опытом: 1000-10000 строк на запрос. Больше — растёт память транзакции, меньше — не окупается round-trip.

### CALL {} IN TRANSACTIONS

Когда объём не помещается в одну транзакцию.

```cypher
UNWIND $rows AS row
CALL (row) {
  MERGE (p:Product {sku: row.sku})
  SET p.price = row.price
} IN TRANSACTIONS OF 10000 ROWS;
```

| Параметр | Назначение |
|---|---|
| `OF N ROWS` | Размер батча |
| `ON ERROR FAIL` | Прервать и откатить текущий батч — по умолчанию |
| `ON ERROR CONTINUE` | Пропустить сбойный батч |
| `ON ERROR BREAK` | Остановиться, сохранив предыдущие батчи |
| `REPORT STATUS AS s` | Вернуть статус каждого батча |

> **Внимание**: конструкция не является одной транзакцией. Сбой посреди работы оставляет часть данных записанной. Все запросы внутри обязаны быть идемпотентными — только `MERGE`, чтобы повторный запуск довёл дело до конца.

### Удаление больших объёмов

```cypher
// Не сработает на большом графе: одна транзакция не влезет в heap
MATCH (n:Synthetic) DETACH DELETE n;

// Сработает
MATCH (n:Synthetic)
CALL (n) { DETACH DELETE n } IN TRANSACTIONS OF 10000 ROWS;
```

## Избегать Eager

Разбор оператора был в уроке 13, здесь — приёмы обхода.

```cypher
// Eager: пишем и читаем одно свойство в одном запросе
MATCH (p:Product) SET p.discounted = p.price * 0.9
WITH p MATCH (q:Product) WHERE q.discounted > 5000 RETURN count(q);
```

Три способа убрать:

```cypher
// 1. Разделить на два запроса
MATCH (p:Product) SET p.discounted = p.price * 0.9;
MATCH (q:Product) WHERE q.discounted > 5000 RETURN count(q);

// 2. Не читать то, что только что записал
MATCH (p:Product) WHERE p.price * 0.9 > 5000 RETURN count(p);

// 3. Изолировать батчами
MATCH (p:Product)
CALL (p) { SET p.discounted = p.price * 0.9 } IN TRANSACTIONS OF 10000 ROWS;
```

## Считать через count store

Neo4j хранит готовые счётчики по меткам и типам связей. Запросы, которые в них попадают, отвечают мгновенно независимо от размера графа.

```cypher
// Попадает в count store: NodeCountFromCountStore, 1 db hit
MATCH (u:User) RETURN count(u);

// Попадает: RelationshipCountFromCountStore
MATCH ()-[r:PLACED]->() RETURN count(r);

// НЕ попадает: есть фильтр по свойству
MATCH (u:User) WHERE u.city = 'Минск' RETURN count(u);
```

Признак в плане — оператор `NodeCountFromCountStore` или `RelationshipCountFromCountStore`. Любой фильтр по свойству выводит запрос из count store и превращает его в сканирование.

## Кэширование свойств

В планах урока 13 встречался оператор `CacheProperties`. Движок сам замечает, что свойство читается несколько раз, и кэширует его на время запроса.

Помочь этому можно, не читая одно и то же свойство разными способами:

```cypher
// Плохо: два независимых чтения одного свойства
MATCH (u:User)-[:PLACED]->(o:Order)
WHERE u.city = 'Минск'
RETURN u.city, u.email, count(o);

// Лучше: свойство один раз попадает в переменную
MATCH (u:User)-[:PLACED]->(o:Order)
WITH u, u.city AS city WHERE city = 'Минск'
RETURN city, u.email, count(o);
```

Эффект небольшой, но на горячих запросах измерим.

## Проекции вместо целых узлов

Возврат узла целиком тянет все его свойства. Если нужны три поля из двадцати, дешевле спроецировать.

```cypher
// Тянет все свойства
MATCH (p:Product) RETURN p LIMIT 100;

// Тянет три
MATCH (p:Product) RETURN p {.sku, .title, .price} LIMIT 100;
```

На узлах с большими текстовыми полями или векторами эмбеддингов разница принципиальная — в треке 6 узлы товаров получат вектор на 384 числа, и случайный `RETURN p` начнёт гонять по сети мегабайты.

## Таблица приёмов

| Симптом в плане | Приём |
|---|---|
| `AllNodesScan` | Добавить метку в паттерн |
| `NodeByLabelScan` на большой метке | Создать индекс на свойство фильтра |
| `CartesianProduct` | Связать части паттерна связью |
| `ValueHashJoin` | Пересмотреть модель: отношение должно быть связью |
| `Eager` | Разделить чтение и запись или уйти в батчи |
| Резкий рост `Rows` | Поставить `LIMIT` или фильтр раньше |
| `Expand(All)` от узла высокой степени при известных концах | Переписать через проверку связи в `WHERE`, замерив `PROFILE` до и после |
| Большая `Memory` на `Sort` | Заменить `ORDER BY ... LIMIT` так, чтобы получился `Top` |
| Много `Page Cache Misses` | Увеличить page cache или уменьшить объём читаемых данных |
| План перестраивается на каждый запрос | Перейти на параметры |

## Итоги урока

- Ключ кэша планов — текст запроса, поэтому литералы в горячем пути заставляют планировать заново каждый раз; параметры решают это.
- Автопараметризация заменяет литералы на `$autostring_0`, но работает не всегда и не отменяет необходимости писать параметры явно.
- Планирование по параметру идёт по средней селективности, поэтому при сильно неравномерном распределении значений литерал изредка оправдан.
- `LIMIT` и фильтры ставятся до тяжёлых обходов: сокращённый поток дешевле любой последующей оптимизации.
- Обход переменной длины всегда ограничивают сверху — три лишних шага на плотном графе увеличивают количество путей в тысячи раз.
- Когда оба конца связи известны, проверка связи в `WHERE` даёт `Expand(Into)` вместо разворачивания всех связей, но выигрыш появляется только при высокой степени одной из сторон — иначе планировщик и так выберет дешёвый порядок, а переписывание добавит `Apply`.
- `UNWIND $rows` вместо цикла в приложении убирает round-trip на каждую строку — основной приём записи из Java.
- `CALL {} IN TRANSACTIONS` снимает ограничение по heap, но не является одной транзакцией и требует идемпотентных запросов.
- Счётчики по меткам и типам связей отвечают из count store за один db hit; любой фильтр по свойству выводит запрос из него.
- Возврат узла целиком тянет все свойства, включая большие тексты и векторы; проекция `p {.sku, .title}` возвращает только нужное.
