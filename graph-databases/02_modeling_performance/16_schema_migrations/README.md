## Что мигрировать, если схемы нет

Neo4j не требует объявлять структуру: узел с новым свойством просто появляется. Это соблазняет думать, что миграции не нужны. На практике мигрировать приходится три вещи.

| Что | Пример | Почему нельзя без миграции |
|---|---|---|
| **Индексы и ограничения** | Новый уникальный ключ, индекс под новый запрос | Это настоящая схема: она объявляется явно и должна совпадать во всех окружениях |
| **Структура графа** | Переименование типа связи, вынос свойства в узел | Старые данные останутся в прежнем виде |
| **Данные** | Заполнение нового обязательного свойства | Приложение упадёт на узлах, где свойства нет |

Ключевое отличие от PostgreSQL: там `ALTER TABLE ADD COLUMN` меняет все строки разом. В графе изменения структуры **не применяются к существующим данным** — их нужно переписать запросом.

```cypher
// Переименование типа связи: старые связи сами не изменятся
MATCH (a)-[old:PURCHASED]->(b)
CALL (a, old, b) {
  CREATE (a)-[new:BOUGHT]->(b)
  SET new = properties(old)
  DELETE old
} IN TRANSACTIONS OF 10000 ROWS;
```

> **Внимание**: в Cypher 25 `SET new = properties(old)` требует явного `properties()` — присваивать связь напрямую больше нельзя. Это изменение из урока 8, и старые скрипты миграций на нём ломаются.

## Neo4j-Migrations

Стандартный инструмент для Java-стека. Аналог Flyway, только для Cypher.

```groovy
// build.gradle.kts — версия под Spring Boot 4.1.x
dependencies {
    implementation("eu.michael-simons.neo4j:neo4j-migrations-spring-boot-starter:4.1.2")
}
```

Стартер поднимает миграции при старте приложения, используя то же подключение, что и Spring Data Neo4j.

### Структура файлов

Скрипты лежат в `src/main/resources/neo4j/migrations` и подчиняются жёсткому соглашению об именовании.

```
V1__Create_constraints.cypher
V2__Create_indexes.cypher
V3__Add_user_status.cypher
V4_1__Rename_purchased_to_bought.cypher
R__Refresh_denormalized_purchases.cypher
```

| Часть имени | Значение |
|---|---|
| `V` | Versioned — выполняется один раз |
| `R` | Repeatable — выполняется заново при изменении содержимого |
| `1`, `4_1` | Версия, части разделяются подчёркиванием |
| `__` | Два подчёркивания — разделитель |
| `Create_constraints` | Обязательное описание |
| `.cypher` | Расширение |

### Пример миграций

```cypher
// V1__Create_constraints.cypher
CREATE CONSTRAINT user_email     IF NOT EXISTS FOR (u:User)     REQUIRE u.email      IS UNIQUE;
CREATE CONSTRAINT product_sku    IF NOT EXISTS FOR (p:Product)  REQUIRE p.sku        IS UNIQUE;
CREATE CONSTRAINT order_id       IF NOT EXISTS FOR (o:Order)    REQUIRE o.orderId    IS UNIQUE;
CREATE CONSTRAINT category_id    IF NOT EXISTS FOR (c:Category) REQUIRE c.categoryId IS UNIQUE;
```

```cypher
// V2__Create_indexes.cypher
CREATE INDEX product_price     IF NOT EXISTS FOR (p:Product) ON (p.price);
CREATE INDEX order_created     IF NOT EXISTS FOR (o:Order)   ON (o.createdAt);
CREATE TEXT INDEX product_title IF NOT EXISTS FOR (p:Product) ON (p.title);
```

```cypher
// V3__Add_user_status.cypher
// Новое обязательное свойство: заполняем существующие узлы значением по умолчанию
MATCH (u:User)
WHERE u.status IS NULL
CALL (u) {
  SET u.status = 'active'
} IN TRANSACTIONS OF 10000 ROWS;
```

```cypher
// R__Refresh_denormalized_purchases.cypher
// Repeatable: пересобирает денормализованные связи из урока 11.
// Выполняется заново каждый раз, когда меняется содержимое файла
MATCH (u:User)-[old:PURCHASED]->(:Product) DELETE old;

MATCH (u:User)-[:PLACED]->(o:Order)-[:CONTAINS]->(p:Product)
CALL (u, o, p) {
  MERGE (u)-[r:PURCHASED]->(p)
    ON CREATE SET r.firstAt = o.createdAt, r.times = 1
    ON MATCH  SET r.times = r.times + 1
} IN TRANSACTIONS OF 10000 ROWS;
```

### Как хранится состояние

Neo4j-Migrations пишет историю применённых миграций в сам граф — отдельным подграфом с меткой `__Neo4jMigration`.

```cypher
// Что уже применено
MATCH (m:__Neo4jMigration)
RETURN m.version, m.description, m.type, m.checksum
ORDER BY m.version;
```

Контрольная сумма означает то же, что в Flyway: изменение уже применённого файла ломает миграцию с ошибкой несовпадения checksum. Правильный путь — новая версия, а не правка старой.

### Настройки

```yaml
# application.yml
org:
  neo4j:
    migrations:
      enabled: true
      locations-to-scan:
        - classpath:neo4j/migrations
      transaction-mode: PER_MIGRATION   # или PER_STATEMENT
      validate-on-migrate: true
```

`transaction-mode` — важный параметр. `PER_MIGRATION` выполняет весь файл одной транзакцией, что даёт атомарность, но упирается в heap на больших данных. `PER_STATEMENT` выполняет каждый стейтмент отдельно — атомарности нет, зато проходят тяжёлые миграции.

> **Важно**: `CALL {} IN TRANSACTIONS` сам управляет транзакциями и не выполняется внутри явной — это ограничение сервера, разобранное в уроке 21. Neo4j-Migrations про него знает и в свежих версиях выполняет такие стейтменты в autocommit даже под `PER_MIGRATION`, поэтому миграция может пройти без ошибки. Полагаться на это не стоит: для миграций данных с батчами явно ставь `PER_STATEMENT` — тогда поведение не зависит от версии инструмента. Если же увидишь ошибку о вложенных транзакциях, причина именно в этом.

## Liquibase для Neo4j

Альтернатива — расширение Liquibase. Имеет смысл в одном случае: проект уже использует Liquibase для PostgreSQL, и хочется единый инструмент и единый формат changelog.

```xml
<changeSet id="1" author="team">
    <ext:cypher>CREATE CONSTRAINT user_email IF NOT EXISTS
                FOR (u:User) REQUIRE u.email IS UNIQUE</ext:cypher>
</changeSet>
```

Для проекта, где Neo4j — единственная база, Neo4j-Migrations удобнее: он ближе к Cypher, знает про многобазовость и не требует XML.

## Миграции в CI

```
1. Поднять чистый Neo4j в Testcontainers
2. Применить все миграции с нуля
3. Прогнать интеграционные тесты
4. Отдельно: применить миграции на копии production-дампа
```

Четвёртый шаг обязателен для миграций данных. Миграция, безупречно работающая на пустой базе, может упасть по памяти или таймауту на реальном объёме — а узнать об этом на проде дорого.

Интеграция с Testcontainers разбирается в уроке 22.

## Разрушающие изменения

Одномоментное изменение схемы на живой системе почти всегда невозможно: приложение и база обновляются не синхронно. Работает схема с промежуточным состоянием, как и в реляционном мире.

```
Шаг 1. Миграция: добавить новое, старое не трогать
       (:User)-[:PURCHASED]->(:Product)   ← старое, работает
       (:User)-[:BOUGHT]->(:Product)      ← новое, заполнено

Шаг 2. Выкатить приложение, которое пишет в оба и читает из нового

Шаг 3. Убедиться, что старое больше никто не читает

Шаг 4. Миграция: удалить старое
```

Для графа этот приём особенно уместен, потому что добавление нового типа связи не мешает существующим запросам — они просто его не видят. В реляционной схеме лишняя колонка ощутимее.

## Версионирование самих данных

Отдельная задача — хранить историю изменений узла, а не только мигрировать схему. Два подхода.

**Свойства с интервалом действия** — паттерн из урока 11:

```cypher
// Закрыть действующий период и открыть новый.
// Узел :Price из урока 11 создавался сразу с заполненным to, поэтому
// на графе курса первый MATCH ничего не найдёт и SET не выполнится —
// чтобы увидеть работу приёма, заведи цену с to: null
MATCH (p:Product {sku: 'CM-100'})-[:HAS_PRICE]->(pr:Price)
WHERE pr.to IS NULL
SET pr.to = date()
CREATE (p)-[:HAS_PRICE]->(:Price {value: 5490.0, from: date(), to: null});
```

> **Внимание**: запрос молча ничего не делает, если открытого периода нет. В продакшне это выливается в потерю истории — правильнее проверять результат счётчиком изменённых узлов, а актуальную цену помечать явным признаком, а не отсутствием `to`.

**Узлы-версии со связным списком**:

```cypher
MATCH (p:Product {sku: 'CM-100'})-[cur:CURRENT_VERSION]->(old:ProductVersion)
CREATE (p)-[:CURRENT_VERSION]->(new:ProductVersion {title: 'Кофеварка Aroma Pro 2', at: datetime()})
CREATE (new)-[:PREVIOUS]->(old)
DELETE cur;
```

Первый вариант проще и покрывает большинство случаев. Второй нужен, когда версионируется вся сущность целиком, а не отдельное поле.

## Практика

1. Создай в проекте структуру `src/main/resources/neo4j/migrations` и напиши `V1__Create_constraints.cypher` со всеми ограничениями из урока 9.
2. Напиши `V2__Create_indexes.cypher` с индексами из урока 12.
3. Напиши миграцию `V3`, которая добавляет всем пользователям свойство `status` со значением по умолчанию, и сделай её идемпотентной через проверку `IS NULL`.
4. Напиши repeatable-миграцию, пересобирающую денормализованные связи `PURCHASED`.
5. Примени миграции и посмотри через запрос к `__Neo4jMigration`, что записалось в граф.
6. Измени содержимое уже применённого файла `V1` и запусти миграции заново — зафиксируй ошибку несовпадения контрольной суммы.
7. Напиши миграцию с `CALL {} IN TRANSACTIONS` и запусти её сначала в режиме `PER_MIGRATION`, потом в `PER_STATEMENT`. Зафиксируй, обошёл инструмент ограничение сам или упал с ошибкой о вложенных транзакциях.
8. Напиши миграцию переименования типа связи `PURCHASED` в `BOUGHT` батчами и убедись, что свойства перенеслись.
9. Спланируй на бумаге четыре шага безопасного разрушающего изменения для этого переименования.
10. Смоделируй историю цены товара узлами `:Price` с интервалами и напиши запрос цены на произвольную дату.

## Итоги урока

- Несмотря на отсутствие обязательной схемы, мигрировать приходится три вещи: индексы и ограничения, структуру графа и данные.
- В отличие от `ALTER TABLE`, изменение модели в графе не применяется к существующим данным — их переписывают запросом.
- Neo4j-Migrations — аналог Flyway для Cypher: скрипты `V1__Description.cypher` в `classpath:neo4j/migrations`, стартер применяет их при запуске приложения.
- Префикс `V` означает однократную миграцию, `R` — повторяемую, которая выполняется заново при изменении содержимого файла.
- История применённых миграций хранится в самом графе узлами `__Neo4jMigration` с контрольными суммами: правка применённого файла ломает миграцию.
- `transaction-mode: PER_MIGRATION` даёт атомарность файла, `PER_STATEMENT` нужен для тяжёлых миграций данных.
- Для миграций с `CALL {} IN TRANSACTIONS` явно ставят `PER_STATEMENT`: свежие версии инструмента обходят ограничение сами, но зависеть от этого не нужно.
- Liquibase с расширением для Neo4j оправдан, только когда проект уже стандартизирован на Liquibase для реляционной базы.
- Миграции данных обязательно прогоняются на копии production-объёма, а не только на пустой базе в CI.
- Разрушающие изменения делаются в четыре шага через промежуточное состояние; в графе это дешевле, чем в реляционной схеме, потому что новый тип связи не мешает существующим запросам.
