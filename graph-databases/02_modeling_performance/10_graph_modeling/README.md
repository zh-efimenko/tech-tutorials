# Урок 10. Проектирование графовой модели

## Откуда начинается модель

В реляционном мире схему проектируют от данных: выделяют сущности, нормализуют, потом пишут запросы. В графе порядок обратный — **модель проектируется от запросов**.

Причина в том, что граф не имеет обязательной схемы, зато имеет физическую стоимость обхода. Схема, удобная для одного набора вопросов, может делать другой набор вопросов дорогим. Поэтому первый артефакт проектирования — не диаграмма сущностей, а список вопросов к данным.

```
Вопросы к данным  ──▶  Модель графа  ──▶  Запросы  ──▶  Индексы
       ▲                                                    │
       └──────────────── проверка и правки ─────────────────┘
```

## Шаг 1: сформулировать вопросы

Вопрос формулируется на языке предметной области, без Cypher.

```
1. Какие товары чаще всего покупают вместе с этим товаром?
2. Какие товары порекомендовать пользователю на основе покупок похожих людей?
3. С каких устройств заходили пользователи, платившие этой картой?
4. Кого пригласил этот пользователь, и кого пригласили они, до пятого уровня?
5. Какая выручка по категории за месяц?
6. Какие товары пользователь смотрел, но не купил?
```

Вопрос 5 отличается от остальных: это агрегация по всем данным, а не обход от известной точки. Такие вопросы отмечают отдельно — они плохо ложатся на граф, и в реальной архитектуре их отдают реляционной СУБД или ClickHouse. Определить это на этапе проектирования дешевле, чем через полгода эксплуатации.

## Шаг 2: выделить узлы

Узлом становится то, о чём **задают вопросы** и на что **ссылаются несколько раз**.

| Кандидат | Узел или свойство | Почему |
|---|---|---|
| Пользователь | Узел | Центральная сущность, есть вопросы про него |
| Товар | Узел | То же |
| Город пользователя | Свойство | Про города вопросов нет, обходов через город не будет |
| Бренд товара | Узел | Есть вопрос «другие товары этого бренда» — нужен обход |
| Цена товара | Свойство | Скалярное значение, обходов нет |
| Устройство входа | Узел | Ключевой вопрос про общие устройства требует обхода через него |

Правило: **если через сущность нужно пройти, это узел; если её нужно только прочитать — свойство**.

Проверка от обратного: город хранится свойством, но если появится вопрос «покажи пользователей из того же города, что и этот», через город придётся идти. Тогда `City` становится узлом. Это нормальная эволюция модели, а не ошибка проектирования — важно лишь замечать момент, когда вопросы изменились.

## Шаг 3: выделить связи

Связь — это глагол между двумя узлами. Три решения на каждую связь.

### Направление

Выбирается по естественному чтению. Обход в обратную сторону стоит столько же, поэтому направление не влияет на производительность, зато влияет на читаемость.

```cypher
// Читается: пользователь разместил заказ
(:User)-[:PLACED]->(:Order)

// Обратное чтение работает и стоит столько же
MATCH (o:Order)<-[:PLACED]-(u:User) RETURN u.name;
```

Исключение — симметричные связи. Дружба, «похожий товар», «был в одной сессии» не имеют направления. Для них создаётся **одна** связь и читается без стрелки.

### Гранулярность типа

Один общий тип со свойством или несколько узких типов?

```cypher
// Вариант А: один тип, вид в свойстве
(:User)-[:INTERACTED {kind: 'view'}]->(:Product)
(:User)-[:INTERACTED {kind: 'purchase'}]->(:Product)

// Вариант Б: отдельные типы
(:User)-[:VIEWED]->(:Product)
(:User)-[:PURCHASED]->(:Product)
```

Вариант Б почти всегда лучше. Тип связи — единственный способ отсечь ненужные рёбра **до** их чтения: обход `-[:PURCHASED]->` не трогает просмотры вообще. В варианте А движок прочитает все связи и отфильтрует по свойству, а просмотров обычно в сотни раз больше, чем покупок.

Общий тип оправдан, только когда видов много (десятки), они не влияют на обходы и по ним не фильтруют.

### Свойства на связи

На связь выносится то, что описывает **факт отношения**, а не любую из сторон.

```cypher
// Правильно: цена в момент покупки — свойство факта, а не товара
(:Order)-[:CONTAINS {qty: 2, priceAtPurchase: 4990.0}]->(:Product)

// Неправильно: текущая цена товара — свойство товара
(:Order)-[:CONTAINS {currentPrice: 4990.0}]->(:Product)
```

## Шаг 4: проверить модель запросами

Модель проверяется тем, что на каждый вопрос из шага 1 пишется запрос, и оценивается, сколько шагов он делает.

```cypher
// Вопрос 1: что покупают вместе с этим товаром
MATCH (p:Product {sku: 'CM-100'})<-[:CONTAINS]-(o:Order)-[:CONTAINS]->(other:Product)
WHERE other <> p
RETURN other.title, count(*) AS together
ORDER BY together DESC LIMIT 5;
```

Два шага, старт от узла с уникальным индексом. Модель для этого вопроса подходит.

```cypher
// Вопрос 3: устройства пользователей, плативших этой картой
MATCH (c:PaymentMethod {cardId: 'card-999'})<-[:PAID_WITH]-(u:User)-[:LOGGED_IN_FROM]->(d:Device)
RETURN u.email, collect(d.deviceId) AS devices;
```

Тоже два шага. А вот вопрос 5 на этой модели выглядит так:

```cypher
// Вопрос 5: выручка по категории — обход всех заказов
MATCH (c:Category)<-[:IN_CATEGORY]-(p:Product)<-[ci:CONTAINS]-(o:Order)
WHERE o.createdAt >= date('2026-03-01')
RETURN c.name, sum(ci.qty * ci.priceAtPurchase) AS revenue
ORDER BY revenue DESC;
```

Нет стартовой точки — запрос обходит все позиции всех заказов. На датасете курса это мгновенно, на реальных объёмах — минуты. Подтверждается вывод из шага 1: агрегации в графе живут плохо.

## Сравнение с ER-моделированием

| Шаг ER-моделирования | Аналог в графе | Отличие |
|---|---|---|
| Выделение сущностей | Выделение узлов | В графе критерий — «нужен ли обход», а не «есть ли у неё атрибуты» |
| Нормализация | Отсутствует как этап | Дублирование не считается злом, если ускоряет обход |
| Связи один-ко-многим | Связь | Внешний ключ не нужен |
| Связи многие-ко-многим | Связь со свойствами | Промежуточная таблица исчезает |
| Индексы под запросы | Индексы под стартовые точки | Индекс нужен только для входа в граф, дальше работает обход |
| Денормализация как крайняя мера | Штатный приём оптимизации | Урок 11 |

Ключевой сдвиг мышления: в реляционной схеме дублирование данных — дефект, в графе денормализованная связь — обычный инструмент, такой же как индекс.

## Типичные ошибки проектирования

**Перенос реляционной схемы один в один.** Таблица `order_items` превращается в узел `:OrderItem`, хотя должна была стать связью `CONTAINS` со свойствами. Признак: узел, у которого ровно две связи и никогда не бывает больше.

```cypher
// Лишняя сущность: OrderItem не отвечает ни на один вопрос сам по себе
(:Order)-[:HAS_ITEM]->(:OrderItem {qty: 2})-[:OF_PRODUCT]->(:Product)

// Правильно
(:Order)-[:CONTAINS {qty: 2}]->(:Product)
```

Обратный случай тоже бывает: если по позиции заказа нужны собственные вопросы (возврат позиции, отдельная доставка, отзыв именно на позицию), она становится узлом заслуженно.

**Всё в свойствах одного узла.** Пользователь с полями `deviceId`, `cardId`, `city` вместо связей. Такая модель не отвечает на вопрос «кто ещё заходил с этого устройства» — придётся сканировать всех пользователей.

**Универсальные типы связей.** Одна связь `:RELATED` на всё. Убивает главное преимущество графа — отсечение по типу связи до чтения.

**Свойства-списки вместо связей.** `p.tags = ['coffee','kitchen']` работает, пока по тегам не нужно ходить. Как только появляется вопрос «другие товары с этим тегом», список превращается в полное сканирование, и тег должен стать узлом.

## Whiteboard-модель

Практический приём: модель рисуется кружками и стрелками, и каждая стрелка проговаривается вслух предложением. Если предложение не звучит по-русски — связь названа неправильно.

```
   (Пользователь) ──разместил──▶ (Заказ) ──содержит──▶ (Товар)
         │                                                │
    подписан на                                    относится к
         │                                                ▼
         ▼                                          (Категория)
   (Пользователь)                                         │
                                                  подкатегория чего
                                                          ▼
                                                    (Категория)
```

Главное свойство этого приёма: нарисованная модель **совпадает** с тем, что попадёт в базу. В реляционном проектировании между картинкой на доске и схемой в PostgreSQL лежит нормализация, промежуточные таблицы и внешние ключи. В графе картинка и есть модель.

## Практика

1. Выпиши шесть вопросов к данным своего проекта — таких, где ответ требует обхода связей.
2. Помечь среди них те, что на самом деле являются агрегациями, и отложи их в сторону.
3. Для оставшихся выдели узлы по правилу «через неё ходят — узел, её только читают — свойство».
4. Назови все связи глаголами и проговори каждую вслух как предложение.
5. Найди в модели курса связь, где направление выбрано по смыслу, а не по необходимости, и перепиши запрос в обратную сторону — убедись, что результат тот же.
6. Возьми модель `(:User)-[:INTERACTED {kind}]->(:Product)` и объясни на числах датасета, почему разделение на `VIEWED` и `CONTAINS` дешевле.
7. Найди в модели курса свойство, которое стало бы узлом при появлении вопроса «покажи всех с таким же значением».
8. Напиши запросы на все свои вопросы и посчитай для каждого количество шагов обхода. Запросы длиннее четырёх шагов — кандидаты на пересмотр модели.

## Итоги урока

- Графовая модель проектируется от вопросов к данным, а не от структуры данных: первый артефакт — список вопросов, а не диаграмма сущностей.
- Узлом становится то, через что нужно проходить; то, что только читают, остаётся свойством.
- Вопросы-агрегации по всем данным нужно распознавать на этапе проектирования — граф на них работает плохо, и их отдают реляционной СУБД или ClickHouse.
- Направление связи не влияет на стоимость обхода и выбирается по читаемости; симметричные связи создаются в одном экземпляре.
- Узкие типы связей лучше одного типа со свойством-дискриминатором: тип отсекает ненужные рёбра до их чтения.
- На связь выносят свойства самого факта отношения, а не свойства любой из сторон.
- Промежуточный узел с ровно двумя связями почти всегда должен быть связью со свойствами — это след перенесённой реляционной схемы.
- В графе денормализация — штатный инструмент оптимизации, а не дефект нормализации.
- Нарисованная на доске модель совпадает с тем, что попадёт в базу, — промежуточного слоя между картинкой и схемой нет.
