# Урок 13. Профилирование запросов

> **Важно**: весь урок построен на чтении таблицы операторов. В `cypher-shell` она появляется только с флагом `--format verbose` — по умолчанию оболочка печатает лишь итоговую сводку по времени и db hits. Запускай так:
>
> ```bash
> docker exec -it neo4j cypher-shell -u neo4j -p graphpassword --format verbose
> ```
>
> В Neo4j Browser план рисуется схемой без дополнительных флагов.

> **Внимание**: приведённые в уроке планы сняты на базовом датасете из урока 9, без синтетики — отсюда числа вроде «277 db hits на графе из 276 узлов». Практика же начинается с запуска генератора: после него операторы в планах останутся теми же, а db hits вырастут на три порядка. Сверяй операторы и пропорции, а не абсолютные значения.

## EXPLAIN и PROFILE

Два способа увидеть, что движок собирается делать с запросом.

| Команда | Выполняет запрос | Показывает |
|---|---|---|
| `EXPLAIN` | Нет | План с оценками планировщика |
| `PROFILE` | Да | План с фактическими числами: строки, db hits, память |

`EXPLAIN` безопасен — им можно проверять любой запрос, включая изменяющий данные. `PROFILE` запрос выполняет, поэтому на записи его применяют осознанно.

```cypher
EXPLAIN MATCH (u:User {email: 'anna@shop.io'})-[:PLACED]->(o:Order) RETURN count(o);
PROFILE MATCH (u:User {email: 'anna@shop.io'})-[:PLACED]->(o:Order) RETURN count(o);
```

Работать нужно с `PROFILE`: расхождение между оценкой планировщика и фактом — сам по себе важный сигнал, и увидеть его можно только когда есть обе величины.

## Как читать план

План — дерево операторов, которое выполняется **снизу вверх**. Нижний оператор находит стартовые узлы, каждый следующий обрабатывает то, что пришло от нижнего.

```
PROFILE MATCH (u:User {email: 'anna@shop.io'})-[:PLACED]->(o:Order)-[:CONTAINS]->(p:Product)
RETURN p.title;
```

```
| Operator             | Details                                          | Est. Rows | Rows | DB Hits | Indexes Used  |
| +ProduceResults      | `p.title`                                        |         4 |    4 |       0 |               |
| +Projection          | p.title AS `p.title`                             |         4 |    4 |       4 |               |
| +Filter              | p:Product                                        |         4 |    4 |       4 |               |
| +Expand(All)         | (o)-[:CONTAINS]->(p)                             |         4 |    4 |       8 |               |
| +Filter              | o:Order                                          |         2 |    2 |       2 |               |
| +Expand(All)         | (u)-[:PLACED]->(o)                               |         2 |    2 |      16 |               |
| +NodeUniqueIndexSeek | UNIQUE u:User(email) WHERE email = $autostring_0 |         1 |    1 |       2 | user_email: 1 |
```

Чтение снизу вверх: нашли одного пользователя по индексу (2 db hits), развернули связи `PLACED`, отфильтровали по метке `Order`, развернули связи `CONTAINS`, спроецировали название. Итого несколько десятков db hits — это здоровый план. Точное число зависит от того, сколько связей накопилось у узлов к этому уроку: денормализованная связь `PURCHASED` из урока 11 добавляет пользователю рёбер, и та же выборка обойдётся дороже.

### Ключевые колонки

| Колонка | Что означает | На что смотреть |
|---|---|---|
| **Estimated Rows** | Оценка планировщика | Сравнить с фактом |
| **Rows** | Фактическое количество строк | Резкий рост на каком-то шаге — узкое место |
| **DB Hits** | Обращений к хранилищу | Главная метрика стоимости |
| **Memory (Bytes)** | Пиковая память оператора | Важно для агрегаций и сортировок |
| **Page Cache Hits/Misses** | Попадания в кэш страниц | Много misses — данные не помещаются в page cache |
| **Indexes Used** | Какие индексы сработали | Пусто там, где ожидался индекс — проблема |

**DB hits — не время.** Это количество обращений к слою хранения: чтение узла, связи, свойства, элемента индекса. Метрика стабильна между запусками, в отличие от времени, поэтому оптимизацию меряют именно ей.

**Расхождение оценки и факта** — отдельный диагноз. Если планировщик ожидал 10 строк, а пришло 100 000, он выбрал план под маленькую выборку, и этот план на реальных данных плох. Причина обычно в устаревшей статистике.

## Операторы: словарь

### Стартовые

| Оператор | Что делает | Оценка |
|---|---|---|
| `NodeUniqueIndexSeek` | Точечный поиск по уникальному индексу | Лучший вариант |
| `NodeIndexSeek` | Поиск по обычному индексу | Хорошо |
| `NodeIndexScan` | Полное чтение индекса | Терпимо |
| `NodeByLabelScan` | Чтение всех узлов метки | Плохо на больших метках |
| `AllNodesScan` | Чтение всех узлов базы | Почти всегда ошибка |

```cypher
// В паттерне забыта метка — план читает всю базу
PROFILE MATCH (n {sku: 'CM-100'}) RETURN n;
```

```
| +Filter       | n.sku = $autostring_0 |  276 |
| +AllNodesScan | n                     |  277 |
```

277 db hits ради одного узла на графе из 276 узлов. С меткой и индексом было бы 2.

### Обход

| Оператор | Что делает |
|---|---|
| `Expand(All)` | Разворачивает связи от узла |
| `Expand(Into)` | Проверяет наличие связи между двумя уже известными узлами |
| `OptionalExpand(All)` | То же, что `Expand`, но для `OPTIONAL MATCH` |
| `VarLengthExpand(All)` | Обход переменной длины |
| `StatefulShortestPath` | Поиск кратчайшего пути |

`Expand(Into)` дешевле `Expand(All)`, когда оба конца уже найдены — движок проверяет связь, а не разворачивает все.

### Соединение и фильтрация

| Оператор | Что делает | Комментарий |
|---|---|---|
| `Filter` | Отсекает строки по предикату | Норма |
| `CartesianProduct` | Декартово произведение двух несвязанных частей | Почти всегда ошибка |
| `ValueHashJoin` | Хеш-соединение по значению свойства | Признак того, что связь заменили сравнением свойств |
| `NodeHashJoin` | Соединение двух ветвей плана по узлу | Норма при сложных паттернах |
| `Apply` | Выполняет правую ветвь для каждой строки левой | Норма для подзапросов |

### Материализация

| Оператор | Что делает | Риск |
|---|---|---|
| `EagerAggregation` | Копит все строки для агрегации | Память |
| `Sort` / `Top` | Сортировка; `Top` — сортировка с `LIMIT` | `Top` дешевле |
| `Eager` | Полностью материализует поток | Разбирается ниже |

## Три диагноза

### 1. CartesianProduct

Появляется, когда в `MATCH` две части паттерна не связаны между собой.

```cypher
PROFILE MATCH (u:User), (p:Product)
WHERE u.registeredAt < date('2026-01-01') AND p.price > 5000
RETURN u.email, p.sku LIMIT 10;
```

```
| +Limit            | 10                   |   10 |
| +CartesianProduct |                      |   10 |
| +Filter           | p.price > $autoint_1 |    2 |
| +NodeByLabelScan  | p:Product            |    5 |
```

Количество строк — произведение размеров частей. На 30 пользователях и 24 товарах это 720 комбинаций, на реальных данных — миллиарды.

Лечение: связать части паттерна связью, если она есть по смыслу, либо разделить на два запроса, либо явно ограничить одну из частей до одного узла.

> **Внимание**: `CartesianProduct` иногда закономерен — когда действительно нужны все пары. Но в 95% случаев это забытая связь в паттерне.

### 2. ValueHashJoin

```cypher
PROFILE MATCH (u:User), (p:Product) WHERE u.city = p.title RETURN u.email, p.sku;
```

```
| +ValueHashJoin   | p.title = u.city |   54 |
| +NodeByLabelScan | p:Product        |   25 |
```

Планировщик выкрутился и вместо декартова произведения сделал хеш-соединение. Само по себе это не катастрофа, но появление `ValueHashJoin` — сигнал, что в модели отношение выражено сравнением свойств вместо связи. Именно этот случай урок 10 называет главным антипаттерном: если через сущность сравнивают, значит через неё ходят, значит это должен быть узел.

### 3. Eager

Самый коварный. `Eager` появляется, когда изменяющий запрос читает то же, что пишет: движок обязан полностью материализовать поток, иначе результат зависел бы от порядка обработки строк.

```cypher
PROFILE MATCH (p:Product) WITH p LIMIT 5
SET p.touched = true
WITH p MATCH (q:Product) WHERE q.touched RETURN count(q);
```

```
| +Filter      | CoerceToPredicate(q.touched)                               |  240 |
| +Apply       |                                                            |    0 |
| +Eager       | read/set conflict for property: touched (Operator: 6 vs 2)  |    0 |
| +SetProperty | p.touched = true                                           |    8 |
```

Колонка `Details` прямо называет причину: `read/set conflict for property: touched`. На пяти товарах это незаметно, при загрузке миллиона строк `Eager` складывает весь поток в память и роняет запрос по heap.

Лечение: разделить чтение и запись на два запроса, либо использовать `CALL {} IN TRANSACTIONS`, где батчи изолированы.

> **Важно**: `Eager` в плане загрузки данных — главная причина неожиданного `OutOfMemory` при импорте. Проверять план загрузочных запросов через `EXPLAIN` нужно до, а не после запуска на полном файле.

## Статистика планировщика

Планировщик опирается на статистику: количество узлов по меткам, связей по типам, распределение значений индексов. Она обновляется автоматически, но после массовой загрузки может отставать.

```cypher
// Признак проблемы: оценка расходится с фактом на порядки
PROFILE MATCH (u:User:Synthetic)-[:FOLLOWS]->(o:User) RETURN count(o);
```

Если `Estimated Rows` и `Rows` расходятся в сотни раз, стоит проверить, актуальна ли статистика по затронутым индексам:

```cypher
SHOW INDEXES YIELD name, type, state, populationPercent, lastRead;
```

Отдельная причина расхождений — параметры. Планировщик не знает значения `$param` в момент планирования и использует усреднённую оценку. Это плата за переиспользование плана, и обычно она себя окупает.

## Подсказки планировщику

Крайняя мера, когда планировщик устойчиво выбирает плохой план.

```cypher
// Заставить использовать конкретный индекс
MATCH (o:Order)
USING INDEX o:Order(status)
WHERE o.status = 'delivered' AND o.createdAt > date('2026-03-01')
RETURN count(o);

// Заставить сканировать метку вместо индекса
MATCH (p:Product)
USING SCAN p:Product
WHERE p.price > 1000
RETURN count(p);
```

> **Внимание**: подсказка фиксирует решение навсегда. Когда данные изменятся и правильным станет другой план, подсказка будет мешать. Прежде чем ставить hint, надо убедиться, что проблема не в отсутствующем индексе и не в устаревшей статистике.

## Методика оптимизации

```
1. Снять PROFILE, записать общее число db hits
2. Найти оператор, где Rows резко вырастает
3. Найти оператор с наибольшим DB Hits
4. Проверить нижний оператор: это Seek или Scan?
5. Исправить одно место
6. Снять PROFILE заново и сравнить db hits
```

Ключевое правило: **менять по одному и мерить**. Три правки за раз не дают понять, что помогло, а что ухудшило.

Ориентиры для здорового плана:

- нижний оператор — `NodeUniqueIndexSeek` или `NodeIndexSeek`;
- нет `AllNodesScan`;
- нет `CartesianProduct`, если пары не нужны по смыслу;
- нет `Eager` в изменяющих запросах;
- `Rows` не растёт скачками на порядки между соседними операторами;
- `Page Cache Misses` близки к нулю на повторном запуске.

## Практика

1. Запусти генератор синтетических данных из урока 9 — на маленьком графе разница между планами не видна.
2. Сними `PROFILE` с запроса поиска пользователя по email и запиши db hits.
3. Убери метку из паттерна и сравни план — найди `AllNodesScan` и посчитай разницу в db hits.
4. Напиши запрос с двумя несвязанными частями паттерна и найди `CartesianProduct`. Свяжи части и сравни количество строк.
5. Воспроизведи `ValueHashJoin`, сравнив свойства двух узлов, и перепиши запрос через связь.
6. Воспроизведи `Eager`: запрос, который в одном стейтменте пишет свойство и тут же его читает. Найди в `Details` текст конфликта.
7. Перепиши тот же запрос через `CALL {} IN TRANSACTIONS` и убедись, что `Eager` исчез.
8. Найди запрос, где `Estimated Rows` расходится с `Rows` больше чем в 10 раз, и объясни причину.
9. Сравни планы одного запроса с литералом и с параметром — найди отличия в оценках.
10. Возьми любой свой запрос из уроков 5-7, оптимизируй его и зафиксируй db hits до и после.

## Итоги урока

- `EXPLAIN` показывает план без выполнения, `PROFILE` выполняет запрос и даёт фактические числа; работать нужно с `PROFILE`, потому что важно расхождение оценки и факта.
- План читается снизу вверх: нижний оператор находит стартовые узлы, верхний формирует результат.
- DB hits — обращения к слою хранения, а не время; метрика стабильна между запусками и именно по ней меряют оптимизацию.
- `NodeUniqueIndexSeek` и `NodeIndexSeek` — здоровое начало плана, `NodeByLabelScan` — отсутствие индекса, `AllNodesScan` — почти всегда забытая метка.
- `CartesianProduct` означает несвязанные части паттерна, и количество строк становится произведением размеров частей.
- `ValueHashJoin` сигнализирует, что отношение в модели выражено сравнением свойств вместо связи.
- `Eager` возникает при конфликте чтения и записи одного свойства в одном запросе, материализует весь поток в память и является главной причиной `OutOfMemory` при импорте.
- Расхождение `Estimated Rows` и `Rows` на порядки указывает на устаревшую статистику или на планирование по параметру.
- Подсказки `USING INDEX` и `USING SCAN` фиксируют план навсегда и применяются только после проверки индексов и статистики.
- Оптимизация ведётся по одному изменению за раз с измерением db hits до и после.
