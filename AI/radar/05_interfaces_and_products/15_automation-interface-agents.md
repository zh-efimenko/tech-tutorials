Рассмотрим:

- Готовые no-code платформы и их пределы: Retool, Appsmith, Budibase, Refine
- AI-генерацию интерфейсов: v0.dev, Bolt.new и третий путь Claude Design с передачей в Claude Code
- Архитектуру админки для скриптов и агентов: очереди задач, HITL через LangGraph, безопасность API по стандарту OWASP 2023
- Прототип на Streamlit и продакшн-сборку Next.js + FastAPI с named SSE-events
- shadcn MCP как способ дать агенту прямой доступ к компонентной библиотеке

CLI и cron справляются, пока инструментов мало и пользуется ими один человек. Как только число скриптов переваливает за десяток, а среди потребителей появляются коллеги без терминала и AI-агенты с собственным жизненным циклом, появляется потребность в панели: кнопки, формы, статусы, журнал событий, остановка зависшей задачи в один клик. Эта тема — про то, как собрать такую панель быстро, без месяцев фронтенд-работы, и не загнать себя в архитектурные углы при переходе от прототипа к продакшну.

## Готовые no-code платформы для админок

Если задача — собрать CRUD-интерфейс над таблицей, запустить пару хранимых процедур и дать его трём аналитикам, писать React с нуля бессмысленно. Категория no-code-платформ для внутренних инструментов зрелая: у **Retool** 27 000+ корпоративных клиентов, у **Appsmith** 34K+ звёзд на GitHub, **Budibase** идёт ниже по цене и сложности. Выбор между Retool, Appsmith и Budibase на самом деле не про инструмент, а про несколько осей: цена при росте команды, контроль над данными, сложность бизнес-логики и кто будет чинить.

### Retool, Appsmith и Budibase: где какая платформа уместна

**Retool** — рыночный лидер. Сильные стороны: 100+ готовых компонентов, 80+ интеграций с базами и API, развитая поддержка JavaScript для произвольной логики. Слабые: тарификация по числу пользователей (от 10 до 50 долларов за пользователя в месяц), которая на 50 сотрудниках превращается в 30 тысяч в год; SSO и журнал аудита доступны только в дорогих тарифах; SaaS-модель — данные проходят через инфраструктуру поставщика. Подходит, когда у команды есть бюджет, нужна интеграция с десятками источников и enterprise-возможности (audit, RBAC, SSO) важнее open source.

**Appsmith** — главный open source-конкурент. Self-hosted бесплатно, Docker-развёртывание из коробки, схожие с Retool возможности по JavaScript-кастомизации. **Ограничения:** интеграций пока меньше, корпоративные функции (SSO, расширенный RBAC) — за деньги, экосистема плагинов скромнее. Хороший выбор, когда требуется self-hosting по внутренним требованиям к хранению данных и есть инженер, готовый поддерживать инсталляцию.

**Budibase** — самая простая из тройки. Авто-генерация CRUD-приложений из схемы базы, встроенная BudibaseDB, визуальный редактор автоматизаций. Потолок наступает быстро: сложная бизнес-логика и нестандартные интеграции упираются в ограничения визуального билдера. Подходит для типовой админки уровня — показать таблицу пользователей, дать редактировать пару полей, логировать кто что сделал.

Главный антипаттерн при выборе — игнорирование безопасности. SSO, журнал аудита, RBAC у всех платформ доступны не в базовом тарифе. Если в админке будут действия с пользовательскими данными или операциями над продакшн-инфраструктурой — закладывайте именно платный тариф с этими функциями, иначе через год аудит соответствия требованиям заставит мигрировать.

### Code-first альтернатива: Refine, TanStack Table, shadcn/ui

У no-code-платформ есть потолок: когда логика перестаёт укладываться в визуальный редактор, а типобезопасность над данными становится требованием — команды переходят на code-first стек. К 2026 году индустриальный золотой стандарт для технических команд выглядит так: Next.js + shadcn/ui + TanStack Table + Prisma + Casbin или Permit.io для модели прав. Refine — open source фреймворк поверх React, в котором CRUD, RBAC и интеграции с популярными бэкендами уже встроены, остаётся дописывать домен.

Что даёт code-first путь по сравнению с Retool: полный контроль над кодом, отсутствие vendor lock-in, TypeScript-типизация сквозь всю систему данных, проще ставить нестандартные кастомные виджеты, дешевле в долгосрочной перспективе при росте команды (нет цены за каждого пользователя). Что отбирает: время на старт. Если Retool-приложение запускается за день, то Refine-стек требует полноценного фронтенд-инженера и пары спринтов, чтобы дойти до того же объёма функциональности.

Когда выбор кода однозначно оправдан: типизированный data layer с десятками сущностей и сложными отношениями; RBAC- или ABAC-модели прав сложнее, чем admin / editor / viewer; интеграции с внутренней инфраструктурой, на которые нет коннектора в Retool; долгий горизонт эксплуатации (>2 лет) с ростом аудитории. Когда нет — для разовой админки аналитика, которую через полгода никто не откроет, code-first путь — оверинженеринг.

## AI-генерация интерфейсов

Категория prompt-to-UI за последний год прошла путь от забавных демо до продакшн-ready инструментов. Главный сдвиг: код на выходе теперь читаем и пригоден для интеграции в существующий проект, особенно если проект на Next.js + shadcn/ui. Ниже — три ветки этой категории, каждая со своим позиционированием, и принципы выбора.

### v0.dev и Bolt.new: prompt-to-UI и prompt-to-app

**v0.dev** — инструмент Vercel, ориентированный на генерацию React-компонентов с shadcn/ui и Tailwind. Это не генератор полного стека: бэкенда не делает, аутентификации не настраивает, схему базы не проектирует. Что делает хорошо — выдаёт компонент, который можно скопировать в `components/ui/` существующего проекта и доработать. Цена — 20 долларов в месяц на тарифе Premium, бесплатный лимит — 7 сообщений в день. Подходит, когда бэкенд уже есть, нужны качественные UI-блоки.

**Bolt.new** построен на StackBlitz WebContainers — это полноценная среда Node.js, работающая в браузере. Bolt принимает промпт уровня **собрать SaaS-дашборд с auth и базой** и пытается выдать рабочее приложение целиком: схема Drizzle, API-роуты, фронтенд. С 2026 года добавлены многоагентные процессы, где один агент проектирует данные, другой — UI, что заметно стабилизирует генерацию полного стека. Слабости: качество кода менее предсказуемо, чем у v0; для продакшена нужна ревизия инженером.

Третий игрок — **Lovable** — заточен под Supabase-стек: auth, БД, хостинг — всё интегрировано. Это самый короткий путь от идеи до работающего MVP, но за это платят vendor lock-in: вынуть проект из Lovable и перевести на собственную инфраструктуру — отдельная работа.

**Общее ограничение трёх инструментов:** для прототипа они дают 60–70% результата, оставшиеся 30% — архитектурные решения, обработку ошибок, тесты, CI/CD — делает живой инженер. Дополнительно: у всех трёх инструментов сгенерированный код показывает заметный процент уязвимостей безопасности при автоматизированной проверке, поэтому ревизия безопасности — обязательный шаг перед выкаткой.

### Третий путь: Claude Design с передачей в Claude Code

В апреле 2026 Anthropic запустил Claude Design — исследовательскую версию инструмента для создания дизайнов, прототипов, презентаций и одностраничников через чат и интерактивный холст. Это отдельная категория от v0/Bolt/Lovable: основной артефакт — дизайн на холсте, а не сразу код. На код Claude Design передаёт через bundle, который Claude Code читает напрямую через свой инструмент.

Конкретные особенности, важные для админки:

- **Auto-inherit дизайн-системы.** Если в организации настроены брендовые цвета, шрифты, компоненты — Claude применяет их автоматически, без ручной загрузки ассетов.
- **Импорт существующей кодовой базы из GitHub или локальной директории.** Claude видит, какие React-компоненты уже есть в проекте, какая архитектура, какой стиль — и генерирует дизайн, совместимый с реальностью.
- **Встроенные комментарии прямо на холсте.** Точечные правки кликом по элементу, а не описанием в чате.
- **Передача в Claude Code (hand-off bundle).** При экспорте Claude Design собирает архив: манифест со структурой компонентов, использованные на холсте дизайн-токены, иерархия слоёв и ассеты. Claude Code не просто копирует это в проект — читает манифест и пытается интегрировать результат в существующую кодовую базу.

Чтобы передача не превратилась в каскад правок, дизайн-систему нужно объявить декларативно в `CLAUDE.md` корня проекта до запуска: основной цвет, шрифт, компонентная библиотека (например, shadcn/ui без второй параллельной), CSS-подход (Tailwind only). Тогда Claude Code при интеграции опирается на ваш канон, а не пытается слить два дизайн-канона в один.

Когда выбирать этот путь над v0/Bolt/Lovable: у команды уже есть React-кодовая база (типичный сценарий после модулей про MCP-серверы и prompt-to-UI), нужна быстрая итерация визуала, важно сохранить замысел дизайна при переходе к коду и команда уже работает в экосистеме Anthropic. Ограничения исследовательской версии к моменту написания: совместная работа не многопользовательская, монорепы лагают при линковании, холст не такой точный, как в Figma, встроенные комментарии иногда теряются. Это вопросы, которые Anthropic обещает закрыть к выходу из исследовательской версии.

### Стратегия выбора инструмента

Краткий навигатор:

- Нужен компонент для существующего Next.js-проекта, бэкенд уже есть — **v0.dev**.
- Нужен прототип приложения с полным стеком за час, не жалко времени на ревизию кода и не пугает Supabase как платформа — **Bolt.new** или **Lovable**.
- Команда уже в экосистеме Anthropic, есть React-кодовая база, итерация дизайна с передачей в разработку с учётом специфики продакшна — **Claude Design → Claude Code**.
- Продакшн-логика должна работать строго предсказуемо, стек нестандартный, нужен полный контроль — **Cursor** или **Claude Code** поверх каркаса (Refine, или собственный Next.js-шаблон).

Главный антипаттерн — позволить инструменту определить архитектуру. Если Bolt сгенерировал приложение со схемой, которая удобна Bolt, а не вашему домену, через два месяца команда будет переписывать половину. Используйте AI-инструменты как ускоритель скаффолдинга, а не как авторитет в архитектурных решениях.

## Архитектура админки для скриптов и агентов

Минимальная архитектурная карта панели управления для скриптов и AI-агентов состоит из пяти частей: фронтенд (UI и состояние интерфейса), API Gateway (единая точка входа), очередь задач (асинхронное исполнение), хранилище состояния (Postgres + Redis) и слой мониторинга и логирования. Эта карта одинакова и для no-code-платформы поверх Retool, и для собственной сборки. Различия начинаются в деталях — как именно выполнять долгие задачи, как управлять запущенным агентом через UI и как защищать админ-эндпоинты.

### Очереди задач и фоновое исполнение

Запуск скрипта или агента из админки практически никогда не имеет права быть синхронным HTTP-вызовом: скрипт может работать минуты, агент — часы и дольше. Стандартная архитектура — отдельный пул воркеров, который читает задачи из очереди.

Выбор очереди привязан к языку:

- **Python-стек** — Celery (16 лет в продакшене, самая большая экосистема) или RQ (проще, без асинхронности). С 2025 года появился BullMQ Python — вариант, где async-архитектура даёт ощутимый прирост пропускной способности.
- **Node.js** — BullMQ. Около 10 тысяч задач в секунду на одном инстансе, развитая экосистема, бесплатные Bull Board или Taskforce.sh для дашборда очереди.
- **Долгие multi-step-процессы (часы и дни) с гарантированным восстановлением** — Temporal. Это другой класс инструмента: workflow-движок с гарантированным выполнением (durable execution), а не простая очередь.

Архитектурный антипаттерн — пытаться эмулировать workflow-движок цепочкой задач в обычной очереди. Если шаги имеют сложную ветвящуюся логику и должны переживать рестарты воркеров — Celery или BullMQ пишут код, который через полгода невозможно сопровождать. В таких случаях проще сразу взять Temporal или реализовать собственное отказоустойчивое состояние (durable state) в Postgres с явным конечным автоматом (state machine).

Обязательная инфраструктурная деталь — Dead Letter Queue для poison-сообщений. Без неё сбойная задача бесконечно откладывается воркером и блокирует очередь. Инцидент случается на третий месяц работы системы и сжирает несколько часов на разбор.

### Управление AI-агентами через UI: HITL и checkpoints

AI-агент, в отличие от скрипта, имеет жизненный цикл: запуск, шаги размышления и вызовов инструментов, точки, где разумно дать человеку проверить решение до его исполнения. В UI это превращается в набор операций: создать, запустить, остановить, продолжить с шага, инспектировать состояние, удалить. Реализация этих операций упирается в архитектуру самого агента.

**LangGraph** — фреймворк, в котором HITL встроен в модель исполнения, а не прибит сбоку:

- `interrupt_before` и `interrupt_after` — пауза до или после именованной ноды графа.
- `interrupt()` внутри ноды — пауза посередине, чтобы задать человеку конкретный вопрос (продолжать, изменить параметр, отказаться).
- `Command(resume=value)` — возобновление с тем же thread_id и состоянием, сохранённым в checkpointer.

Для продакшна важно использовать durable checkpointer — `PostgresSaver` или `RedisSaver`. `InMemorySaver`, который часто остаётся в туториалах, теряет состояние при рестарте процесса. Архивная очередь review-задач превращается в строки в Postgres, которые ждут человека столько, сколько нужно — час, сутки, неделю.

Чего LangGraph `interrupt()` не делает из коробки и что приходится решать на уровне приложения:

- **Тайм-ауты и эскалация.** Прерванный thread живёт в checkpointer бесконечно. Надо отдельно: фоновое задание, которое отбрасывает или эскалирует threads старше N часов.
- **Уведомления и журнал аудита.** Кому пришло на ревью, кто принял решение, в какой момент — отдельная таблица в БД и интеграция со Slack или email.
- **Out-of-band-аппрувы.** Если человек, принимающий решение, не у терминала и не в той же сессии — логичнее заменить `interrupt()` на вызов внешнего approval API, оставив структуру графа без изменений.

Хорошее правило: `interrupt()` подходит для in-session-сценариев (внутренний инструмент, где человек у экрана), а для процессов, требующих аппрува из другой команды или другого часового пояса — нужен отдельный сервис аппрувов с базой, тайм-аутами и эскалацией.

### Безопасность и контроль доступа

Внутренний инструмент — не значит безопасный по умолчанию. В топ-10 OWASP по безопасности API за 2023 год первые позиции заняты именно проблемами авторизации, а не аутентификации, и админ-панели — типичный источник этих проблем.

Главные классы уязвимостей, релевантных для админок:

- **API1:2023 — Broken Object Level Authorization (BOLA).** Эндпоинт принимает ID объекта в URL и не проверяет, принадлежит ли объект пользователю. Любой авторизованный пользователь может подменить ID и получить чужие данные. Защита — проверка владения на каждом эндпоинте плюс UUID вместо последовательных целочисленных ID как эшелонированная защита.
- **API2:2023 — Broken Authentication.** Долгоживущие токены без ротации, отсутствие ограничения частоты запросов на эндпоинте входа, JWT с алгоритмом `none`. Базовый чеклист: токены доступа не дольше 15 минут, токены обновления с ротацией, ограничение частоты запросов с экспоненциальной задержкой на эндпоинтах аутентификации, MFA для чувствительных операций.
- **API3:2023 — Broken Object Property Level Authorization.** Сериализатор отдаёт лишние поля объекта (массовое присвоение, избыточное раскрытие данных). Защита — явный белый список полей на входе и на выходе.
- **API5:2023 — Broken Function Level Authorization.** Эндпоинт `/admin/users/:id/delete` доступен любому аутентифицированному пользователю, потому что промежуточная проверка валидирует только аутентификацию, а роль не проверяет. Защита — отдельная промежуточная проверка роли на всех админских эндпоинтах, плюс журнал аудита всех привилегированных действий, плюс изоляция админ-API от пользовательского (отдельный поддомен, ограничения по IP).

Минимальный чеклист безопасности для админки агентов: короткий токен доступа, обязательная проверка роли на каждом административном эндпоинте, журнал аудита с полями кто/когда/что/над каким объектом, UUID вместо числовых ID, ограничение частоты запросов на эндпоинтах входа и запуска агента, белый список полей в сериализаторах.

## Реализация: прототип и продакшн

Один и тот же набор требований — запуск агента с параметрами, таблица активных задач, журнал в реальном времени, метрики токенов и стоимости — реализуется по-разному в зависимости от стадии. Прототип, который должен проверить идею за вечер, и продакшн-сборка, которая годами поддерживается командой, имеют разные сильные стороны и несовместимые антипаттерны.

### Прототип на Streamlit

**Streamlit** подходит, когда нужно превратить Python-скрипт в интерактивный интерфейс за час. Виджеты декларируются как переменные, состояние живёт в `st.session_state`, обновление UI происходит автоматически. Для панели запуска одного-двух агентов с парой параметров и таблицей результатов — оптимум по скорости.

Подводные камни Streamlit, которые на прототипе выглядят терпимо, а в продакшене ломают всё:

- `session_state` живёт пока открыта вкладка браузера и стоит соединение с сервером. Закрыли вкладку — всё потеряно. Перезапустился процесс — всё потеряно. Это не замена базе, а только состояние между перезапусками скрипта.
- Изменяемое состояние на уровне модуля — главный антипаттерн. Если в импортированном модуле объявлен `cache = {}`, он сохраняется не только между перезапусками скрипта одного пользователя, но и становится общим для всех пользователей. Закрытая дыра в данных, которую невозможно увидеть на прототипе с одним тестировщиком.
- Виджеты не сохраняют состояние между страницами в многостраничном приложении. При навигации значения сбрасываются. Если нужно сохранять — явный ключ в `session_state`.
- Streamlit не масштабируется горизонтально из коробки. Каждый воркер — отдельный процесс с изолированной памятью; закрепление сессий обязательно, состояние пользователя — в общем хранилище (Redis или Postgres).

Когда переходить со Streamlit на нормальную сборку: больше десятка одновременных пользователей, любые требования по аудиту, длительные фоновые задачи, нужны превью-окружения для веток, появляется потребность в SSO. До этих порогов Streamlit работает.

### Продакшн-сборка: Next.js + FastAPI с named SSE-events

Продакшн-сборка панели управления агентами выглядит типично: фронтенд на Next.js (App Router, Server Components, shadcn/ui), бэкенд на FastAPI, очередь на BullMQ или Celery, Postgres для персистентного состояния, Redis для сессий и pub/sub. Главный архитектурный вопрос — как доставлять прогресс агента в UI в реальном времени.

Для односторонней доставки от сервера к клиенту в подавляющем большинстве сценариев SSE (Server-Sent Events) предпочтительнее WebSocket: проходит через любые HTTP-прокси и балансировщики без специальной настройки, нативно поддерживается браузером через `EventSource`, не требует менеджмента дуплексного соединения. WebSocket нужен только там, где клиент должен прерывать сервер посередине ответа или нужен полный дуплекс (например, голос с аудио в реальном времени).

Ключевая практика SSE для AI-приложений — именованные события. Вместо одного потока фрагментов с `data: {...}` бэкенд отправляет типизированные события: `text_delta` (токен от LLM), `tool_start` (агент начал вызывать инструмент), `tool_result` (получил результат инструмента), `error`, `done`. На фронтенде `EventSource` слушает каждое событие отдельно и обновляет соответствующую часть UI. Это чище, чем встраивать поле `type` в тело сообщения и переключаться на клиенте.

Обязательные практики observability для SSE-потока: структурированные логи на открытие, закрытие, ошибку — со связкой `session_id`, `user_id`, количеством токенов и wall-clock latency. Стандартное HTTP-логирование SSE не видит, потому что соединение открыто минутами; без явного логирования отладка проблем в продакшене превращается в гадание.

Один аккуратный нюанс при использовании SSE через POST: браузерный `EventSource` поддерживает только GET. Для POST приходится использовать `fetch` с ручным чтением `ReadableStream`. Это типичная ошибка, через которую проходят все, кто пишет SSE первый раз.

## Workflow быстрой генерации UI

Отдельный продуктивный приём для разработчика, строящего админку поверх собственного React-стека — дать AI-инструменту прямой доступ к компонентной библиотеке через MCP. Самый зрелый пример — **shadcn MCP server**, который выставляет компоненты shadcn/ui как набор инструментов для агента.

Что меняется в workflow:

- Агент сам видит, какие компоненты доступны в shadcn/ui registry — без передачи списка вручную в промпт.
- Агент сам устанавливает нужный компонент в проект через `install_component`. Контекст агента отражает реально установленные компоненты, а не предполагаемые.
- Подключаются третьи и приватные registry. Внутренняя библиотека команды (например, `@acme/ui`) видна агенту наравне с публичной.

В админках это закрывает типичную боль: разработчик просит сгенерировать форму с табом, графиком и таблицей, агент пытается выдать всё через `<div>` и Tailwind, потому что не знает о готовых компонентах. С shadcn MCP агент сначала запрашивает список доступных компонентов, потом собирает форму из них.

Хороший паттерн на практике:

- Команда определяет свои составные компоненты поверх shadcn-примитивов (`ProfileCard`, `StatusBadge`, `AgentRunRow`) и публикует их во внутренний registry.
- Подключается shadcn MCP с указанием обоих registry — публичного и внутреннего.
- В чате с агентом команда формулирует требование к форме UI; агент сам выбирает между примитивами и обёртками, ставит то, чего не хватает, генерирует страницу из готовых блоков.

Базовый антипаттерн — позволять агенту устанавливать компоненты через CLI вручную мимо shadcn MCP. Контекст рассинхронизируется: агент думает, что поставил `Button`, фактически в проекте `Button` другой версии. Лучше — все установки через MCP-вызов, тогда манифест проекта и контекст агента совпадают.

## Мониторинг и observability агента

Стандартный мониторинг приложения, рассчитанный на HTTP-запросы со средним временем 50 миллисекунд, не видит агента: один вызов идёт минуту, делает десяток обращений к LLM и другим сервисам, поведение зависит от рантайма и недетерминированных выборок модели. Что считать нормальной задержкой и нормальной стоимостью — заранее неясно. Слой observability для агентов отличается от классического.

Базовые метрики, которые осмысленны для админ-панели агентов:

- **Распределение latency по типам шагов**: вызов LLM, вызов инструмента, запрос к БД. Обычно нужен P50 и P95 отдельно по каждому, иначе среднее съедает выбросы.
- **Стоимость в токенах и в долларах**. По модели, по пользователю, по дню. Один зацикленный агент способен сжечь дневной бюджет за час; оповещение по дневной сумме обязательно.
- **Количество шагов агента до завершения**. Резкий рост — сигнал нового сценария или цикла, которого не было раньше.
- **Качественные метрики** — онлайн-оценщики (LLM-as-judge или программные оценщики), которые считают сами по продакшн-трейсам и присваивают оценку по конкретным осям: безопасность ответа, соответствие формату, релевантность запросу.

Ключевое отличие observability для агентов от классической: трейсы — единственный надёжный артефакт того, что произошло, потому что кода поведения нет (поведение определяет модель в момент исполнения). LangSmith ушёл в эту нишу первым: помимо стандартных трейсов и метрик, у него есть Insights Agent — кластеризатор трейсов, который сам находит группы похожих сценариев, типичные причины ошибок и зоны нестабильности без явного запроса от инженера. Альтернатива для команд вне LangChain — TraceHawk и любые OpenTelemetry-совместимые системы; они не умеют группировать так же умно, но не привязывают команду к одному поставщику.

Антипаттерн, через который проходят все: писать в один проект трейсов и dev, и staging, и продакшн. К моменту первого инцидента в проде нужная информация теряется в потоке dev-запусков. Минимум — три отдельных проекта (`agent-dev`, `agent-staging`, `agent-prod`), плюс отдельный пул датасетов для оценки на каждый.

## Развёртывание

Раздел про развёртывание в админ-панелях исторически ориентируется на продакшн-масштаб: Docker, Kubernetes, Helm-чарты, CI/CD-конвейеры. Это всё применимо, когда у проекта есть стабильная команда и ожидания по надёжности. Но для прототипа Dashboard, который нужно показать команде и решить, идти ли дальше, эти варианты — избыточное усложнение.

Самый простой путь от localhost до продакшн-URL — Vercel:

- 30 секунд от `git push` до автоматического развёртывания и публичного URL. Не нужно поднимать Docker, не нужен реестр образов, не нужна отдельная команда DevOps.
- Превью-URL на каждую ветку. Удобно для демо заинтересованным сторонам без слияния в main — ссылка работает, а ветка живёт отдельно.
- Бесплатный тариф с лимитами, достаточными для большинства прототипов. Платить начинаете, когда становится понятно, что проект остаётся.
- Прямая интеграция с v0.dev. UI, сгенерированный в v0, разворачивается на Vercel в один клик.
- Serverless-маршруты API в Next.js — сделать заглушку MCP-эндпоинта прямо в приложении, не поднимая отдельный бэкенд. Для прототипа это сильно ускоряет демо.

Vercel не заменяет полноценное продакшн-развёртывание, когда становятся нужны: длинные фоновые задачи, авторизация и сессии в собственной БД с ограничениями данных, строгие SLO по холодному старту, вычислительно тяжёлые задачи. На этих границах прототип переезжает на Railway, Render, Fly.io или собственный Docker/Kubernetes-кластер.

Главный смысл этой опции — снять с разработчика психологический барьер: будто перед первым деплоем обязательно настроить всю продакшн-инфраструктуру. Для проверки идеи и демо команде работающий URL за полминуты лучше, чем идеальная инфраструктура через две недели.

## Best practices и Spec-Driven Development

Базовые правила построения админки уровня Senior-инженера сводятся к нескольким повторяющимся принципам.

Что делать:

- Начинать с MVP в 1–2 ключевые операции, выкатывать и собирать обратную связь. Не пытаться сразу описать всю будущую панель управления одним замахом.
- Опираться на существующие компонентные библиотеки (shadcn/ui, MUI, Chakra) вместо собственных визуальных решений. Дизайн — самое затратное по времени и самое неблагодарное место для кастомизации.
- Версионировать API между админкой и сервисами, поверх которых она работает. Без этого сменить сигнатуру в сервисе — значит обязательно сломать админку у части пользователей.
- Документировать интеграции в самой админке (`/admin/integrations` со списком и статусами), а не в README. README никто не читает, статус на странице — читают.

Чего избегать:

- Усложнять архитектуру до того, как появилась реальная нагрузка. Шардированный Postgres и отдельный кластер Redis для админки на 30 пользователей — это операционный долг, оправданный только постфактум.
- Игнорировать безопасность под предлогом internal-only. Через год у компании будут клиенты, партнёры и подрядчики с доступом к админке.
- Хардкодить креденшелы и конфигурацию. Vault, AWS Secrets Manager, Doppler — выбор есть, оправданий нет.
- Пропускать мобильную адаптивность. Дежурный инженер часто открывает админку с телефона.

### Spec-Driven Development для крупных админок

Когда Dashboard перерастает 5–6 компонентов, подход **один промпт — готовый UI** перестаёт работать. Агент теряет контекст: первые 3 компонента получаются нормальными, четвёртый ломается, пятый переписывает первые три, на десятом проще вернуться в Figma и переделать всё с нуля. Это не дефект конкретной модели — это структурный предел prompt-driven подхода для задач, не помещающихся в один сценарий.

Решение, которое к 2026 году стало индустриальной практикой Anthropic (research-plan-implement workflow), состоит из четырёх фаз:

- **Research.md.** Агент глубоко исследует существующую кодовую базу и пишет в персистентный markdown-файл всё, что узнал: какие компоненты есть, откуда берутся данные, где живёт состояние, какие соглашения по стилю. Без этого этапа агент делает уверенные правки поверх непонятого фундамента.
- **Plan.md.** Детальная пошаговая стратегия в отдельном markdown-файле: что строим, как разбиваем на компоненты, какой state management, какие API-контракты. План — это контракт между человеком и агентом.
- **Annotation cycle.** План открывается в редакторе, человек добавляет встроенные заметки прямо в документ: поправить здесь, отвергнуть подход там, добавить ограничение, уточнить домен. Итерация повторяется 1–6 раз. Правка markdown в десять раз дешевле и быстрее, чем переписывать сгенерированный код.
- **Implementation.** Когда план одобрен, агент выполняет его без остановок, с жёсткими директивами: не останавливаться до завершения, постоянно запускать typecheck, не добавлять лишних комментариев.

Ключевой принцип, по которому весь воркфлоу держится: архитектурный breakpoint — человек проверяет план, а не код. Если план хорош — по нему любая модель напишет приемлемый код. Если плохой — никакие 100 итераций кода ситуацию не спасут.

Антипаттерн, который этот подход закрывает: давать агенту сразу писать большой дашборд без утверждённого плана. Результат всегда один и тот же — каскад взаимоисключающих правок и финальный переписать-заново. Spec-Driven Development снимает этот класс проблем за счёт сдвига дискуссии из кода в спецификацию.

## Ключевые выводы

- Современные AI-инструменты позволяют собрать рабочую админку за 15–30 минут без глубоких фронтенд-знаний; реальная цена — оставшиеся 30% работы по архитектуре, безопасности и тестам, которые AI не закроет.

- Выбор между no-code-платформой, prompt-to-UI и кодом — про долгий горизонт и команду: Retool/Appsmith — для CRUD на месяцы; v0/Bolt — для прототипа; Claude Design → Claude Code и Refine — когда есть продакшн-кодовая база и команда готова поддерживать.

- HITL-агент в продакшне немыслим без durable checkpointer: `PostgresSaver` или `RedisSaver` превращает прерванный thread в строку в БД, которая ждёт человека столько, сколько нужно.

- Стандарт OWASP по безопасности API за 2023 год для админки — это в первую очередь авторизация, а не аутентификация: BOLA и Broken Function Level Authorization дают больше реальных инцидентов, чем украденные пароли.

- Vercel закрывает разрыв между localhost и продакшн-URL за 30 секунд для прототипа; Docker и Kubernetes уместны позже, когда станут реальные продакшн-нагрузки.

- Когда Dashboard перерастает 5–6 компонентов, Spec-Driven Development (Research → Plan → Annotate → Implement) спасает от каскада взаимоисключающих правок, в который превращается попытка получить готовый UI одним промптом.
