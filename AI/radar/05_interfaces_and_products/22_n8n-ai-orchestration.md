# AI-цепочки в n8n: low-code-оркестрация и граница выхода в код

n8n за год вырос из конструктора интеграций в платформу для AI-цепочек с агентами, памятью, роутингом и встроенным контролем качества. Вопрос при работе с ним не в том, умеет ли инструмент что-то, а в том, что каждая его возможность стоит: где холст экономит недели, а где закрытая абстракция и отсутствие юнит-тестов флоу становятся фиксированной платой.

## Место n8n в стеке

Ниша n8n — прототип и нагрузка уровня небольшого бизнеса: там, где важнее быстро проверить гипотезу, чем сразу строить надёжную систему.

На срез 30 июля 2026 года актуальна ветка 2.x: 2.33.x в бете, стабильная линия — 2.32.x, около 199 тысяч звёзд на GitHub. Темп релизов почти еженедельный, и это важно практически: возможность, которой не было месяц назад, могла появиться, а версия из чужой инструкции — устареть.

### Что появилось в первой половине 2026

- **Встроенный веб-поиск для агентов** (версия 2.25, 2 июня 2026): поиск через собственные инструменты провайдера модели, при их отсутствии — резерв на Brave Search или self-hosted SearXNG. Важная оговорка о том, **где** он живёт: это не опция cluster-ноды AI Agent, а возможность отдельного продукта n8n Agents (Agent Builder) — настраивается в панели Advanced агента, вызывается из флоу узлом Message an Agent. В схеме `nodes-langchain.agent` опции веб-поиска нет.
- **Передача бинарных PDF напрямую модели** (версия 2.28, около 23 июня 2026): переключатель Automatically Passthrough Binary PDFs, конвертация в base64, настраиваемый лимит по умолчанию 50 МБ.
- **Узел Message an Agent v2** (релиз 2.31.0 от 14 июля 2026): вторая версия узла обращения к агенту, используется по умолчанию.
- **Human-in-the-loop на уровне инструментов**: опасный вызов инструмента ставит рабочий процесс на паузу до явного одобрения человека.

Модельных провайдеров добавили встроенными узлами: Moonshot Kimi (по умолчанию kimi-k2.5) и Alibaba Cloud Model Studio с семейством Qwen — последний введён в 2.25 под этим именем, но в текущих версиях узлы в панели называются Qwen Cloud и Qwen Cloud Chat Model, и по старому имени поиск ничего не найдёт.

### Цена ошибки в выборе уровня инструмента

Ошибиться можно в обе стороны.

Ошибка первая — писать на кодовом фреймворке то, что живёт неделю. Прототип разбора заявок в n8n собирается за день против недели собственной обвязки: демо заказчику раньше, гипотеза дешевле, выброшенный код не жалко.

Ошибка вторая — тянуть в n8n систему с ветвящейся логикой на десятки узлов, версионированием промптов и юнит-тестами. Флоу превращается в нечитаемую диаграмму, ревью и откаты которой трудоёмки. Возможности для такой системы у n8n есть; цена — в сопровождении, а не в отсутствии функций.

Смягчает обе ошибки правильно проведённая граница инструментов. MCP-сервер одинаково вызывается и из n8n, и из кодового оркестратора — если бизнес-логика живёт за контрактом MCP, а не внутри флоу, миграция становится заменой оркестратора, а не переписыванием интеграций.

## AI Agent node и cluster-ноды

### Устройство агентного узла

Cluster-ноды — это архитектура агента в n8n: корневой AI Agent node плюс дочерние узлы (Chat Model, Memory, Tools), подключаемые специальными портами. На уровне реализации — абстракции LangChain: с версии 1.82.0 все агентные узлы работают как Tools Agent, то есть реализуют tool-calling LangChain. Минимум одна tool-нода обязательна.

Инструментом агента может быть почти что угодно: HTTP Request Tool, Code Tool, векторное хранилище, другой рабочий процесс через Call n8n Sub-Workflow Tool, MCP Client Tool. Агент оркестрирует то, что команда уже построила, а не требует переписывать интеграции под себя.

Конфигурация узла — это System Message, выбор модели и её параметров. Вывод агента — либо свободный текст, либо структура: включив Require Specific Output Format, вы подключаете Structured Output Parser и получаете строгий JSON для передачи следующему узлу.

Отдельно — human-in-the-loop. Возможность остановить агента на опасном вызове реализована не через опцию Require Approval (такого пункта в узле нет), а через шаг Human review в панели инструментов: выбирается канал одобрения — Chat, Slack, Telegram, Teams, Gmail и другие — и к нему подключаются инструменты, требующие подтверждения.

### Тонкая настройка поведения

- **Max Iterations** (по умолчанию 10) ограничивает цикл «рассуждение — вызов». Это защита от бесконечного перебора инструментов и от неконтролируемого счёта за токены.
- **Return Intermediate Steps** отдаёт трассу вызовов инструментов в выходные данные — по сути единственный способ понять, что агент решал внутри флоу.
- **Резервная модель** (переключатель Enable Fallback Model, в схеме узла — `needsFallback`) подхватывает запрос при отказе основной; вместе с повторами узла это даёт базовую отказоустойчивость без единой строки кода.

Правило, не привязанное к конкретной настройке: между агентами в цепочке ходит только структурированный JSON. Свободный текст на границах узлов накапливает искажения по цепочке.

### Цена абстракции

AI Agent node делает много и столько же скрывает:

- **Агентный цикл закрыт.** Стратегию рассуждения, формат внутренних промптов и версию LangChain выбирает n8n. Переопределить отдельный шаг цикла нельзя — только принять целиком или выйти в Code-ноду и собрать логику руками.
- **Отладка ограничена трассой** intermediate steps. Пошагового отладчика внутреннего цикла нет; гипотезы проверяются перезапуском всего флоу.
- **Детерминированного прогона нет.** Юнит-тест на отдельный узел не написать, регрессии ловятся только прогонами.

Формула цены: агент в n8n собирается за час, но контроль над циклом, версиями и тестируемостью — фиксированная плата за скорость. Для прототипа она пренебрежима, для ядра продукта — нет.

## Память диалога

| Узел памяти | Где хранит | Когда брать |
|---|---|---|
| Simple Memory | буфер в памяти инстанса, последние N обменов текущей сессии | прототип, один воркер, ноль настройки; гибнет с перезапуском, не общий между воркерами |
| Postgres Chat Memory | внешняя БД PostgreSQL | продакшн: переживает перезапуск и масштабирование |
| Redis Chat Memory | внешний Redis | то же, где Redis уже в стеке |

Постоянные варианты не сводятся к Postgres и Redis: те же гарантии дают сервисы вроде Motorhead или Zep.

Нить диалога выбирает ключ сессии: по идентификатору пользователя, тикету или каналу. В интерфейсе memory-нод это поля **Session ID** и **Key** — подписи Session Key там нет. Один ключ — одна история; без корректного ключа реплики разных пользователей смешиваются в один буфер.

Память — это тоже контекстный бюджет. Длинное окно тянет всю историю в каждый вызов модели, и за это растёт счёт за токены. Ограничение размера окна подбирается по цене токенов, а не по максимуму, который допускает узел.

### Долгоживущее состояние выносится руками

Память агента хранит реплики. Статус заявки, счётчик попыток, накопленный контекст решения — это не реплики, а отдельные записи во внешней БД, которые флоу читает и пишет явными узлами. Возможность хранить состояние у n8n есть; цена — в том, что долгоживущее состояние вы моделируете и сопровождаете вручную.

Рабочий паттерн: состояние процесса — в Postgres или Data Store, в память агента — только диалоговый контекст. Смешение двух видов состояния в одном буфере памяти — классическая причина загадочных регрессий после перезапуска: часть контекста исчезла, а часть осталась.

Хранилищем состояния может быть и MCP-сервер проекта. Тогда одно и то же состояние видят n8n-флоу, IDE-агент и кодовый сервис — состояние живёт за контрактом, а не внутри конкретного оркестратора.

## Циклы, ветвление и роутинг

### Loop и обратные связи

Loop Over Items (Split in Batches) обрабатывает коллекцию порциями: размер задаётся параметром Batch Size, у узла два выхода — **loop** и **done**. Это типовой паттерн пакетной обработки.

Обратные связи строятся соединением выхода узла на более ранний вход. Цикл-до-условия — генерация, проверка, доработка — выражается прямо на холсте.

Цена у циклов эксплуатационная, и её надо закладывать заранее:

- Каждая итерация раздувает данные execution — весь JSON каждого шага сохраняется в лог прогона.
- Обратные рёбра делают диаграмму нечитаемой уже на нескольких витках: глазами трассу не собрать.
- Циклу всегда нужен жёсткий лимит итераций. Визуальный бесконечный цикл расходует токены так же, как кодовый, только заметить его труднее.

Больше двух вложенных уровней цикличности — сигнал, что топология просится в код, где цикл выражается явно и тестируется.

### Switch и динамический выбор инструментов

Роутинг в n8n двух природ: детерминированный узлами и вероятностный моделью.

- **Детерминированный роутинг.** Switch ветвит поток по правилам (значение поля, выражение) на несколько выходов, есть Fallback Output; IF — бинарный. Правила дёшевы и предсказуемы: им отдают всё, что можно формализовать.
- **LLM-роутинг.** Text Classifier или лёгкий AI Agent со structured output выбирает ветку по смыслу. Дороже и вероятностнее, зато работает по неструктурированному тексту.
- **Динамический выбор инструментов.** Агент сам решает, какой инструмент вызвать, а параметры вызова заполняет функция `$fromAI()` (доступна только для tools у AI Agent). У неё есть исключение: с Code Tool и другими не-tool cluster-суб-нодами `$fromAI()` **не работает** — а Code Tool при этом штатно подключается к агенту как инструмент. Сузить набор инструментов на стороне агента нечем, кроме как не подключать лишние узлы; фильтр по инструментам есть только у MCP Client Tool.

Правило проектирования: сначала правило, потом классификатор, потом агент. Каждый шаг вверх добавляет стоимость вызова и неопределённость поведения — и одновременно расширяет класс входов, которые роутинг вытянет.

## MCP в n8n: две стороны протокола

n8n умеет быть и MCP-сервером, и MCP-клиентом.

### MCP Server Trigger — рабочий процесс как сервер

Узел MCP Server Trigger превращает рабочий процесс в MCP-сервер. Он публикует два URL — тестовый и продакшн, — по которым MCP-клиенты видят и вызывают tool-ноды, подключённые к триггеру. Транспорты — Streamable HTTP и SSE; stdio узел не поддерживает.

В отличие от обычных триггеров, MCP Server Trigger не передаёт данные дальше по флоу. Он исполняет только присоединённые к нему tool-ноды; другие рабочие процессы подключаются как инструменты через Call n8n Sub-Workflow Tool.

stdio-клиенты вроде Claude Desktop подключаются через мост `mcp-remote` — Node.js-прокси, который соединяет клиента, работающего только по stdio, с удалённым сервером по HTTP/SSE и пробрасывает заголовок авторизации. Сама авторизация узла — bearer или заголовки в учётных данных.

Практический сценарий: автоматизация, собранная в n8n, становится инструментом IDE-агента — по тому же протоколу, что у кодового сервера, без единой строки кода.

### MCP Client Tool — внешние серверы в агенте

MCP Client Tool — дочерний узел, который подключает к AI Agent любой внешний MCP-сервер. Указывается эндпоинт, аутентификация — Bearer, произвольные заголовки или OAuth2. С версии узла 1.2 транспорт по умолчанию — HTTP Streamable, а SSE помечен как deprecated.

Ключевое ограничение, из-за которого ломается первая же попытка подключить свой сервер: **узел ходит по HTTP-эндпоинту и stdio не умеет**. Сервер, работающий по stdio, подключить напрямую нельзя — нужно либо добавить ему транспорт Streamable HTTP (в SDK это отдельная строка запуска, логика не меняется), либо поставить между ними мост `mcp-remote`. Ограничение «только для self-hosted» тут ни при чём: это обычная cluster-нода ядра, и на Cloud она доступна. Проблема Cloud в другом — до `localhost` на вашей машине облако не достучится, поэтому сервер должен быть виден из интернета.

Фильтр Tools to Include (All / Selected / All Except) — это параметр именно MCP Client Tool (`include`), а не общая настройка агента: он ограничивает, какие инструменты конкретного сервера видит агент. Меньше инструментов в контексте — меньше ошибочных выборов и дешевле каждый вызов модели.

Архитектурное следствие: бизнес-логика живёт в MCP-сервере, n8n отвечает только за оркестрацию. При переезде на кодовый оркестратор меняется оркестратор, интеграции остаются на месте.

Историческая деталь про узлы сообщества. MCP-клиенты долго поставлялись узлами сообщества, и их использование как инструментов требовало переменной `N8N_COMMUNITY_PACKAGES_ALLOW_TOOL_USAGE=true` — частой причины, почему установленный узел не был виден агенту. В ядре n8n этот флаг убрали в версии 1.85.0 (март 2025): узлы сообщества как инструменты включены по умолчанию. README отдельных пакетов сообщества до сих пор называет переменную обязательной — это устаревшая инструкция.

### MCP-сервер на уровне инстанса

Появился в версии 1.120 (анонс 18 ноября 2025 года) в статусе beta. Это одна точка подключения ко всей инсталляции: внешний агент ищет рабочие процессы, запускает их и читает статусы прогонов. Метку предварительной версии сняли в 2.31 (14 июля 2026 года).

Набор инструментов рос релизами и помечен версиями:

- **`search_nodes`** (с 2.12) — поиск узлов по каталогу.
- **`get_execution`** (с 2.12) — чтение статуса и данных прогона по executionId.
- **построение и правка рабочих процессов** (с 2.13).
- **`test_workflow`** (с 2.15) — прогон флоу на закреплённых данных без внешних вызовов.

Это не весь набор: там же `search_workflows`, `get_workflow_details`, `execute_workflow`, `search_executions` и инструменты работы с data tables. Перечень меняется релизами быстрее, чем любой конспект.

Отличие от MCP Server Trigger принципиальное. Триггер публикует один флоу с вручную набранными tools; сервер на уровне инстанса — централизованный доступ с общей авторизацией (OAuth2 или токен доступа) и включением по каждому рабочему процессу.

## Встроенные Evaluations

### Как устроены

Механика: датасет вида «вход — эталон», прогон рабочего процесса по каждому кейсу, оценка результата по метрикам. Категории метрик:

- **AI-based** (LLM-as-a-Judge) — Correctness, Helpfulness по шкале 1–5.
- **String similarity** — близость строк, 0–1.
- **Categorization** — совпадение категории, 0 или 1.
- **Tools used** — использование ожидаемых инструментов, 0–1.
- **Custom** — собственная метрика.

Страница прогона показывает карточки метрик с процентами и дельтой к прошлому прогону, статусы кейсов в реальном времени, перезапуск упавших и ссылки на executions.

Результаты доступны через публичный API с версии 2.30 (июль 2026). Три нюанса, которые решают, соберётся ли CI-контур:

- **API 2.30 — только на чтение** (три эндпоинта); запуск и отмена прогонов появились позже. Собрать отчёт можно, а запустить прогон из пайплайна — ещё нет.
- **Ключам нужны два scope**, `testRun:list` и `testRun:read`. API-ключи, созданные до 2.30, их не имеют, и такие ключи нужно пересоздать.
- **Метрическая оценка доступна на тарифах Pro и Enterprise** — именно на этих двух, Business в список не входит. На зарегистрированной Community Edition и на Starter метрики работают на одном рабочем процессе; на незарегистрированной Community их нет вовсе.

Ещё лимит прямо про цену владения: **параллельность прогона тест-кейсов зависит от тарифа** — Community и Pro дают 1, Business — 3, Enterprise — 5. На self-hosted это переопределяется переменной `N8N_CONCURRENCY_EVALUATION_LIMIT`. На датасете в сотню кейсов разница между 1 и 5 — это разница между кофе и обедом.

Практика: до правки промпта классификатора зафиксируйте датасет из 20–30 размеченных заявок; после правки сравнивайте метрики, а не впечатления.

### Границы встроенного eval-контура

- **Уровень детализации — только весь рабочий процесс.** Изолированно проверить один узел или один промпт нельзя; юнит-уровня нет. Это та же закрытость агентного цикла под другим углом.
- **LLM-судья наследует проблемы LLM-судей** — смещения, нестабильность оценок. Калибровка судьи против ручной разметки остаётся на инженере.
- **Датасеты и метрики живут внутри n8n.** Переносимость в другой оркестратор ограничена.

Но базовое правило действует уже сейчас: AI-флоу без тестового набора — это флоу, качество которого никто не измерял.

## Пример: пайплайн обработки заявок

### Архитектура

Пять ступеней, каждая — на подходящем ей узле:

- **Приём.** Webhook, Chat Trigger или почтовый триггер нормализует заявку в единый JSON: id, канал, текст, автор, время.
- **Классификация.** Text Classifier или лёгкий агент со structured output размечает категорию, срочность и язык; результат пишется в состояние заявки.
- **Роутинг.** Switch по категории: типовые вопросы уходят агенту первой линии, платёжные и юридические — сразу человеку.
- **Обработка.** AI Agent с инструментами готовит ответ; уверенность ниже порога уводит в ветку эскалации. Поиск по базе знаний подключается как инструмент — векторное хранилище, HTTP Request Tool к своему сервису или MCP Client Tool. Встроенного веб-поиска у этого узла нет.
- **Эскалация.** Шаг Human review (канал Chat, Slack или почта), уведомление ответственному и запись полного контекста в БД — человек видит трассу, а не начинает с нуля.

### Что делает пайплайн живучим

Разницу между демо и рабочим прототипом дают инженерные детали, которых на схеме не видно:

- **Строгие границы.** Каждая граница между ступенями — JSON со схемой; классификатор возвращает enum категорий, а не свободный текст, и Switch не ломается о синоним.
- **Лимиты по умолчанию.** Max Iterations у агентов, таймауты внешних вызовов, ветка Error Workflow на падение — заявка не исчезает молча, а попадает в очередь разбора.
- **Внешнее состояние.** Данные заявки и статусы — в Data Store или Postgres. Повторный запуск флоу идемпотентен, статистика по категориям доступна без ручного разбора логов прогонов.
- **Evaluations поверх пайплайна.** Датасет реальных заявок с эталонными категориями и действиями; прогон после каждого изменения промптов делает регрессию видимой до продакшна.

Те же четыре решения переносятся на любой оркестратор.

## Когда n8n достаточно, а когда пора в код

**Переход в код запускает превышение цены возможности, а не её отсутствие.** Инструмент умеет почти всё, что нужно AI-цепочке; вопрос в том, сколько стоит каждая возможность на вашей нагрузке.

### Что n8n умеет — и чего это стоит

| Возможность | Есть в n8n | Цена владения |
|---|---|---|
| Циклы | Loop Over Items, обратные рёбра | раздувание данных execution и падение читаемости при вложенности |
| Память | memory-узлы + внешние БД | долгоживущее бизнес-состояние выносится и сопровождается вручную |
| Роутинг и динамические инструменты | Switch, IF, Text Classifier, `$fromAI` | вероятностные ветки трудно покрыть тестами |
| Контроль качества | встроенные Evaluations | детализация только целого флоу, юнит-уровня нет |
| Версионирование | история workflow, Git-интеграция (от Business) | не полноценный git-flow с ревью диффов на всех тарифах |
| Обмен данными между узлами | JSON в логе execution | крупные бинарные объёмы требуют внешнего хранилища |

Системный предел, который в ячейку не вынести: детерминированного прогона и юнит-тестов отдельного флоу нет, регрессии ловятся прогонами датасета, а не изолированным тестом узла.

### Сигналы, что пора в код

- **Число инструментов у агента.** На практике поведение агентного узла начинает сыпаться уже после четырёх-пяти подключённых инструментов — заметно раньше, чем упирается топология флоу. Это первый сигнал, который вы увидите.
- **Топология.** Больше \~20 узлов с ветвлениями, вложенные циклы, полноценная машина состояний — диаграмма перестала быть документацией.
- **Нагрузка.** Порог по нагрузке наступает раньше порога по топологии: уже на 10–20 одновременных запросах стоит считать кодовое решение. Это два независимых предела, и упрётесь вы в тот, что ближе.
- **Процесс разработки.** Нужны код-ревью диффов логики, юнит-тесты узлов, поэтапная раскатка промптов — low-code-артефакты сопротивляются каждому пункту.
- **Производительность и SLA.** Жёсткие бюджеты задержки, тонкий контроль повторов и параллелизма, потоковая обработка.
- **Команда.** Над логикой работают три и более инженера одновременно — конфликт на общем холсте больнее merge-конфликта в git.
- **Экономика.** Цена Cloud-тарифа за executions превысила цену небольшого кодового сервиса — считать калькулятором, а не по ощущениям.
- **Соотношение поддержки и развития.** На поддержку уходит больше времени, чем на развитие. Мерить предлагается буквально: две недели трекинга часов на инциденты против часов на фичи.

Два наблюдения, которые дают ранние индикаторы:

- **Low-code перестаёт быть low-code раньше, чем кажется.** В сколько-нибудь серьёзном кейсе Code-нода появляется почти всегда: разбор JSON, пагинация, подписи запросов. Как только Code-нод становится больше, чем интеграционных, флоу уже наполовину код, просто в неудобной среде.
- **Типовая траектория команд** — прототип на визуальном оркестраторе, затем переписывание на код-сервис. В enterprise это прямо оформляют как стратегию: POC на n8n, продакшн на своём сервисе.

### Что теряется при выходе в код

Список выше — только цена. За визуальным оркестратором команды остаются не из-за скорости прототипа.

> Визуальный лог прогонов — один из самых сильных отладочных инструментов в классе: видно каждый шаг, каждый вход и выход, без настройки трассировки. И это единственный формат, в котором процесс понятен нетехническому человеку. Схему из ста узлов заказчик прочитает, а трассу агента в консоли — нет.

Отсюда более честный критерий выхода, чем чисто ценовой:

> Уходим в код, когда цена сопровождения превысила цену кода **и** когда наблюдаемость перестала быть аргументом — то есть за флоу больше никто не смотрит руками.

### Гибрид как норма

Зрелый паттерн — не выбор одного из двух, а n8n и код в одной системе.

Прямой паттерн: n8n держит интеграционную обвязку (триггеры, вебхуки, уведомления, повторы по расписанию), код — плотную агентную логику; стык между ними — HTTP или MCP.

Обратный паттерн: кодовый сервис вызывает n8n-workflow как инструмент через MCP Server Trigger — уже собранные интеграции не переписываются.

## Лицензия и тарифы

### Fair-code: Sustainable Use License

n8n распространяется под Sustainable Use License (модель fair-code), применённой с 17 марта 2022 года при переходе с Apache 2.0 плюс Commons Clause. Это source-available, но не open source по определению OSI, и различие имеет практические следствия:

- Свободное использование и модификация для внутренних бизнес-целей разрешены. Запрещено продавать n8n как хостинг-сервис или white-label без коммерческого соглашения.
- Для типового внутреннего продукта ограничение не срабатывает: автоматизация собственных процессов и коммерческий консалтинг по n8n разрешены явно.
- Enterprise-функции (файлы с `.ee` в имени: SSO/SAML, внешние секреты, multi-main-масштабирование) — под отдельной платной лицензией даже в self-hosted.
- Community Edition — полнофункциональное ядро: неограниченные executions и пользователи, весь набор интеграций и AI-возможности. Карточка репозитория называет 400+ интеграций, тело README — 1500+; на маркетинговую цифру полагаться не стоит. Бесплатная регистрация self-hosted-инстанса по email дополнительно открывает папки и отладку в редакторе.

### Тарифы и модель executions

Единица тарификации — прогон целого рабочего процесса независимо от числа шагов. Против модели оплаты за задачу у конкурентов вроде Zapier это выгодно для длинных флоу: десять узлов в потоке — всё ещё один execution.

| Тариф | Цена (годовая) | Executions/мес | Параллельных | Что добавляет |
|---|---|---|---|---|
| Starter | €20/мес | 2 500 | 5 | базовый Cloud |
| Pro | €50/мес | 10 000 | 20 | больший объём |
| Business | €667/мес | 40 000 | не раскрыта | SSO/SAML/LDAP, Git-версионирование, окружения; лицензия на self-hosted, а не Cloud-тариф |
| Enterprise | по договору | по договору | 200+ | корпоративные функции |
| Self-hosted Community | бесплатно | без лимита | — | эксплуатация на команде |

Для Business параллельность на карточке тарифа не указана, а вторичные источники расходятся (от 30 до 200+), поэтому опираться на конкретное число не стоит. Цены сверены на 30 июля 2026 года.

Важная поправка к чтению таблицы: **Business не продаётся на Cloud** — это лицензия на self-hosted. Остальные строки — Cloud-тарифы, и из-за этой разницы прыжок €50 → €667 стоит понимать шире: вместе с SSO покупается ещё и право на поддерживаемый self-host.

Три вывода:

- Помесячная оплата примерно на 17–20% дороже годовой: Starter €24 против €20, Pro €60 против €50, Business €800 против €667.
- Self-hosted Community бесплатен при любых объёмах; продакшн-нагрузку тянет от одного VPS за \$20–30 в месяц (рыночная оценка стоимости сервера).
- Разрыв €50 → €667 между Pro и Business — ценовой обрыв, который проходят ради соответствия требованиям (SSO, Git, окружения) и права на поддерживаемый self-host, а не ради лимитов executions.

Компромисс прямой: Cloud снимает эксплуатацию, но вводит лимиты executions и хранения; self-hosted работает без ограничений, но обновления, бэкапы и мониторинг — на команде.

## Итоги

- n8n оправдан на прототипе и нагрузке уровня небольшого бизнеса: линейный пайплайн собирается за день. Всё, что переживёт прототип, прячьте за контрактом MCP, чтобы миграция была заменой оркестратора, а не переписыванием.
- AI Agent node даёт агента за час, но закрывает цикл рассуждений, версию LangChain и тестируемость — фиксированная плата за скорость, пренебрежимая для прототипа и неприемлемая для ядра продукта.
- В память агента кладите только диалог; статус, счётчики и накопленный контекст выносите во внешнее хранилище, иначе перезапуск станет источником невоспроизводимых багов.
- Роутинг стройте по лестнице: правило (Switch/IF), затем классификатор, затем свобода вызова у агента — каждый шаг вверх добавляет цену и вероятностность.
- Через MCP n8n взаимозаменяем с внешним кодом в обе стороны: MCP Server Trigger публикует флоу как инструмент, MCP Client Tool и сервер на уровне инстанса втягивают внешние серверы в агента.
- Evaluations используйте как регрессионный контур уже на прототипе, но не ждите от них юнит-уровня и переносимости.
- Переход в код запускает превышение цены возможности, а не её отсутствие. Раньше всего срабатывают два сигнала, которых обычно не ждут: четыре-пять подключённых инструментов у агента и 10–20 одновременных запросов.
- Цена — только половина решения. Визуальный лог прогонов остаётся сильнейшим отладочным инструментом в классе и единственным форматом, понятным нетехническому заказчику. Уходите в код, когда цена сопровождения превысила цену кода **и** за флоу больше никто не смотрит руками.
- Community Edition закрывает всю инженерию бесплатно, Cloud продаёт снятую эксплуатацию, а Business (€667) — это уже не Cloud-тариф, а лицензия на поддерживаемый self-host с SSO и Git.
