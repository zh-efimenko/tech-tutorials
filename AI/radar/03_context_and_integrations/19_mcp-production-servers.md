# Продакшн MCP-серверы: протокол, контракт tools, состояние и авторизация

Демо-сервер собирается за час. Продакшн-сервер отличается от него не объёмом кода, а тремя слоями: продуманным контрактом tools, явным управлением состоянием и авторизацией. Без них сервер ломается предсказуемо, а не случайно.

## Почему ставка на MCP оправдана

Anthropic анонсировала Model Context Protocol в ноябре 2024 года, а 9 декабря 2025 года передала его в Agentic AI Foundation под управление Linux Foundation. Со-учредители фонда — Anthropic, Block и OpenAI; среди поддерживающих компаний Google, Microsoft, AWS, Cloudflare и Bloomberg. Управление протоколом больше не принадлежит одному вендору.

Динамика показательна: на декабрь 2025 года суммарные загрузки Python- и TypeScript-SDK составляли свыше 97 млн в месяц, на конец июля 2026 года — свыше 400 млн, рост вчетверо за семь месяцев. Публичных серверов было свыше 10 000, стало около 18 700 в одном только официальном реестре. MCP как первоклассную интеграцию поддерживают Claude, ChatGPT, Cursor, Gemini, Microsoft Copilot и VS Code.

Все эти числа живут неделями, поэтому переносить их куда-либо имеет смысл только вместе с датой среза.

Следствие для инженера прямое: один контракт tools делает MCP-сервер единой точкой интеграции продукта со всеми AI-клиентами сразу, а не отдельным адаптером под каждого вендора.

### Цена поверхностного сервера

Сервер уровня демо отказывает в продакшне по трём предсказуемым причинам:

- **Небрежные описания tools.** Модель вызывает не тот инструмент или не вызывает нужный. По аудиту PolicyLayer (снимок на июль 2026 года, 32 820 серверов и 517 973 tools) 96,4% описаний не предупреждают модель о последствиях вызова — и агент выбирает `delete_rows` по совпадению глагола в запросе.
- **Состояние в памяти процесса.** Сервер работает на ноутбуке и ломается за балансировщиком: любой повтор запроса уходит на другой инстанс, где контекста нет.
- **Отсутствие авторизации.** По аудиту Astrix (октябрь 2025 года, 5 200+ открытых GitHub-репозиториев) OAuth используют лишь 8,5% серверов; такой сервер нельзя выставить наружу.

## Архитектура протокола

### Трёхзвенная модель и JSON-RPC 2.0

MCP описывает обмен между тремя ролями. **Хост** — приложение с LLM (Claude Code, Cursor, ChatGPT). **Клиент** — коннектор внутри хоста, по одному на каждый сервер. **Сервер** — процесс, который отдаёт tools, resources и prompts.

Все сообщения — JSON-RPC 2.0: запросы с полем `id`, ответы на них и нотификации без `id`. А вот жизненный цикл поверх сообщений в действующей ревизии выглядит иначе, чем описывают руководства годичной давности: **рукопожатия `initialize` больше нет**.

Согласование возможностей теперь работает так:

- **Клиент ничего не объявляет заранее.** Версия протокола и возможности клиента едут в поле `_meta` каждого запроса — ключ `io.modelcontextprotocol/protocolVersion`.
- **Сервер идентифицируется в `_meta` каждого результата**, а свои возможности отдаёт по отдельному RPC `server/discover`. Этот метод сервер обязан реализовать (MUST). Клиент вправе `server/discover` не вызывать и сразу слать рабочий запрос.
- **При несовпадении версий поведение явное.** Сервер отвечает `UnsupportedProtocolVersionError` со списком поддерживаемых версий; клиент осознанно повторяет запрос с совместимой версией либо показывает ошибку. Автоматического плавного перехода протокол не обещает.

Версия протокола — строка-дата: 2025-06-18, 2025-11-25, 2026-07-28. Действующая (Current) ревизия — **2026-07-28**; 2025-11-25 имеет статус Final, то есть это закрытая прошлая спецификация. Путать эти статусы опасно: сервер, написанный по Final-ревизии как по актуальной, не реализует обязательный `server/discover`.

### Транспорты

| Транспорт | Как работает | Где применяется | Цена |
|---|---|---|---|
| stdio | сервер — дочерний процесс клиента, обмен через stdin/stdout | локальные серверы в Claude Desktop, Claude Code, Cursor | нулевая сетевая поверхность и прямой доступ к локальной ФС и БД, но не масштабируется на команду |
| Streamable HTTP | один HTTP-эндпоинт, отдаёт и обычный ответ, и поток | remote-серверы; обязателен для приложений и коннекторов внутри ChatGPT | требует авторизации и инфраструктуры, но превращает сервер в общий сервис |
| SSE (наследие) | отдельный транспорт для потоковых ответов | клиенты ещё принимают, новые серверы не строят | мост от stdio-клиента к HTTP-серверу даёт прокси `mcp-remote` |

Выбор транспорта — это выбор между личным инструментом и общим сервисом команды.

Две оговорки, о которые спотыкаются на практике:

- **У HTTP+SSE самое короткое окно депрекации** — три месяца после того, как соответствующее предложение достигнет статуса Final, а не двенадцать месяцев, как у Roots, Sampling и Logging. Планировать миграцию с SSE надо отдельно от остальных устаревших возможностей.
- **ChatGPT принимает stdio, но не везде.** Требование HTTPS действует для приложений и коннекторов внутри самого ChatGPT. Десктопное приложение, Codex CLI и IDE-расширение поддерживают stdio явно — в конфигурации есть выбор транспорта с полями `command`, `args`, `env`, `cwd`.

### Что принесла ревизия 2025-11-25

Предыдущая ревизия закрыта и больше не меняется. Читать её стоит как слой обратной совместимости — на ней говорят уже развёрнутые клиенты.

- **Tasks (экспериментально).** Любой запрос можно обернуть в задачу со статусами `working` / `input_required` / `completed` / `failed` / `cancelled`.
- **Client ID Metadata Documents (CIMD).** Идентификация клиента по URL-документу метаданных вместо обязательной динамической регистрации.
- **URL mode elicitation.** Чувствительные сценарии (ввод учётных данных, оплата) выносятся в браузер пользователя.
- **Extensions.** Формальный механизм необязательных расширений с независимым версионированием, включая client credentials для machine-to-machine и Cross App Access для корпоративных IdP.
- **Sampling получил поддержку tools** — сервер стал вправе запускать собственный агентный цикл на токенах клиента.

### Релиз 2026-07-28: stateless-first и большая чистка

Крупнейшая ревизия протокола с момента запуска, уже действующая: кандидат зафиксирован 21 мая 2026 года, финал опубликован 28 июля 2026 года.

- **Вывод из употребления трёх механизмов.** Roots, Sampling и протокольный Logging объявлены устаревшими: работают ещё минимум год, но новые серверы их не используют. Миграции — директории через параметры tools, LLM-вызовы напрямую через API провайдера, логи в stderr или OpenTelemetry.
- **Протокол становится stateless и бессессионным.** Удалены `initialize` и идентификатор сессии; согласование возможностей переехало в обязательный `server/discover` и поле `_meta`. Состояние теперь — явные непрозрачные state handles в результатах и аргументах tools.
- **Multi Round-Trip Requests.** Вместо удержания SSE-потока сервер возвращает результат `input_required` с состоянием запроса, а клиент повторяет исходный вызов с ответами — повтор может принять любой инстанс за балансировщиком.
- **JSON Schema 2020-12.** `inputSchema` и `outputSchema` подняты до полного диалекта: `oneOf`/`anyOf`/`allOf`, условия, `$ref`; `structuredContent` стал любым JSON-значением, а не только объектом.
- **Ужесточение авторизации.** Обязательный `iss` по RFC 9207 (закрывает mix-up между авторизационными серверами), привязка client credentials к issuer, `application_type` при динамической регистрации ради localhost-редиректов у десктопных и CLI-клиентов, депрекация самой динамической регистрации.
- **Подписки вместо опроса.** Прежние `resources/subscribe` / `unsubscribe` и отдельный HTTP GET заменены одним долгоживущим потоком `subscriptions/listen`.
- **Tasks уехали из ядра в расширение** `io.modelcontextprotocol/tasks`. Блокирующий `tasks/result` заменён опросом через `tasks/get`, добавлен `tasks/update`, `tasks/list` удалён.
- **Механизмы экономии контекста.** `CacheableResult` добавил обязательные `ttlMs` и `cacheScope` на списочные методы и `resources/read`. Плюс требование отдавать `tools/list` в стабильном порядке, чтобы клиент попадал в кэш промпта.
- **Обязательное поле `resultType`** во всех результатах (`complete` или `input_required`); результат старого сервера без него клиент обязан трактовать как `complete`.
- **Заголовки `Mcp-Method` и `Mcp-Name`** обязательны на Streamable HTTP POST, плюс `x-mcp-header` для проброса параметров tool в заголовки. Смысл прикладной: шлюз, ограничитель частоты запросов или WAF роутят и считают по этим заголовкам, не разбирая тело. При расхождении заголовков с телом сервер обязан отвергнуть запрос.
- **OpenTelemetry вместо протокольного Logging**: конвенции `traceparent`, `tracestate` и `baggage` в `_meta`.
- **Политика жизненного цикла возможностей**: Active → Deprecated → Removed, минимум двенадцать месяцев на переход и публичный реестр устаревших возможностей.
- **Удалены `ping`, `logging/setLevel`, `notifications/roots/list_changed`** и возможность возобновить оборванный SSE-поток: потерянный запрос клиент обязан переотправить с **новым** идентификатором. Отсюда прямое требование к мутирующим tools — идемпотентность.

Практический вывод: базовая ревизия для нового сервера — **2026-07-28**, на ней говорят все четыре Tier-1 SDK. Ревизию 2025-11-25 держите как слой обратной совместимости. Обещания, что миграция сведётся к обновлению SDK, никто не даёт: стоимость перехода есть, особенно у тех, кто завязался на идентификаторы сессии, а `server/discover` придётся реализовать с нуля.

## Примитивы сервера

Сервер отдаёт возможности тремя примитивами, и за каждым стоит своя модель контроля над действием.

### Tools — действия по решению модели

Tool — это имя, описание, `inputSchema` и опционально `outputSchema` с annotations. Клиент получает список через `tools/list`, модель вызывает инструмент через `tools/call`. Ключевое свойство: решение о вызове принимает модель, а не человек.

Отсюда требование к контракту. Раз выбор делает модель, контракт обязан кодировать инварианты предметной области: валидацию входа, проверку предусловий и осмысленные ошибки, которые модель сможет исправить. Annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`) — это подсказки клиенту для UI-подтверждений, а не контроль доступа; доверять им безопасность нельзя.

### Resources — данные под контролем приложения

Resource — это данные с URI: файл, запись БД, схема таблицы, конфиг. Чтение идёт через `resources/read` и по определению не имеет побочных эффектов. Resource templates — параметризованные URI вида `db://tickets/{id}`. Об изменении данных клиент узнаёт через `subscriptions/listen`, подписываясь на типы событий (`toolsListChanged`, `promptsListChanged`, `resourcesListChanged`, `resourceSubscriptions`).

Практическое правило: всё, что агент только читает как контекст, выносится из tools в resources. Так меньше tool-вызовов, дешевле контекст и безопаснее поведение по умолчанию — читающий примитив не может ничего сломать.

**Отложенная загрузка справочного слоя.** Длинные инструкции, регламенты и справочники не обязаны жить в описаниях инструментов и в поле `instructions` сервера: там достаточно оставить ссылки на resources. Модель подтянет полный текст только тогда, когда он реально понадобится. Постоянная стоимость контекста падает, а доступность материала не меняется.

### Prompts — шаблоны под контролем пользователя

Prompt — именованный шаблон сообщений с аргументами; клиенты показывают его как slash-команды или пункты меню, и выбор делает пользователь. Типовое применение — упакованный сценарий работы с сервером: промпт для разбора тикета подставляет данные из resources и ведёт модель по регламенту команды.

Трио складывается в понятную модель контроля: **tools — решает модель, resources — решает приложение-хост, prompts — решает пользователь**. Выбор примитива — это выбор того, кто принимает решение о действии.

## Structured output, elicitation и судьба sampling

### Structured output

Tool может объявить `outputSchema` и возвращать `structuredContent` — JSON, который клиент валидирует против схемы, а следующий узел пайплайна потребляет без парсинга текста. С ревизии 2026-07-28 `structuredContent` — любое JSON-значение, а `outputSchema` — полный JSON Schema 2020-12.

Это фундамент межагентных цепочек: выход одного агента становится входом другого через структурированные результаты, без хрупкого разбора текста.

На практике `outputSchema` не пишут руками — его порождает типизированная сигнатура функции. Возврат `list[dict]` даёт бесполезную схему, возврат типизированной структуры — рабочую:

```python
from dataclasses import dataclass

@dataclass
class Ticket:
    id: str
    name: str
    status: str        # open | in_progress | closed
    score: int         # 0-100

@mcp.tool()
def search_tickets(query: str, limit: int = 20) -> list[Ticket]:
    """Поиск тикетов по тексту. Возвращает id, name, status, score."""
    ...
```

Две оговорки, без которых обещание строгой границы не выполняется:

- **Схема не переносима между провайдерами.** Одни и те же конструкции ведут себя по-разному: `allOf` уходит в ошибку у одного провайдера, другой молча возвращает пустой объект вместо отказа, третий поддерживает с ограничениями.
- **Валидация — место, где агенты ломаются тихо.** Модель вернула почти правильный JSON, парсер упал, пользователь получил ошибку, а в логе не осталось ничего осмысленного.

Рабочий минимум: валидатор на выходе плюс повтор с текстом ошибки в следующем проходе. И держите диалект схемы простым, пока не проверили поведение на всех целевых провайдерах.

### Elicitation

Elicitation — дозапрос данных посреди операции: сервер запрашивает у пользователя недостающее (подтверждение опасной операции, выбор из вариантов, значение поля), а клиент строит форму по JSON-схеме.

URL mode выносит чувствительный ввод в браузер: сервер отдаёт ссылку, пользователь завершает OAuth-флоу или оплату вне чата, и секреты не проходят через LLM-клиент. Спецификация прямо запрещает form mode для секретов в сильнейшей модальности — **MUST NOT**: сервер не имеет права запрашивать через форму пароли, API-ключи, токены доступа и платёжные данные.

Две детали, на которых легко споткнуться: имя, email и username под этот запрет **не** подпадают; и сама схема form mode сильно ограничена — плоский объект с примитивами, без вложенности и массивов объектов, кроме multi-select через enum.

С ревизии 2026-07-28 elicitation доставляется через Multi Round-Trip Requests: сервер возвращает `input_required`, клиент собирает ответы и повторяет вызов. Важное ограничение: сервер может спрашивать только во время обработки запроса клиента, всплывающих вопросов из ниоткуда протокол не допускает.

### Почему sampling выводят из протокола

Замысел был такой: сервер просит клиента сделать LLM-вызов на токенах и модели пользователя, то есть сервер без собственного API-ключа получает доступ к модели.

В 2025-11-25 sampling даже усилили поддержкой tools. А в 2026-07-28 объявили устаревшим по трём основаниям: сложность реализации, низкое принятие (мало клиентов поддержали механизм, хотя он доступен с ноября 2024 года) и наличие прямых альтернатив. Общий критерий отбора выведенных механизмов — слабейшее отношение принятия к сложности. Безопасность (размытая ответственность за выбор модели, цену, согласия пользователя и защиту от prompt injection внутри цикла) идёт отдельным пунктом как побочный положительный эффект, а не как причина.

Урок для архитектора виден на паре: **elicitation при этом не депрекирован**. Протокол сознательно оставляет серверу канал спросить человека и отрезает канал взять модель клиента. Закладывайтесь на явные контракты и явное согласие пользователя, а не на клиентские токены.

## Разработка: SDK и управление состоянием

| Инструмент | Что это | Ниша | Когда брать |
|---|---|---|---|
| Официальный Python SDK (`mcp`) | эталонная реализация с высокоуровневым классом сервера | минимум зависимостей, максимум контроля | нужен тонкий контроль над протоколом и мало внешней логики |
| FastMCP (пакет `fastmcp`) | фреймворк поверх той же модели, ветка 3.x | продакшн-обвязка без настройки | нужны OAuth, middleware, генерация из OpenAPI, тесты |
| Официальный TypeScript SDK | сервер плюс схемы на Zod или Standard Schema | веб-стек и статическая типизация | команда живёт в TypeScript |

### Какую версию SDK ставить

Обе официальные линии выпустили мажорные релизы в конце июля 2026 года — и разъехались по-разному. Большинство чужих инструкций уже устарело.

**Python.** С 28 июля 2026 года стабильная линия — **v2**: `pip install mcp` ставит именно её. v2 говорит на ревизии 2026-07-28 и при этом обслуживает клиентов прежних ревизий с того же сервера. Высокоуровневый класс сервера в v2 называется `MCPServer` (в v1 он назывался `FastMCP`), типы уехали в отдельный пакет `mcp-types`, декораторы `@tool` и `@resource` не изменились. Остаться на v1 можно только с явным потолком `mcp>=1.28,<2`; сама v1.x переведена в режим поддержки и получает только исправления безопасности. Известный пробел v2.0.0: расширение tasks в него не вошло.

**TypeScript.** Ловушка обратная. v2 вышла 27 июля 2026 года, но уехала в **новые пакеты**: `@modelcontextprotocol/core`, `/client`, `/server`, `/server-legacy` плюс адаптеры `/node`, `/express`, `/hono`, `/fastify`. Старый пакет `@modelcontextprotocol/sdk` **остался на v1** (1.30.0). Кто поставил `@modelcontextprotocol/sdk@latest`, получил v1 и никогда не увидит Standard Schema.

### Python

```python
# mcp >= 2.0 (ставится по умолчанию с 28.07.2026)
from dataclasses import dataclass
from mcp.server.mcpserver import MCPServer

mcp = MCPServer("tickets")

@dataclass
class Ticket:
    name: str
    status: str

@mcp.tool()
def search_tickets(query: str, limit: int = 20) -> list[Ticket]:
```

Темп релизов у фреймворка выше, чем у SDK, и это часть цены: путь от 2.0 до 3.0 занял десять месяцев, а ещё через пять появилась первая альфа 4.0. Бета 4.0 несёт бессессионную ревизию 2026-07-28, и в ней из серверного API убраны server-initiated sampling и roots.

### Состояние: от глобальной переменной к handles

Управление состоянием — главное отличие продакшн-сервера от демо. Антипаттерн — состояние в глобальной переменной процесса: работает по stdio на одной машине и разваливается при HTTP-развёртывании в несколько инстансов.

Паттерн **state handles**: сервер кладёт состояние во внешнее хранилище, а клиенту возвращает непрозрачный идентификатор в результате tool. Каждый следующий вызов валидирует handle вместе с auth-контекстом; у handle есть TTL и политика очистки.

Важная оговорка о статусе паттерна. Раздел Stateful Tools помечен в спецификации как **non-normative** и прямо предупреждает: у протокола нет понятия state handle, с точки зрения провода это обычная строка в результате tool и обычный аргумент последующих вызовов. Искать поле `stateHandle` в схеме бесполезно. Оттуда же три практических требования:

- **Авторизацию валидировать против handle на каждом вызове**, а не только при выдаче.
- **Для неаутентифицированных серверов handle де-факто становится bearer-токеном** — значит, нужна энтропия (UUIDv4) и ограниченный срок жизни.
- **Политику удержания состояния писать в описание tool**, чтобы модель видела её в момент решения создавать состояние.

Подключаемые хранилища FastMCP (память, файл на диске, Redis) дают единый key-value-интерфейс — состояние переживает рестарт и делится между инстансами.

Отдельное правило поверх этого: **мутирующие tools проектируются идемпотентными**, где это возможно. Повтор со стороны клиента не должен дублировать запись в БД — иначе Multi Round-Trip Requests и повторы за балансировщиком превратятся в дублированные заказы и списания.

## Проектирование tools: описание — это промпт

Контракт инструмента — не документация для человека, а промпт для модели, и его качество измеримо влияет на поведение агента.

### Принципы

- **Не оборачивать API один в один.** Агент мыслит задачами, а не эндпоинтами: вместо `list_contacts` полезнее `search_contacts`, и каждый инструмент решает отдельную подзадачу целиком.
- **Namespacing.** Префиксы вида `tickets_search`, `tickets_update` снижают ошибки выбора при большом наборе.
- **Высокосигнальные поля.** Возвращать `name` и `status`, а не низкоуровневые `uuid` и `mime_type` — модель тратит контекст на то, чем будет пользоваться.
- **Экономия контекста.** Пагинация, фильтры, усечение с внятной подсказкой; для сравнения, Claude Code по умолчанию ограничивает ответ инструмента 25 000 токенов.

Главный тезис методики Anthropic — улучшения проверяются через evals, а не на вкус. Точечные правки описаний tools дали Claude Sonnet 3.5 лучший результат отрасли на SWE-bench Verified (49% против прежних 45%; результат получен на обновлённой версии модели, поэтому чистого эксперимента с одной моделью здесь нет, но вклад описаний назван прямо).

Второй тезис обычно опускают, а он прямо применим: описания инструментов стоит оптимизировать **силами самого агента**. Рабочий цикл — склеить транскрипты прогонов evals и отдать их агенту на рефакторинг описаний, а не переписывать формулировки вручную до бесконечности.

### Когда вызывать и когда не вызывать

Канон описания: что делает, когда вызывать, когда НЕ вызывать, формат входа и выхода, один-три примера; критичные ограничения — императивом `You MUST`.

```
tickets_search(query, status?, limit?)
Поиск тикетов по тексту и статусу. Возвращает name и status.
Когда вызывать: пользователь ищет существующие тикеты.
Когда НЕ вызывать: для создания используйте tickets_create.
You MUST передавать status из набора: open|in_progress|closed.
Ошибка: поле due_date должно быть в формате YYYY-MM-DD —
повторите вызов с исправленным форматом.
```

**Секцию «когда НЕ вызывать» заполняйте не запретами.** Модели заметно лучше отрабатывают позитивные инструкции, чем ограничения: формулировка «сначала проверь бюджет через `get_budget`» работает надёжнее, чем «не вызывай без проверки бюджета». Поэтому каждое «не вызывай, если…» переписывайте одним из двух способов:

- в **предусловие** — «вызывай только после того, как…»;
- в **редирект на конкретный другой инструмент** — «для создания используйте `tickets_create`».

Голый запрет без адресата — самая слабая форма: модель видит ограничение, но не видит, что делать вместо.

Ошибки инструмента — тоже промпт: вместо кода 500 возвращать действие (какое поле в каком формате исправить). Poka-yoke сигнатур закрывает целые классы сбоев заранее: абсолютные пути вместо относительных, `user_id` вместо `user`, enum вместо свободной строки. И описание обязано предупреждать о необратимости действия — 96,4% описаний в экосистеме этого не делают, ровно поэтому агент путает `delete` и `list`.

### Сколько tools нужно серверу

По аудиту PolicyLayer (июль 2026 года) медианный сервер экосистемы отдаёт 7 tools, средний — 15,8, 99-й перцентиль — 138, а рекорд выборки — 824. Каждый инструмент — это токены контекста и лишняя точка ошибочного выбора в каждом диалоге.

Консолидация уменьшает и то, и другое: три инструмента `get_ticket`, `get_ticket_comments` и `get_ticket_history` сворачиваются в один `get_ticket` с параметром детализации. Компромисс двусторонний — крупные инструменты экономят выбор, но раздувают схему и усложняют валидацию; мелкие прозрачнее, но заставляют модель строить длинные цепочки.

| Порог | Что происходит |
|---|---|
| до 20 инструментов | поведение агента управляемо |
| 20–50 | границы между инструментами размываются, растут ошибки выбора |
| больше 50 | «смерть от тысячи инструкций» |
| 5–15 на сервер | рабочий ориентир: один сервер — одна задача, неиспользуемые удалять |
| 128 | жёсткий потолок инструментов на сессию в VS Code |

Показательный кейс: команда продукта запустилась с 30–40 инструментами, получила полностью неюзабельный продукт и после переработки оставила **три**. Формулируют вывод так: поверхность инструментов — это меню, которое модель перечитывает каждый ход.

Обратный полюс не менее важен. Есть разбор продакшн-сервера на 118 инструментов, где команда выросла с 25 до 118 за три переписывания и удержала управляемость группировкой по доменам (один файл — один домен), OAuth-scope на чтение и запись и единой пятишаговой структурой всех обработчиков.

**Бюджет задан на сервер, а реальный лимит сидит на агенте.** К одному агенту подключают несколько серверов и упираются в двухслойный потолок:

- **Мягкий потолок — внимание модели.** Практики называют 20–30 инструментов на агента: дальше даже крупные модели теряют фокус.
- **Жёсткий потолок — сторона API.** У OpenAI при превышении примерно 75–85 инструментов запрос начинает возвращать ошибку.

Рабочий рецепт при выходе за эти рамки — не резать домен, а разбивать: группировать инструменты по доменам и роутить запрос в доменного субагента, который видит только свои. Типовой продакшн-приём: выбор подмножества инструментов под конкретную задачу выносят в обычный код **перед** агентом, и агент никогда не видит полный каталог.

### Динамическая загрузка вместо урезания набора

С конца 2025 года провайдеры дают механики, при которых большой каталог перестаёт быть проблемой контекста:

- **Tool Search Tool** — инструменты помечаются `defer_loading` и не грузятся в контекст, модель находит их по требованию;
- **Programmatic Tool Calling** — агент оркестрирует вызовы кодом, и промежуточные результаты не попадают в контекст;
- **Tool Use Examples** — примеры вызовов прямо в определении инструмента.

Порядок выигрыша по замерам Anthropic: Tool Search Tool сохраняет 191 300 токенов контекста против 122 800 при обычной загрузке (около 85% экономии) и на MCP-эвалах с большими наборами поднимает точность с 49% до 74% (Opus 4) и с 79,5% до 88,1% (Opus 4.5). Programmatic Tool Calling снижает средний расход с 43 588 до 27 297 токенов. Tool Use Examples поднимают точность на сложных параметрах с 72% до 90%. Оттуда же цифра, объясняющая, зачем это нужно: определения и результаты инструментов иногда съедают 50 000+ токенов ещё до того, как агент прочитал запрос.

Практический вывод: сначала считайте стоимость выбора, а не число инструментов. Пока каталог небольшой — держите его небольшим. Когда домен требует десятков инструментов, правильный ход — переход на динамическое обнаружение, а не урезание домена.

## Авторизация OAuth 2.1 для remote-серверов

### Модель авторизации

MCP-сервер в терминах OAuth — это **protected resource**. Метаданные ресурса — RFC 9728, PKCE обязателен.

**Обнаружение авторизационного сервера — не только RFC 8414.** Спецификация требует от авторизационного сервера поддержать хотя бы один из двух механизмов: RFC 8414 **или** OpenID Connect Discovery 1.0; а клиент обязан поддержать оба. Клиент, написанный строго под RFC 8414, не отработает серверы на чистом OIDC — частая причина, по которой интеграция не поднимается на корпоративном IdP.

**Регистрация клиента: приоритет изменился.** Классическая динамическая регистрация (DCR, RFC 7591) больше не равноправная альтернатива, а Deprecated. Действующий порядок: **CIMD (SHOULD) → предварительная регистрация → DCR (MAY)**. В CIMD клиент идентифицируется URL-документом метаданных; самая полная реализация этого стека сегодня у Claude-клиентов.

Для machine-to-machine сценариев (фоновые агенты, CI) есть расширение client credentials: токен выдаётся без human-in-the-loop. Токены проверяются на каждом запросе — audience, scope, срок жизни.

Две детали, которые обычно приписывают не той ревизии. Валидация resource indicators (RFC 8707) — норма с **2025-06-18**, а не с 2026-07-28. А ужесточение базового уровня в 2026-07-28 — это работа с issuer и регистрацией клиента, а не переход на JSON Schema 2020-12, с которым это иногда склеивают.

### Практика: OAuth-провайдеры

FastMCP без настройки поддерживает Google, GitHub, Azure (Entra ID), Auth0, WorkOS/AuthKit, AWS Cognito, Descope, а также проверку JWT и token introspection (RFC 7662) — авторизация подключается провайдером с парой `client_id` и secret.

Отдельная проблема — провайдеры без DCR: её решает OAuth proxy, который сам регистрирует клиентов и замыкает полный OAuth 2.1 с PKCE. Важная деталь безопасности: прокси выпускает собственные JWT, а не пробрасывает upstream-токены провайдера, — так граница audience не протекает. Продакшн-требования: явный ключ подписи JWT и постоянное хранилище клиентов (Redis); авто-ключи из системного хранилища годятся только для локальной разработки.

Минимальный уровень для внутреннего сервера — статический bearer-токен из секрет-менеджера, но это осознанный компромисс с зафиксированным сроком жизни, а не постоянное решение.

### Состояние экосистемы

По данным Astrix (октябрь 2025 года, 5 200+ открытых репозиториев), 88% серверов требуют учётные данные, но 53% из них — статические API-ключи и personal access tokens, 79% передают ключи через переменные окружения, а OAuth используют лишь 8,5%. Оговорка о методике: это аудит исходников, а не развёрнутых продакшн-серверов, и покрывает он около 19% от оценочного числа реализаций, преимущественно высокозвёздные проекты.

Хуже того, Trend Micro в июле 2025 года нашла 492 MCP-сервера, открытых в интернет вообще без аутентификации и шифрования; к повторному замеру в апреле 2026 года счёт вырос почти втрое — до 1 467.

Вывод для проектирования прямой: как только сервер внутренней БД выставляется наружу, bearer-слой обязан быть уже в первой remote-версии. Именно привычка «сначала заработает, потом закроем» и порождает эту статистику.

## Интеграция с локальными БД и скриптами

### Сервер поверх SQLite или Postgres

Слой tools над БД строится от инвариантов домена, а не от SQL:

- **Чтение** — через resources и поисковые tools с параметризованными запросами; произвольный SQL от модели запрещён по умолчанию, потому что инъекция руками агента ничем не лучше классической.
- **Мутации** — отдельные явные tools с бизнес-валидацией: переход статуса проверяет инварианты (нельзя закрыть тикет с открытыми блокерами), числовые поля — диапазоны, каждая запись обновляет `last_modified`.
- **Схема как ресурс.** Модель, видящая структуру таблиц, строит осмысленные цепочки вызовов вместо слепого перебора.
- **Разделение прав на уровне подключения.** Read-only-подключение для читающих tools, отдельный ограниченный аккаунт для мутаций — тогда ошибка сервера не превращается в `DROP TABLE`.

### Скрипты, CLI и долгие операции

Обёртка процессов — самый частый сценарий после БД и самый опасный. Обёртка скрипта — это subprocess с фиксированной командой и валидированными аргументами; конкатенация строк в shell ведёт прямо к command injection, который Equixly (март 2025 года) находит в 43% проверенных им популярных реализаций. Цифру стоит читать как направленную оценку, а не как статистику по экосистеме: размер выборки и критерии отбора не раскрыты.

Обязательный минимум для любой обёртки процесса: timeout, лимит вывода, преобразование кодов возврата в осмысленную для модели ошибку; вывод длинного процесса отдаётся усечённым хвостом с указанием, где лежит полный лог.

Операции дольше десятков секунд — кандидаты на Tasks: сервер сразу отдаёт идентификатор задачи, агент опрашивает статус через `tasks/get` и забирает результат позже. Перед тем как закладывать Tasks в архитектуру, проверьте поддержку в своём SDK: с ревизии 2026-07-28 это официальное расширение, и в Python SDK v2.0.0 оно не вошло.

И правило allowlist: сервер исполняет только перечисленные команды с перечисленными флагами — свобода агента заканчивается на границе списка.

## MCP, CLI и Agent Skills: где проходит граница

| Механизм | Что даёт | Цена | Когда брать |
|---|---|---|---|
| CLI-инструмент | агент вызывает через shell, нулевая протокольная обвязка | нет схемы параметров и структурированных результатов, каждый клиент интегрируется заново, безопасность на совести shell-доступа | локальная автоматизация для себя |
| Agent Skills | упакованные инструкции и скрипты, подгружаются в контекст по необходимости | это знание для одного агентного окружения, а не сервис: нет авторизации, remote-доступа, мультиклиентности | методика и регламент для агента |
| MCP | схемы, обнаружение, авторизация; один сервер — все клиенты | протокольная обвязка, развёртывание и сопровождение сервиса, постоянная стоимость описаний tools в контексте | общий доступ к данным или действиям для нескольких клиентов или людей |

### Ось спора: eager против lazy loading

Настоящая линия раздела проходит по моменту загрузки. MCP грузит полные схемы всех инструментов в начало контекстного окна при старте сессии. Agent Skills держат в контексте только короткий frontmatter, а тело подгружают в момент срабатывания. CLI не грузит ничего.

Порядок цифр здесь важнее точных значений:

- пять подключённых MCP-серверов могут стоить порядка 55 000 токенов **до того, как начался разговор**;
- сто MCP-инструментов — около 50 000 токенов одних описаний; сто CLI-команд заменяются одним инструментом `execute_command` плюс лёгким поиском нужной команды;
- двести skills обходятся контексту почти бесплатно — в нём лежит только frontmatter, порядка 30–50 токенов на штуку.

Ключевая асимметрия: описания висят в контексте постоянно, независимо от того, вызывали инструмент или нет, тогда как CLI тратит несколько раундов на разбор один раз. Там, где сравнивали напрямую, CLI выходил примерно в 17 раз дешевле (\$3,20 против \$55,20 в месяц) при 100% успешных вызовов против 72% у MCP, где оставшиеся 28% — падения по TCP-таймаутам. Это цифры одного сравнения, а не отраслевая норма, но порядок величин показателен.

### Критерии, которые работают лучше числа потребителей

> **Skill — это ЧТО делать, MCP — это КАК вызвать.** Skills несут доменное знание, регламент и порядок шагов; MCP даёт структурированный аутентифицированный доступ к действию.

> **Быстрый тест:** если в задаче агента звучит «запросить», «получить», «проверить текущее состояние» — нужен MCP. В остальных случаях начинайте со skill.

И критерий среды. CLI даёт агенту доступ ко всей машине и требует технической подготовки пользователя — он хорош для single-tenant, личной автоматизации и кодинг-агентов. MCP приносит remote-доступ, OAuth, централизованное управление и аудит — и поэтому выигрывает в B2B-SaaS, корпоративной среде и чат-клиентах. Дело не в числе потребителей самом по себе, а в том, нужны ли вам аудит и управление доступом.

### Цена описаний снимается кодом

Постоянная стоимость описаний снимаема. В подходе code execution with MCP серверы подаются модели как код-API на виртуальной файловой системе: определения инструментов не грузятся в контекст целиком, агент импортирует нужное по месту. В примере Anthropic расход падает примерно со 150 000 токенов до 2 000 — минус 98,7%.

Практики меряют исходную цену буквально: команда `/context` показывает порядка 46 000 токенов на один только официальный GitHub-сервер (около четверти окна на пустой сессии).

### Композиция вместо выбора

- **Skill поверх MCP.** Сервер даёт примитивы (запросы к БД тикетов), а skill — регламент их применения (порядок вызовов, критерии эскалации).
- **CLI внутри MCP.** Сервер оборачивает существующую консольную утилиту в типизированный tool — команда не переписывает инструментарий, а публикует его для агентов.
- **Антипаттерн «MCP ради MCP».** Обёртка одной функции для одного локального агента протоколом не окупается. Сигнал к MCP — появление второго потребителя.

### Кто решает делать свой сервер

| Критерий | Что смотреть | Куда склоняет |
|---|---|---|
| Число потребителей | один агент или несколько клиентов, команд, людей | второй потребитель — сигнал к MCP |
| Чувствительность данных | нужны ли аудит доступа и разграничение прав | чувствительные данные — MCP с OAuth |
| Частота изменений контракта | как часто меняется набор действий и их схема | частые изменения дешевле в skill, дороже в протоколе |
| Требования к аудиту | нужно ли знать, кто и когда вызвал действие | аудит — только MCP |
| Кто сопровождает | есть ли владелец сервиса и дежурство | нет владельца — не начинайте |

Постоянная стоимость владения, которую надо назвать вслух до старта: описания инструментов едят контекст в каждом диалоге, сервер требует дежурства и обновлений, авторизация требует владельца. Эти три строки не исчезают после запуска.

## Экосистема: Registry и поддержка в клиентах

### MCP Registry

Официальный реестр запущен в превью 8 сентября 2025 года — это централизованные метаданные публичных серверов: пространство имён через DNS-верификацию и REST API для клиентов и агрегаторов.

По срезу на 7 июля 2026 года в реестре 15 382 уникальных сервера, 47% (7 203) — с hosted-эндпоинтами (streamable-http/sse), остальные ставятся локально из npm/PyPI/OCI. Снимок стареет быстро: за двадцать дней после него реестр вырос примерно на четверть, до \~18 700 записей.

Реестр служит источником правды для субреестров; в агрегаторах при этом накапливаются мёртвые записи. Перепись всего реестра даёт разбивку: 79,6% записей рабочие, 15,2% деградировавшие, 4,1% мёртвые. Самый хрупкий слой — hosted-remote: 13,6% эндпоинтов не отвечают, а 25,9% мертвы или сломаны. На срез любого агрегатора нельзя полагаться как на живой список.

Публикация своего сервера — это манифест с метаданными плюс подтверждение namespace, и тот же формат работает в приватных реестрах компании.

### Поддержка в клиентах (июль 2026)

| Хост | Транспорты и доступ | Авторизация | Особенности |
|---|---|---|---|
| Claude Code / Desktop | stdio, SSE, Streamable HTTP | самый полный стек: DCR, CIMD, RFC 9728 | три уровня конфигурации (local/project/user) |
| ChatGPT | внутри самого ChatGPT — только remote по HTTPS; десктопное приложение, Codex CLI и IDE-расширение поддерживают и stdio | OAuth для remote | Apps SDK принимает SSE и Streamable HTTP, отображает вывод tools как интерактивные виджеты; коннекторы переименованы в apps с 17 декабря 2025 года |
| Cursor и AI-IDE (Windsurf, Cline) | MCP — основная модель расширения, конфиг `mcp.json` | чаще API-ключи | VS Code поддерживает MCP-серверы в agent mode с v1.99 (март 2025) |
| Gemini | Gemini CLI (`~/.gemini/settings.json`); управляемый remote в Gemini Enterprise Agent Platform | Cloud IAM для управляемых | платформа запущена 22 апреля 2026 года, тогда же анонсированы 50+ управляемых MCP-серверов Google; 30 июня 2026 года добавлен собственный remote-сервер с OAuth 2.0 |

Официальный каталог коннекторов Claude на 28 июля 2026 года насчитывает свыше 950 серверов. Поверх этого MCP Apps (январь 2026 года) — первое официальное расширение протокола — добавили интерактивные UI-превью прямо в чат клиента.

Следствие для проектирования: сервер, рассчитанный на несколько **чат-клиентов**, делается как remote Streamable HTTP с OAuth — это пересечение их требований. Для CLI и IDE-клиентов stdio остаётся полноценным вариантом, а не только режимом разработки.

## Безопасность MCP

### Tool poisoning и rug pull

Описание инструмента — немодерируемый вход в контекст модели, и именно он стал главной поверхностью атаки.

- **Tool poisoning.** Злонамеренные инструкции прячутся в описании tool: пользователь их не видит, а модель читает и исполняет. Механизм впервые описан Invariant Labs в апреле 2025 года и вошёл в OWASP MCP Top 10 как MCP03:2025.
- **Масштаб уязвимости.** Бенчмарк MCPTox (препринт август 2025 года, рецензированная публикация AAAI 2026) прогнал 353 реальных tool с 45 живых серверов против 20 конфигураций моделей. Средний успех атаки — 36,5%, максимум — 72,8%; более способные модели нередко уязвимее, потому что лучше следуют инструкциям. Самая показательная цифра другая: **максимальный refusal rate — менее 3%**, то есть safety alignment против этой атаки практически не срабатывает.
- **Rug pull.** Сервер честен при установке и ревью, а затем удалённо меняет описание или логику tool — статический аудит на момент установки ничего не гарантирует.
- **Демонстрации против инцидентов.** Различать два уровня важно. **Демонстрация:** PoC, где отравленный tool читал `~/.ssh/id_rsa` и отдавал содержимое скрытым параметром через Cursor (апрель 2025 года) — контролируемое исследование. **Инцидент уровня CVE:** MCPoison (CVE-2025-54136, High, CVSS 7.2–8.8) подменял содержимое уже одобренного конфига `.cursor` в общем репозитории и заражал всю команду.

### Минимальная гигиена

Первое правило касается не чужих серверов, а собственной обвязки — её надо держать обновлённой. CVE-2025-6514 в `mcp-remote` (CVSS 9.6, удалённое исполнение кода при подключении к недоверенному серверу, 437 000+ загрузок пакета на момент раскрытия) и CVE-2025-49596 в MCP Inspector (CVSS 9.4, закрыт в 0.14.1). Одной версией дело не ограничилось: позже в Inspector нашли CVE-2025-58444 (XSS с переходом в исполнение команд), закрытую только в 0.16.6. Поэтому правило формулируется не через минимальную версию, а через актуальную.

Остальные правила короткие: серверы — только из allowlist команды; изменение mcp-конфига в репозитории — событие code review; секреты не хранятся в переменных окружения открытым текстом, права на БД и ФС минимальны.

Масштаб проблемы измерен: по аудиту PolicyLayer 28,1% серверов экосистемы содержат деструктивный инструмент, а 43% дают агенту необратимое действие или исполнение команд. Дальше считается вероятность: стек из пяти непроверенных серверов содержит деструктивный инструмент с вероятностью 94,1%, из десяти — 99,7%.

Достаточно одного рефлекса: **MCP-сервер — это код с правами разработчика, а не плагин из магазина**.

### Пять требований к собственному серверу

**1. Token passthrough запрещён спецификацией прямо.** Сервер **MUST NOT** принимать токены, выпущенные не для него, и **MUST NOT** пробрасывать полученный от клиента токен в нижестоящий API. Если сервер ходит в upstream-API, он делает это как отдельный OAuth-клиент со своим токеном. Цена нарушения — confused deputy: ломается аудит, обходятся ограничение частоты запросов и валидация, а украденный токен превращает сервер в прокси для выкачивания данных.

**2. Привязка к localhost и проверка `Origin`.** Локальный сервер по HTTP обязан слушать `127.0.0.1`, а не `0.0.0.0`, и валидировать заголовок `Origin`. Иначе браузер на той же машине становится вектором атаки через DNS rebinding.

**3. Автозапуск серверов в IDE — это поверхность для исполнения кода.** IDE запускают MCP-серверы из файлов проекта с полными правами разработчика и без изоляции. Подкинуть вредоносный `mcp.json` в репозиторий достаточно, чтобы получить исполнение кода у всех, кто открыл проект. Это и есть причина, по которой изменение mcp-конфига — событие code review: конфиг исполняем.

**4. Изоляция локальных серверов.** Allowlist и параметризация в обёртке процесса — верно, но не полно. Контейнер или микро-ВМ плюс запрет исходящего трафика по умолчанию закрывают целый класс сценариев, который allowlist не ловит.

**5. Против rug pull работает пиннинг манифеста.** Хешируйте набор описаний инструментов и сверяйте его с зафиксированным слепком при каждом подключении. Тогда изменение уже одобренного описания становится видимым событием, а не тихой подменой.

В разборах инцидентов ходит случай, когда агент самостоятельно выполнил `terraform destroy` и снёс продакшн. Причина ровно та, о которой речь: отсутствие лимитов и подтверждения на разрушительном действии. Отсюда пара, которую стоит заложить сразу: `destructiveHint` в annotations плюс подтверждение через elicitation.

## Отладка и развёртывание

### MCP Inspector

`npx @modelcontextprotocol/inspector` поднимает веб-UI: подключение к серверу по stdio или HTTP, просмотр tools/resources/prompts, ручной вызов с параметрами и история JSON-RPC-сообщений.

Порядок отладки экономит и время, и токены: сначала сервер проверяется Inspector-ом (схемы валидны, ошибки осмысленны) — и только потом агентом (описания ведут модель к правильным вызовам). Берите актуальную линию Inspector: на июль 2026 года это 2.x. Запускать его стоит только против доверенных серверов и не держать открытым в сеть.

Дополнение к Inspector — лог самого клиента: Claude Code и Cursor показывают фактические вызовы и ответы, и расхождение между планом и фактом видно именно там.

### Локально против remote

Локальное развёртывание — это конфиг клиента: команда запуска в `.mcp.json`, `claude_desktop_config.json` или `mcp.json`; распространение командой — пакет в npm/PyPI плюс строка конфига в README.

Remote-развёртывание — контейнер со Streamable HTTP за реверс-прокси, авторизация из раздела про OAuth и состояние во внешнем хранилище; инстансы получаются stateless и масштабируются горизонтально, что совпадает с моделью действующей спецификации.

Управляемые варианты снимают часть работы, но внутренние данные едут через чужую инфраструктуру.

Критерий выбора прямой: сервер с локальной ФС и личными данными — stdio навсегда; сервер с общей БД проекта — remote с первого дня, иначе каждый участник команды заводит свою копию и свои секреты.

## Итоги

- Продакшн-сервер отличается от демо тремя слоями: продуманный контракт tools, явное состояние во внешнем хранилище через state handles и авторизация.
- Пишите сервер под действующую ревизию 2026-07-28 и stateless: `initialize` удалён, `server/discover` и `resultType` обязательны, а 2025-11-25 держите как слой обратной совместимости.
- Проверьте версию SDK до первой строки кода: `pip install mcp` ставит v2, где класс сервера называется `MCPServer`; а `@modelcontextprotocol/sdk@latest` в npm — это ещё v1, потому что TypeScript v2 уехала в новые пакеты.
- Описание tool — это промпт: канон «что / когда / когда не / формат / примеры» и высокосигнальные поля измеримо снижают ошибочные вызовы; секцию «когда НЕ вызывать» пишите предусловием или редиректом, не запретом.
- В проде решает не число инструментов, а стоимость выбора: мягкий потолок внимания модели 20–30 на агента, жёсткий потолок API — около 75–85, и за ними идут динамическое обнаружение и доменные субагенты, а не урезание домена.
- Remote-сервер выставляется только с OAuth 2.1 и валидацией токенов на каждом запросе; статический bearer-токен из секрет-менеджера — временный минимум. Динамическая регистрация клиентов (DCR) устарела, приоритет — CIMD.
- Выбор MCP / CLI / Agent Skills — это выбор, за что платить: Skill отвечает на вопрос «что делать», MCP — на вопрос «как вызвать»; сигнал к MCP — не только второй потребитель, но и требование к аудиту и управлению доступом.
- Чужой MCP-сервер — код с правами разработчика: allowlist, конфиг под code review, минимальные права; 43% публичных серверов дают агенту необратимое действие, и стек из пяти непроверенных содержит деструктивный инструмент с вероятностью 94,1%.
- В своём сервере закройте сразу четыре вещи, которые потом дорого переделывать: token passthrough, привязку к `127.0.0.1` с проверкой `Origin`, изоляцию процесса и пиннинг манифеста инструментов.
