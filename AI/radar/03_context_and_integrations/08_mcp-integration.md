# Model Context Protocol: подключение LLM к внешним системам

## Проблема до MCP: зоопарк интеграций

До появления MCP каждая LLM-платформа разрабатывала собственный механизм подключения внешних инструментов. Результат — **M×N уникальных интеграций**: M моделей (или хостов) умножить на N инструментов.

Примеры изолированных решений, существовавших параллельно:
- OpenAI function calling — tool schema в формате, специфичном для OpenAI API
- LangChain tools — Python-first абстракция, привязанная к фреймворку
- Google Vertex AI Extensions — проприетарная схема под Gemini
- Amazon Bedrock Agents — закрытый формат для агентов в AWS

Интеграция, написанная под OpenAI function calling, не работает в Claude без переписывания. Смена LLM-провайдера становилась не заменой API-ключа, а полным переписыванием интеграционного слоя — vendor lock-in на уровне инструментальной инфраструктуры.

---

## Что такое MCP

**Model Context Protocol (MCP)** — открытый стандарт для подключения LLM к внешним системам, данным и инструментам. Разработан Anthropic, опубликован в ноябре 2024 как open-source.

Ключевая идея: вместо M×N интеграций — единый протокол между хостом (где работает модель) и сервером (где реализованы инструменты). Любой сервер, соответствующий спецификации, работает с любым совместимым хостом.

Аналогия: USB-C унифицировал физическое подключение устройств. MCP делает то же для AI-инструментов: один стандарт для любого хоста и любого источника данных.

### Статус экосистемы (2025–2026)

К началу 2026 года протокол поддержан: OpenAI (март 2025), Google DeepMind, Microsoft, Anthropic, Block, Replit.

Официальные серверы предоставляют: GitHub, Atlassian (Jira, Confluence), Notion, Cloudflare, Stripe, Postgres, Sentry, Slack.

## Архитектура MCP

### Три роли в протоколе

**Host** — приложение, в котором работает LLM и которое видит пользователь:
- Примеры: Claude Desktop, Cursor, Warp, VS Code с Copilot, Cline, Zed
- Управляет жизненным циклом MCP Client соединений
- Определяет политику безопасности
- Предоставляет UI для работы с ответами сервера

**Client** — компонент внутри хоста, технический слой протокола:
- Устанавливает и поддерживает соединение с конкретным MCP-сервером
- Отношение один Client — один Server (1:1)
- Реализует протокол на базе JSON-RPC 2.0

**Server** — независимый процесс или удалённый сервис:
- Реализует три примитива протокола: Tools, Resources, Prompts
- Не имеет прямого доступа к LLM-контексту
- Может быть локальным (stdio) или удалённым (HTTP)

### JSON-RPC 2.0

MCP базируется на JSON-RPC 2.0 — простом и широко поддержанном стандарте:

| Тип сообщения | Описание |
|--------------|----------|
| **Request** | Запрос с уникальным id, требует ответа |
| **Response** | Ответ на Request с тем же id |
| **Notification** | Одностороннее сообщение без id (например, уведомление об изменении ресурса) |

Соединения stateful — стороны поддерживают состояние сессии. При инициализации — capability negotiation: обмен поддерживаемыми функциями.

### Схема взаимодействия

```
Host (Claude Desktop / Cursor / Warp)
├── LLM (Claude / GPT / Gemini)
├── Client A ──stdio──► Local MCP Server (filesystem, sqlite)
├── Client B ──stdio──► Local MCP Server (postgres)
└── Client C ──HTTPS──► Remote MCP Server (GitHub, Jira, Notion)
```

## Три примитива MCP

### Tools (инструменты)

Функции, которые LLM может вызывать для выполнения действий. Входные параметры описываются через JSON Schema.

Модель выбирает инструмент самостоятельно на основании поля `description`. Это ключевое отличие от ручного вызова.

Типичные примеры:
- `create_issue(title, body, labels)` — создание тикета в GitHub или Jira
- `search_github(query, repo, language)` — поиск по кодовой базе
- `query_database(sql, parameters)` — SQL-запрос к базе данных

**Ключевое:** поле `description` критично. Плохое описание — модель путается или пропускает tool. Хорошее — выбирает правильный даже при неочевидных формулировках.

Хост может требовать явного подтверждения пользователя перед деструктивными операциями (настраивается через annotations).

### Resources (ресурсы)

Данные, которые LLM может читать, адресованные через URI. Аналог GET-запроса: только чтение, без побочных эффектов.

Типичные URI-схемы:
- `file:///path/to/document.pdf` — локальный файл
- `github://repos/owner/repo/README.md` — файл в GitHub
- `postgres://localhost/db/table/schema` — схема таблицы PostgreSQL

Сервер может уведомлять хост об изменении ресурса через subscription-механизм.

### Prompts (шаблоны)

Предопределённые шаблоны взаимодействия, которые пользователь активирует вручную. Принимают аргументы. **Важное отличие от Tools:** Prompts вызываются пользователем через UI хоста, не LLM.

Типичные примеры:
- `review_pull_request(pr_url)` — стандартный промпт для code review
- `summarize_jira_sprint(sprint_id)` — отчёт о ходе спринта

Применение: стандартизация повторяющихся задач в команде, встроенные команды в интерфейс хоста (slash commands в Cursor).

## Жизненный цикл запроса

### Фаза инициализации

1. Хост запускает сервер (stdio) или открывает соединение (HTTP)
2. Client отправляет `initialize` с версией протокола и capabilities
3. Server отвечает своими capabilities
4. Client подтверждает `initialized`
5. Хост запрашивает `tools/list`, `resources/list`, `prompts/list`
6. Список инструментов и их description включается в системный промпт модели

### Фаза выполнения

1. Пользователь отправляет сообщение хосту
2. LLM получает контекст + список Tools из системного промпта
3. LLM принимает решение вызвать инструмент
4. Хост передаёт вызов через MCP Client на сервер
5. Server выполняет действие, возвращает content-блоки
6. Хост добавляет результат в контекст диалога
7. LLM формирует финальный ответ

### Sampling: LLM на стороне сервера

Sampling — механизм, при котором сервер может запросить у хоста LLM-completion в ходе обработки запроса. Позволяет серверу использовать модель для промежуточных вычислений: суммаризация больших результатов до передачи в контекст.

Хост контролирует все параметры Sampling: модель, температуру, max_tokens. Сервер не может самостоятельно вызвать LLM — только через посредничество хоста.

## Транспорты: stdio vs HTTP+SSE

### stdio (локальный транспорт)

Хост запускает сервер как дочерний процесс. Обмен через stdin/stdout (newline-delimited JSON).

**Когда использовать:**
- Доступ к локальной файловой системе
- Локальные базы данных (SQLite, PostgreSQL на localhost)
- Инструменты командной строки: git, docker, kubectl
- IDE-плагины для среды разработчика

**Преимущества:** простота, нет сетевых зависимостей, изоляция на уровне процессов ОС.

**Ограничения:** только локально, один экземпляр на один Client, сервер живёт пока жив хост.

### HTTP + SSE (удалённый транспорт)

Запросы от Client — через HTTP POST. Ответы — через Server-Sent Events (SSE). Streamable HTTP (версия 2025-03-26) — более гибкий вариант с двусторонней потоковой передачей.

**Когда использовать:**
- Облачные сервисы: GitHub, Jira, Notion, Slack
- Корпоративные системы за firewall
- Multi-tenant серверы: один сервер для нескольких пользователей

**Требования безопасности:** HTTPS обязателен в production, OAuth 2.1, CORS-политики для веб-клиентов.

## Подключение к реальным системам

### GitHub

`github/github-mcp-server` — официальный сервер, написан на Go.

Возможности: управление репозиториями, Issues и Pull Requests, GitHub Actions, поиск по коду.

```json
{
  "mcpServers": {
    "github": {
      "command": "docker",
      "args": [
        "run", "-i", "--rm",
        "-e", "GITHUB_PERSONAL_ACCESS_TOKEN",
        "ghcr.io/github/github-mcp-server"
      ],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_xxxxx"
      }
    }
  }
}
```

Токен передаётся через переменную окружения, не в аргументах командной строки. Без Docker: собрать бинарник через `go build ./cmd/github-mcp-server` и использовать его как `command`.

### Jira (Atlassian)

Официальный удалённый сервер от Atlassian. Работает как облачный сервис без локальной установки.

Возможности: создание, поиск и обновление задач, JQL-запросы (`assignee = currentUser() AND status != Done`), управление спринтами.

Аутентификация: OAuth 2.1 через Atlassian Identity Provider.

### Notion

Официальный текущий вариант — удалённый сервер от Notion, без локальной установки.

```json
{
  "mcpServers": {
    "notion": {
      "url": "https://mcp.notion.com/mcp"
    }
  }
}
```

Аутентификация: OAuth через браузер при первом подключении. Если клиент не поддерживает remote MCP — использовать `mcp-remote` как прокси:

```json
{
  "mcpServers": {
    "notion": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "https://mcp.notion.com/mcp"]
    }
  }
}
```

Возможности: чтение и создание страниц, работа с базами данных Notion, полнотекстовый поиск по рабочему пространству.

### Локальные базы данных

**PostgreSQL:**
- Транспорт: stdio
- По умолчанию read-only режим
- Рекомендация: отдельный database user с минимальными правами специально для MCP

**SQLite:**
- Поддержка чтения и записи (настраивается)
- Удобен для прототипов и локальной разработки

**Архитектурные рекомендации для БД:**
- Логировать все SQL-запросы от MCP в отдельный audit-лог
- В production не давать MCP права на `DROP`, `DELETE`, `TRUNCATE` без явного разрешения
- Connection pooling (PgBouncer) для управления нагрузкой

## Безопасность и авторизация

### Угрозы, специфичные для MCP

**Tool Poisoning** — вредоносный сервер внедряет скрытые инструкции через description инструмента. Description попадает в системный промпт модели.

Защита: хост отображает описания инструментов до установки соединения, пользователь подтверждает добавление сервера.

**Prompt Injection через ресурсы** — контент ресурса (файл, результат API) содержит инструкции для LLM, замаскированные под данные.

Защита: разграничение trusted/untrusted контента в системном промпте, output filtering, обязательное подтверждение для критичных операций.

**Эскалация привилегий через Sampling** — сервер формирует prompt для Sampling с скрытыми инструкциями.

Защита: хост контролирует все Sampling-запросы, аудит с полным промптом, quotas на количество запросов.

### Принципы безопасной архитектуры

| Принцип | Реализация |
|---------|-----------|
| **Минимальные привилегии** | Для GitHub — scope `repo` вместо полного доступа; для PostgreSQL — read-only пользователь |
| **Human-in-the-loop** | Деструктивные операции требуют явного согласия пользователя |
| **Изоляция серверов** | Сервер не знает о других серверах в том же хосте |
| **Аудит** | Логирование всех вызовов инструментов и возвращаемых результатов |
| **Sandboxing** | Запуск локальных серверов в контейнере или chroot |

### OAuth 2.1 для удалённых серверов

- PKCE (RFC 7636) обязателен для публичных клиентов
- Dynamic Client Registration (RFC 7591) — автоматическая регистрация хостов
- Access tokens короткоживущие; refresh tokens хранятся в защищённом хранилище ОС (Keychain на macOS), не в конфигурационных файлах

## Trade-offs: MCP против альтернатив

### MCP vs прямые API-вызовы

| | Прямые API | MCP |
|-|-----------|-----|
| Контроль | Максимальный | Стандартизированный |
| Переносимость | Привязка к среде | Любой совместимый хост |
| Разработка | Ручная под каждую платформу | Один раз, работает везде |

Когда API: одноразовый скрипт, нужен тонкий контроль над HTTP, нет планов переносить.
Когда MCP: инструмент используется в нескольких хостах, нужна стандартизированная observability.

### MCP vs OpenAI function calling

- Function calling — механизм на уровне API конкретного провайдера
- MCP — архитектурный уровень выше: один сервер для нескольких провайдеров
- Хосты автоматически переводят MCP Tools в native tool calling целевой модели

### MCP vs LangChain tools

- LangChain и LlamaIndex tools — Python-first, тесная связь с фреймворком
- MCP — языко-независимый протокол (Python, TypeScript, Go, Rust)
- LangChain адаптируется к MCP через `langchain-mcp-adapters`
- MCP и AI-фреймворки не конкурируют — фреймворки принимают MCP как стандарт нижнего уровня

## Проектирование MCP-сервера: продуктовые компромиссы

### Количество тулов

Оптимум — **3–7 тулов** на один сервер. Больше 10 — модель начинает путаться при выборе. При большом функционале — дробить на несколько узких серверов.

### Качество description

AI выбирает инструмент по тексту в `description`. Это не документация для людей — это промпт для модели.

```
# Плохой description:
Creates a Jira issue

# Хороший description:
Создаёт задачу в Jira. Использовать, когда пользователь просит завести тикет
или багрепорт. НЕ использовать для комментариев — для них есть add_comment.
Требует project_key и summary. Возвращает JSON с issue_key.
```

### Деструктивные операции

Tools, которые удаляют или необратимо меняют состояние, должны требовать явного подтверждения. Используй annotations (`destructive: true`, `idempotent: false`).

Паттерн двух шагов: `prepare_delete()` возвращает план и токен подтверждения, `confirm_delete(token)` выполняет.

### Eager loading и расход контекста

MCP-серверы загружают все tool descriptions в системный промпт сразу при подключении. Три подключённых сервера (GitHub, Jira, Notion) занимают около 8% контекстного окна до первого запроса пользователя.

Рекомендации:
- Подключать только те серверы, которые реально нужны в текущей задаче
- Отключать неиспользуемые серверы между сессиями
- Для редко используемых инструментов рассматривать Skills (lazy loading) вместо MCP

### MCP vs Skills

| Стандарт | Паттерн | Когда использовать |
|----------|---------|-------------------|
| **MCP** | Eager loading — всегда доступен | Прямой доступ к системам: GitHub, Jira, БД |
| **Skills** | Lazy loading — загружается по необходимости | Procedural knowledge: методологии, процедуры деплоя |

Community-консенсус 2026: для долгосрочной экспертизы — Skills (экономия контекста); для интеграций с реальными системами — MCP.

### MCP vs CLI

Для инструментов с зрелым CLI (git, gh, docker, kubectl, aws-cli) bash-команды через terminal оказываются дешевле и надёжнее. Бенчмарк 2026 года:
- MCP использует в 4–32 раза больше токенов, чем CLI на идентичных задачах
- Reliability: 100% у CLI vs 72% у MCP (TCP-таймауты)
- Стоимость на 10K операций в месяц: \$3.20 (CLI) vs \$55.20 (MCP)

Когда MCP оправдан:
- Remote SaaS с OAuth (Workday, Salesforce, Notion, Linear, Figma) — нет CLI
- Multi-tenant с per-user auth
- Enterprise governance с audit trails

Гибридный паттерн (как в Claude Code): Bash для git, file operations, grep; MCP для Firecrawl, Playwright, Slack.

## Ключевые выводы

- MCP устраняет M×N проблему интеграций: один сервер работает в любом совместимом хосте. Миграция между LLM-провайдерами — вопрос конфигурации, не переписывания кода.
- Три примитива (Tools, Resources, Prompts) покрывают все ключевые сценарии. Правильный выбор примитива — половина успеха интеграции.
- Безопасность требует явного проектирования: минимальные привилегии, human-in-the-loop, аудит и защита от Tool Poisoning.
- MCP не конкурирует с function calling и AI-фреймворками, а создаёт слой переносимости поверх них.
- Продуктовые компромиссы 2026: 3–7 тулов на сервер, description как промпт, явное подтверждение для деструктивных операций, учёт eager loading, гибрид с CLI для инструментов с зрелым терминальным интерфейсом.
