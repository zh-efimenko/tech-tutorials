Ведущие AI-инструменты разработки несовместимы с жёсткими NDA по умолчанию, и это не дефект продукта и не недосмотр провайдеров. Большинство API сохраняют входящие данные на 30 дней для целей мониторинга злоупотреблений (abuse-мониторинга) — внутренней проверки запросов на нарушение правил использования (генерация вредоносного кода, попытки jailbreak, спам). Потребительские интерфейсы — ChatGPT и веб-чат Claude — удерживают данные дольше и в части случаев используют их для дообучения моделей. Команда, развернувшая AI-разработку без понимания этих моментов, рано или поздно сталкивается с утечкой конфиденциальных данных.

## Кейс Samsung

30 марта 2023 года стало широко известно, что инженеры подразделения Samsung Semiconductor за 20 дней допустили три независимые утечки конфиденциальных данных в ChatGPT. Запрет на использование сервиса был снят 11 марта — формально для того, чтобы не сдерживать продуктивность команды. Дальнейшая цепочка событий выглядит так:

- сотрудник скопировал в ChatGPT исходный код программы для скачивания внутренней базы полупроводниковых данных и попросил предложить вариант оптимизации;
- другой инженер загрузил код, идентифицирующий дефектное оборудование, и попросил отладить его;
- третий загрузил запись внутреннего совещания, чтобы автоматически сгенерировать протокол.

Инциденты вскрыла внутренняя система мониторинга, зафиксировавшая аномальные передачи данных. Реакция Samsung была мгновенной и архитектурной по характеру:

- лимит на запрос **1024 байта** (около 256 слов), физически исключающий загрузку существенного блока кода или документа;
- развёртывание DLP-системы с pattern matching и поведенческим анализом;
- обязательное обучение всех сотрудников с разбором конкретных сценариев нарушений;
- запуск собственной внутренней AI-платформы;
- предупреждение о возможности увольнения за повторные нарушения.

Главный архитектурный вывод: политика зависит от соблюдения требований сотрудниками, а это соблюдение, в свою очередь, опирается на индивидуальное суждение в каждом промпте, каждой сессии и каждый день. Архитектурные решения — локальные модели, прокси с PII-маскировкой, клиентская обработка — переносят защиту с уровня поведения сотрудника на уровень системного ограничения. **Архитектура надёжнее политики** именно потому, что не требует непрерывного идеального соблюдения правил.

Параллельная история подтверждает обратный полюс той же проблемы. Компании, которые после появления ChatGPT ввели тотальный запрет, столкнулись с тем, что сотрудники начали использовать AI с личных устройств и аккаунтов, делая утечки менее заметными и неподконтрольными. Запрет без замены ломается так же надёжно, как разрешение без архитектурных ограничений.

## Что попадает в обучающие данные провайдеров

Само по себе наличие у провайдера политики о том, что обучение на пользовательских данных не ведётся, не означает, что данные не сохраняются. У крупных провайдеров по умолчанию сохранение включено, а обучение — отключено; это два независимых параметра, и для архитектора важно понимать, какой именно из них отключён в его конкретной конфигурации.

**OpenAI: что хранится по умолчанию:**

- `chat/completions`, `responses`, `embeddings`, `moderations` — 30 дней для мониторинга злоупотреблений, без обучения.
- `assistants`, `threads`, `vector_stores`, `files`, `batches`, `fine_tuning` — хранятся до явного удаления через API; это сервисы с сохранением состояния по дизайну.

**Anthropic API: что хранится по умолчанию:**

- Messages API и Token Counting — 30 дней для мониторинга злоупотреблений.
- Claude Code (коммерческий) — 30 дней.

В планах **Free, Pro и Max** Anthropic данные хранятся **пять лет**, если пользователь разрешил использование для улучшения модели, и 30 дней — если не разрешил. У OpenAI **потребительский ChatGPT** работает по модели **opt-out**: сотрудник по умолчанию делится данными с провайдером, пока явно не отключит эту опцию в настройках. Этим объясняется, почему инциденты уровня Samsung происходят именно через веб-интерфейс ChatGPT, а не через корпоративные API.

## Модели классификации данных для AI-разработки

Вывод из кейса Samsung — архитектурное ограничение надёжнее политики — нужно превратить в **инженерный артефакт**. Начинается это с **классификации данных**: команда явно перечисляет классы, проходящие через её системы — от публичной документации до клиентских PII и производственных секретов, — и для каждого фиксирует список разрешённых AI-инструментов.

Без такого перечня обсуждение упирается в один из двух крайних вариантов — запретить ChatGPT целиком или разрешить целиком, — и в обоих случаях команда не понимает, какие именно данные защищает запрет и какие рабочие сценарии блокируются разрешением.

### Методология анализа чувствительности

Базовая четырёхуровневая схема — то, что Samsung был вынужден построить уже после инцидента, и то, что у западных банков и медтех-компаний работает по умолчанию:

- **Публичные данные.** Документация, код с открытым исходным кодом, публичные спецификации API. Допустимы любые инструменты, включая потребительские ChatGPT и Claude.
- **Внутренние данные.** Бизнес-логика, архитектура сервисов, внутренние процессы. Допустимы корпоративные API с подписанным DPA и включённым ZDR; потребительский ChatGPT недопустим.
- **Конфиденциальные данные.** API-ключи, данные клиентов, интеллектуальная собственность. Допустимы только локальные модели или управляемые решения в собственной VPC (Bedrock в собственной VPC, Azure OpenAI с Private Link); внешние API запрещены.
- **Критические данные.** Секреты, PII, финансовые транзакции, медицинская информация. Допустимы только локальные модели с дополнительной фильтрацией; даже управляемый провайдер с BAA не всегда покрывает все требования.

### Матрица данных и инструментов

Конкретная архитектурная привязка может выглядеть следующим образом:

- **Публичные данные.** Любой инструмент по выбору команды.
- **Внутренние данные.** Claude API или OpenAI API в коммерческом плане с подписанным DPA; обязательная маршрутизация через корпоративный шлюз с логированием.
- **Конфиденциальные данные.** Bedrock с PrivateLink, Azure OpenAI с Private Link или Vertex AI с [VPC Service Controls](https://cloud.google.com/vpc-service-controls/docs/overview); в качестве альтернативы — локальный Qwen 2.5-Coder.
- **Критические данные.** Локальная модель плюс PII-маска на прокси; обмен с любым внешним провайдером исключён.

Эта матрица не является догмой. Она задаёт отправную точку для разговора с командой соответствия требованиям и переводит обсуждение в структурированный выбор инструмента под класс данных.

### Инструменты автоматической классификации и их пределы

Идея переложить классификацию на инструмент привлекательна, но работает только частично:

- [Microsoft Purview](https://learn.microsoft.com/en-us/purview/information-protection) размечает документы и письма по уровню чувствительности, и эта разметка наследуется через интеграцию с DLP-системами в момент передачи данных.
- **DLP-системы** ловят PII по паттернам (номера карт, телефоны, SSN), API-ключи и стандартные форматы документов.
- [Pre-commit-хуки](https://pre-commit.com/) на уровне git-репозитория блокируют попадание секретов уже в исходный код.

Что **не ловится** автоматическими инструментами:

- Исходный код как таковой: DLP не способна интерпретировать блок Python-кода как интеллектуальную собственность, потому что паттерны не совпадают;
- Стратегические тексты, аналитика, проектные спецификации: формат произвольный, ключевых слов нет;
- Технические спецификации без явных маркеров чувствительности.

Из этого следует, что технические средства контроля образуют **первую линию многоуровневой защиты**, но не полную защиту. Их необходимо дополнять архитектурным ограничением (что в принципе доступно из инструмента) и культурой команды.

## Локальные модели: бенчмарки, лицензии, VRAM

Матрица классификации показывает, что для конфиденциального и критического классов данных альтернативой внешним API служит **локальная модель**. Дальнейший разбор фиксирует конкретные цифры, лицензии и требования по VRAM, на которые опирается этот выбор.

### Текущий ландшафт моделей с открытым исходным кодом

Наиболее практичным single-GPU выбором для кода на текущий момент является [Qwen 2.5-Coder 32B Instruct](https://qwenlm.github.io/blog/qwen2.5-coder-family/) от Alibaba, выпущенный 11 ноября 2024 года:

- [HumanEval](https://arxiv.org/abs/2107.03374) pass@1 — **92,7%** (для сравнения: GPT-4o показывает примерно тот же уровень; Claude Sonnet 4.6 и Opus 4.7 опережают на задачах сложного reasoning, но отрыв уже не кратный);
- Aider (code repair, whole) — **73,7%**, сопоставимо с GPT-4o;
- BigCodeBench (full, instruct) — **49,6%**;
- контекст 128K токенов;
- лицензия [**Apache-2.0**](https://www.apache.org/licenses/LICENSE-2.0) без ограничений на коммерческое использование.

[DeepSeek Coder V2 Lite](https://github.com/deepseek-ai/DeepSeek-Coder-V2) (16B параметров в MoE, 2,4B активных) — альтернатива для GPU объёмом 12 GB: HumanEval 81%, контекст 128K, лицензия DeepSeek custom (коммерческое использование разрешено, но требует отдельного юридического обзора).

[Qwen3-Coder-480B-A35B-Instruct](https://qwenlm.github.io/blog/qwen3-coder/) (MoE, 480B total, 35B активных, native context 256K, расширяется до 1M через YaRN) — передовой уровень среди моделей с открытым исходным кодом на SWE-Bench, но требует около 220–230 GB VRAM в квантизации Q3 и multi-GPU-сетапа. Это уже не локальная разработка на ноутбуке, а серьёзная серверная инвестиция.

В феврале 2026 года Qwen выпустили [**Qwen3-Coder-Next**](https://qwen.ai/blog?id=qwen3-coder-next) — гибридный MoE на базе Qwen3-Next с 80B total / **3B активных** параметров. Apache-2.0, native context 256K. На SWE-Bench Verified модель набирает **70,6%** (SWE-Agent scaffold) — на уровне DeepSeek-V3.2 (70,2%) и заметно ниже Claude Sonnet 4.6 (79,6%) и Opus 4.7 (87,6%). Главное преимущество — сверхнизкий активный footprint: 3B активных параметров делают её самым быстрым open-source-вариантом для агентских рабочих нагрузок и снимают требование multi-GPU-конфигурации. Для команд, готовых терпеть отставание от проприетарных моделей в обмен на полный контроль, это сейчас наиболее практичный выбор поверх Qwen 2.5-Coder 32B.

[CodeLlama](https://arxiv.org/abs/2308.12950) в любой конфигурации представляет собой устаревший выбор: HumanEval 67,8% для версии 70B-Instruct против 88,4% у Qwen 2.5-Coder 7B-Instruct. В новых проектах применять её не имеет смысла.

### Карта VRAM для практического выбора

Реальные цифры в квантизации Q4, на которые можно опираться при планировании железа:

- **6–8 GB.** Qwen 2.5-Coder 7B-Instruct Q4 (HumanEval 88,4%) — единственный разумный выбор для слабого GPU. На CPU i7 модель выдаёт около 9 ток/с, чего достаточно для коротких автокомплитов, но не для агентных задач.
- **10–12 GB.** DeepSeek Coder V2 Lite Q4 (81%) или Qwen 2.5-Coder 14B Q4. Подходящее железо — RTX 3090, 4080, M2/M3 Pro.
- **20–24 GB.** **Qwen 2.5-Coder 32B Q4** (92,7%) на RTX 3090 или 4090. Около 25 ток/с на 4090 — этого хватает для интерактивной работы и для агентов.
- **48+ GB.** Qwen 2.5-Coder 32B в более высокой квантизации или DeepSeek V2 Lite в FP16.
- **Multi-GPU, 130+ GB.** DeepSeek Coder V2 full (236B, 21B активных).
- **Multi-GPU, 220–230 GB.** Qwen3-Coder-480B в квантизации Q3 — серверная конфигурация, а не локальная разработка.
- **Single-GPU 40–60 GB.** Qwen3-Coder-Next (80B / 3B активных) в FP8/AWQ — топовая open-source-модель для агентских нагрузок без multi-GPU-стека.

### Лицензии моделей и ограничения на коммерческое использование

Эту часть часто упускают, хотя именно она определяет, что в итоге разрешит юридический отдел:

- **Apache-2.0** (Qwen) — без ограничений на коммерческое использование, без условий по числу MAU и без обязательств по атрибуции в продукте. Самый чистый вариант для бизнеса.
- [Llama Community License](https://www.llama.com/llama3_1/license/) (Meta) — действует ограничение по числу MAU; для крупных компаний это может оказаться блокером.
- [DeepSeek custom](https://github.com/deepseek-ai/DeepSeek-Coder-V2/blob/main/LICENSE-MODEL) — коммерческое использование разрешено, но условия отличаются от стандартных OSI-лицензий и требуют обзора со стороны юридической команды.

## Инференс-инфраструктура для self-hosting в продакшене

Выбрать локальную модель — это половина задачи; вторая половина состоит в том, чтобы **запустить** её под продакшн-нагрузкой так, чтобы пропускная способность и задержка соответствовали реальным сценариям использования. Скачать веса и поднять процесс — это ещё не self-hosting, а прототип; разрыв между прототипом и продакшн-инфраструктурой измеряется порядками величин по пропускной способности, надёжности и операционной нагрузке.

### Когда self-hosted перестаёт быть игрушкой

Почти весь спектр потребностей закрывают два рабочих инструмента:

- [Ollama](https://ollama.com/) — без настройки, один бинарник, поддержка резервного режима на CPU. Подходит для разработки на ноутбуке, прототипа и локальной работы одного инженера.
- [vLLM](https://docs.vllm.ai/en/latest/) — движок производственного уровня с [PagedAttention](https://arxiv.org/abs/2309.06180), [continuous batching](https://www.anyscale.com/blog/continuous-batching-llm-inference) и OpenAI-совместимым HTTP-API. Фактический стандарт self-hosted-инференса в продакшене.

Дополнительно полезно знать про два инструмента нишевого применения:

- [SGLang](https://github.com/sgl-project/sglang) с [RadixAttention](https://arxiv.org/abs/2312.07104) выигрывает у vLLM на нагрузках с большим количеством одинаковых префиксов в запросах.
- [TensorRT-LLM](https://github.com/NVIDIA/TensorRT-LLM) от NVIDIA даёт лучший результат на одиночном запросе за счёт компиляции под конкретное железо, но хуже масштабируется на высокой параллельной нагрузке.

### Прямое сравнение: Ollama против vLLM

[Подробный бенчмарк от Red Hat Developers](https://developers.redhat.com/articles/2025/08/08/ollama-vs-vllm-deep-dive-performance-benchmarking) на одном NVIDIA A100 (40 GB) с моделью [Llama 3.1 8B](https://ai.meta.com/blog/meta-llama-3-1/) даёт точные цифры:

- **Пропускная способность.** vLLM — около 793 ток/с на пике, Ollama — 41 ток/с.
- **Задержка P99.** vLLM — около 80 мс, Ollama — 673 мс.
- **Time to first token при низкой параллельной нагрузке.** vLLM — 10–14 мс, Ollama — 65 мс.
- **Поведение при 50+ параллельных запросах.** Ollama с конфигом по умолчанию начинает таймаутить, vLLM продолжает линейно масштабироваться.

Даже после тюнинга Ollama под параллельные запросы (`OLLAMA_NUM_PARALLEL=32`) разрыв сохраняется: архитектурно Ollama не рассчитана на continuous batching, и поэтому рост параллельной нагрузки не помогает — помогает только смена инструмента.

### Production Stack vLLM: что мониторить

В январе 2025 года команда vLLM выпустила [Production Stack](https://github.com/vllm-project/production-stack) — Helm-чарт для Kubernetes с маршрутизацией запросов, поддержкой нескольких моделей, выгрузкой KV-кэша на CPU-память и автомасштабированием через [KEDA](https://keda.sh/). Этот пакет переводит развёртывание в собственной инфраструктуре с уровня отдельного процесса на уровень полноценной продакшн-инфраструктуры.

**Метрики vLLM в Prometheus**

- `vllm:num_requests_running` — актуальная нагрузка инференс-сервера.
- `vllm:num_requests_waiting` — глубина очереди ожидания; главный сигнал для масштабирования.
- `vllm:gpu_cache_usage_perc` — заполнение KV-кеша; превышение 90% указывает на то, что параллельные запросы необходимо ограничивать.
- `vllm:time_to_first_token_seconds` и `vllm:time_per_output_token_seconds` — метрики качества обслуживания.

### Квантизация и форматы весов

**vLLM** работает с [AWQ](https://arxiv.org/abs/2306.00978) и [GPTQ](https://arxiv.org/abs/2210.17323) — форматами, оптимизированными под GPU-ядра NVIDIA. [GGUF](https://github.com/ggerganov/ggml/blob/master/docs/gguf.md), формат **Ollama** и [llama.cpp](https://github.com/ggerganov/llama.cpp), относится к другому миру и ориентирован на CPU и Apple Silicon с Metal. Между этими форматами нельзя просто переключиться: для смены целевого движка веса требуется переконвертировать.

Практическое следствие следующее: переход с **Ollama** на **vLLM** на той же модели означает скачивание нового варианта весов (например, не **Qwen2.5-Coder-32B GGUF**, а **Qwen2.5-Coder-32B-AWQ**), а не просто смену процесса.

### Агенты-кодеры как специфическая нагрузка

Агенты-кодеры представляют собой одну из самых сложных рабочих нагрузок для инференса:

- Один шаг агента включает системный промпт с контекстом репозитория (10K+ токенов), многоэтапную историю диалога и вызовы инструментов;
- Одна задача решается за 10–50 вызовов модели;
- Одновременно критичны пропускная способность, низкий TTFT и эффективное кэширование префиксов.

Под такую нагрузку **Ollama** не подходит структурно — необходим движок с **continuous batching**. И именно здесь **SGLang** с **RadixAttention** бывает сильнее, чем **vLLM**: значительная часть префикса (системный промпт) переиспользуется между шагами агента, и **RadixAttention** утилизирует этот факт более эффективно.

## Гибридные архитектуры: три рабочих паттерна

Локальный инференс закрывает критический и конфиденциальный классы данных, но не отменяет ценности внешних моделей на сложных рассуждениях. Из этого следует, что устойчивая архитектура почти всегда оказывается гибридной.

### Паттерн 1: PII-маска на прокси перед внешней моделью

Архитектура такого паттерна построена следующим образом:

- Команда обращается к LLM через корпоративный шлюз — например, через [LiteLLM](https://docs.litellm.ai/) в режиме OpenAI-совместимого прокси;
- На прокси подключён [Microsoft Presidio](https://microsoft.github.io/presidio/samples) в роли защитного фильтра; Presidio распознаёт PII (имена, email, номера карт, телефоны), PHI (медицинские идентификаторы) и доменные сущности через настраиваемые распознаватели;
- Прокси работает в одном из четырёх режимов: `pre_call` (фильтрация входа), `during_call` (фильтрация по ходу стриминга), `post_call` (фильтрация выхода), `logging_only` (фильтрация только перед записью в логи);
- Доступные действия — **MASK** (замена плейсхолдером, например `<EMAIL_ADDRESS>`) или **BLOCK** (полное отклонение запроса с возвратом ошибки пользователю).

Конфигурация пороговых значений по типам сущностей образует важную часть тюнинга:

```yaml
presidio_score_thresholds:
  ALL: 0.7
  CREDIT_CARD: 0.8
  EMAIL_ADDRESS: 0.6
pii_entities_config:
  CREDIT_CARD: BLOCK
  EMAIL_ADDRESS: MASK
```

**Presidio** надёжно ловит стандартные форматы PII и PHI, но — как и DLP — не видит исходный код, внутренние идентификаторы систем и описательные тексты с конфиденциальной информацией. Из этого следует, что PII-маска не заменяет локальную модель для критических данных — она защищает от случайной утечки PII в промптах команды.

### Паттерн 2: RAG с локальным эмбеддингом

Архитектура паттерна выглядит следующим образом:

- Векторное хранилище развёрнуто в собственной инфраструктуре — [Qdrant](https://qdrant.tech/), [Weaviate](https://weaviate.io/), [Milvus](https://milvus.io/) или альтернативы с открытым исходным кодом;
- Эмбеддинг-модели запускаются локально ([Sentence Transformers](https://www.sbert.net/) или открытые модели с Hugging Face);
- Внешняя LLM получает только обобщённые фрагменты документов в качестве контекста, а не оригинальные файлы целиком.

Подводный камень, который часто упускают: **фрагменты могут содержать секреты**. Если в коде где-то захардкожен ключ, то RAG-фрагмент с этой строкой уйдёт наружу так же, как и сам код. Поэтому RAG-конвейер требует той же фильтрации (Presidio, git-secrets, regex-сканеры), что и прямой промпт.

### Паттерн 3: маршрутизация по уровню секретности

Архитектура паттерна:

- Промежуточный классификатор анализирует входящий запрос и определяет уровень чувствительности;
- Маршрутизация выглядит так: публичные запросы уходят в Claude API (Sonnet 4.6) или GPT-5.2, чувствительный код — в локальный Qwen 2.5-Coder или Qwen3-Coder-Next на vLLM;
- Реализация — [LangChain](https://www.langchain.com/) с собственным маршрутизатором или LiteLLM с правилами маршрутизации.

Главный риск этого паттерна состоит в том, что **ложноотрицательное срабатывание классификатора равно утечке**. Если маршрутизатор по ошибке считает чувствительный запрос публичным и отправляет его в Claude API, это и есть тот самый инцидент. Поэтому классификатор должен оставаться **консервативным**: в любом спорном случае запрос уходит на локальную модель.

Тестирование маршрутизатора представляет собой отдельную задачу: red-team со специально сконструированными запросами, мониторинг качества классификации, регулярная переразметка корпусов.

### Управляемые альтернативы корпоративного уровня

Если команда не готова строить и поддерживать собственный прокси, рынок предлагает управляемые решения с похожей семантикой:

- [Azure OpenAI Data Zones](https://azure.microsoft.com/en-us/blog/announcing-the-availability-of-azure-openai-data-zones-and-latest-updates-from-azure-ai/): data residency в зонах US и EU, CMEK для шифрования собственными ключами, Private Link для изоляции от публичного интернета, сертификаты HIPAA, SOC 2 и FedRAMP.
- [Amazon Bedrock Guardrails](https://aws.amazon.com/bedrock/security-privacy-responsible-ai/): PII detection и редактирование, фильтрация до 88% токсичности на нескольких моделях, эндпоинты PrivateLink, KMS для шифрования.
- [Google Vertex AI](https://cloud.google.com/vertex-ai): CMEK, [VPC Service Controls](https://cloud.google.com/vpc-service-controls/docs) для строгой сегментации, журналы аудита.

**Компромисс управляемых вариантов очевиден**: меньше работы для команды, но больше vendor lock-in и выше расходы. Для команды до 30 человек это часто рациональный выбор; для крупного банка, который хочет независимости от конкретного облака, такой выбор уже не подходит.

## Фильтрация и очистка данных

Гибридная архитектура отвечает на вопрос **где** обрабатывать данные. Этот раздел отвечает на вопрос **чем** их чистить на каждом уровне.

### Поиск секретов в репозитории и в истории git

Базовый набор инструментов, который должен присутствовать в каждом проекте независимо от использования AI:

- [git-secrets](https://github.com/awslabs/git-secrets) — pre-commit-хук, ловит учётные данные AWS и расширяемые паттерны (внутренние ключи, токены).
- [TruffleHog](https://github.com/trufflesecurity/trufflehog) — поиск секретов в **полной истории репозитория**, включая удалённые коммиты. Это важно, если AI-инструмент имеет доступ ко всей истории через git-команды.
- [detect-secrets](https://github.com/Yelp/detect-secrets) от Yelp — файл-эталон, фиксирующий существующие известные ложноположительные срабатывания, плюс регулярные сканы в CI.

Эти инструменты ловят известные форматы: ключи AWS, токены GitHub, JWT, API-ключи популярных сервисов. Внутренние секреты с произвольным форматом требуется описывать как кастомные правила.

### Очистка промптов в реальном времени

На уровне прокси перед LLM работают несколько слоёв фильтрации:

- **Регулярные выражения.** Самый быстрый и предсказуемый слой. Ловит явные API-ключи, email-адреса, телефоны, IP-адреса. Недостатки — ложноположительные срабатывания и неспособность поймать парафраз.
- **NLP-классификация через Presidio Text Analyzer.** NER-модели распознают имена, географические объекты, организации, идентификаторы. Точнее, чем регулярные выражения, но добавляет 50–200 мс задержки на запрос и сама требует гарантий приватности — модель должна жить внутри периметра.
- **Обнаружение на базе LLM через [Presidio LangExtract](https://microsoft.github.io/presidio/samples/python/langextract/).** Гибкий вариант для нестандартных сущностей. Может работать через Ollama локально с моделью вроде Gemma или Llama. Недостатки — дороговизна по токенам, медленность, нестабильность на пограничных случаях.

**Практическая комбинация для продакшна выглядит так:** регулярные выражения для очевидных паттернов в `pre_call`, NLP-классификация для PII в `post_call` (ловит то, что модель случайно сгенерировала в ответе), LLM-обнаружение — для особых сценариев вроде поиска внутренних идентификаторов клиента в свободном тексте.

### Защита от prompt injection и jailbreak во время выполнения

Поиск секретов и очистка промптов защищают данные **до** их отправки в модель и ничего не делают со второй половиной угрозы — с тем, как модель реагирует на уже полученный ввод. За это отвечает отдельный слой — **guardrails**, работающие во время выполнения запроса (runtime guardrails): они проверяют ввод, рассуждения агента и вывод на признаки prompt injection, jailbreak и ухода агента от исходной цели.

Рабочие инструменты этого слоя:

- [LlamaFirewall](https://ai.meta.com/research/publications/llamafirewall-an-open-source-guardrail-system-for-building-secure-ai-agents/) от Meta (открытый исходный код, применяется в продакшене самой Meta) — три сканера: PromptGuard 2 как детектор jailbreak, Agent Alignment Checks как аудитор цепочки рассуждений агента на перехват цели, CodeShield как статический анализатор генерируемого кода. На бенчмарке AgentDojo базовая доля успешных атак без защиты составляет 17,6%; слоистая защита LlamaFirewall, по данным авторов, снижает её примерно до 1,75%.
- [NeMo Guardrails](https://github.com/NVIDIA/NeMo-Guardrails) от NVIDIA (Apache-2.0) — программируемые ограничения через DSL Colang, включая детекцию jailbreak и инъекций в промпте.
- [Lakera Guard](https://docs.lakera.ai/docs/prompt-defense) — коммерческий сервис проверки запросов в реальном времени: распознаёт prompt injection и jailbreak во вводе, выводе и на каждом шаге работы агента.

Ключевое ограничение, которое нельзя забывать: [исследование 2025 года](https://arxiv.org/abs/2504.11168) показало, что шесть распространённых систем защиты — включая Azure Prompt Shield и Meta Prompt Guard — обходятся инъекцией Unicode-символов (невидимые символы, омоглифы, маскировка через эмодзи) и состязательными техниками, в отдельных случаях вплоть до 100% успешного обхода. Вывод тот же, что и для фильтрации промптов: ни один слой не является непробиваемым, защита строится эшелонированно — проверка ввода, детекция инъекций, валидация вывода, поведенческий мониторинг.

### Политики для команды

Все перечисленные слои фильтрации остаются техническими — и потому неполными. Без культурных и процессных дополнений в них остаются дыры:

- **Чек-лист в code review.** Раздел о том, что нельзя отправлять в AI-чат, встраивается прямо в стандартный ревью-чек-лист. Не отдельный документ, который никто не читает, а ровно одна галочка в стандартной процедуре.
- **Обучение с конкретными примерами тревожных сигналов.** Не общее напутствие быть внимательным, а тренировка на реальных кейсах: вот пример промпта, который выглядит безобидно, но утекает архитектура; вот пример комментария в коде, который превращается в prompt injection.
- **Процедура реагирования на инциденты.** Сотрудник нашёл утечку — что делать дальше: кого уведомить, какие секреты ротировать, какие запросы на удаление отправлять провайдеру. Шаблон должен лежать в Confluence или Notion заранее, а не выдумываться в момент стресса.

## Модель угроз: OWASP Top 10 для LLM в AI-разработке

Фильтрация и архитектурные паттерны защищают от тех угроз, которые команда умеет назвать. Чтобы перечень угроз был не интуитивным, а систематическим, требуется опорная карта.

Для сетевых приложений у архитектора есть устоявшаяся карта угроз — OWASP Top 10. Для **LLM-приложений** ту же роль играет [OWASP Top 10 for LLM Applications](https://genai.owasp.org/resource/owasp-top-10-for-llm-applications-2025/).

### Актуальный список 2025

Десять рисков, отсортированных по комбинации вероятности и воздействия:

- **LLM01.** Prompt Injection.
- **LLM02.** Sensitive Information Disclosure.
- **LLM03.** Supply Chain Vulnerabilities.
- **LLM04.** Data and Model Poisoning.
- **LLM05.** Improper Output Handling.
- **LLM06.** Excessive Agency.
- **LLM07.** System Prompt Leakage.
- **LLM08.** Vector and Embedding Weaknesses.
- **LLM09.** Misinformation.
- **LLM10.** Unbounded Consumption.

### LLM01 Prompt Injection в AI-разработке

[Prompt injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection) эксплуатирует фундаментальное ограничение LLM: модель неспособна отличить системные инструкции от пользовательского ввода. Всё поступает в одно окно внимания, и атакующий получает возможность через данные перехватить управление.

Прямой prompt injection — это случай, когда пользователь напрямую вводит инструкцию вида **игнорируй предыдущие инструкции и сделай X**. Это базовый сценарий, который ловится большинством системных промптов и поверхностной фильтрацией.

Гораздо опаснее **indirect prompt injection**:

- атакующий коммитит в публичный репозиторий файл README с вредоносными инструкциями;
- агент-кодер в CI/CD читает этот README, чтобы понять структуру проекта;
- инструкции из README трактуются моделью как команды и выполняются с правами агента.

Реальный пример — [CVE-2024-5184](https://nvd.nist.gov/vuln/detail/CVE-2024-5184): уязвимость в LLM-почтовом ассистенте EmailGPT, через которую атакующий внедрял промпт в письмо и получал доступ к чувствительной информации в почте жертвы.

**Частичные меры защиты:**

- **Разделение привилегий.** Агент-кодер не должен иметь прав уровня admin. Если задача агента — предложить рефакторинг, ему не нужны права на `rm -rf` и `git push --force`.
- **Фильтрация вывода.** Вывод модели сканируется на признаки успешного injection — утечку системного промпта, неожиданные вызовы инструментов.
- **Canary-токены в системном промпте.** В системный промпт встраивается уникальная строка, которая не должна появляться в выводе. Если она появилась, кто-то занимается извлечением данных.
- **Регулярные red-team-проверки.** Автоматический red-team через [Promptfoo](https://promptfoo.dev/docs/red-team/owasp-llm-top-10), [Garak](https://github.com/NVIDIA/garak) или [PyRIT](https://github.com/Azure/PyRIT) встраивается в CI/CD как шаг верификации.

**Что не работает в чистом виде:** фильтрация ввода как единственная защита. Одну и ту же вредоносную инструкцию можно сформулировать тысячами способов — через парафразы, перевод на другой язык, кодирование в base64, разбивку по словам, ролевые сценарии. Сигнатурный фильтр перехватывает только варианты, заранее описанные в правилах, и атакующий всегда находит формулировку, которой в этих правилах нет.

### LLM02 Sensitive Information Disclosure

[LLM02 Sensitive Information Disclosure](https://genai.owasp.org/llmrisk/llm02-sensitive-information-disclosure) описывает риск раскрытия конфиденциальной информации несколькими путями:

- **Запоминание обучающих данных.** Базовая модель помнит фрагменты обучающего корпуса и может воспроизвести их дословно. Если в корпусе оказался чужой проприетарный код, он способен всплыть в ответе.
- **Утечка через context window.** Данные из предыдущих сессий или из RAG-источников появляются в выводе для пользователя, который не должен иметь к ним доступа.
- **Атаки выводом.** Атакующий через серию специально сконструированных запросов восстанавливает информацию о данных, на которых модель училась или которые она видит в RAG.

**Меры защиты:**

- **RBAC (Role-Based Access Control) на RAG-источники**: модель извлекает только то, что конкретный пользователь имеет право видеть.
- **Классификаторы вывода** для редактирования PII, API-ключей и внутренних URL в ответах модели.
- **Регулярный red-team** специально на атаки извлечения данных.

### LLM07 System Prompt Leakage

[LLM07 System Prompt Leakage](https://genai.owasp.org/llmrisk/llm07-system-prompt-leakage) особенно болезненно бьёт по AI IDE и агентам-кодерам, поскольку их системные промпты часто содержат **рабочие секреты**: URL внутренних API, идентификаторы проектов, а порой и API-ключи.

Правило, которое необходимо принять как архитектурную данность, звучит так: **системный промпт — это публичная информация по дизайну**. Атакующий извлекает его через стандартные jailbreak-техники (техники обхода ограничений): просьба повторить инструкции, кодирование в base64, эмуляция ролей. Всё, что помещено в системный промпт, нужно рассматривать как утёкшее с момента деплоя.

**Меры защиты:**

- В системном промпте остаются **только бизнес-логика** и **роль агента**; никаких секретов, ключей и внутренних URL.
- Чувствительные значения располагаются **в отдельном слое доступа** (ограничение частоты, ACL, RBAC), а не в промпте.
- Мониторинг логов на признаки утечки (см. canary-токены выше).

## Юридические аспекты и соответствие требованиям

Модель угроз OWASP описывает технические риски; параллельный слой — юридические обязательства, которые часто диктуют, какие технические решения вообще доступны команде.

Архитектор не обязан быть юристом, но обязан понимать, что именно подписывает DPO от его имени и какие технические ограничения это накладывает.

### Что реально означает Zero Data Retention

**Zero Data Retention (ZDR)** — это договорное обязательство провайдера **не сохранять** пользовательский ввод и вывод модели после обработки запроса. Это не равно утверждению **никогда ничего не хранится**, и архитектору важно видеть исключения из этого режима.

**ZDR у Anthropic API:**

- Применяется к Messages API и Token Counting.
- **Не применяется** к Code Execution и Programmatic Tool Calling: контейнеры исполнения кода хранят данные до 30 дней по дизайну этих фич.
- ZDR на Claude Code — отдельное соглашение на уровне организации через Anthropic Sales.
- ZDR на Bedrock, Vertex AI и Foundry — это уже не ZDR от Anthropic, а политика хранения данных соответствующей платформы.
- При обнаружении нарушения [Usage Policy](https://www.anthropic.com/legal/aup) Anthropic может удерживать данные до **двух лет** даже у организации с включённым ZDR.

**ZDR у OpenAI:** граница совпадает с разобранным выше разделением эндпоинтов. ZDR доступен для stateless-эндпоинтов (`chat/completions`, `responses`, `embeddings`, `moderations`, а также `audio/transcriptions`, `audio/translations`, `realtime`, `completions`) и несовместим с сервисами, удерживающими состояние до явного удаления (`assistants`, `threads`, `vector_stores`, `files`, `batches`, `fine_tuning`, `conversations`, `chatkit/threads`).

Дополнительно у OpenAI существует [EKM (External Key Management)](https://help.openai.com/en/collections/20000941-enterprise-key-management-ekm) — отдельная фича для шифрования собственными ключами через внешний KMS.

**Главное практическое следствие:** если команда хочет ZDR и при этом активно использует Assistants API или Batch API, эти требования несовместимы. Придётся либо отказаться от API с сохранением состояния, либо принять стандартный retention.

### HIPAA, GDPR, BAA и их следствия

**BAA (Business Associate Agreement)** — это документ, который провайдер подписывает с организацией, обрабатывающей PHI (защищённую медицинскую информацию). Без BAA любая работа с PHI через сервис по умолчанию означает нарушение HIPAA.

**Стандартные пути для PHI**

- [AWS Bedrock](https://aws.amazon.com/compliance/hipaa-eligible-services-reference/) с BAA: PrivateLink, KMS для шифрования, IAM для RBAC, CloudTrail для журналов аудита.
- [Google Vertex AI](https://cloud.google.com/security/compliance/hipaa-compliance) с BAA: VPC Service Controls для сегментации, CMEK, IAM, Cloud Logging.
- [Azure OpenAI](https://learn.microsoft.com/en-us/azure/compliance/offerings/offering-hipaa-us) с BAA: Private Link, Entra ID для RBAC, Key Vault, Microsoft Defender for Cloud.

Подводный камень BAA состоит в том, что подписание соглашения блокирует часть фич. У Anthropic BAA не покрывает web search и часть интеграций, и это означает невозможность одновременно иметь HIPAA-готовность и пользоваться встроенным поиском.

**GDPR.** Основной риск для AI-разработки в том, что [право на забвение (right to be forgotten)](https://gdpr-info.eu/art-17-gdpr/) конфликтует с обучением модели на данных. Если данные ушли в обучающий корпус, отозвать их оттуда практически невозможно. Режим ZDR частично снимает этот конфликт, потому что данные не сохраняются на стороне провайдера.

### NIST AI 600-1 Generative AI Profile

[Документ NIST AI 600-1](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-generative-artificial-intelligence), выпущенный в июле 2024 года, представляет собой адаптацию общего AI Risk Management Framework под специфику генеративного AI.

Структура документа:

- **12 рисков GenAI**, включая конфабуляции, приватность данных, IP, риски обесценивания человеческого труда, harmful bias (вредная предвзятость).
- **Четыре функции:** Govern (политики и роли), Map (контекст и риски), Measure (метрики и тесты), Manage (реакция и мониторинг).
- Привязка к [Executive Order 14110](https://www.federalregister.gov/documents/2023/11/01/2023-24283/safe-secure-and-trustworthy-development-and-use-of-artificial-intelligence) в США; европейский аналог — [AI Act 2024](https://eur-lex.europa.eu/eli/reg/2024/1689/oj).

NIST AI 600-1 задаёт **структуру для аудита**, а не готовый чек-лист. Он помогает ответить на вопрос **какие риски мы вообще учитываем**, но не снимает с архитектора ответственности за конкретные технические решения.

### EU AI Act и стандарты управления AI

NIST AI 600-1 — это рамка для добровольного аудита. Параллельно с ней с 2024 года вступает в силу первый обязательный закон об AI — [EU AI Act](https://artificialintelligenceact.eu/implementation-timeline/) (Regulation (EU) 2024/1689). Для команды, у которой есть европейские пользователи, это не теоретический документ: закон применяется по фазам, и ближайшие даты — рабочие.

**Фазы вступления в силу**

- 2 февраля 2025 — запрещённые практики (социальный скоринг, ряд биометрических сценариев) и требование к AI-грамотности персонала.
- 2 августа 2025 — обязательства провайдеров моделей общего назначения (GPAI): документация, описание обучающих данных, соблюдение авторских прав; запуск органов надзора, включая EU AI Office. 10 июля 2025 опубликован [GPAI Code of Practice](https://digital-strategy.ec.europa.eu/en/policies/contents-code-gpai) — добровольный инструмент для демонстрации соответствия; среди подписантов Anthropic, OpenAI, Google, Microsoft, Mistral, Amazon, IBM, Cohere.
- **2 августа 2026** — вступает в силу основная часть закона, включая режим для высокорисковых систем из Annex III, и становятся применимы все штрафы. Полномочия по штрафам GPAI (Article 101) активируются той же датой, но Комиссия объявила годичный grace period для подписантов Code of Practice, действующих добросовестно.
- 2 августа 2028 — требования к высокорисковому AI внутри уже регулируемых продуктов (Annex I). Срок продлён с 2027 года в результате политического соглашения по AI Omnibus от 7 мая 2026.

Штрафы привязаны к мировому обороту: до **7%** или 35 млн евро за запрещённые практики, до **3%** или 15 млн евро за нарушение прочих требований, включая высокорисковые системы и обязательства GPAI, и до 1% — за недостоверную информацию регулятору.

Рядом с законом стоит [ISO/IEC 42001:2023](https://www.iso.org/standard/42001) — первый сертифицируемый стандарт системы управления AI (AI Management System). Он не предписывает конкретные технические решения, а задаёт процесс — политики, роли, оценку рисков по циклу Plan-Do-Check-Act. Сертификацию по нему всё чаще запрашивают в корпоративных тендерах, поэтому для архитектора это ещё один внешний фактор, ограничивающий выбор инструментов.

## Три типовых сценария

### Сценарий 1: стартап с закрытым кодом

Условия задачи:

- команда 5–10 человек;
- закрытый исходный код без жёстких регуляторных требований;
- бюджет ограничен;
- скорость разработки важнее долгосрочной независимости от провайдера.

Архитектура решения:

- Claude API в коммерческом плане с подписанным DPA и включённым ZDR на уровне организации.
- Корпоративный шлюз (LiteLLM) с базовой фильтрацией секретов через регулярные выражения.
- Логирование запросов в виде метаданных, без payload, для аудита соответствия требованиям.
- Чёткая политика для команды: потребительский ChatGPT и Claude запрещены, вся AI-разработка идёт через корпоративный шлюз.

Что остаётся открытым: vendor lock-in на Anthropic, регуляторные ограничения сработают, если бизнес начнёт работать с европейскими клиентами или с медициной. План перехода — заранее предусмотреть возможность миграции на нескольких провайдеров через абстракцию LiteLLM.

### Сценарий 2: банк с данными клиентов

Условия задачи:

- работа с PII клиентов;
- сформированная команда соответствия требованиям;
- регуляторные требования (GDPR для зарубежных клиентов, в части случаев HIPAA);
- запрет на отправку данных клиентов наружу.

Архитектура решения:

- Qwen 2.5-Coder 32B AWQ на vLLM в Kubernetes-кластере с GPU-нодами.
- vLLM в режиме продакшн-стека с автомасштабированием через KEDA и метриками в Prometheus и Grafana.
- PII-маска через Presidio в режиме `pre_call` плюс `post_call` на корпоративном шлюзе.
- Локальное векторное хранилище (Qdrant) для RAG по внутренней документации.
- Журналы аудита в SIEM с retention по политике компании.
- Периодический red-team через Promptfoo для проверки модели угроз по OWASP.

Между двумя крайностями — внешний API и полностью собственное железо — есть третий путь, который часто оказывается рабочим для банка: **конфиденциальные вычисления (confidential computing)**. Это GPU-серверы с аппаратной доверенной средой исполнения (TEE) и сквозной аттестацией, где облачный провайдер не имеет доступа к данным внутри сервера. Примеры — [Azure NCCadsH100v5](https://learn.microsoft.com/en-us/azure/confidential-computing/overview-azure-products) (AMD SEV-SNP плюс NVIDIA H100, единая TEE на CPU и GPU), [Apple Private Cloud Compute](https://security.apple.com/blog/private-cloud-compute/) и [AWS Nitro Enclaves](https://aws.amazon.com/ec2/nitro/nitro-enclaves/). Такой вариант снимает часть инфраструктурной нагрузки собственного кластера, сохраняя гарантию, что данные клиентов не видны провайдеру.

Что остаётся открытым: инфраструктурная нагрузка существенна (GPU-команда, on-call для vLLM-кластера), а качество ответов модели на сложном reasoning ниже, чем у Claude Sonnet 4.6 / Opus 4.7. План — отслеживать выпуски моделей с открытым исходным кодом (Qwen3-Coder-Next, DeepSeek-V3.2, GLM-4.7) и обновлять веса по мере появления качественных вариантов.

### Сценарий 3: консалтинг с разными клиентами

Условия задачи:

- проекты разных уровней секретности;
- разные NDA с разными клиентами;
- команда 30+ человек;
- требуется гибкость в выборе модели под конкретную задачу.

Архитектура решения:

- LiteLLM-router в режиме маршрутизации по уровню секретности проекта (метка из CI/CD-окружения или из метаданных репозитория).
- Публичные задачи и проекты с открытым исходным кодом — Claude API (Sonnet 4.6 / Opus 4.7) или GPT-5.2 через управляемого провайдера с DPA.
- Чувствительные клиентские проекты — Bedrock в собственной VPC или Azure OpenAI с Private Link.
- Критические задачи (NDA с особыми требованиями) — локальный Qwen на vLLM.
- Presidio на каждом уровне маршрутизации.
- Регулярный red-team специально для проверки маршрутизатора (сценарии с ложноотрицательными срабатываниями).

Что остаётся открытым: классификатор-маршрутизатор представляет собой критическую точку риска и требует постоянного тестирования и переобучения. План — изолировать маршрутизатор как отдельный сервис с собственными обязательствами SLA и независимыми интеграционными тестами.

## Чек-лист внедрения по NIST: Govern, Map, Measure, Manage

[NIST AI 600-1](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-generative-artificial-intelligence) даёт удобную структуру из четырёх функций.

### Govern: политики и роли

- Политика использования AI с привязкой к классификации данных. Не **запрещаем ChatGPT**, а **матрица классов данных и разрешённых инструментов**.
- Назначенный ответственный (владелец направления) за AI-безопасность. На практике это обычно связка Security и Architecture; один человек на стыке двух дисциплин.
- DPA, BAA, ZDR-договор с провайдером подписаны и хранятся в одном месте; обсуждение в email недопустимо.
- Согласованная процедура одобрения новых AI-инструментов перед их добавлением в стек.

### Map: контекст и риски

- Аудит классификации данных перед запуском любого AI-инструмента.
- Модель угроз по OWASP Top 10 for LLM с разбором каждого риска применительно к конкретным сценариям использования.
- Инвентаризация всех AI-инструментов, которыми реально пользуется команда, включая теневые — расширения IDE, личные аккаунты ChatGPT. Наличие теневого использования сигнализирует о том, что разрешённого стека команде недостаточно.

### Measure: метрики и тесты

- Регулярный red-team через Garak или Promptfoo, встроенный в CI/CD как шаг верификации.
- Метрика **количество предотвращённых утечек** — события git-secrets, действия BLOCK в Presidio, отклонённые запросы маршрутизатора. Эта метрика растёт по мере обучения команды.
- Метрика **уровень освоения безопасных инструментов** относительно теневых. Её снижение указывает на проблемы в UX корпоративного стека.
- Журналы аудита AI-запросов (метаданные без payload) с retention по политике.

### Manage: реакция и мониторинг

- Процедура реагирования на инциденты: ротация секретов, запрос на удаление данных у провайдера, уведомление DPO, разбор с инициатором.
- Ежеквартальный обзор логов с фокусом на паттерны обхода фильтров.
- Непрерывное обучение команды — не одноразовое при найме, а с обновлением сценариев по мере появления новых типов атак.

## Ключевые выводы

- Безопасность AI не означает отказ от AI: рабочие архитектуры существуют даже под строгие NDA и регуляторные требования. Полный запрет не работает; теневое использование делает ситуацию только хуже.
- Локальные модели достигли качества, достаточного для большинства задач разработки кода. Qwen 2.5-Coder 32B находится на уровне GPT-4o по HumanEval, Qwen3-Coder-Next (80B/3B-A) набирает 70,6% на SWE-bench Verified при беспрецедентной эффективности на инференсе; сложный reasoning всё ещё за передовыми моделями (Claude Opus 4.7 = 87,6% SWE-bench Verified), но отрыв уже не кратный.
- Ollama годится для разработки и прототипа, vLLM — для продакшена. Точка перехода — от работы одного инженера к параллельной нагрузке команды. Это архитектурное решение, а не вопрос вкуса.
- Гибридные архитектуры позволяют балансировать безопасность и качество, но концентрируют риск в классификаторе-маршрутизаторе: его ошибка отправляет чувствительный запрос наружу, поэтому эта точка требует постоянного тестирования.
- Zero Data Retention не является магией: точные ограничения зависят от эндпоинта, платформы и фич и должны быть проверены по документации провайдера, а не по обещаниям команды продаж.
- Архитектура надёжнее политики: технические ограничения доступа защищают там, где человеческая дисциплина рано или поздно ломается. По этой причине матрица выбора AI-инструмента под класс данных должна быть встроена в сам стек, а не оставаться инструкцией на бумаге.
