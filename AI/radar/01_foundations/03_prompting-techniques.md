# Промптинг как инженерная дисциплина

## Промпт как проектный артефакт

Разработчики, пришедшие из традиционного кодирования, нередко воспринимают промпт как свободный текстовый запрос — что-то вроде поискового запроса, только длиннее. Это вайбкодинг: формулировка по наитию, без структуры. Такой подход даёт непредсказуемые результаты, а в продакшене становится источником нестабильности.

**Промпт** — это интерфейс между намерением инженера и языковой моделью. Как любой интерфейс, он должен быть явным, тестируемым и версионируемым.

**Вайбкодинг:**
```
Напиши функцию, которая парсит JSON.
```

**Промпт как проектный артефакт:**
```
Ты — senior Go-разработчик.
Задача: реализовать устойчивый парсер конфигурации в формате JSON
с обработкой ошибок по паттерну sentinel errors.

Входные данные:
{"host": "localhost", "port": 5432}

Ожидаемый результат:
- структура Config с полями Host и Port
- ошибка типа ErrInvalidConfig при отсутствии обязательных полей

Требования: Go 1.22, без внешних зависимостей.
```

### Анатомия производственного промпта

| Слой | Назначение |
|------|-----------|
| **Системная роль** | Персона и ограничения модели на весь диалог |
| **Контекст задачи** | Что модель должна знать до начала работы |
| **Инструкция** | Что именно нужно сделать, в каком формате |
| **Примеры** | Демонстрация ожидаемого результата |
| **Формат вывода** | JSON, Markdown, XML, простой текст |

## Chain-of-Thought: цепочка рассуждений

**Chain-of-Thought (CoT)** — метод, при котором модель явно формулирует промежуточные шаги рассуждения перед ответом. Техника формализована в 2022 году: если снабдить модель примерами, где ответ сопровождается цепочкой рассуждений, точность на сложных задачах резко возрастает.

### Zero-shot CoT

Самый простой вариант — добавить явную инструкцию рассуждать по шагам:

```
Проверь этот Go-код на наличие состояний гонки. Рассуждай пошагово:
сначала определи все точки конкурентного доступа, затем оцени
синхронизацию каждой, затем сформулируй итоговый вывод.

[код]
```

Фраза `Let's think step by step` кратно повысила точность на математических задачах: MultiArith вырос с 17.7% до 78.7%, GSM8K — с 10.4% до 40.7% (Kojima et al., 2022, InstructGPT 175B).

### Few-shot CoT

В few-shot CoT модели демонстрируют не просто правильные ответы, но и **ход рассуждений**.

Few-shot незаменим когда:
- Нестандартный формат вывода (специфическая JSON-структура, внутренний синтаксис)
- Корпоративный стиль документации (тон, уровень детализации, терминология)
- Внутренняя классификация (категории тикетов, severity по внутренней таксономии)
- Кодовые паттерны команды (стиль именования, архитектурные соглашения)

Качество примеров важнее количества. 3–5 тщательно подобранных примеров эффективнее 20 случайных.

**Пример few-shot для автоматического code review:**
```
Ты — ведущий инженер, проводящий code review.
Формат каждого замечания:

Пример 1:
Код: for i in range(len(arr)): ...
Замечание:
  уровень: предупреждение
  категория: стиль
  сообщение: Используй enumerate() вместо range(len())
  предложение: for i, v in enumerate(arr): ...

Пример 2:
Код: db.query(f"SELECT * FROM users WHERE id={user_id}")
Замечание:
  уровень: критический
  категория: безопасность
  сообщение: SQL-инъекция. Используй параметризованные запросы.
  предложение: db.query("SELECT * FROM users WHERE id=%s", (user_id,))

Проведи ревью следующего кода:
[код]
```

### Auto-CoT

Auto-CoT автоматизирует создание демонстраций для few-shot CoT. Система кластеризует задачи по семантической близости, выбирает представительный вопрос из каждого кластера и генерирует для него цепочку рассуждений через zero-shot CoT.

### Chain-of-Draft: экономия токенов

Техника 2025 года: модель делает очень краткие промежуточные шаги (не более 5 слов на шаг) перед итоговым ответом. Сохраняет 85–90% прироста точности от полного CoT при значительно меньшем числе токенов.

```
Проанализируй этот SQL-запрос на производительность.
Рассуждай кратко (максимум пять слов на шаг), затем дай развёрнутый итоговый ответ.
```

### CoT и reasoning-модели

Для reasoning-моделей (o3, o4, Claude Opus с extended thinking, Gemini 2.5 Thinking) явный CoT в промпте менее критичен — они рассуждают внутренне.

| Тип модели | Рекомендация |
|-----------|-------------|
| Стандартные (GPT-4o, Claude Sonnet без thinking) | Явный CoT даёт +15–30% на сложных задачах |
| Reasoning-модели | Чёткие структурированные задания без избыточных инструкций о шагах |

## Системные роли: архитектурный слой

**Системный промпт** — контракт между разработчиком продукта и моделью. Задаётся при инициализации сессии, определяет поведение на всё время диалога.

Хороший системный промпт отвечает на вопросы:
- **Персона:** кто отвечает и в рамках какой экспертизы
- **Область знаний:** чем ограничена компетентность
- **Ограничения поведения:** что не делать (GDPR, устаревшие API, признание неопределённости)
- **Формат:** как структурировать ответ (язык, длина, заголовки)
- **Тон:** технический, деловой, обучающий

```
Ты — senior-инженер с глубокой экспертизой в backend-разработке на Go и Python.
Специализация: высоконагруженные системы, распределённые архитектуры, безопасность.

Стиль ответов:
- Давай конкретные рекомендации; избегай неопределённых формулировок.
- Если задача требует уточнений — задай один конкретный вопрос.

Ограничения:
- Не предлагай решения, нарушающие GDPR.
- При неуверенности в ответе — явно сообщай об этом.

Формат:
- Код — в блоках с указанием языка.
- Ответы длиннее 200 слов структурируй по разделам.
```

**Важно:** роль влияет на стиль и фокус ответов, но не добавляет знаний, которых нет в модели. Назначил роль эксперта — получил более детальный и технический ответ, а не новые знания.

## Продвинутые техники рассуждения

### Tree of Thoughts

Расширяет CoT: вместо единственной цепочки рассуждений модель генерирует несколько веток, оценивает каждую и выбирает лучшую. Аналог поиска с бэктрекингом в задачах планирования.

```
Нужно выбрать подход к реализации распределённой блокировки.

Шаг 1: Предложи три разных варианта (Redis SETNX, Apache ZooKeeper, etcd).

Шаг 2: Для каждого оцени:
- Задержку при 10 000 RPS.
- Поведение при сетевом разделении.
- Сложность операционного обслуживания.

Шаг 3: Выбери оптимальный вариант для следующих требований: [требования].
```

### Self-Consistency

Техника запуска одного запроса несколько раз с ненулевой температурой и последующего выбора наиболее часто встречающегося ответа. Улучшила результаты на GSM8K на 17.9%, на SVAMP на 11%.

Применение для команд:
- **Оценка рисков безопасности:** три независимых ответа покрывают больший спектр уязвимостей
- **Архитектурные решения:** расхождение ответов сигнализирует о неоднозначности
- **Ревью кода:** несовпадающие результаты выявляют спорные места

### Структурированные выходы через XML

Для Claude особенно эффективно использование XML-тегов как для разметки входных данных, так и для явного задания формата вывода:

```xml
Проанализируй эту архитектуру:

<architecture>
  [описание системы]
</architecture>

Ответ предоставь в формате:

<analysis>
  <risks>список рисков</risks>
  <strengths>список сильных сторон</strengths>
  <recommendations>рекомендации по улучшению</recommendations>
</analysis>
```

XML-теги надёжно разделяют секции ответа при программной обработке и снижают вариативность формата при повторных запросах.

## Мета-промптинг: AI пишет промпт за тебя

**Мета-промптинг** — использование языковой модели для создания, анализа и улучшения самих промптов.

Принципиальное отличие: **few-shot** задаёт примеры содержания (что делать), **мета-промптинг** задаёт структуру мышления (как об этом думать).

### Базовый пример

```
Я разрабатываю систему автоматического code review на базе Claude.
Мне нужен системный промпт для ревьюера кода на Go.

Напиши идеальный системный промпт, учитывая:
- Команда из восьми инженеров уровня middle и senior.
- Фокус на безопасности и производительности.
- Формат вывода: структурированный JSON с полями severity, category, message, suggestion.

После промпта объясни ключевые решения.
```

### Итеративное улучшение

Паттерн рефлексии — показываешь модели существующий промпт, реальный вывод и проблему:

```
Вот мой промпт для security review:

<prompt>
  [промпт]
</prompt>

Вот что модель выдала в ответ:

<output>
  [полученный результат]
</output>

Проблема: вывод слишком общий, не привязан к конкретному коду.

Улучши промпт так, чтобы:
1. Модель анализировала конкретные строки, а не абстрактные категории.
2. Каждая находка содержала ссылку на строку и CWE-идентификатор.
3. Критические уязвимости приоритизировались в начале вывода.

Объясни каждое изменение.
```

### DSPy: программирование вместо промптинга

DSPy от Stanford NLP переводит разработку с LLM с уровня текстовых инструкций на уровень структурных сигнатур. Описываешь что система должна делать, DSPy автоматически оптимизирует промпты под эти сигнатуры на данных.

Исследование 2025 года: DSPy поднял точность с 46.2% до 64.0% на задачах оценки промптов без ручных изменений.

DSPy оправдан когда:
- Нужен сложный многошаговый пайплайн
- Важна воспроизводимость и версионирование промптов как кода
- Есть размеченные данные для оценки качества
- Задача долгосрочная

### TextGrad

Аналог градиентного спуска для текстовых систем. Цикл: генерация ответа → текстовая критика от оценщика → уточнение промпта → повтор. Эффективен для задач с объективной оценкой: написание тестов, генерация документации, code generation с верификацией.

## Галлюцинации: природа и способы снижения

**Галлюцинация в LLM** — генерация правдоподобного, но фактически неверного контента. Это не баг, а фундаментальное следствие авторегрессионной генерации: модель выбирает наиболее вероятное продолжение текста, а не проверяет истинность утверждений.

Правильно сконструированные промпты снизили частоту галлюцинаций GPT-4o с 53% до 23%. Структура промпта важнее настройки параметров генерации.

### Таксономия галлюцинаций

| Тип | Описание | Риск в разработке |
|-----|----------|------------------|
| **Фактические** | Несуществующие библиотеки, неверные API | dependency confusion attack — выдуманная зависимость может оказаться вредоносной |
| **Контекстные** | Ответ противоречит данным из промпта | Модель генерирует код, вызывающий несуществующий эндпоинт |
| **Логические** | Факты верны, вывод ошибочен | Неверное архитектурное решение при правильных предпосылках |
| **Высокой уверенности** | Ошибается с выраженной убеждённостью | Внешне неотличимы от правильных ответов |

### Причины галлюцинаций

- **Обучение вознаграждает уверенность:** RLHF систематически вознаграждает уверенные ответы. Модели буквально обучены не признавать незнание.
- **Knowledge cutoff:** пробелы в знаниях не мешают генерировать правдоподобные ответы об актуальных событиях.
- **OOD (out-of-distribution):** специфика кодовой базы, внутренние API — вне обучающего распределения. Модель домысливает по аналогии.
- **Промпт как провокатор:** размытые инструкции, отсутствие контекста, неявное требование «всегда давать ответ».

### Пять техник снижения галлюцинаций

**1. Явное разрешение "не знать"**

В системный промпт:
```
Если ты не уверен в ответе — явно сообщи об этом.
Фраза "я не знаю" предпочтительнее неверного ответа.
Не изобретай названия библиотек, API, стандартов или CVE-идентификаторов.
Если информация может быть устаревшей, укажи это.
```

**2. Заземление через контекст**

```xml
Вот текущая архитектура системы:

<architecture>
  ADR-001: Redis для управления сессиями
  ADR-007: PostgreSQL как основная БД
</architecture>

Отвечай строго на основе этих данных. Если для ответа недостаточно информации —
укажи, какие данные нужны дополнительно.
```

**3. Верификационный запрос**

```
Перепроверь свой ответ по трём пунктам:
1. Какие утверждения подтверждаются предоставленным контекстом?
2. Какие основаны на общих знаниях без верификации?
3. В чём ты не уверен?

Исправь ответ при необходимости.
```

**4. Chain-of-Thought как защита**

CoT особенно эффективен против логических галлюцинаций. Каждый промежуточный шаг становится точкой проверки.

**5. Температура и детерминизм**

- `temperature 0.0–0.3` — для генерации кода, работы с API, конфигураций
- `temperature 0.7–1.0` — для нейминга, brainstorming, генерации тестовых данных
- Температура в изоляции слабо влияет на системные галлюцинации — вспомогательная настройка, не самостоятельное решение

## Context rot: деградация в длинных диалогах

Языковые модели работают хуже по мере роста контекста. Это не баг конкретной модели — архитектурное свойство трансформеров. Все 18 протестированных передовых моделей (GPT-4.1, Claude Opus 4, Gemini 2.5 Pro) показывают деградацию. Деградация начинается задолго до заполнения окна: на простых задачах (базовое извлечение, репликация текста) модели деградируют с 95%+ до 60–70% точности по мере роста контекста (Chroma Research, 2025).

### Lost-in-the-middle

Производительность описывается U-образной кривой в зависимости от позиции нужной информации в контексте. При 20 документах в контексте точность падала с 70–75% до 55–60%, когда релевантный документ находился на позициях 5–15. Снижение на 15–20 п.п. только из-за позиции.

### Симптомы деградации

- Модель начинает противоречить собственным более ранним ответам
- Ограничения из системного промпта перестают соблюдаться
- Формат вывода деградирует (структура разрушается постепенно)
- Ответы становятся более общими
- Важные детали из начала диалога теряются

### Стратегии борьбы

**1. Сессионный сброс через сжатие**

После каждого значимого этапа:
```
Подведи итог нашей работы за последние сообщения в 3-5 предложениях.
Включи: принятые решения, открытые вопросы, текущий статус задачи.
```
Используй резюме как стартовый контекст следующей сессии.

**2. Явное переакцентирование**

В длинных диалогах периодически:
```
Напомню ключевые ограничения нашей задачи: [ключевые факты].
С учётом этого: [конкретный вопрос].
```

**3. Разбивка на независимые подсессии**

Каждая подсессия начинается со свежего полного контекста, решает одну задачу, завершается явным резюме.

**4. Якорные напоминания**

Важные ограничения повторяй в каждом сообщении:
```
[Контекст: Go 1.22, без внешних зависимостей, GDPR-требования активны]

Вопрос: [вопрос]
```

**5. Программное управление историей**

Для production: хранить только последние N сообщений плюс сжатое резюме предыдущих.

## Context engineering: следующий уровень

В 2025–2026 годах закрепилось понятие **context engineering** — дисциплина управления всем контекстным окном как ресурсом. Если промпт-инжиниринг фокусируется на формулировке запроса, то context engineering — на управлении тем, что попадает в контекст на каждом шаге.

Ключевые принципы:
- **Минимальность:** в контекст включается минимально необходимый набор высокорелевантных данных
- **Позиционирование:** критически важная информация размещается в начале или конце контекста, не в середине
- **Цикличность:** в агентных системах контекст обновляется и очищается на каждом шаге
- **Актуальность:** устаревшие промежуточные результаты не хранятся, а суммируются или удаляются

## Ключевые выводы

- Промпт — это интерфейс, а не свободный текст. Проектируй его с той же строгостью, что и API.
- CoT принципиально повышает точность на сложных задачах для стандартных моделей. Для reasoning-моделей (o3, Claude с extended thinking) его ценность снижается — они уже рассуждают внутренне.
- Мета-промптинг экономит часы ручного перебора. DSPy и TextGrad автоматизируют этот цикл для production-систем.
- Галлюцинации — архитектурное следствие обучения на следующий токен. Правильно сконструированный промпт снижает их частоту более чем вдвое.
- Context rot реален и универсален. Длинные диалоги требуют явного управления состоянием и позиционирования критической информации в начале или конце контекста.
