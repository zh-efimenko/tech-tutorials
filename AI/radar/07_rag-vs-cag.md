# RAG vs CAG: стратегии передачи внешних данных в LLM

## Зачем нужны внешние механизмы

Большие языковые модели обучены на фиксированном срезе данных и не знают о событиях после training cutoff. Корпоративные документы, внутренние wiki, закрытые источники недоступны публичным моделям по определению.

**RAG (Retrieval-Augmented Generation)** и **CAG (Cache-Augmented Generation)** — два основных архитектурных паттерна с принципиально разными trade-offs:
- RAG строит поисковую систему поверх корпуса и подмешивает релевантные фрагменты в prompt
- CAG помещает весь корпус в контекстное окно модели и опирается на кэширование для контроля стоимости

### Хронология развития

| Период | Событие |
|--------|---------|
| 2020 | Оригинальная статья RAG — базовая архитектура |
| 2022–2023 | Взрывной рост экосистемы векторных БД (Pinecone, Qdrant, Chroma, Milvus) |
| 2023–2024 | Контекстные окна моделей растут с 8K–32K до 128K–1M+ токенов |
| 2024–2025 | Prompt caching у Anthropic, OpenAI, Google удешевляет повторные запросы на 50–90% |
| 2025–2026 | CAG оформляется как осознанная альтернатива RAG; Agentic RAG — де-факто стандарт production |

## RAG: архитектура и компоненты

### Принцип работы

```
Query → Embed → Retrieve → Augment → Generate
```

1. Пользователь задаёт вопрос (query)
2. Query кодируется в embedding — векторное представление
3. По cosine similarity находятся ближайшие векторы в предварительно построенной базе
4. Найденные чанки добавляются в prompt как контекст
5. LLM генерирует ответ на основе этого контекста

Ключевая идея: разделить знания модели (веса после обучения) и оперативные данные (внешний индекс). Данные можно обновлять без переобучения модели, ответ опирается на проверяемые источники.

### Слой индексации (ingestion)

Принцип garbage in, garbage out: качество данных на входе определяет качество ответов сильнее, чем выбор модели эмбеддингов.

Практическое правило: приводить все типы документов (PDF, DOCX, HTML, XLSX) к единому формату Markdown перед чанкингом. Markdown даёт чистую структуру для сплиттеров.

**Chunking-стратегии:**

| Стратегия | Описание |
|-----------|----------|
| fixed-size | Деление по фиксированному числу токенов. Просто, но рвёт смысл |
| semantic chunking | Деление по смысловым границам через embedding similarity |
| sentence window | Предложение как единица + окружающий контекст |
| hierarchical | Иерархические индексы для многоуровневого поиска |

Overlap между чанками обязателен (~10% от размера чанка).

**Embedding-модели 2026:**
- `text-embedding-3-large` (OpenAI) — массовый выбор для англоязычных проектов
- `Cohere Embed multilingual v3` — лучше работает с русским
- `BGE-M3` (BAAI) — open-source, 100+ языков, self-hosted
- `Gemini Embedding 2` (Google, GA апрель 2026) — первая нативно мультимодальная embedding-модель: текст, изображения, видео, аудио, PDF в едином векторном пространстве

**Векторные хранилища:** Pinecone, Weaviate, Qdrant, Chroma, Milvus; pgvector как расширение PostgreSQL.

### Слой retrieval

| Тип | Метод | Когда использовать |
|-----|-------|-------------------|
| Sparse | BM25, TF-IDF | Редкие термины, точные совпадения |
| Dense | Embedding similarity | Семантическое сходство при разной лексике |
| Hybrid | RRF (Reciprocal Rank Fusion) | Наиболее надёжный в production |
| Re-ranking | Cross-encoder (Cohere Rerank, FlashRank) | Точная переоценка top-k кандидатов |

### Типы RAG-архитектур

**Naive RAG** — базовый pipeline без оптимизаций. Подходит для прототипов, в production даёт низкое качество.

**Advanced RAG** — оптимизации поверх базового:
- Query rewriting и expansion
- HyDE (гипотетический ответ как запрос для поиска)
- Step-back prompting (сначала общий вопрос, потом конкретный)

**Agentic RAG** — стандарт production 2026:
1. Query classifier — определяет тип запроса и маршрутизирует к retriever-ветке
2. Несколько параллельных retriever-веток: векторный поиск, SQL, web search, графовый retrieval
3. Agent как LLM-оркестратор — может выполнять multi-step retrieval
4. Merge и synthesis с цитатами из разных источников

**Ключевой принцип:** структурированные данные (CSV, SQL-таблицы) — точные запросы через SQL, не RAG. Типичный антипаттерн — пытаться через векторный поиск посчитать сумму или количество: эмбеддинги не сохраняют арифметические свойства.

### Метрики качества RAG

| Метрика | Что измеряет |
|---------|-------------|
| Context Precision | Точность retrieved контекста |
| Context Recall | Полнота извлечения нужного контекста |
| Answer Relevancy | Релевантность ответа вопросу |
| Faithfulness | Верность источнику, отсутствие галлюцинаций |

Инструменты оценки: **RAGAS** (де-факто стандарт), **DeepEval** (расширенный набор метрик, интеграция с CI/CD).

## CAG: длинный контекст и кэширование

### Суть подхода

Весь корпус данных помещается в контекстное окно модели, retrieval происходит внутри LLM через attention. Нет векторной БД, нет embedding-инфраструктуры, нет pipeline индексации.

Два ключевых условия делают CAG практичным:
- Контекстное окно достаточно большое (128K, 200K, 1M+ токенов)
- KV-cache снижает стоимость повторных запросов

### Как работает KV-cache

```
Статичная часть (системный промпт, база знаний) → кэшируется
Динамическая часть (вопрос пользователя) → не кэшируется
```

Модель вычисляет attention keys и values для входного промпта и сохраняет как KV-cache. При повторном запросе с тем же префиксом вычисления не выполняются заново.

**Ключевое ограничение:** префикс должен совпадать побайтово. Любое изменение в начале промпта инвалидирует кэш для всего последующего текста.

### Параметры prompt caching по провайдерам

| Провайдер | Модели | Минимум токенов | Скидка | TTL |
|-----------|--------|----------------|--------|-----|
| Anthropic | Claude 3.5+, 3.7, 4.x | 1024–4096 (зависит от модели) | ~90% | 5 мин, опционально 1 час |
| OpenAI | GPT-4o и новее | 1024 | 50–90% (зависит от модели) | Авто (5 мин – 24 ч для новых моделей) |
| Google | Gemini 1.5 Pro | 32K | ~75% | Настраивается, по умолчанию 1 час |
| Google | Gemini 2.0+, 2.5 | 1024–4096 (зависит от модели) | ~75–90% | Настраивается, по умолчанию 1 час |

### Ограничения длинного контекста

- **Lost-in-the-middle:** модели хуже обрабатывают информацию из середины контекста. В сеттинге с 20 документами у GPT-3.5-Turbo точность падала более чем на 20%, в худшем случае — ниже closed-book baseline (56.1%). U-образная кривая: лучший результат на начале и конце контекста (Liu et al., TACL 2024)
- Стоимость без кэша растёт линейно с длиной — первый запрос с 500K токенов дорогой
- TTFT (Time to First Token) растёт с объёмом контекста
- Потолок объёма: корпус должен помещаться в контекстное окно
- Нет гранулярного контроля над тем, что именно модель использует

## Сравнительный анализ: RAG vs CAG

### По шести осям

| Ось | RAG | CAG |
|-----|-----|-----|
| **Стоимость** | Единовременная индексация + дешёвый поиск | Дорогой первый запрос, дешёвые повторные (кэш) |
| **Задержка** | Overhead retrieval 100–500 мс, быстрая генерация | Нет retrieval overhead, высокий TTFT без кэша |
| **Точность** | Зависит от чанкинга; Advanced RAG даёт высокую | Видит весь документ, риск lost-in-the-middle при > 500K |
| **Масштабируемость** | Миллионы документов, O(log N) поиск | Ограничен контекстным окном (потолок ~2M у Gemini) |
| **Актуальность** | Инкрементальная переиндексация, подходит для частых обновлений | Обновление = повторная загрузка и прогрев кэша |
| **Сложность** | Высокая: chunking, embedding, vector store, evaluation | Низкая: загрузка файлов + API-вызов |

## Матрица выбора подхода

### По объёму корпуса данных

| Объём | Рекомендация |
|-------|-------------|
| < 200K токенов | CAG |
| 200K – 2M токенов | CAG или гибрид |
| > 2M токенов | RAG |

### По частоте обновлений

- **Статичный корпус** (документация, книги, архивные данные) → CAG
- **Часто обновляемые данные** (новости, логи, тикеты, wiki) → RAG

### По паттерну запросов

- Многократные запросы к одному корпусу → CAG
- Разные корпуса на каждый запрос (мультитенантные системы) → RAG

### По требованиям к атрибуции

- Нужна точная атрибуция с source citations на уровне чанков → RAG
- Нужен общий синтез без строгой атрибуции → CAG

### По операционным ограничениям

- Нет ресурсов на инфраструктуру и ML-команду → CAG
- Нужна фильтрация по метаданным (дата, автор, тег) → RAG
- Требования compliance и аудитируемости источников → RAG

## Когда RAG — единственный выбор

Production-примеры:
- Корпоративные knowledge bases на базе Confluence или SharePoint
- Юридические системы поиска по миллионам документов
- Медицинские справочные системы с актуальными рекомендациями
- Customer support с ответами на основе базы тикетов

## Когда CAG — оптимальный выбор

Production-примеры:
- Анализ одного большого документа: контракт, финансовый отчёт, кодовая база
- AI-ассистент по фиксированной документации (< 500K токенов)
- Coding assistant с кодовой базой целиком в контексте
- Юридический анализ конкретного договора с ссылками на внутренние секции

---

## Гибридные стратегии

На практике production-системы редко выбирают один подход:

**Макро-retrieval + микро-анализ:** RAG находит релевантные документы, все они целиком помещаются в длинный контекст для финального анализа.

**Двухуровневый:** sparse retrieval для отбора кандидатов из огромного корпуса, CAG для генерации ответа по отобранному подмножеству.

**Кэшированный системный промпт + динамический RAG:** база знаний в начале промпта кэшируется, retrieval-контекст подмешивается в конце. Снижение стоимости повторных запросов на 80–90%.

## Инструменты и фреймворки

### RAG-фреймворки

- **LangChain** — наиболее распространённый, много интеграций, LCEL для декларативных pipelines
- **LlamaIndex** — глубокая специализация на RAG, иерархические индексы, knowledge graphs
- **Haystack** — enterprise-ориентированный, hybrid search и evaluation pipeline из коробки

### Векторные базы данных

| БД | Характеристики |
|----|---------------|
| **Qdrant** | Rust, высокая производительность, удобный API, хорошо on-premise |
| **Weaviate** | Hybrid search из коробки, встроенные модули для классификации |
| **Pinecone** | Managed, serverless, минимум операционной нагрузки |
| **pgvector** | Расширение PostgreSQL — если PostgreSQL уже используется |

### Графовый RAG

Построение графа знаний (concepts, entities, relationships) вместо плоского векторного индекса:

- **GraphRAG** (Microsoft) — win rate 72–83% над naive RAG по comprehensiveness и diversity на global queries (LLM-as-judge, Edge et al. 2024). Trade-off: медленная и дорогая индексация (\$50–200 за 500 страниц), статичный граф
- **LightRAG** — быстрее обновляется, ~\$0.50 на индексацию 500 страниц (~1/100 стоимости GraphRAG). Хороший компромисс
- Когда выбирать: статичная база знаний с насыщенными cross-document связями

## Ключевые выводы

- RAG и CAG — не конкуренты, а инструменты с разными областями применения: выбор определяется объёмом данных, паттерном запросов и операционными требованиями
- CAG становится всё более конкурентоспособным по мере роста контекстных окон и снижения стоимости через кэширование; для корпусов до 200K токенов — часто оптимальный выбор по соотношению цена/сложность
- RAG необходим при объёмах > 2M токенов, частых обновлениях и требованиях к точной атрибуции
- Качество RAG-системы определяется слабейшим звеном pipeline: приведение к Markdown, правильный чанкинг, выбор embedding-модели под язык и тип контента
- Agentic RAG с маршрутизацией к разным retriever-ам (SQL, векторный, графовый, web) — стандарт production 2026; структурированные данные — через SQL, не RAG
- Метрики RAGAS должны быть частью CI/CD любой production RAG-системы
- Для большинства корпоративных задач оптимальна гибридная стратегия: кэшированный системный промпт с базой знаний + динамический RAG для запросов пользователя
